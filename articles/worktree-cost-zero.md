`git worktree` は便利です。それは知っていました。コマンドも知っていました。

それでも僕は、何年も使いませんでした。チームの誰も使っていませんでした。

最近、**チーム全員が使うようになりました。** コマンドを覚えたからではありません。むしろ逆で、**覚えておくことがゼロになったから**です。

その話を書きます。まず worktree が何なのかから。

## そもそも git worktree とは

ふつう、1 つのリポジトリには**作業ディレクトリが 1 つ**です。ブランチを変えたいときは `git checkout` して、**同じディレクトリの中身を丸ごと入れ替えます。**

`git worktree` は、これを増やす機能です。**同じリポジトリから、別のブランチをチェックアウトした作業ディレクトリを、もう 1 つ生やせます。**

```bash
# いまここが main
cd ~/work/myapp

# もう1つ、別のディレクトリを生やす（ブランチ hotfix で）
git worktree add ~/work/myapp-hotfix -b hotfix
```

これで、こうなります。

```
~/work/myapp          ← main         （さっきまでの作業がそのまま残っている）
~/work/myapp-hotfix   ← hotfix       （新しく生えたほう）
```

**2 つのディレクトリは、履歴を共有しています。** `.git` の実体は 1 つで、片方でコミットすれば、もう片方からも `git log` で見えます。

**クローンをもう 1 個作るのとは違います。** クローンだと履歴が丸ごと複製されて、片方のコミットはもう片方から見えません。`git fetch` して持ってくることになります。worktree なら最初から 1 つのリポジトリです。ディスクも食いません。

## 何が便利なのか ── ブランチを「切り替えない」で済む

`git checkout` の何が嫌かというと、**足元が入れ替わること**です。

作りかけの機能があって、そこに「本番が落ちてる」と言われたとします。ふつうはこうです。

```bash
git stash                # 作りかけを退避（これがまず面倒）
git checkout -b hotfix
# ...直す...
git checkout feature/x
git stash pop            # 戻す（そして何かがコンフリクトする）
```

しかも `checkout` で全ファイルのタイムスタンプが変わるので、**ビルドキャッシュが吹き飛びます。** `node_modules` の状態が合わなくなって `yarn install` からやり直し。開発サーバは再起動。エディタで開いていたファイルは、別ブランチの中身に置き換わる。

worktree だと、これが全部いりません。

```bash
git worktree add ~/work/myapp-hotfix -b hotfix
cd ~/work/myapp-hotfix
# ...直す...
```

**元のディレクトリは、一切触られていません。** 作りかけのコードも、起動中の開発サーバも、ビルドキャッシュも、そのまま。用が済んだら `cd` で戻るだけです。

つまり worktree の本質は、**「切り替える」を「歩いていく」に変えること**です。

### こういうときに使う

- **作業中に割り込みが入った** ── hotfix、緊急の調査。上の例そのもの
- **人の PR をレビューしたい** ── 手元を止めずに、別ディレクトリで動かして試せる
- **重いテストやビルドを別ブランチで流したい** ── 走らせておいて、こっちは書き続ける
- **同じコードの 2 つのバージョンを並べて見たい** ── 2 つのエディタで開くだけ
- **AI エージェントを複数走らせたい** ← 今回の本題です

## 使いこなすのが難しい理由 ── dir とブランチを、自分で管理することになる

ここまで読むと、いいことしかないように見えます。実際、**コマンドは簡単です。** `git worktree add` を打つだけ。難しいところはどこにもありません。

それでも使わなかったのは、**ディレクトリとブランチを、自分で管理することになる**からです。

worktree を作るというのは、**「新しいディレクトリ」と「新しいブランチ」を 2 つ同時に増やす**行為です。そして git は、**それらを増やしてくれるだけで、覚えておいてはくれません。**

具体的に、自分で持つことになるのはこれです。

- **どこに作ったか** ── `~/work/myapp-hotfix`？ `../hotfix`？ `/tmp` に作ったやつもあった気がする
- **どういう名前にしたか** ── 3 日前の自分がつけた名前を、3 日後の自分は覚えていない
- **どのディレクトリが、どのブランチか** ── ディレクトリ名とブランチ名を揃えていないと、もう分からない
- **いま自分はどこにいるのか** ── シェルのプロンプトには `myapp` としか出ない。本体なのか worktree なのか、見て分からない
- **あれ、コミットしたっけ。push したっけ** ── 消していいかどうかは、これ次第
- **消したあと、ブランチが残っていないか** ── `git worktree remove` はブランチを消しません

**そして一番効くのが、「どこで何を作ったか忘れる」**です。

3 本くらいまでは覚えていられます。並行して 5 本、6 本になり、それが数日にまたがると、もう無理です。`git worktree list` を打てば分かります。分かりますが、**打つことを思い出す必要がある。** そして思い出したときには、もう本題から気がそれています。

忘れると、こうなります。

- **同じ作業の worktree を、2 本作る**（1 本目を忘れているので）
- **消し忘れて溜まる** ── 気づくと十数本あって、どれが生きているのか分からない
- **消すのが怖くなる** ── 中に何か残っているかもしれないので、結局そのまま
- **ブランチだけ残る** ── `git branch` の一覧が読めなくなる

つまり worktree のコストは、コマンドを打つ手間ではなく、**ディレクトリとブランチの対応表を、頭の中に置いておく負担**でした。しかもこの負担は、作業している間ずっと発生し続けます。

そして重要なのは、**この負担は本題と 1 ミリも関係がない**ということです。僕が考えたいのはコードのことであって、「いま何本あって、どれがどのブランチか」ではありません。

### stash も、まったく同じ構造

`git stash` も同じです。退避するのは一瞬。問題はそのあとです。

```
stash@{0}: WIP on main: 3a4f5b6 fix: ...
stash@{1}: WIP on main: 8c1d2e9 feat: ...
stash@{2}: WIP on feature/x: 1a2b3c4 refactor: ...
```

**この一覧は、説明になっていません。** `WIP on main` は「何かの作業中」としか言っていない。どれが何だったか、思い出せない。

思い出せないから `pop` するのが怖くなる。怖いから溜まる。溜まるからますます分からなくなる。僕の stash は、そうやって永遠に消えないゴミ箱になっていました。

**便利な機能が使われないのは、たいてい難しいからではなく、覚えておくことが増えるからです。**

## AI エージェントを並列で回すと、避けて通れなくなった

しばらくは、使わないままで済んでいました。ブランチを切り替えながら 1 本ずつやればいいので。

それが変わったのは、Claude Code や Codex を**同時に何体も走らせる**ようになってからです。

同じリポジトリで 2 体走らせると、こうなります。

- 片方が書きかけのファイルを、もう片方が読む
- ブランチは 1 本しかないので、2 体の変更が混ざる
- 片方が `git checkout` すると、もう片方の足元のファイルが入れ替わる

**並列化の前提が worktree**でした。避けて通れなくなったわけです。

でも、頭の中で管理するコストは変わりません。むしろ 5〜6 本同時になるので、悪化します。

![並行するエージェント](https://raw.githubusercontent.com/receptron/mulmoterminal/main/docs/guide/images/grid-2x2.png)

### 追記：Claude Code 本体にも worktree 機能があります

**この記事を書いたあとに指摘されて気づいたので、正直に足しておきます。** Claude Code には `--worktree`（`-w`）が **v2.1.49 から**あります。

```bash
claude --worktree feature-auth        # worktree を切ってそこで起動
claude --worktree feature-auth --tmux # tmux セッションも作る
```

[公式ドキュメント](https://code.claude.com/docs/en/worktrees)には cleanup も `.worktreeinclude`（worktree に持ち込むファイルの指定）も、大きなモノレポ向けの `worktree.sparsePaths` もあります。**1体を隔離して走らせたいだけなら、これで足ります。** 何も入れなくていい。

さらに **`claude agents`**（v2.1.139、Research Preview）というセッション一覧もあります。全セッションを状態別（Working / Needs input / Completed）に並べて、Haiku が各セッションの作業内容を1行で要約してくれる。**知らなかった人はぜひ一度打ってみてください。**

そのうえで、この記事の話は消えません。

- **どこに作ったか・何本あるか**は、結局こちらが把握することになります。`claude agents` は**セッション**の一覧であって、worktree の一覧ではありません
- **消すきっかけ**が要ります。作るのが1コマンドでも、消し忘れは起きます

以下は「**作る・消すを、既にやっている操作に完全に埋める**」とどうなるか、という話です。本体の機能で足りる人は、それでいいと思います。

## やったこと ── コマンドを簡単にするのをやめた

僕たちが作っている [MulmoTerminal](https://github.com/receptron/mulmoterminal)（Claude Code / Codex を並べて監督するブラウザ UI）で、この問題に手を付けました。

最初に考えたのは「worktree を作るボタンを付ける」でした。でもそれだと、**worktree のことを考える瞬間が残ります。** ボタンを押すかどうかを決めるのは、結局こちらだからです。

そこで方針を変えました。

> **worktree のライフサイクルを、こちらが「もともとやっている操作」に丸ごと結びつける。**

つまり、**worktree のためだけの操作を、1 つも作らない**。

結果、こうなりました。

| worktree の | 結びつけた操作 |
|---|---|
| 作る | **ターミナルを開く**とき |
| 作る（issue から） | **issue の「着手」を押す**とき |
| 消す | **ターミナルを閉じる**とき |

1 つずつ見ていきます。

## 1. ターミナルを開くとき、そこで作る

空いているセルには、こういうランチャが出ます。

![空きセルのランチャフォーム](https://raw.githubusercontent.com/receptron/mulmoterminal/main/docs/guide/images/grid-launch-form.png)

真ん中あたりに **OR ISOLATE IN A WORKTREE** という欄があります。git リポジトリなら、ここにタスク名を入れて **New worktree** を押すだけです。

裏側で起きること:

- `~/.mulmoterminal/worktrees/<リポ名>-<ハッシュ8桁>/<タスク名>` に worktree を作る
- ブランチは `agent/<タスク名>`。ベースブランチから分岐する
- できた worktree でエージェントを起動する

ここで、さっきの「自分で管理することになる」もののうち **2 つが消えます。**

**どこに作るか、決めなくてよくなりました。** 置き場所は常に同じ 1 箇所です。worktree を「リポジトリの隣」に作ると、`ls` するたびに目に入ってリポジトリ本体と混ざるし、`.gitignore` に書き忘れて事故ることもある。だから**リポジトリの外の、決まった 1 箇所**にまとめました。ハッシュを付けているのは、同じ名前のリポジトリを複数クローンしていても衝突しないようにするためです。

**ディレクトリ名とブランチ名も、考えなくてよくなりました。** タスク名を 1 回打てば、両方それに揃います。ディレクトリが `fix-grid-order` なら、ブランチは `agent/fix-grid-order`。**対応表を頭に持つ必要がありません。** 見れば分かるので。

そしてもう 1 つ。**既にある worktree は、この欄の下にそのまま一覧されます。**

これが地味に効きます。「いま何本あるんだっけ」「どこで何を作ったんだっけ」を、**思い出す必要がなくなる**からです。次に何かを始めようとした瞬間に、目の前に並んでいる。`git worktree list` を打つことを思い出す必要がない。

**同じ作業の worktree を 2 本作ってしまう**のも、これで起きなくなりました。作ろうとした瞬間に、1 本目が視界に入るからです。

一覧の各行は、3 通りのどれかになります。

| 行の表示 | 押したときの動作 |
|---|---|
| 何も付いていない | その worktree の最初のセッションを起動 |
| `resume` | その worktree が持っているセッションを再開 |
| `in use` | 別のターミナルで開いているので押せない |

**1 つの worktree に 1 セッションまで**、というルールにしています。worktree はブランチに紐づくので、そこに 2 体目を立てるのは隔離になっていません。同じ作業ツリーを 2 体が編集するだけです。

なお、複数のセルから**同時に**作成しても大丈夫なように、作成処理は直列化しています。並列で `git worktree add` を撃つと、同じブランチ名を 2 つが同時に取りにいったり、git のインデックスロックで衝突したりするためです。並列で使う前提の機能なので、ここは避けられませんでした。

そして起動したあとの「**いま自分はどこにいるのか**」は、セルのヘッダーが答えます。worktree のセルだけ、パスの代わりに **`⎇ リポ名 (タスク名)`** と出るようにしました。管理下のパスは長いだけで読む価値がないのと、**知りたいのは「本体か worktree か、どの作業か」だけ**だからです。

![起動したセル（2段ヘッダー）](https://raw.githubusercontent.com/receptron/mulmoterminal/main/docs/guide/images/grid-one-cell.png)

## 2. issue から作る ── ▶ を 1 回押すだけ

もう 1 つの入口が、GitHub の issue です。

![issue の行と着手ボタン](https://raw.githubusercontent.com/receptron/mulmoterminal/main/docs/guide/images/v3.0.0-issue-rows.png)

issue 行の右端にある **▶** を押すと、こうなります。

1. issue を読む（タイトルと本文）
2. `issue/<番号>-<slug>` の worktree を作る
3. その worktree で Claude をセルとして起動する。**issue の本文が入力欄に入った状態**で

分岐元は、**`fetch` した `origin/<ベースブランチ>`** です。ここだけネットワークを 1 往復します。ランチャから作る場合は手元のベースブランチから分岐するので、動きが違います。

これは意図的な非対称です。issue から始める作業は「これから新しく取りかかるもの」なので、**古いベースから分岐すると、その時点で無駄な差分を背負う**。一方でタスク名を打って始めるほうは、手元で今やっていることの続きであることが多いので、毎回ネットワークを待たせたくない。

そして **Enter は押しません。** 入力欄に置いたままにします。issue の本文は、たいてい**他人が書いたテキスト**だからです。読んで、必要なら直して、送信するのは自分。

ブランチ名が issue 番号を持っているので、以降は何も指定しなくても繋がります。PR を出すときに本文へ `Fixes #<番号>` が入り、セルのヘッダーにも issue が出て、マージ時に自動でクローズされます。

![work item チップ](https://raw.githubusercontent.com/receptron/mulmoterminal/main/docs/guide/images/v2.5.0-work-item-chip.png)

**同じ issue をもう一度押しても、2 本目の worktree は作りません。** 1 issue に worktree は 1 本です。既にあるものが開き、セッションが残っていればそれが開きます。

これも「覚えておくこと」を減らすための決まりです。**「この issue、もう worktree 作ったっけ？」を考えなくていい。** 押せば正しいところに着きます。

## 3. 閉じるとき、そこで消す ── ここが本丸

作るのは、正直それほど難しくありません。**溜まるのは、消し忘れるからです。**

なので、削除を「閉じる」に結びつけました。worktree で動いているセルの × を押すと、閉じる前にこう聞かれます。

![worktree のセルを閉じるときの確認](https://raw.githubusercontent.com/receptron/mulmoterminal/main/docs/guide/images/worktree-close-keep.png)

**Remove worktree** を押すと、こうなります。

- `git worktree remove` で worktree を消す
- `git worktree prune` で管理情報も掃除する
- **`git branch -D` でブランチも一緒に消す**

3 つ目が大事です。worktree だけ消してブランチが残ると、`git branch` の一覧がだんだん読めなくなる。**あとで手で掃除する必要があるなら、コストはゼロになっていません。**

### 未コミット・未 push があるとき

そのまま消したら、作業が消えます。なので、その場合は文面が変わります。

![未コミット・未 push があるときの確認](https://raw.githubusercontent.com/receptron/mulmoterminal/main/docs/guide/images/worktree-close-discard.png)

**2 unpushed commits + 5 uncommitted changes** と、何がどれだけ消えるかを数えて出します。ボタンのラベルも `Remove worktree` から **`Discard & remove`** に変わります。何が起きるかを、押す前にボタン自身が言うようにしました。

ヘッダーの `+2` と `●5` も同じものを指しています。**閉じようとした瞬間に初めて知る、ということにならない**ように、作業中からずっと出ています。

細かいところですが、**この確認を出す瞬間に、差分を取り直しています。** 取り直している間、削除ボタンは `Checking…` になって押せません。

理由は、キャッシュされた古い状態で判断させないためです。エージェントは非同期に動いているので、「さっき見たときは綺麗だった」が今も綺麗である保証はない。速くクリックしたせいで、**その 1 秒の間に生まれた変更**が消える、というのは起こしてはいけない事故です。

### 消してはいけないものを消さないために

削除は取り返しがつかないので、サーバ側で 2 つ確認しています。

1. **管理下のルートの配下にあるか。** `~/.mulmoterminal/worktrees/<リポ>-<ハッシュ>/` の**中**でなければ拒否します。ルート自身も拒否します（ルートは worktree ではなく、worktree の入れ物なので）
2. **パスは両側とも realpath 解決してから比較する。** 単なる文字列の前方一致だと、ルートの下に外を指すシンボリックリンクを置かれたときに通ってしまうためです

要するに、**このアプリが作ったもの以外は消せない**ようにしてあります。

### PR がマージされたら、向こうから言ってくる

もう 1 つ。そのブランチの PR がマージされると、セルが気づいて「片付けますか」と出します。

ただし**勝手には消しません。** 上の確認画面に連れて行くだけです。判断するのはこちらで、アプリは**思い出させる係**に徹する。ここは意図的に線を引きました。

## 実際どうなったか

いま手元を数えてみました。

```bash
$ find ~/.mulmoterminal/worktrees -mindepth 2 -maxdepth 2 -type d | wc -l
0

$ ls ~/.mulmoterminal/worktrees/
mulmoclaude-dbc4ed20     mulmoterminal-ca93907d
mulmoclaude3-8dcc62ce    mulmoterminal2-36f4177c
mulmoclaude5-17408686    mulmoterminal5-722db8f8
```

**6 リポジトリ分のフォルダがあって、worktree は 0 本。**

使っていないのではありません。**使ったあと、残っていない**んです。

正直に書いておくと、ブランチは 1 本だけ残っていました（`issue/1253-...`）。この画面を通さずに手で片付けたぶんだと思います。**アプリの中で完結させたときだけ**ゼロになる、というのが実際のところです。

そして肝心なのは、**この間、僕は worktree のことを一度も考えていない**ということです。

最初に挙げた「自分で管理することになるもの」が、どうなったか並べてみます。

| 自分で持っていたもの | いま |
|---|---|
| どこに作ったか | 置き場所は常に同じ 1 箇所。決めていない |
| どういう名前にしたか | タスク名を 1 回打つだけ |
| どのディレクトリが、どのブランチか | 名前が揃っているので、見れば分かる |
| いま自分はどこにいるのか | セルのヘッダーに `⎇ リポ名 (タスク名)` と出ている |
| コミットしたっけ、push したっけ | 閉じるときに、向こうから数字で言ってくる |
| 消したあとブランチが残っていないか | 一緒に消える |
| **どこで何を作ったか** | **次に開くとき、目の前に並んでいる** |

**ディレクトリとブランチの対応表を、頭に持たなくてよくなりました。** これが全部です。

チームも同じです。**今まで誰も worktree を使っていませんでした。今は全員が使っています。** コマンドを覚えたからではなく、覚えることがなくなったからです。

## 一般化すると

この件から学んだことを、1 つに絞るとこうなります。

> **機能が使われない理由は、たいてい「難しいから」ではなく「覚えておくことが増えるから」。**

だから、使われるようにする方法も変わります。**機能を簡単にするのではなく、ライフサイクルを、その人が既にやっている操作に結びつける。**

`git worktree add` はもともと簡単でした。簡単だったのに使われなかった。**簡単さは、そもそも問題ではなかった**んです。

そしてこの視点で見ると、worktree を作る操作は今もありません。**ターミナルを開く操作しかない。** 消す操作もありません。**閉じる操作しかない。**

コストがゼロになったのではなく、**コストを払う場所が、もともと払っていた場所に移った**、というほうが正確かもしれません。

（`git stash` のほうは、まだ解けていません。あれを解くには「これは何の作業だったか」を人間の代わりに覚えておく必要があって、たぶん別のアプローチが要ります。誰か良い方法を知っていたら教えてください）

## 試してみてください

インストールは要りません。

```bash
npx mulmoterminal@latest
# → http://localhost:34567
```

Node.js 22.9 以上と、`claude` か `codex` の CLI が PATH にあれば動きます。ローカルで完結します（コードも API キーもどこにも送りません）。MIT ライセンス。

worktree だけ試すなら、こうです。

1. 空いているセルの **WORKING DIRECTORY** に、git リポジトリのパスを入れる
2. **OR ISOLATE IN A WORKTREE** にタスク名を入れて **New worktree**
3. 適当に何かやる
4. セルの × を押して **Remove worktree**

`git worktree list` を一度も打たずに、ここまで来られるはずです。
