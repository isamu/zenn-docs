海外の記事にこういうコメントをもらいました。

> エージェントだけがルールの対象になった結果、**実際に「厳しすぎる」と判明した閾値**はありましたか？

背景はこうです。うちは `as` を全面禁止し、型情報を使うルールを片っ端から入れて、そのうえでコードのほとんどをエージェントに書かせています。**lint の厳しさは、ずっと人間の忍耐との交渉でした。エージェントはその交渉の席に来ません。** では人間のコストが消えたとき、純粋に中身として「厳しすぎる」ものはあったのか。

**入れたルールの中には、1つもありませんでした。** 「正しいけれど、直す価値がない」と正直に言えるルールは無かった。

ただしこの言い方には但し書きが要ります。**生存バイアスの形をしている**からです。実際には tsconfig のフラグを2つ**測ったうえで却下**しています。

- `noImplicitReturns` — 58件。ほぼ全部が**正しい Express ハンドラ**
- `noPropertyAccessFromIndexSignature` — 1,785件。`obj.key` を `obj["key"]` にするだけで、**アクセスの安全性は何も変わらない**

「割に合わないと判断したルール」として数えるなら、答えは「はい、2つ」です。私は数えていません ── どちらも偽陽性を1件も出していないし、依存する前に却下したので。ただ、**そう区別したことは書いておきます。**

代わりに出てきたのは、**閾値では表現できない形で間違っているルール**でした。そして**そもそも間違っていなかったもの**が1つ。それはこの記事を書いている最中に判明しました。

以下、確かめるべき順に3つ。最後の判断リストは5項目ありますが、5つ目は「ルールが正しい場合」なので数に入れていません。

## 1. ルールを読み違えていた

**これが一番多く、そしてこの記事を書きながら私がやった間違いです。**

設定ファイルに、何週間もこう書いてありました。

```js
// `void` is what no-floating-promises asks for to mark a deliberate fire-and-forget.
// The two rules contradict each other; we chose the one that catches a forgotten `await`.
"sonarjs/void-use": "off",
```

`no-floating-promises` は「意図的に待たない」印として `void router.push(...)` を要求します。`sonarjs/void-use` は `void` 演算子を禁止します。**どう見ても矛盾**します。だから await 忘れを捕まえる側を選び、理由を書いて、先に進みました。

**違いました。** ルールの実装（S3735）はこうなっています。

```js
'UnaryExpression[operator="void"]': (node) => {
  if (isVoid0(node) || isIIFE(node) || isPromiseLike(context, node)) {
    return;                                    // ← 報告しない
  }
```

**promise を除外しています。** `no-floating-promises` が書けと言っているもの、まさにそれが報告対象外でした。

3行で確かめました。**型情報を有効にした状態で**です（ここが後で効きます）。

```ts
async function work(): Promise<void> {}
function sync(): void {}
void work();   // 報告されない
void sync();   // 報告される
```

⚠️ **parser services が無いと、ルールは「呼び出しっぽい式」を全部除外するフォールバックに落ちます。** その状態だと `void sync()` も黙るので、実験しても何も分かりません。自分で試すなら、先に `parserOptions.project` を通してください。**そうしないと、間違ったことを確認して終わります。**

そのうえで実リポジトリで有効にしました。**66件出ると思っていました** ── fire-and-forget の印を66箇所に付けたので。

**3件でした。** 全部1つのファイルにあって、全部この形です。

```ts
forget:   (id: string): void => void holder.delete(id),
remember: (id: string, …): void => void seen.set(id, key(client, window)),
clear:    (id: string): void => void seen.delete(id),
```

`Map` のメソッドの戻り値を、`: void` と宣言したアロー関数の式本体で捨てるための `void` です。**promise とは何の関係もありません。** つまり、このルールを `error` で常設するのに必要だったのは、**この3件を直すことだけ**でした。

**見分け方: 読んでも分かりません。** 設定コメントは自信たっぷりで、具体的で、間違っていて、読むたびに私を納得させていました。これを捕まえられるのは**ルールを戻して数える**ことだけです ── **1分の作業を、私は何週間も飛ばしていました。**

これを最初に置いたのは、面白いからではありません。**あなたが持っている確率が一番高く、探す確率が一番低い**からです。

## 2. 偽陽性が構造的で、一時的でない

これは最初やり方を間違えました。偽陽性を見たら**その行を抑制して次に行く**のが私の癖です。ルールがだいたい正しいときは、それで合っています。**そのコードについてルールが決して正しくなり得ないときは、間違いです。**

例を2つ。

`sonarjs/function-return-type` が、複数の型を返す関数を3つ指摘しました。3つとも**戻り値の union を宣言している**関数です ── ヘッダのセルに何を出すか解決してチップか `null` を返すもの、`JsonValue`（定義からして union）を返すもの。

**union は雑さではありません。union が契約です。** これを潰すには、ルールが黙るように全部をラッパーに詰めて、呼び出し側で毎回開けることになります。**リンタを満たすためにコードが悪くなります。**

`sonarjs/reduce-initial-value` は、2つの reduce に初期値を要求しました。

```ts
const near = candidates.filter((c) => Math.abs(c.minutes - target) <= TOLERANCE);
if (near.length === 0) return null;
return near.reduce((best, c) =>
  Math.abs(c.minutes - target) < Math.abs(best.minutes - target) ? c : best
).window;                                              // ← 指摘される
```

ガードは2行上にあります。**ルールからは見えません。** そして初期値は不活性ではありません ── **畳み込みに参加します**。つまり「**最悪の候補**」を発明して種にする必要があり、そのセンチネルは、後日リストが予期しない形で空になったときに**うっかり返ってくる**類のものです。

どちらも「厳しすぎる」ではありません。**ルールとコードの形が変わらない限り、正しいコードに対して同じ指摘を出し続けます。** なので**ルール単位で off**にして、理由を書いてあります ── 呼び出し箇所ごとに50個の抑制コメントを置くのではなく。

**見分け方: このコードが、API と意味を変えずにルールを満たせるかを問う。** 唯一の道がラッパー型やセンチネル値なら、行単位の抑制は**恒久的な不一致を1箇所ではなく50箇所に隠している**だけです。

## 3. ルールは正しく、渡された型が嘘をついていた

これが一番時間がかかり、そして**私の仕事のしかたを変えました。**

`sonarjs/different-types-comparison` が、9つのガードを「常に偽」と指摘しました。この1つを含めて。

```ts
const command = process.argv[2];
if (command === undefined) {
  printHelp();   // ルールは「到達しない」と言う
  return;
}
```

**到達します。** 引数なしで CLI を起動すれば `process.argv[2]` は `undefined` です。**ルールに従っていたら、本物の分岐 ── 引数なしでヘルプを出す経路を消していました。**

では厳しすぎた？ ルールが悪い？ **どちらでもありません。**

これは `noUncheckedIndexedAccess` を入れる前の話です（**いまは on** なので、いまリポジトリを clone するとこのガードは正しく型が付き、ルールは黙ります）。当時は **off** で、それが無いと TypeScript は `process.argv[2]` を `string` と型付けします ── `string | undefined` ではなく。**ルールはコンパイラに型を尋ね、間違った答えを受け取り、そこから正しく推論して間違った結論に着いた**わけです。

フラグを入れました。9件が4件になりました。残った4件は**本当に冗長な、私が手で書いたチェック**だったので消しました。

**ルールの論理は最初から正しかった。** 間違っていたのは結論で、渡された型モデルが不完全だったからです。**この2つは別の失敗で、ルール側で直せるのは片方だけです。**

**見分け方: 偽陽性が1つの形に集まる。** うちの9件は全部インデックスアクセスでした ── `process.argv[n]`、`params[key]`、`dict[k]`、分割代入の残り。**指摘が韻を踏み始めたら**、コードに触る前にコンパイラ設定と parser services を見る価値があります。証明ではありません。**先に上流を見る理由**です。

## ここから出てくるもの

正しいと信じているコードにルールが火を吹いたとき、可能性は5つです。**「ルールが厳しすぎる」はその中にありません。**

1. **ルールの挙動を読み違えている** → 戻して数える。1分。**唯一、理屈で抜け出せない種類**
2. **正しいコードでは満たせないルール** → **ルール単位で off**、理由つき。50個の inline disable ではなく
3. **ルールが正しく、型が嘘をついている** → **設定を直す。** 他のルールもまとめて正確になる
4. **両方妥当で、単に意見が違う** → 欠陥ではなく、**設計や書き方のトレードオフ**。うちにとっては `noImplicitReturns` がこれ。記録に残して却下する
5. **ルールが正しく、コードが間違い** → 本来の目的

**確かめる順番は、3 が先です。** 直すと他のルールまで正確になるのは、これだけなので。そして**いまは、自分が書いたコメントを信じる前に 1 を確認します。**

見せていない off が他に2つあります。面白いからではなく、網羅のために書いておきます ── `sonarjs/no-selector-parameter`（唯一の本番呼び出しが boolean を計算して渡すので、関数を割っても分岐が呼び出し側に移るだけ）と、`.vue` に限った `sonarjs/no-useless-intersection`（呼び出しシグネチャだけを持つ interface を「メンバーの無い型」と誤読する）。**どちらも「2」に当たります。**「sonarjs のルールを4つ off にした」は疑って当然なので、**確かめられるように書いておきます。**

## 例外リストについて、ひとつ

コメントをくれた人が、こう書いていました。

> 理由つきで例外を設定に書くというルールは、**リポジトリで一番役に立つ監査証跡**になった。「ここではルールが間違っていた」が根拠つきで生き残る唯一の場所だから

私が書いたどの説明より的確です。私は allowlist を**例外を置く場所**として扱っていました。実際には**ルールが現実と出会った場所の記録**です。

足すとすればこれです ── 各項目に「なぜあるか」だけでなく **「いつ消せるか」** を書く。うちの2件は upstream の issue 番号を書いてあるので、issue が閉じれば項目も死にます。**allowlist が墓場からキューに変わります。**

そしてひとつ注意。これは 1 の話そのものです。

**根拠は添えられたまま生き残ります ── 書かれた日から間違っていた場合も含めて。** うちのは「2つのルールは矛盾する」でした。自信たっぷりで、具体的で、間違っていて、何週間も「誰かが意図して下した判断」の顔をして座っていました。**素の inline disable より信用していました。** そこが問題です ── **自信のある具体的な理由は、無いよりも説得力があり、そして偽であっても説得力を失いません。**

だからキューには、暗黙にもう1つ欄が要ります。なぜ・いつ、に加えて **「これが今も成り立つには、何が真であればよいか」。**

私のなら「`void-use` は `void <promise>` を報告する」でした。**そしてそれは、どの時点でも1分で確かめられました。**

---

*本当に「厳しすぎる」ルールを見つけた人がいたら聞きたいです ── 矛盾しているのでもなく、構造的に満たせないのでもなく、別の設定が抜けていたせいでもなく、ただ正しくて割に合わないもの。私は見つけられませんでした。それがリンタについての事実なのか、うちのコードベースについての事実なのかは分かっていません。*
