Claude Code などで使うスキル（`SKILL.md`）は、書いて終わりにすると、使われなかったり、使われても効いていなかったりします。本稿では、スキルを良くする方法を、Anthropic 公式の書き方の指針、公式の `skill-creator` のソース、Claude Code の文書、GEPA、2026 年の論文から集め、**手間の少ない順**に並べました。

どの方法にも、**そのまま写して使えるもの**（ひな形、Claude に渡す指示文、スクリプト、設定）を付けています。

:::message
数字はそれぞれの出典の設定での値です。自分の環境に持ち込めるのは数字ではなく、やり方と結論の向きです。スクリプトは Claude Code 2.1.292 のフラグで書いています。動かす前に `claude --help` でフラグを確かめ、問い合わせ 1 件で試してください。
:::

## 0. 先に全体像

スキルの良し悪しは、2 つで決まります。

1. **使われるか。** ほぼ `description`（説明文）だけで決まります。本文は、使うと決めてから読まれます。
2. **使われたときに効くか。** 本文で決まります。

これを直す方法を、4 つの段階に分けました。

| 段階 | かかる時間 | やること |
|---|---|---|
| 1. 読み直して直す | 30 分 | 説明文、長さ、並び順、強調の仕方、用語、スキルの数 |
| 2. 試して直す | 半日 | スキルなしで失敗させてから書く。作る係と使う係を分ける |
| 3. 測りながら回す | 1 回 1〜2 時間 | スキルあり・なしの比較、発火率の測定、使用回数の記録 |
| 4. 自動で直す | 1 日〜 | 改善の往復を自動にする |

段階 1 だけでも効果があります。段階 3 以降は、「答え合わせのできる問題」を用意できるかどうかで、やれるかどうかが決まります。

## 1. 段階 1：読み直して直す（30 分）

### 1.1 まず全スキルの長さを測る

手元のスキルの行数と説明文の長さを一覧にします。

```bash
for f in ~/.claude/skills/*/SKILL.md .claude/skills/*/SKILL.md; do
  [ -f "$f" ] || continue
  lines=$(wc -l < "$f")
  desc=$(awk '/^---$/{n++; next} n==1 && /^description:/{sub(/^description:[ ]*/,""); print; exit}' "$f")
  printf '%5d 行  説明 %4d 文字  %s\n' "$lines" "${#desc}" "$f"
done | sort -rn
```

（説明文を複数行で書いている場合は 1 行目しか数えません。）

目安は次のとおりです。

- **本文は 500 行未満**（公式の指針）
- **説明文は 1,024 文字以内**（公式の上限）。Claude Code の一覧では、説明文と `when_to_use` を合わせて 1,536 文字で切られるので、大事なことは先頭に書く

### 1.2 説明文は「いつ使うか」の条件として書く

モデルがスキルを使うかどうかは、説明文で決まります。

- **公式の指針：** 「何をするか」と「いつ使うか」の両方を入れる。悪い例は "Helps with documents"
- **Claude Code チームの記事：** 人向けの要約ではなく、**発火の条件**として書く（例：「'babysit' や 'watch CI' と言われたら使う」）
- **superpowers（公開スキル集）：** 説明文に**手順の要約を書かない**。要約があると、モデルが本文を読まずに要約どおりに動いてしまう
- **公式の `skill-creator`：** Claude はもともとスキルを使わない方に偏っているので、**少し強引なくらい**に書く

**ひな形：**

```yaml
description: >
  <何をするか、1 文>。
  ユーザーが「<言い方 1>」「<言い方 2>」と言ったとき、または <渡されるもの> が渡されたときに使う。
  <似た場面> のときは使わない（<別の道具> を使う）。
```

**直す前と後：**

```yaml
# 前
description: PR のレビューを手伝います。

# 後
description: >
  プルリクエストの差分を、チームのレビュー観点（認証・エラー処理・テスト）で確認する。
  ユーザーが「レビューして」「PR を見て」と言ったとき、またはプルリクエストの番号や URL が渡されたときに使う。
  コードの書き換えまで頼まれたときは使わない（通常の編集で行う）。
```

最後の「使わない場合」は、似たスキルとの取り違えを防ぎます（1.6 節）。

### 1.3 本文を削り、大事なことを上に置く

公式の指針は「**Claude はもともと十分に賢い**」ことを前提にしています。モデルが知っていることを書いても、文脈を使うだけです。

論文でも、短い方が効いています。[SkillsBench](https://arxiv.org/abs/2602.12670) は同じスキルを長さ 4 段階で比べ、簡潔な版で +19.0 ポイント、網羅的な版で +0.7 ポイントでした。網羅的に書くと、効果がほぼ消えます。

残すのは**モデルが知らないこと**だけです。

- チームの規約、社内のツールの使い方
- 過去につまずいた点と避け方
- 終わったと判定する条件

並び順も大事です。Claude Code では、会話が要約されたあと、各スキルは**先頭の 5,000 トークンだけ**が添付し直されます。守らせたい規則と完了の条件は、上の方に置きます。

**Claude に削らせる指示文：**

```text
次の SKILL.md を短くしてください。条件:
- Claude がすでに知っている一般的な知識や説明は消す
- 残すのは、このチーム固有の規約、ツールの使い方、過去の失敗と避け方、完了の判定条件だけ
- 完了の条件と、必ず守る規則を本文の先頭に移す
- 全部大文字の強調（ALWAYS / NEVER / MUST）は、理由を書いた文に置き換える
- 固定のパスや日付に依存する記述は、消すか条件として書き直す
- 最後に「消した内容」を一覧で示す（判断を私が確認するため）

<ここに SKILL.md を貼る>
```

最後の一覧は必ず読みます。モデルは、要約するたびに固有の知見を落とす傾向があります（[ACE](https://arxiv.org/abs/2510.04618) の言う「簡潔さへの偏り」）。消してはいけないものが消えていたら戻します。

### 1.4 本文のひな形

```markdown
---
name: review-pr
description: >
  （1.2 節のひな形で書く）
---

# PR レビュー

## 完了の条件
- 観点（認証・エラー処理・テスト）ごとに、問題の有無と根拠の行番号を書いている
- 問題がない観点も「問題なし」と書いている

## 手順
1. `gh pr diff <番号>` で差分を取る
2. 観点ごとに確認する。詳細は [reference.md](reference.md)
3. `scripts/check.sh` を実行する。失敗したら直して、通るまで再実行する

## つまずきどころ
- 生成されたファイルの差分までレビューしてしまう → `*.gen.ts` は読まない（自動生成で、手で直さないため）
```

形の決まりは次のとおりです。

- **`name` は 64 文字以内**で、小文字・数字・ハイフンだけ。`anthropic` と `claude` は使えない。`helper` や `utils` のような何でも入る名前は避ける
- **詳しい資料は別ファイル**に分け、`SKILL.md` から **1 階層だけ**参照する。参照ファイルからさらに別のファイルを参照すると、途中までしか読まれないことがある
- **100 行を超える参照ファイル**には、冒頭に目次を置く
- パスは `/` 区切りで書く

```text
review-pr/
├── SKILL.md          # 完了の条件、手順、つまずきどころ
├── reference.md      # 観点の詳細（冒頭に目次）
└── scripts/
    └── check.sh      # 検証スクリプト
```

### 1.5 強調より理由、用語はそろえる

- **全部大文字の強調より、理由を書く。** 公式の `skill-creator` は `ALWAYS` や `NEVER` を「黄色信号」と呼んでいます。理由が書いてあれば、モデルは書かれていない場面でも正しく判断できます
  - 悪い例：`NEVER edit generated files.`
  - 良い例：「`*.gen.ts` は手で直さない。次の生成で上書きされ、変更が消えるため。」
- **但し書きを付けない。** 「ただし重要な場合を除く」のような但し書きを付けると、結果が不安定になります（superpowers）。例外を書くなら、どの場合が例外かを具体的に書きます
- **1 つの概念に 1 つの語。** 「フィールド」と書いたら、「欄」「項目」と混ぜない（公式の指針）
- **時期に依存する書き方をしない。** 「2025 年 8 月までは旧 API」はいつか誤りになります。古い手順は「古いやり方」という節に分けます
- **固定パスとテンプレートを書かない。** 公開スキル 98 本を測った [SWE-Skills-Bench](https://arxiv.org/abs/2603.15401) では、有害だったスキルは、本文の固定パスやテンプレートが作業ごとの指示を上書きしていました
- **選択肢を並べすぎない。** 既定のやり方を 1 つ示し、例外のときだけ別のやり方を書きます

### 1.6 似たスキルを統合し、同時に使うのは 3 つまで

スキルは増やすほど良いわけではありません。

- [Skill Shadowing](https://arxiv.org/abs/2605.24050)：スキルを 202 個まで増やすと、性能が最大 21% 落ちた。主な原因は文脈が長くなることではなく、**別のスキルを誤って選ぶこと**
- SkillsBench：1 つの作業に渡すスキルが 2〜3 個なら +19.0 ポイント、4 個以上だと +10.1 ポイント

説明文が似ているスキルを探して、統合するか、説明文に「使わない場合」を書いて使い分けます。

**Claude に重なりを探させる指示文：**

```text
~/.claude/skills/*/SKILL.md と .claude/skills/*/SKILL.md の name と description を読んで、
説明文が似ていて取り違えが起きそうな組を挙げてください。
組ごとに「統合する」「説明文で使い分ける（それぞれに足す一文の案つき）」のどちらが良いか提案してください。
```

## 2. 段階 2：試して直す（半日）

### 2.1 先にスキルなしで失敗させる

公式の指針は「**評価を先に作る**」ことを勧めています。

1. スキルなしで、代表的な作業をさせる。失敗を記録する
2. その失敗を突く場面を 3 つ作る
3. スキルなしの出来を記録する
4. 失敗を直すのに必要な、最小限の指示だけを書く
5. スキルなしと比べながら直す

superpowers も同じ流れを、テストを先に書く開発のやり方として説明しています。コツは、スキルなしで失敗したときの**モデルの言い訳を、そのまま書き留める**ことです。言い訳の一つ一つが、スキルで塞ぐべき抜け道です。

先に失敗を見ずに書くと、モデルがもともとできることを長々と説明したスキルになります。

**場面のファイル（`evals/cases.json`）：**

```json
[
  {
    "prompt": "PR #123 をレビューして",
    "checks": [
      "認証まわりの変更について、問題の有無を書いている",
      "テストが追加されていないことを指摘している",
      "自動生成されたファイルにはコメントしていない"
    ]
  }
]
```

`checks` には、スキルなしで実際に失敗した点を書きます。どちらでも通る項目は、スキルの良し悪しを測りません（3.1 節）。

### 2.2 作る係と使う係を分ける

公式の指針は、これを「Claude A と Claude B」と呼んでいます。

- **Claude A：** スキルを作り、直すセッション
- **Claude B：** スキルを入れた**新しい**セッションで、実際の作業をさせる

スキルを作ったセッションで試すと、作ったときの文脈を覚えているので、スキルの穴が見えません。

Claude B では、次のことを観察します。

- 想定していない順に読んでいないか
- 読まれていない参照ファイルはないか
- 同じファイルを何度も読み直していないか

**Claude B に作業させたあとで聞く指示文：**

```text
いま使ったスキル <スキル名> について教えてください。
- 指示が曖昧で、どちらにするか迷った箇所
- 読まなかった参照ファイルと、読まなかった理由
- スキルに書いてあったのに守れなかったことと、その理由
- スキルに書いてあれば迷わずに済んだこと
推測ではなく、この作業で実際に起きたことだけを書いてください。
```

答えを Claude A に渡して、スキルを直します。

### 2.3 「つまずきどころ」の節に、失敗のたびに足す

Claude Code チームの記事は、スキルの中で**一番価値が高いのは「つまずきどころ」の節**だと書いています。失敗したら、その原因と避け方を 1〜2 行で足します。

**書き方：**

```markdown
## つまずきどころ
- <どんな状況で> <何をしてしまう> → <代わりにどうする>（<理由>）
```

足すときは**項目単位**で足し、全文は書き直しません。全文を書き直すたびに要約されて、細部が少しずつ失われていくからです（ACE の言う「文脈の崩壊」）。1.3 節の「削る」と矛盾するようですが、削るのはモデルが知っていること、足すのはモデルが知らないことです。

### 2.4 壊れやすい手順はスクリプトにして、検証の往復を書く

公式の指針は、作業に合わせて**自由度**を変えるよう勧めています。

| 作業 | 書き方 |
|---|---|
| 壊れやすい手順（データの移行、決まった形式のファイル生成） | スクリプトにして「`scripts/x.sh` をそのまま実行する」と書く |
| 判断が要る作業（レビュー、設計） | 方針と完了の条件だけを書く |

そして、**検証 → 直す → 再実行**の往復を手順に書きます。

```markdown
3. `scripts/validate.py output.json` を実行する
4. エラーが出たら、メッセージに従って直し、3 に戻る。エラーがなくなるまで続ける
```

検証スクリプトのエラーメッセージは具体的に書きます。「不正な入力です」ではなく、「`signature_date` という欄がありません。ある欄: `name`, `date`, `amount`」のようにします。公式の指針は、この往復で出力の質が大きく上がると書いています。

`skill-creator` には、もう一つ目安があります。試すたびにモデルが**同じ補助スクリプトを毎回書いている**なら、それを `scripts/` に入れて同梱します。

### 2.5 使う予定のモデルすべてで試す

公式の確認項目には、Haiku・Sonnet・Opus のそれぞれで試すことが入っています。上位のモデルで足りる説明が、下位のモデルでは足りないことがあります。逆に、下位のモデル向けに細かく書いた手順が、上位のモデルの判断を邪魔することもあります。

```bash
for m in haiku sonnet opus; do
  claude -p --model "$m" "PR #123 をレビューして" > "out_${m}.md"
done
```

## 3. 段階 3：測りながら回す（1 回 1〜2 時間）

### 3.1 スキルあり・なしを並べて比べる

公式の `skill-creator` は、スキルありと比較の相手（新しく作るならスキルなし、直すなら旧版）を**同じ依頼で同時に**走らせ、検証項目ごとに合否と根拠を記録し、平均と標準偏差を出しています。同じことを手元でやるスクリプトです。

`--disable-slash-commands` は、すべてのスキルを無効にするフラグです。

```bash
#!/usr/bin/env bash
# 使い方: ./compare.sh evals/cases.json 3
set -euo pipefail
cases=$1; runs=${2:-3}; out=results; mkdir -p "$out"
n=$(jq length "$cases")
for i in $(seq 0 $((n - 1))); do
  prompt=$(jq -r ".[$i].prompt" "$cases")
  for r in $(seq 1 "$runs"); do
    claude -p "$prompt" > "$out/case${i}_with_${r}.md"
    claude -p --disable-slash-commands "$prompt" > "$out/case${i}_without_${r}.md"
  done
done
```

注意が 2 つあります。

- ファイルを書き換える作業なら、使い捨てのブランチか複製したディレクトリで走らせます
- 道具の許可が必要な作業では、`--allowedTools` で必要な道具だけを許可します

**採点させる指示文：**

```text
次の「依頼」に対する「回答」を、「検証項目」ごとに判定してください。
各項目について、合否（合格 / 不合格）と、回答の中の根拠（引用）を 1 行で書いてください。
根拠が引用できない場合は不合格にしてください。

依頼: <prompt>
検証項目:
<checks を 1 行ずつ>
回答:
<results/caseN_with_R.md の中身>
```

結果を表にして、次の 3 つを見ます。

1. **スキルありの方が合格が多いか。** 差がなければ、そのスキルは効いていません
2. **どちらでも合格する検証項目はないか。** スキルの良し悪しを測っていないので、消すか、差が出るように書き直します（`skill-creator` の分析係も、これを指摘します）
3. **同じ条件の 3 回で結果がばらついていないか。** ばらつきより小さい差は、差とみなしません

**採点を機械でできる項目は機械で。** 「`scripts/check.sh` が通る」「出力が JSON として読める」「特定の語を含まない」のように、プログラムで判定できる項目はプログラムで判定します。AI に判定させるのは、判断が必要な項目だけにします。

### 3.2 発火率を測って、説明文を直す

スキルの中身が良くても、使われなければ意味がありません。公式の `skill-creator` の `scripts/run_loop.py` は、次の手順で説明文を自動で直しています。

1. 問い合わせを 20 件作る。**使うべきもの**と**使うべきでないもの**を約半分ずつ
2. 6 対 4 で、直すための組と、確かめるための組に分ける
3. 各問い合わせを 3 回走らせ、半分以上で使われれば合格
4. 失敗した問い合わせと過去の案を見せて、新しい説明文を書かせる
5. 最大 5 回繰り返し、**確かめるための組の点数**で最良の案を選ぶ

直すための組の点数で選ぶと、その 12 件にだけ合わせた説明文になります。確かめるための組で選ぶのは、そのためです。

**問い合わせの作り方：**

- 使うべきもの：言い方を変える（「レビューして」「PR 見て」「#123 どう？」）。丁寧な言い方と雑な言い方を混ぜる
- 使うべきでないもの：**関連はあるが別の道具を使うべき「際どい」もの**にする（「PR を作って」「このコードを直して」）。まったく無関係な問い合わせは、測っても意味がありません
- 1 手で終わる単純な依頼は入れない。説明文に関係なく、スキルを使わずに済ませてしまうからです

**問い合わせのファイル（`evals/trigger.tsv`、1 列目が期待、2 列目が問い合わせ）：**

```text
yes	PR #123 をレビューして
yes	このプルリクどう思う？ https://github.com/org/repo/pull/45
no	いまの変更で PR を作って
no	この関数のバグを直して
```

**測るスクリプト：**

```bash
#!/usr/bin/env bash
# 使い方: ./trigger.sh review-pr evals/trigger.tsv
set -uo pipefail
skill=$1; file=$2; runs=3; ok=0; total=0
while IFS=$'\t' read -r expect prompt; do
  hits=0
  for r in $(seq 1 "$runs"); do
    if claude -p --output-format stream-json --verbose --max-turns 3 "$prompt" \
      | jq -c --arg s "$skill" 'select(.type=="assistant") | .message.content[]?
          | select(.type=="tool_use" and .name=="Skill" and ((.input.skill // "") | endswith($s)))' \
      | grep -q .; then hits=$((hits + 1)); fi
  done
  fired=no; [ $((hits * 2)) -ge "$runs" ] && fired=yes
  total=$((total + 1)); [ "$fired" = "$expect" ] && ok=$((ok + 1))
  printf '%s\t期待=%s\t発火=%d/%d\t%s\n' "$([ "$fired" = "$expect" ] && echo OK || echo NG)" "$expect" "$hits" "$runs" "$prompt"
done < "$file"
echo "正解 $ok / $total"
```

出力の形は版によって変わることがあります。動かなければ、1 件だけ `--output-format stream-json --verbose` の出力を見て、スキルを呼んだ行の形を確かめてください。

**NG になったものを Claude に渡して、説明文を直させる指示文：**

```text
スキル <スキル名> の説明文を書き直してください。
いまの説明文: <description>
使うべきなのに使われなかった問い合わせ: <一覧>
使うべきでないのに使われた問い合わせ: <一覧>
条件:
- 1,024 文字以内。何をするか、いつ使うか、使わない場合を書く
- 手順の要約は書かない
- 特定の問い合わせの言い回しをそのまま並べるのではなく、共通する条件として書く
- いまの説明文とは構造の違う案を 3 つ出す
```

3 つの案をそれぞれ確かめるための組で測り、一番良いものを採用します。

### 3.3 使用回数を記録して、使われないスキルを見つける

Claude Code チームは、`PreToolUse` フックでスキルが使われるたびに記録し、発火が足りないスキルを見つけています。同じことをする設定です（`~/.claude/settings.json`）。

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Skill",
        "hooks": [
          {
            "type": "command",
            "command": "jq -c '{ts: (now | todate), skill: .tool_input.skill, cwd: .cwd}' >> ~/.claude/skill-usage.jsonl"
          }
        ]
      }
    ]
  }
}
```

1〜2 週間たったら集計します。

```bash
jq -r .skill ~/.claude/skill-usage.jsonl | sort | uniq -c | sort -rn
```

一度も使われていないスキルは、説明文が悪いか、そもそも要らないかのどちらかです。前者なら 3.2 節で直し、後者なら消します（1.6 節のとおり、要らないスキルは他のスキルの取り違えを増やします）。

Claude Code には、ほかにも測る道具があります。

| 道具 | 分かること |
|---|---|
| `/skill-doctor` | 各スキルが文脈をどれだけ使っているか、どれだけ使われているか |
| `claude plugin eval` | プラグインのスキルあり・なしの比較と、発火率。閾値を下回ると失敗で終わるので、CI に入れられる |
| `claude plugin validate` | 先頭の設定欄が壊れていないか |

## 4. 段階 4：自動で直す（1 日〜）

### 4.1 改善の往復を自動にするときの作法

段階 3 の「測る → 直す → 測る」を自動で回すと、スキルは勝手に良くなっていきそうに見えます。しかし、そのまま回すと効きません。

- [BiPA](https://arxiv.org/abs/2610.37201)：汎用の最適化器で直したスキルは、手書きの初期版と比べて平均 +0.1 ポイントしか変わらず、試験用のデータでは差が消え、入力トークンは約 16% 増えた
- SkillsBench：モデルに一から書かせたスキルは、スキルなしより悪くなった

効いた例は、**直し方に縛りを入れて**います。[SkillOpt](https://arxiv.org/abs/2605.23904) の作法は次のとおりです。

- 編集は**部分的な追加・置換・削除**に限る。全文を書き直さない
- 1 回に入れる編集の数に**上限**を設ける（論文では 4 件が最良）
- 確かめるための組の点数が**厳密に上がったときだけ**採用する。同点は却下する
- **却下した編集を記録**して、同じ案を繰り返し出さないようにする

この作法で、人が書いたスキルより平均 +5.4 ポイント良くなったと報告しています。

**半自動で回すときの指示文：**

```text
スキル <スキル名> を改善する編集案を出してください。
材料:
- いまの SKILL.md: <本文>
- 失敗した場面と、採点の理由: <3.1 節の不合格の一覧>
- これまでに却下した編集: <一覧>
条件:
- 編集は「追加」「置換」「削除」のどれかで、1 件ずつ、対象の行を示して書く
- 編集は最大 4 件
- 失敗をまず種類ごとに分け、一番多い種類から直す
- 却下した編集と同じものは出さない
- 本文の全体を書き直さない
```

編集を当てたら、3.1 節のスクリプトで測り直します。**確かめるための組で点数が上がったときだけ**採用し、上がらなければ却下の一覧に足します。データは、直すための組、確かめるための組、最後まで使わない試験用の組の 3 つに分け、最後に試験用の組で差が残ることを確かめます。

### 4.2 GEPA に任せる

[GEPA](https://gepa.dev) は、実行の記録と採点の理由を読ませて文章を書き直させ、問題ごとに最高点を取った案を残しながら進化させる最適化器です。その仕組みを `SKILL.md` に当てたのが [gskill](https://gepa.dev/blog/2026/02/18/automatically-learning-skills-for-coding-agents) です。答え合わせのできるコーディングの課題を自動で作り、課題を解かせて、その結果からスキルを書き直します。

報告では、Bleve というリポジトリで解決率が 24% から 93% に上がりました。最適化に使ったのは別のエージェントですが、できたスキルを Claude Code（Haiku 4.5）に移しても、解決率が上がり、作業時間も短くなっています。

```bash
pip install "gepa[gskill]"   # Docker も必要
```

前提として、**答え合わせのできる課題**が数百件必要です（ガイドの例では、直すための組 200 件、確かめるための組 50 件、試験用 100 件）。採点の関数は、点数に加えて**理由の文章**を返すようにします。GEPA は、その理由を読んで書き直すからです。手順は [gskill のガイド](https://gepa.dev/guides/gskill) にあります。

コーディング以外の業務では課題を自動で作れないので、3.1 節の場面のファイルを増やしていくところから始めます。

## 5. 出典どうしの食い違い

調べた範囲では、次の点で出典の言っていることが違いました。

| 論点 | 言っていること |
|---|---|
| 説明文の書き方 | 公式の指針は「三人称で書く」。`skill-creator` の自動改善は命令形（"Use this skill for…"）で書かせる。superpowers は「いつ使うかだけを書く」 |
| 強調の仕方 | 公式の指針には `MUST` で守られるようになった例がある。`skill-creator` は全部大文字を避けるよう勧める |
| スキルの数 | SkillsBench の数字は論文の版ごとに違う。本稿の数字は最新版の付録の値 |

説明文の書き方は決着していないので、**3.2 節で自分の環境の発火率を測って決める**のが確実です。

## まとめ

- スキルの良し悪しは、**使われるか**（説明文）と、**使われたときに効くか**（本文）の 2 つで決まります。
- 説明文は、人向けの要約ではなく発火の条件として書きます。使わない場合も書き、手順の要約は書きません。
- 本文は短く。モデルが知らないこと（規約、つまずきどころ、完了の条件）だけを残し、大事なことを上に置きます。
- 書く前にスキルなしで失敗させ、作ったのとは別のセッションで試します。
- 測るときは、スキルあり・なしを対で比べ、どちらでも通る検証項目を捨て、確かめるための組の点数で選びます。
- 自動で直すなら、部分的な編集に限り、点数が厳密に上がったときだけ採用します。測れていない改善は、改善ではありません。
