スキル（`SKILL.md`）を自動で直す手法は、2026 年に入って一気に増えました。どれも「実行して、失敗を見て、直す」と説明されますが、**1 回の改善で具体的に何をしているか**は手法ごとにかなり違います。その違いが、どの場面に向くかを決めています。

本稿では、論文の本文と公開されているソースを読み、各手法を次の観点で分解しました。

- 何が要るか（正解、採点関数、実行記録）
- 1 回の改善で何をするか
- 直した案をどう採用するか
- どれくらい費用がかかるか
- 何が報告されているか
- どう使うか
- 弱点

:::message
数字はそれぞれの論文の設定での値です。論文はどれも提案者自身が書いたもので、比較相手も提案者が動かしています（一部は他の論文からの転記です。本文で明記します）。第三者による検証は、本稿で扱う中では BiPA だけで、その結論は否定的です。
:::

## 1. 先に全体像

### 1.1 直したいものごとの地図

| 直したいもの | 手法 | 正解は要るか |
|---|---|---|
| 発火しない・誤って発火する（説明文） | skill-creator の `run_loop.py`、SkillReducer の段階 1 | 「使うべきか」の真偽だけ |
| 長すぎる | SkillReducer | 不要（元のスキルの出来が基準） |
| 失敗する（自動で採点できる） | SkillOpt、SkillAdam、SkillGrad、GEPA（gskill）、Trace2Skill、EvoSkill | 要る |
| 失敗する（正解がない） | SSO、skill-creator の比較判定 | 不要（2 つを比べる） |
| モデルの重みも一緒に育てる | SkillRL | 環境の報酬 |

### 1.2 共通の骨格と、違いが出る 4 つの部品

ほぼすべての手法は、次の往復を回しています。

1. 今のスキルで課題を実行し、採点する
2. 実行の記録を読み、何が悪かったかを診断する
3. スキルを編集して、候補を作る
4. 候補を採用するか決める

違いが出るのは、次の 4 つの部品です。

| 部品 | 選択肢 |
|---|---|
| 診断の材料 | 失敗だけ／失敗と成功の両方／同じ課題の失敗と成功の対／2 つの結果の比較 |
| 編集の単位 | 全文を書き直す／部分的な追加・置換・削除／項目単位の追記 |
| 採否の判定 | なし（全部適用）／同じ小バッチで比べる／別の検証用データで比べる／検証で繰り返し勝つ |
| 記憶 | なし／却下した編集の記録／繰り返し出る問題の蓄積 |

この表を頭に置くと、各手法の性格がすぐ分かります。たとえば SkillOpt は「失敗と成功の両方、部分編集、別の検証用データで厳密に上回る、却下の記録」、SkillGrad は「失敗と対、部分編集、採否判定なし、問題の蓄積」です。

### 1.3 結論を先に

- **自動で採点できて、データが数百件ある**なら、SkillOpt の作法（部分編集、編集数の上限、別の検証用データで厳密に上回ったときだけ採用）が、いま一番裏付けのある形です。
- **正解がない**なら、SSO の「2 つの結果を比べさせ、違いを振る舞いとして抜き出す」やり方が使えます。
- **使われない**なら、まず skill-creator の `run_loop.py` で説明文だけを直します。
- **長い**なら、SkillReducer の「種類ごとに圧縮し、課題で確かめる」やり方で縮めます。
- ただし、**良い手書きのスキルから始めた長い課題**では、汎用の最適化器の改善は偶然の揺れで説明できてしまい、費用だけが増えた、という第三者の検証があります（BiPA、9 章）。

## 2. 発火を直す：skill-creator の `run_loop.py`

Anthropic 公式の [`skill-creator`](https://github.com/anthropics/skills/tree/main/skills/skill-creator) には、説明文（`description`）を自動で直す仕組みが入っています。**自動で回るのは説明文だけ**で、本文は人が確認しながら直す流れになっています（2.3 節）。

### 2.1 要るもの

`[{"query": "...", "should_trigger": true}, ...]` の形の質問集です。

- 推奨は 20 問で、使うべきもの 8〜10 問、使うべきでないもの 8〜10 問
- 使うべきでないものは、**関連はあるが別の道具を使うべき紛らわしいもの**にする。明らかに無関係な質問は試験にならない
- 質問集は、付属の HTML 画面で人が見直す

### 2.2 1 回の改善で何をするか（ソースどおり）

1. **分ける。** 使うべき・使うべきでないの層ごとにシャッフルし（乱数の種は 42）、4 割を「テスト用」に回す
2. **実行する。** 全部の質問を、それぞれ 3 回、10 並列で実行する。1 回の中身は次のとおり
   - 説明文を書いた一時ファイルを `.claude/commands/` に作る
   - `claude -p <質問> --output-format stream-json --verbose --include-partial-messages` を起動する
   - **最初の道具呼び出しが `Skill` か `Read` で、入力に一時ファイルの名前が含まれていれば発火**とみなす。別の道具が先に来たら不発。時間切れは 30 秒
   - 使うべき質問は、3 回中の発火率が 0.5 以上で合格。使うべきでない質問は 0.5 未満で合格
3. **終わるか決める。** 学習用の質問が全部合格するか、5 回目に達したら終わる
4. **書き直させる。** `claude -p` に新しい説明文を書かせる。指示の要旨は次のとおり
   - 「発火しなかった質問」と「誤って発火した質問」を、発火回数付きで並べる
   - 過去の試行を全部見せ、「繰り返すな、構造ごと変えてみよ」と指示する
   - 「個別の質問を並べて増やすのではなく、利用者の意図の類型に一般化せよ」
   - 100〜200 語程度。1,024 文字が絶対の上限。超えたら 1 回だけ短く書き直させる
   - 命令形で書く（"Use this skill for…"）。他のスキルと見分けがつくように書く
   - **過去の試行の記録から、テスト用の得点は消してある**。書き直す役は、テストの結果を見られない
5. **選ぶ。** 終了後、**テスト用の合格数が一番多い回の説明文**を返す

費用は、20 問 × 3 回で 1 回あたり 60 回の `claude -p`、最大 5 回で 300 回です。

```bash
python -m scripts.run_loop --eval-set trigger-eval.json --skill-path path/to/skill \
  --model <今のセッションのモデル ID> --max-iterations 5 --verbose
```

ほかに `--holdout 0.4`、`--runs-per-query 3`、`--trigger-threshold 0.5`、`--num-workers 10`、`--timeout 30` を変えられます。

**注意点：**

- 「テスト用」は毎回評価され、最良の回を選ぶのにも使われます。実質は検証用で、**完全に手つかずの評価用データは残りません**
- スキルではなくコマンドファイルとして一時登録して確かめているので、本物のスキルの発火と完全に同じとは限りません
- 最初の道具呼び出しだけで判定するので、他の道具を使った後にスキルを読んだ場合は不発と数えます
- 1 手で終わる単純な質問は、説明文が良くても発火しにくい（Claude が自力で済ませる）と、`skill-creator` 自身が注意しています

### 2.3 本文の評価の流れ（人が確認しながら回す）

本文の改善は自動ではありませんが、評価の段取りがよくできています。

1. 試験用の依頼ごとに、「スキルあり」と「基準」（新規作成ならスキルなし、改良なら元のスキルの写し）の下請けエージェントを**同じターンで同時に**起動する
2. 採点役（`agents/grader.md`）が、確認項目ごとに `text`・`passed`・`evidence` を書く。採点役には「弱い確認項目に合格を付けるのは無意味どころか有害。確認項目そのものも批評せよ」と指示してある。機械的に確かめられる項目は、スクリプトで判定させる
3. `aggregate_benchmark` で、合格率・所要時間・トークンの平均と標準偏差、差を出す
4. 分析役（`agents/analyzer.md`）が、**スキルの有無にかかわらず常に合格する項目**や、ばらつきの大きい項目を指摘する
5. 閲覧画面で人が出力を見てコメントし、それをもとに直す
6. 2 つの版を厳密に比べたいときは、どちらの出力か知らせずに比べる判定役（`agents/comparator.md`）を使う

直すときの指針は、「個別の例に合わせた修正をしない」「効いていない部分は削る」「`ALWAYS` や `NEVER` を並べず理由を書く」「複数の試験で同じ補助スクリプトが書かれていたら同梱する」です。

## 3. 長さを直す：SkillReducer

[SkillReducer](https://arxiv.org/abs/2603.29919)（Gao ほか）は、スキルを**縮める**ことに特化した手法です。正解は要りません。元のスキルを使ったときの出来を基準にします。

### 3.1 段階 1：説明文を縮める

1. LLM が説明文を意味の単位に区切る
2. **差分デバッグ**で、発火の判定を保てる最小の単位の組を探す。判定には模擬の判定役を使い、対象のスキルと、紛らわしい他のスキル（TF-IDF で選んだ 4 つと、LLM が作った 1 つ）を並べて、正しく選ばれるかを見る
3. 残った単位を短く言い換えて、文に整える
4. 実際の Claude Code で発火を確かめる。発火率が下がったら、削った単位を戻す（最大 3 回）。それでもだめなら元の説明文に戻す
5. 説明文がない、または 40 トークン以下なら、本文から「主な能力・発火条件・固有の識別子」を抜き出して説明文を作る

### 3.2 段階 2：本文を組み直す

1. 本文を段落に切り、LLM が「中核の規則／背景／例／ひな形／重複」の 5 種類に分ける
2. 種類ごとに縮める
   - 規則：似たものを統合し、元より必ず短い箇条書きにする
   - 例：概念ごとに代表 1 つだけ残す
   - 背景：数値・閾値・接続先などの事実を残して要約する
3. 本文と重複する参照ファイルの部分を除く。残った参照ファイルには「いつ読むか」と話題の語を 3〜5 個付ける
4. **関門 1（内容）：** 操作に必要な概念が、本文か参照ファイルのどこかに全部残っているか確かめる。欠けた種類は戻す
5. **関門 2（課題）：** 自動で作った 5 件の課題を、「スキルなし」「元のスキル」「縮めた版」の 3 条件で解かせる。縮めた版が元より悪い課題があれば、落ちた項目に関係する内容を中核の規則に格上げして縮め直す（最大 2 回）

### 3.3 結果と注意

- 費用：スキル 1 つにつき LLM 呼び出し約 20〜40 回。600 スキルで 14〜18 ドル（安いモデルを使った場合）
- 説明文は平均 48% 減、本文は平均 39% 減
- 600 スキル × 5 課題で、86% の課題が「縮めた版の得点 ≥ 元の得点」。25% は改善、14% は悪化
- 縮めた版の方が全体として良かった（0.742 対 0.722）
- GitHub から集めた 55,315 個のスキルを調べると、26% は説明文がなく、本文の 6 割以上は手順として実行できない内容（背景 41%、例 13%、ひな形 8%）だった

**注意：** 関門 2 は改善の手がかりでもあり評価基準でもあるので、86% は自己採点に近い数字です（論文も認めています）。例が暗黙の規則になっている場合は、分類で取りこぼします。コードは採択後に公開とされています。

## 4. 失敗を直す（自動で採点できるとき）

### 4.1 SkillOpt：部分編集、編集数の上限、厳密な採用

[SkillOpt](https://arxiv.org/abs/2605.23904)（Yang ほか、Microsoft）は、いま一番作法が整っている手法です。

**要るもの：**

- 自動で採点できる課題（正誤判定、完全一致、実行して確かめる検査など）
- データを 3 つに分ける：学習用（編集の根拠）、選択用（採否の判定）、テスト用（最後の評価だけ）。既定の比率は 2:1:7
- 重みを変えない対象モデルと、別の「最適化役」のモデル

**1 回の改善で何をするか：**

1. **実行。** 学習用から 1 バッチ（既定 40 件）を今のスキルで実行し、採点済みの記録を集める
2. **分ける。** 失敗と成功に分け、それぞれ 8 件ずつの小バッチにする
3. **振り返る。** 最適化役に小バッチを 1 つずつ渡す
   - 失敗用の指示の要旨：「小バッチ全体に共通する失敗の型を見つけて分類せよ。個別の例外ではなく型に効く、一般化できる編集を提案せよ。編集数の上限を守れ」
   - 成功用の指示の要旨：「複数の記録に共通して効いている振る舞いを見つけ、既存の節を補強せよ。重複させるな」
   - 出力は JSON の編集で、種類は追加・削除・置換の 3 つ
4. **まとめる。** 失敗由来と成功由来の編集を別々にまとめ、重複を除き、各編集が何件の例に支えられているかを見積もる。最後に合わせ、失敗の修正を優先する
5. **文章の学習率。** 期待効果の順に並べ、**上位 4 件（既定）だけ**を適用する。上限は、定数・線形・余弦などの予定表で動かせる
6. **採否。** 候補を選択用データで評価し、**今の得点を厳密に上回ったときだけ採用**する。同点は不採用
7. **却下の記録。** 落ちた編集と、そのとき見えた失敗の型を記録し、次の振り返りに渡す
8. **周回ごとの見直し。** 1 周回ごとに、前の周回のスキルと今のスキルで同じ課題を実行し、「良くなった・悪くなった・ずっと失敗・ずっと成功」に分ける。そこから長い目で見た指針を、保護された区画に書く。これも採否判定を通す
9. **最適化役の手引き。** どの編集の型が効いたかを要約し、以後の最適化役の指示の先頭に付ける。配布するスキルには含めない

**結果（GPT-5.5、ツールなしの対話、テスト用データ、%）：**

| 課題 | スキルなし | 人が書いた | LLM が一度で書いた | Trace2Skill | TextGrad | GEPA | SkillOpt |
|---|---|---|---|---|---|---|---|
| SearchQA | 77.7 | 81.8 | 80.9 | 82.4 | 81.4 | 84.8 | **87.3** |
| SpreadsheetBench | 41.8 | 72.9 | 43.2 | 49.6 | 41.1 | 73.6 | **80.7** |
| OfficeQA | 33.1 | 66.9 | 51.7 | 65.7 | 42.0 | 63.9 | **72.1** |
| DocVQA | 78.8 | 90.1 | 89.6 | 90.6 | 87.2 | 89.1 | **91.2** |
| LiveMath | 37.6 | 38.4 | 40.0 | 52.0 | 49.2 | 43.2 | **66.9** |
| ALFWorld | 83.6 | 91.8 | 93.3 | 87.3 | 82.8 | 85.8 | **95.5** |

- 平均は 58.8 → 82.3。課題ごとに一番良い比較相手の平均（76.9）より +5.4
- Codex 上で +24.8、Claude Code 上で +19.1（GPT-5.5、5 課題）
- Codex で学習したスキルを Claude Code で使うと、SpreadsheetBench が 22.1 → 81.8
- 部品を外した実験：却下の記録を外すと 1.6〜4.6 点下がる。編集数の上限を外して全面的に書き直させると、3 課題すべてで下がる

**費用：** 標準は 4 周回、バッチ 40 件。学習のトークン総量は課題によって 2 千万〜2 億程度。最終的なスキルは 379〜1,995 トークンでした。

**使い方：**

```bash
pip install skillopt
python scripts/train.py --config configs/searchqa/default.yaml --out_root outputs/searchqa_first_run
```

設定の主な項目は `train.num_epochs: 4`、`train.batch_size: 40`、`optimizer.learning_rate: 4`、`evaluation.use_gate: true` です。実行先として `claude_code_exec` と `codex_exec` が用意されています。手元のエージェントの過去の作業記録から夜間にスキルを鍛える `skillopt-sleep` もあります。

**弱点：** 採点器が必須です。選択用データが小さいと、偶然の上振れを採用してしまいます（9 章）。

### 4.2 SkillAdam：問題の記録帳と、揺れに応じた編集量

[SkillAdam](https://arxiv.org/abs/2609.08944)（Li ほか）は、最適化手法の Adam に倣った手法です。

**1 回の改善で何をするか：**

1. 小バッチを今のスキルで実行して採点する
2. **課題の記録帳（Adam の 1 次モーメントに当たる）を更新する。** 項目は「誤りの型・その現状・試した解決策と結果」。LLM が実行結果を見て、既存の項目に結びつけるか、新しく作る
3. **候補を作る。** 今のスキル、記録、採点、記録帳、編集数の上限から、LLM が変更を作る
4. **同じ小バッチで候補を評価する**
5. **採否。** 主な指標か補助の指標が閾値を超えて改善し、守るべき指標が許容範囲内なら採用。**別の検証用データは使わない**
6. **編集量を変える（Adam の 2 次モーメントに当たる）。** 事例ごとの改善量のばらつきを指数移動平均で追い、**結果の揺れが大きいほど、次の編集を小さくする**

**結果：**

- 長い計画の課題（DeepPlanning、Claude Sonnet 4.5）で、SkillOpt の平均 21.7 に対して 28.3。入力トークンは 67% 減、API 呼び出しは 69% 減
- 短い課題 5 種では SkillOpt との差は 0〜1.1 点。**比較相手の数値は SkillOpt の論文からの転記**です
- 記録帳と編集量の調整を順に外すと、28.3 → 21.7 → 19.2

**使い方：** `github.com/ruc-datalab/SkillAdam`。Claude Code 向けには `./integrations/claude-code/install.sh` を実行します。既存のエージェントのログイン状態をそのまま使います。

**弱点：** 同じ小バッチで比べて採用するので、過剰適合しやすい作りです。BiPA は、小さいバッチで得点を積み上げる方式は偶然の勝ちを積み上げやすいと指摘しています。

### 4.3 SkillGrad：繰り返し出る問題をためてから直す

[SkillGrad](https://arxiv.org/abs/2605.27760)（Wang ほか）は、勾配降下法の「慣性」に当たる仕組みを持つ手法です。スキルを 3 層（L1：名前などの見出し、L2：`SKILL.md` 本文、L3：必要なときだけ読む参照ファイル）で扱います。

**1 回の改善で何をするか（10 回、小バッチ 4 件）：**

1. 今のスキルで 4 件を実行する
2. **証拠を集める。** 失敗した記録と採点を集める。さらに、最初は失敗したが今回成功した課題について、失敗と成功の記録を対にする
3. **診断する**
   - 失敗の診断役は、誤りの型に 3〜6 語の名前を付けて説明する。「スキル文書の変更を指示するな」と指示されている
   - 対の診断役は、同じ課題の失敗と成功を比べ、何が変わったか、その成功は安定しているかを判断する
4. **ためる。** 周回をまたいで、繰り返し出てくる失敗の仕組みを「パターン記録」に積み上げる
5. **直す。** パターン記録と今回の診断から、型に対して編集する。内容を L2 に置くか L3 に置くかも決める

**検証による採否判定はありません**（費用と待ち時間のため、と論文に明記）。10 回目のスキルをそのまま最終版にします。

**結果：** SpreadsheetBench で、GPT-5.4 は 55.8 → 71.1、GPT-4.1 は 36.7 → 54.2。学習に使っていない WikiTQ でも伸びています。最も強い比較相手より平均 +6.7。慣性を外すと 72.5 → 65.8。費用は GPT-5.4 で 1 回の学習あたり約 6.4 ドルです。

**弱点：** 採否判定がないので、悪化した更新も残ります。学習課題を「初期スキルが失敗したもの」から選んでいるので、伸びが大きく見えやすい設定です。

### 4.4 GEPA と gskill：振り返りと、問題ごとの最良を残す

[GEPA](https://arxiv.org/abs/2507.19457)（Agrawal ほか）は、スキル専用ではない汎用の文章最適化器です。

**1 回の改善で何をするか：**

1. 候補の集団から、**検証用の課題 1 件ごとに最良の候補**を集め（パレート前線）、そこから親を選ぶ
2. 学習用から小バッチ（既定 3 件）を実行し、実行記録と診断情報（エラー、落ちたテストの出力など）を集める
3. 振り返り役に新しい指示文を書かせる。既定の指示の要旨は「入力・応答・改善の指摘の例を見て、新しい指示を書け。分野特有の事実をすべて指示に含めよ。一般化できる戦略があれば含めよ」
4. 小バッチで親より良ければ、検証用データ全体で評価して集団に加える
5. 予算を使い切ったら、検証用データの平均が最大の候補を返す

平均で 1 つに絞らず、**特定の課題に強い候補も残す**のが特徴です。

**gskill：** これを `SKILL.md` に当てたものです。SWE-smith で、対象のリポジトリの実際のコミットにバグを埋め込んだ課題を約 300 件作り、学習・検証・テストに分けます。mini-swe-agent（gpt-5-mini）の解決率が、Jinja で 55% → 82%、Bleve で 24% → 93% に上がりました。学習したスキルを Claude Code に置くと、Bleve で Haiku 4.5 が 79.3% → 98.3% でした（公式ブログの本文は 100% と書いていて、図と食い違っています）。

**使い方：**

```bash
pip install gepa
```

```python
import gepa.optimize_anything as oa
from gepa.optimize_anything import optimize_anything, GEPAConfig, EngineConfig

def evaluate(candidate: str) -> float:
    result = run_my_system(candidate)      # スキルを入れて課題を実行する自分の関数
    oa.log(f"Error: {result.error}")       # 振り返り役に渡る診断情報
    return result.score

result = optimize_anything(
    seed_candidate="<初期スキル>",
    evaluator=evaluate,
    objective="...",
    config=GEPAConfig(engine=EngineConfig(max_metric_calls=100)),
)
```

データを使う場合、評価関数は `(candidate, example) -> (score, side_info)` の形にし、**第 2 引数の名前は必ず `example`** にします。DSPy からは `dspy.GEPA(metric=..., max_metric_calls=..., reflection_lm=...)` で使えます。

**弱点：** スキル特有の構造（説明文と本文、必要時だけ読む参照ファイル）を考えません。振り返りの指示が「事実をすべて含めよ」なので、文章が膨らみやすい作りです。

### 4.5 Trace2Skill：大量の実行記録から一括で抜き出す

[Trace2Skill](https://arxiv.org/abs/2603.25158)（Ni ほか、Qwen）は、正誤の付いた大量の実行記録から、教訓を並列に抜き出してスキルにまとめます。

1. 初期スキルで課題を実行する
2. 失敗の分析役と成功の分析役が、別々に記録を調べて編集を提案する（128 並列）。失敗の分析役は、成果物を実際に確かめて原因を検証する
3. 32 個ずつ階層的にまとめる。まとめるたびに重複を除き、**複数の独立した記録に繰り返し現れる型**を優先する
4. まとめた編集を**全部適用する**（採否判定なし）

小さいモデル（Qwen3.5-35B）の記録から作ったスキルで、大きいモデル（122B）が学習に使っていない WikiTQ で大きく伸びたと報告しています。逐次に直す方式より約 20 倍速い一方、採否判定がない点が弱点です。

### 4.6 EvoSkill：スキルを足していく

[EvoSkill](https://arxiv.org/abs/2603.02766)（Alzubi ほか）は、既存のスキルを直すだけでなく、**新しいスキルを作る**こともあります。

1. 上位の候補集団（既定 3 つ）から親を選ぶ
2. 閾値以下の失敗を集め、提案役が不足を診断し、スキルの新規作成か修正を提案する
3. スキル作成役が、`SKILL.md`・補助スクリプト・見出しを備えたフォルダとして作る
4. 検証用データで評価し、集団の最下位より良ければ入れ替える。候補は git のブランチで管理する

Claude Code ＋ Opus 4.5 で、OfficeQA が 60.6 → 67.9、SealQA が 26.6 → 38.7。`evoskill init` → `evoskill run` → `evoskill eval` で使えます。各設定 1 回しか実行していない点に注意が必要です。

## 5. 正解なしで直す：SSO

[Self-Supervised Skill Optimization](https://arxiv.org/abs/2607.28777)（Peng ほか）は、**正解も得点も使わずに**スキルを直します。要るのは課題の入力と、判定役の LLM だけです。

**1 回の改善で何をするか：**

1. 今のスキルで学習用の小バッチ（20〜40 件）を実行する。これが比較の基準
2. **試作版を作る。** 直近の「課題と実行結果」8 組を見せて、スキル全文の試作版を 3 本作らせ、同じ小バッチで実行する
3. **1 対 1 で比べる。** 判定役が、各課題で試作版と基準のどちらが良いかを +1・0・−1 で付ける。提示順は無作為に入れ替える
4. **振る舞いを抜き出す。** 別の LLM が、**判定結果を見ないで**、2 つの実行の観察できる違い（例：「書き込み前に範囲を確かめた」）を書き出す
5. **まとめる。** 意味が同じ振る舞いを 1 つにまとめる
6. **証拠を数える。** 振る舞いごとに「判定 × その振る舞いの有無の差」を集計し、証拠の多い上位 4 個を採る
7. **書き起こす。** 上位の振る舞いから、新しいスキル全文を書く
8. **検証する。** 検証用の小バッチで、今のスキルと新しいスキルを判定役に比べさせ、**勝ち数が負け数を上回ったときだけ採用**する

試作版をそのまま採用せず、**試作版との違いから効いた振る舞いを抜き出して書き直す**のが要点です。試作版をそのまま選ぶ方式にすると、平均 8.5 点下がりました。

**結果（GPT-5.5）：** 6 課題の平均がスキルなし 58.8 → 79.2。正解を使う SkillOpt（82.3）の改善幅の 87% を、正解なしで回収しました（SkillOpt の数値は転記）。自由回答の課題でも、スキルなしに対して勝率 62% でした。

**弱点：** 判定役の好み（長い答えを好む、など）がそのままスキルに入ります。検証も同じ判定役なので、偏りを打ち消す仕組みがありません。公開コードは見当たりませんが、5 つの役割はどれも LLM 呼び出し 1 回で書けるので、再実装は容易です。

## 6. 重みも一緒に育てる：SkillRL

[SkillRL](https://arxiv.org/abs/2602.08234)（Xia ほか）は、スキル集とモデルの重みを一緒に育てます。

1. 教師役の強い LLM が、成功した記録から戦略を、失敗した記録から教訓を抜き出し、「汎用」と「課題別」の 2 層のスキル集にする
2. 課題に合うスキルを、意味の近さで取り出す
3. スキルの使い方を教師ありで学習させる
4. 強化学習（GRPO）の途中で、検証で失敗が出たらスキル集を更新する

ALFWorld で 89.9（GRPO だけでは 77.6）。ただし重みを学習させるので、API 経由のモデルには使えません。H100 × 8 で約 30 時間かかります。

## 7. プロンプト最適化の手法（スキルにも当てられる）

スキル専用の手法の多くは、これらの考え方を受け継いでいます。

| 手法 | 1 回の改善で何をするか | 使い方 |
|---|---|---|
| [ACE](https://arxiv.org/abs/2510.04618) | 生成役が解き、振り返り役が教訓を抜き出して既存の項目に「役立った・有害」の印を付け、整理役が**差分だけを項目の追加・更新として反映**する。全体を書き直さないことで、要約しすぎる癖と、書き直すたびに細部が崩れる問題を避ける | `ace-agent/ace` |
| [MIPROv2](https://arxiv.org/abs/2406.11695) | 合格した例を集めてお手本の組を作り、指示文の候補も作る。「指示文 × お手本の組」の組み合わせを、ベイズ最適化で探す | DSPy の `dspy.MIPROv2(metric=..., auto="light")` |
| [TextGrad](https://arxiv.org/abs/2406.07496) | LLM が書いた批評を「文章の勾配」として逆向きに伝え、プロンプトを書き換える。PyTorch と同じ書き方をする | `textgrad` |
| [ProTeGi](https://arxiv.org/abs/2305.03495) | 間違えた例から「なぜ間違えたか」の理由を出させ、理由ごとに書き換えと言い換えを作り、多腕バンディットで有望な候補を残す | 論文の方式を自作 |
| [OPRO](https://arxiv.org/abs/2309.03409) | これまでの指示文の上位 20 個を得点の昇順で並べて見せ、新しい指示文を 8 個ずつ書かせる | 自作が容易 |
| [EvoPrompt](https://arxiv.org/abs/2309.08532) | 親を 2 つ選んで LLM に交配と変異をさせ、良いものを残す | 論文の方式を自作 |
| [Promptbreeder](https://arxiv.org/abs/2309.16797) | 課題用のプロンプトに加えて、それを書き換える「変異用のプロンプト」も一緒に進化させる | 論文の方式を自作 |
| [APE](https://arxiv.org/abs/2211.01910) | 入出力の例から指示文の候補をたくさん作らせ、少数の例で採点して上位だけを多くの例で採点し直す | 自作が容易 |

スキルとの相性で言うと、次のようになります。

- **ACE** の「項目単位の追記と、役立った・有害の回数」は、スキルの「つまずきどころ」の節を育てるのにそのまま使えます。ただし、正解も信頼できる実行結果の信号もない状態で回すと悪化する、と論文が明記しています
- **TextGrad** は、SkillOpt の比較では SpreadsheetBench でスキルなしを下回りました（41.1 対 41.8）
- **MIPROv2** は、お手本の選び方まで探すので、決まった形式の出力を求めるスキルに向きます

## 8. 論文どうしの比較を読むときの注意

各論文の比較をまとめると、次のようになります。

| 論文 | 比較の結果 | 誰が測ったか |
|---|---|---|
| SkillOpt | SkillOpt ＞ GEPA ＞ Trace2Skill ≈ TextGrad。Claude Code 上で EvoSkill に +3.2 | 比較相手も SkillOpt の著者が実行 |
| SkillAdam | 短い課題で SkillOpt に 0〜1.1 点勝ち。長い計画の課題では 21.7 対 28.3 | 短い課題の比較相手は **SkillOpt 論文からの転記** |
| SSO | 正解なしの手法の中で最良。SkillOpt の改善幅の 87% | 正解ありの比較相手は **転記** |
| SkillGrad | SkillGrad ＞ EvoSkill、Trace2Skill | SkillGrad の著者が実行 |
| SkillReducer | 同じトークン予算で、他の圧縮法より品質を保つ | SkillReducer の著者が実行 |
| GEPA | GEPA ＞ MIPROv2 ＞ 強化学習（GRPO） | GEPA の著者が実行 |
| ACE | 金融の課題で ACE ＞ GEPA ＞ MIPROv2 | ACE の著者が実行 |
| **BiPA** | GEPA・SkillOpt・SkillAdam はいずれも、長い課題で手書きの初期スキルと差なし | **第三者** |

読むときは、**どの課題で、何回測った、誰の数値か**を必ず確かめます。提案者自身の比較で勝っているのは当然で、転記の比較は条件がそろっていません。

## 9. 第三者の検証：BiPA

[BiPA](https://arxiv.org/abs/2610.37201)（Zhou ほか）は、「汎用のスキル最適化器は、本当にエージェントの課題を良くしているのか」を検証した論文です。

### 9.1 何を調べたか

- GEPA、SkillOpt、SkillAdam を、長い課題 3 種（Terminal-Bench 2.1、τ³-bench、AutomationBench）で動かした
- 初期スキルは、公開されている汎用の「完了前に必ず確認せよ」という手引き。学習用の記録は 160 件、検証用は 30 件
- テストは各スキル 3 回ずつ実行した平均

### 9.2 何が分かったか

- **16 個の学習済みスキルのテスト成功率は、初期スキルより平均 +0.1 点。** 幅は −11.1〜+2.7
- 最適化器が報告した検証用データでの改善は、**中身が初期スキルとまったく同じ候補でも、25〜94% の確率で出る大きさ**だった。原因は、低めに出た初期スキルの検証結果を基準にし、4〜8 個の候補から最良を選んでいるから。つまり、選ぶだけで偶然の上振れが出る
- **入力トークンは平均 1.16 倍。** 採点済みの編集 97 件のうち 91 件がスキルを長くした。追加された規則 337 個の半分は「確認せよ」だった。「読む量を減らせ」という規則は 1 つもなかった
- 増えたトークンの 73% は**手番（モデルの呼び出し回数）の増加**によるもので、スキルの文章そのものは 21% だった。「確認せよ」と書くと、確認のための手番が増えるため
- 学習したスキルを別のモデルや別の課題に移しても効かなかった。増えた費用だけは移った先でも残った
- 公平のために：3 語だけの貧弱な初期スキルから始めると、SkillOpt も GEPA も 18〜19 点改善した。ただし到達点は、手書きの初期スキルから始めた場合と同じ水準だった

### 9.3 BiPA の設計原則

1. **偶然だけで出る改善より大きいときだけ採用する。** 検証で繰り返し勝つことを条件にすると、中身の変わらない候補を採ってしまう率が 24〜41% から 6〜17% に下がり、本物の改善は 55〜94% 残る
2. **編集の費用は、文章の長さではなく増える手番の数で数える。** スキルの長さの変化は入力トークンの変化の 10% しか説明しないが、手番の数の変化は 93% を説明する
3. **規則の削除と統合をさせる**
4. **以前の規則がどれだけ手番やトークンを増やしたかを、編集役に見せる**

### 9.4 どう受け取るか

論文で報告されている大きな改善は、**短い課題で、検証用データが十分にあり、初期スキルが弱いとき**に出やすいものです。長い課題で、良い手書きのスキルから始めると、改善が揺れに埋もれ、費用だけが増えることがあります。自動で直す前に、まず手で直したスキルと比べて、本当に差が出るかを確かめる必要があります。

## 10. 自分で最小の形を作るなら

ここまでの知見を合わせると、最小の改善の往復は次のようになります。SkillOpt の骨格に、BiPA の採用条件と費用の数え方を足したものです。

```python
EDIT_LIMIT = 4          # 1 回に適用する編集の上限（SkillOpt の既定）
WIN_REPEATS = 3         # 検証で何回続けて勝てば採用するか（BiPA の原則 1）
MINIBATCH_SIZE = 8

def improve(skill: str, train, select, rounds: int) -> str:
    rejected: list[str] = []
    for _ in range(rounds):
        records = run_and_grade(skill, sample(train))           # 実行して採点する
        failures, successes = split_by_result(records)
        edits = propose_edits(skill, chunk(failures, MINIBATCH_SIZE),
                              chunk(successes, MINIBATCH_SIZE), rejected)  # 追加・置換・削除の JSON
        edits = rank_by_support(edits)[:EDIT_LIMIT]              # 支える例の多い順に上位だけ
        candidate = apply_edits(skill, edits)
        if beats_repeatedly(candidate, skill, select, WIN_REPEATS) \
                and not adds_turns(candidate, skill, select):    # 手番が増えるなら却下（BiPA の原則 2）
            skill = candidate
        else:
            rejected += describe(edits)                          # 却下の記録（SkillOpt）
    return skill
```

`run_and_grade` や `propose_edits` は、自分の環境に合わせて書く部分です。`propose_edits` に渡す指示には、次を入れます。

- 失敗を種類ごとに分け、型に効く編集だけを出す（SkillOpt）
- 成功している振る舞いは既存の節を補強する。重複させない（SkillOpt）
- 削除と統合も提案してよい（BiPA の原則 3）
- 却下された編集と同じものを出さない（SkillOpt）
- 以前の規則で手番が増えたものを示す（BiPA の原則 4）

正解がない場合は、`run_and_grade` と `beats_repeatedly` を、判定役による 1 対 1 の比較（SSO）に置き換えます。最後に、**一度も使っていないテスト用データ**で、元のスキルとの差が残ることを確かめます。

## まとめ

- スキルを自動で直す手法は、「実行 → 診断 → 編集 → 採否」の同じ骨格を持ち、**診断の材料・編集の単位・採否の判定・記憶**の 4 つで性格が分かれます。
- 発火を直すなら skill-creator の `run_loop.py`、長さを直すなら SkillReducer、正解なしなら SSO、自動で採点できるなら SkillOpt の作法が出発点です。
- 効いている手法に共通するのは、**全文を書き直さず部分的に編集すること**と、**別の検証用データで上回ったときだけ採用すること**です。
- 第三者の検証（BiPA）では、汎用の最適化器の改善は偶然の揺れで説明でき、手番とトークンだけが増えていました。採用の条件を厳しくし、費用を手番の数で数え、削除と統合を許すことが必要です。
- 論文の比較は、提案者自身の測定か、他の論文からの転記です。**どの課題で、何回、誰が測ったか**を確かめてから信じます。
