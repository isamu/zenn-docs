r/ExperiencedDevs に、こういう相談が上がっていました。239 upvote、203 コメント。

> **シニア開発者がTypeScriptで何でも型アサーションしている – どう対処すればいい？**
>
> 私が見たところ、コードはAIツールのCursorで書かれたように見えることが多く、**コンパイラを喜ばせるためだけに `as` が多用されている**ことがあります。本来なら明確でシンプルな方法で型を適切に狭められるのに。

上位の回答は、ほぼ全部同じでした。

> **あなたのリンターはこれを許可せず、CIビルドを失敗させるべきです。**

その通りだと思います。うちの規約にもそう書いてあります。

```markdown
NEVER use `as` type casts; MUST use type guards instead
```

……と書いてあるので、**自分のリポジトリを数えてみました。**

## 90箇所ありました

| | 箇所 | ファイル |
|---|---|---|
| 本体（src / server / common） | **90** | 51 / 596 |
| テスト | 144 | 62 / 513 |

姉妹プロジェクトも数えました。

| | 箇所 | ファイル |
|---|---|---|
| 本体 | **187** | 101 / 744 |
| テスト | **621** | 142 / 605 |

規約には「NEVER」と書いてあります。**そして277箇所あります。**

## なぜこうなるか

答えは単純で、**ESLint で止めていなかった**からです。

前回の記事で「[規約は人の記憶ではなくファイルに置く](https://zenn.dev/singularity/articles/stopped-reviewing-my-code)」と書きました。それは正しいのですが、**足りませんでした。**

`CLAUDE.md` は**読ませるもの**です。ESLint は**止めるもの**です。この2つは違います。

エージェントは `CLAUDE.md` を読みます。読んで、だいたい守ります。でも「だいたい」なので、1日に何十回も書いていれば漏れます。**漏れたものを拾う仕組みが無ければ、それは永久に残ります。**

しかも厄介なことに、`as` を1つ書いても**何も起きません**。テストは通るし、CI も緑です。だから気づかない。数えるまで、自分のリポジトリに90箇所あるとは思っていませんでした。

**規約に書くことと、規約で止めることは、別の作業でした。**

## じゃあ ESLint に入れよう、と思ったら

`@typescript-eslint/consistent-type-assertions` に `assertionStyle: "never"` という設定があります。名前のとおり、`as` を全部落とします。

入れようとして、手が止まりました。

```ts
// common/keymap.ts
const isSendBinding = (value: unknown): value is SendBinding =>
  typeof value === "object" && value !== null &&
  typeof (value as SendBinding).key === "string" &&
  typeof (value as SendBinding).bytes === "string";
```

これは**型ガード**です。そして規約が「`as` の代わりにこれを使え」と指定している、まさにその書き方です。

**その型ガードを書くのに `as` が要ります。**

つまり規約は、こう言っていたことになります。

> `as` を使うな。代わりに、`as` を使って書く型ガードを使え。

**自己矛盾でした。** 半年くらい、これに気づかずに書いていました。

## 90箇所を読んでみた

`assertionStyle: "never"` が使えないと分かったので、代わりに1つずつ読むことにしました。

内訳はこうです。

| 種類 | 箇所 |
|---|---|
| ドメイン型への `as` | 52 |
| `Record` / `Partial` への `as` | 32 |
| DOM・エラー型 | 6 |
| うち `as unknown as` の二段キャスト | 6 |

そして、**危険なものはなかなか見つかりませんでした。**

```ts
// common/dirConfigSource.ts
function isEmptyValue(value: unknown): boolean {
  if (value === null || value === undefined) return true;   // ← 先に null を弾いている
  if (Array.isArray(value)) return value.length === 0;
  if (typeof value === "object") return Object.keys(value as Record<string, unknown>).length === 0;
  return false;
}
```

`typeof null === "object"` なので、この `as` は本来なら危ない書き方です。でも**2行上で null を弾いています**。安全です。

```ts
// server/backends/shortcuts.ts
const parsed = JSON.parse(text) as Partial<ShortcutsFile>;
return normalizeShortcuts(parsed?.shortcuts);
```

ディスクから読んだ JSON に型を主張しています。ファイルが壊れていれば、この型は嘘です。でも `normalizeShortcuts` が中身を検証しますし、全体が try/catch の中にあります。**嘘をついているが、その嘘に依存していない。**

## これが一番こわい

読んでいて気づいたのは、**「今は動いている」という状態のたちの悪さ**です。

90箇所の `as` は、周りのコードが防御的なので、いまバグを起こしていません。だから**誰も困っていないし、直す動機もありません。**

問題は、**後から誰かがその型を信じたとき**です。Reddit のスレッドにも、まったく同じ指摘がありました。

> `as` の使用はすべて**潜在的な時限爆弾**です。今日うまく機能していても、将来のリファクタリングでデータ構造の変更が下流の使用に破損をもたらす可能性があります。通常、TypeScriptはこれを捕捉しますが、`as` ではその型情報が消去されてしまいます。

そして「後から書き足す人」は、**AI です。** 1日に何十回も。

人間なら「この型、本当に合ってるのか？」と一瞬考えるかもしれません。エージェントは考えません。**書いてある型を信じて、その前提で次を書きます。** 嘘の型は、嘘のまま増幅されます。

## 「厳しい戦い」は、もう発生しない

Reddit のスレッドで、僕が一番おもしろいと思ったのはこのコメントでした。

> TypeScriptの最大の問題は、提供されるすべての安全でない逃避ハッチです。**チーム全体でそれらを決して使わないことに合意するのは、しばしば厳しい戦いです。** リンタールールは役立ちますが、チーム全体でそのリンタールールに合意させる必要があります。

「合意させる」。ここです。

同じスレッドの他の回答も、ほとんどが**政治の話**でした。「マネージャーに報告して承認を得る」「RFC プロセスで投票にかける」「バグを追跡して証拠を集める」「1on1 で話す」。

技術的には答えが出ているのに、**入れられない**。厳しい戦いだから。

前回の記事で、僕はこう書きました。

> lint の厳しさは、ずっと「機械の正しさ」と「開発者の忍耐」のトレードオフでした。緩めるという判断は、技術的な判断ではなく社会的な判断だった。**その社会的コストがゼロになったなら、天秤は片側にしか傾きません。**

このスレッドは、その「社会的コスト」が**実在することの証拠**でした。203 件のコメントのうち、かなりの部分が「どうやって同僚を説得するか」に費やされています。

**エージェントは説得が要りません。** ルールを書けば、次から守ります。文句も言わないし、来週になって緩和 PR を出してくることもない。

僕が90箇所も溜めてしまったのは、**説得の相手がいないのに、ルールを機械に入れる作業を後回しにしていた**からでした。一番安かった作業を、やっていなかった。

## 型は、もう人間が書いてメンテするものではない

ここまで書いて、たどり着いた結論です。

TypeScript の型を、人間が書いて、人間がレビューして、人間がメンテナンスする。この前提はもう成り立ちません。**量が違います。**

だからといって「型はいらない」わけではなく、むしろ逆です。**AI が書くからこそ、型は要ります。** 静的解析が効かない言語だと、エージェントが壊したことに誰も気づけない。

変わるのは、人間が書く場所です。

| | 以前 | これから |
|---|---|---|
| 型そのもの | 人間が書く | **AI が書く** |
| 型のレビュー | 人間がやる | **静的解析がやる** |
| **何を許さないか** | 暗黙のルール・レビューでの指摘 | **人間が書く。ここだけ。** |

`as` を1つずつ指摘して回るのは、もう人間の仕事ではありません。**「`as` を許さない」と1行書くのが人間の仕事**です。

そして僕は、その1行を書き忘れていました。

## で、どうするか

一律禁止は使えないので、こうします。

- `assertionStyle: "never"` は**使わない**（型ガードごと落ちるため）
- **型ガードを1箇所に集約**し、そこだけ許可する
- それ以外での `as` は error
- **例外はインラインの `eslint-disable` ではなく、設定ファイルに1エントリ1理由で**書く（[前回書いた作法](https://zenn.dev/singularity/articles/stopped-reviewing-my-code)と同じ）
- テストは対象外（意図的に不正な入力を作るため）

作業は issue にしてあります。

- [mulmoterminal#1231](https://github.com/receptron/mulmoterminal/issues/1231)
- [mulmoclaude#2692](https://github.com/receptron/mulmoclaude/issues/2692)

ドメイン型への52箇所は、まだ全部読めていません。**本当のバグがあるとすればこの中**なので、直しながら1つずつ見ます。何か出てきたら追記します。

## まとめ

- 規約に「NEVER」と書いてあっても、**機械が止めていなければ守られない**
- `CLAUDE.md` は**読ませるもの**、ESLint は**止めるもの**。この2つは別
- しかも規約は**自己矛盾していた**（型ガードを書くのに `as` が要る）。数えるまで気づかなかった
- `as` の多くは「**嘘をついているが、その嘘に依存していない**」。だから今は無害で、だから直されない
- 危険なのは、**後から書き足す側がその型を信じたとき**。そして書き足すのは AI で、AI は疑わない
- Reddit で 203 件のコメントが費やされていた「**同僚をどう説得するか**」は、書き手がエージェントなら発生しない
- **人間が書くのは、型そのものではなく「何を許さないか」**

自分のリポジトリ、数えてみるといいと思います。**規約に書いてあるからといって、守られているとは限りません。**

```bash
# ざっくり数える（as const と import の別名は除く）
git grep -n -E '\bas +[A-Z]' -- 'src/**/*.ts' 'server/**/*.ts' | grep -v 'as const' | grep -v '^.*import' | wc -l
```
