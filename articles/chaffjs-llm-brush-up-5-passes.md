AI にブログ記事を書かせると、文法は正しいし、情報も揃っています。それでも読み返すと、どうにも「AI が書いた感じ」が抜けきれない — 具体的にどこが悪いのか、どう直せばいいのか、この手触りが掴めないまま公開ボタンを押すか迷っている方は、多いはずです。

本記事では、**実際に AI 生成の技術ブログ 1 本を、chaffjs（日本語の文書健全性チェッカー）と LLM で 5 周ブラッシュアップした記録**を、違和感のあった行がどう進化したか具体例で見ていきます。

対象記事：[勉強会の申し込みフォームを AI に 1 行で頼んで公開するまで](https://singularitysociety.org/articles/tech-blog/2026-09-27-shared-app-attendance-walkthrough/)

## chaffjs とは何か

話を進める前に、chaffjs をまだ知らない読者のために、ざっくり紹介しておきます。

[chaffjs](https://www.npmjs.com/package/chaffjs) は、**文書の読みにくいところと、機械で確かめられる誤りを見つけるコマンドラインツール**です。Markdown だけでなく **plain text (`.txt`) にも対応**していて、技術記事、契約書、法令、手順書といった複数の文書種別を、同じ道具で読めます。日本語と英語の両方に対応していて、同じ入力に対しては何度実行しても同じ結果を返します。公式ドキュメントの表現を引用すると、こうです。

> 文書を読んで書くのは人や AI で、chaff はその隣で、判断の要らない側を受け持ちます。
> 一文の長さや見出しの繰り返し、条文の番号の抜け、書き直しで消えた数字や URL、
> 引用が原文のその番地に本当にあるかどうかは、別の AI の意見を聞かなくても機械で決まります。

LLM による文章校正ツールが山ほどある中、chaffjs の立ち位置は少し特殊です。**AI が書くか、人間が書くか**の判断には踏み込まず、「機械で判定できる範囲」だけを静かに受け持ちます。

### 使い方

Node.js 24 以上があれば、インストールせずに走ります。

```bash
npx chaffjs article.md
```

実行すると、該当行、何が起きているか、なぜ読みにくいか、どう直すかの順に指摘が並びます。設定ファイルも API キーも言語指定も要りません。

```bash
npx chaffjs .                          # カレント配下の .md / .txt を全部
npx chaffjs docs/ README.md            # ディレクトリとファイルを混ぜて
npx chaffjs article.md --watch         # 保存のたび差分で指摘
npx chaffjs article.md --compact       # 1 行要約で CI 向け
npx chaffjs article.md --experimental  # 試験中のルール（まだ測っていない新しいルール）も動かす
```

### 複数の文書ジャンルを使い分ける

chaff は文書の種類（ジャンル）ごとに動かすルールと閾値を変えます。契約書の 1 文はブログより長くて当然ですし、小説は同じ語の繰り返しが特徴です。1 つのツールで型を切り替えられる作りになっています。

```bash
npx chaffjs --genre legal/contract 契約書.md
npx chaffjs init --genre legal/contract
npx chaffjs genres                     # ジャンルの一覧
```

主なジャンル群：

| 群 | ジャンル |
|---|---|
| 技術文書 | `technical/spec` `technical/readme` |
| ブログ | `blog/tech` `blog/essay` `blog/owned-media` |
| ビジネス | `business/proposal` `business/report` `business/press-release` など |
| 法務 | `legal/contract` `legal/statute` `legal/judgment` `legal/patent` |
| 説明書 | `docs/manual` `docs/faq` `docs/glossary` |
| 学術 | `academic/paper` |
| 文学 | `literature/fiction` `literature/essay` など |
| 話し言葉 | `speech/address` `speech/transcript` |

ジャンルを指定しない場合、パスと内容から自動判定します（`README.md`、`*-spec.md`、`docs/` は技術文書扱い、それ以外は `blog/tech` が既定）。

### 代表的なルール

chaffjs の指摘カテゴリは数十種類ありますが、本記事で頻出するのは次あたりです。

| ルール ID | 何を見るか |
|---|---|
| `max-sentence-length` | 1 文が長すぎる（既定: 100 字超で警告） |
| `bold-density` | 太字が密集しすぎている（既定: 1000 字あたり 20 箇所超） |
| `taigen-dome-in-prose` | 本文の体言止めが続いている（既定: 4 文超） |
| `no-doubled-joshi` | 「の」などの助詞が読点なしで 3 回以上続く |
| `list-item-form-mix` | 箇条書きの文体が揃っていない（名詞終わりと文終わりの混在） |
| `heading-numbering-mix` | 見出し番号の付け方が兄弟で揃っていない |
| `heading-echo` | 直後の文が見出しをほぼそのまま繰り返している |
| `code-fence-language-mix` | コードブロックに言語名が付いていない |
| `clause-chain` | 一文に節が連なりすぎている（既定: 5 節まで） |
| `concrete-evidence-density` | 節に数値もコードもリンクもない |
| `orthographic-variant` | 文書内で表記ゆれ（「申し込み / 申込」など） |
| `number-style-consistency` | 数字の書き方が揃っていない（「30 名 / 三十人」の混在） |

機械で白黒つけられる項目に特化しているので、「意味の通り」「比喩の良し悪し」「読者視点の有無」といった**解釈が要る領域には踏み込みません**。そこは別の目（人間 or LLM）の仕事になります。

### 実際の warn 出力の例

本記事を書く過程で chaff が実際に吐いた指摘を、そのまま載せます。

```text
14:37   warning この文は 102 文字あります（100 文字まで）
                max-sentence-length

165:66  warning 「の」が読点を挟まずに 3 回続いています（2 回まで）
                no-doubled-joshi

14:1    warning このセクションは 258 字に太字が 6 箇所あります
                （1000 字あたり 20 箇所まで）
                bold-density

22:3    info    「名前・メール・録画希望の 3 項目のフォーム」は名詞で
                終わっています。この箇条書きのほかの項目は文で終わります
                （4 項目のうち 1 項目）
                list-item-form-mix

24:8    info    「申込」と書いています（この文書はふつう「申し込み」と
                書く語です。5 箇所のうち 1 箇所が違う）
                orthographic-variant

178:28  info    一文に節が 6 つつながっています（5 つまで）
                clause-chain
```

出力の構造を見てみてください。**どう直すかの指針が、指摘の中に埋まっている**のに気付きます。たとえば `orthographic-variant` の「この文書はふつう『申し込み』と書く語です」や、`list-item-form-mix` の「ほかの項目は文で終わります」は、**そのまま LLM に貼れば修正プロンプトになる**書き方になっています。

これは偶然ではなく、chaff の設計思想が、「人間が読む」だけでなく「別の AI が読んで直す」ことを想定した出力フォーマットになっているからです。

### 指摘への応じ方は 3 つ

chaffjs の思想で特筆すべきは、**指摘を無視できる仕組みが最初から組み込まれている**ことです。

| 応じ方 | どんなとき | やること |
|---|---|---|
| 直す | 指摘がもっともなとき | 文章を書き直す |
| この箇所だけ黙らせる | 指摘は正しいが、ここは意図してそう書いた | `<!-- stet: rule-id — 理由 -->` を文書に書く |
| ルールを変える | 自分たちの方針に合わない | `npx chaffjs relax rule-id --why "理由"` でルール自体を緩める |

「うるさいから使わない」という最悪の着地にならないよう、エスケープハッチが設計の中にあります。

### ESLint のように使う

chaff は、ESLint と非常によく似た立ち位置の道具です。コードではなく散文を見るための lint、と考えると構造がすっと入ります。

- 設定ファイルは `chaff.yaml`（`eslint.config.js` 相当）をプロジェクト直下に置いてバージョン管理
- `--compact` で CI 向けの 1 行要約を出す
- 指摘があれば exit code は非ゼロで戻る（CI で落とせる）
- GitHub Actions の 1 ステップに差し込める

```yaml
# .github/workflows/prose.yml
- run: npx chaffjs docs/ --compact
```

ESLint 使いなら「あの感覚で日本語の文書も検査できる」と考えると、入りやすいはずです。

### ルールは自分でカスタマイズできる

既定のルールが合わない場合、ESLint と同じように設定で調整できます。

- **ルールごとに閾値を変える**: `chaff.yaml` に `rules:` で記述
- **ジャンル指定でルールセットを切り替える**: `genres.yaml` で記事種別ごとに有効ルールを変える（「ブログは短文重視」「契約書は番号抜け重視」など）
- **プラグインとして配布する**: `npx chaffjs init --plugin <名前>` でひな形を作り、`npx chaffjs plugin-test` で各ルールを例にかけて検証
- **プラグインを team / repo で共有**: `rules/*.yaml` と `genres.yaml` と `detectors/` の 3 ディレクトリで ESLint プラグインと同じ構造

分岐や式を書かない宣言的な YAML 定義なので、エンジニアでなくても校正ルールを足せます。

### Claude Code 向けの skill が同梱されている

本記事の文脈で特に重要なのが、ここです。chaff には **Claude Code 向けの Agent Skills が最初から入っていて**、1 コマンドでインストールできます。

```bash
npx chaffjs skill             # .claude/skills/chaff/ に入れる（プロジェクト固有）
npx chaffjs skill --global    # ~/.claude/skills/chaff/ に入れる（全プロジェクト共通）
```

これを入れておくと、Claude Code は chaff のかけ方、指摘の読み方、「直すか・黙らせるか・ルールを変えるか」の選び方を把握した状態で起動します。本記事の 5 pass もまさにこの skill 経由で回しました。

skill 本体は `skills/chaff/SKILL.md` に書かれており、[Agent Skills の仕組み](https://www.anthropic.com/engineering/agent-skills)に乗っかっています。chaff を使うエンジニアは、校正ルールだけでなく「どう使うか」のメタ知識も、同じ 1 コマンドで Claude Code に注入できる、という構図になっています。

### AI eval のスコアラとしても使える

付随機能として触れておくと、chaff には `grade` サブコマンドがあり、LLM の出力を評価するスコアラとして使えます。

```bash
npx chaffjs grade outputs.jsonl
```

「引用が原文のその番地に本当にあるか」「数値の合計が合うか」といった**決定論的な採点**を、LLM-as-a-Judge の確率的な採点と並べて記録できます。本記事のスコープを超えるのでここでは触れませんが、Promptfoo / DeepEval / Ragas / Inspect AI といった主要な eval フレームワークとの統合例が [`examples/evals/`](https://github.com/isamu/lab/tree/main/text/examples/evals) に揃っています。

### 文書は書き換えない

最後に、chaff の最重要な方針を書いておきます。**chaffjs 自身は文章を 1 文字も書き換えません**。指摘して、理由を書いて、終わりです。

書き直すのは、chaff を読んだ人間か LLM に任されます。本記事のテーマはまさにそこ、**chaffjs（検査）と LLM（書き直し）をどう組み合わせるか**です。

## ツールの役割分担

> **chaffjs**：決定論的な側（長文、太字過多、助詞の重複、体言止めの連続など）を機械で指摘する
> **LLM**：確率的な側（違和感、硬さ、話者ボイス、流れ）を書き換える

ふたつは排他ではなく、**補い合う**関係です。chaffjs は「同じ入力なら必ず同じ指摘」を返す静かな同僚で、LLM は「読んでみて違和感を言葉にする」同僚、という位置づけになります。片方だけだと、どこか偏った仕上がりに落ち着きます。

## 元記事に対する最初の違和感

元のタイトルを引用します。

> **Before**: 「レシピを読んでいるあいだは全部分かるが、台所に立つと最初の一行で止まる」

タイトルを読んだだけでは、記事の中身が見えてきません。本文も料理のたとえが前面に出ていて、「このツールで何ができるのか」が頭に入ってこない状態でした。

ところが **chaffjs は元記事に対して指摘 0 件** を返します。文法、リズム、太字密度といった機械で判定できる面は、既に綺麗だったわけです。問題はもっと先、chaff が検出しない「読む側に伝わっているか」という領域にありました。

このズレこそが、chaff と LLM が別々の役割を担うべき理由になります。

## 違和感のあった 16 行の進化

実際にブラッシュアップで変わった箇所を、Before/After で見ていきます。各項目には **変更の起点** を注記しています — chaff ルールが引いた指摘なのか、LLM 側の違和感検知なのかを明示しておきます。

結論を先に書いておくと、16 項目中 **chaff が直接きっかけになったのは 2 項目のみ**（item 4 と item 13）で、残りはすべて LLM 側の判断で変わりました。これは chaff が不要という意味ではなく、chaff が普段から走っている前提で、LLM が「chaff の指摘を予防的に避ける書き方」を内面化している、という状態に近いと言えます。chaff の skill（`npx chaffjs skill` で入る `.claude/skills/chaff/SKILL.md`）が LLM に注入されているので、chaff ルールが LLM の判断基準の一部になっているわけです。

### 1. タイトル

```diff
- レシピを読んでいるあいだは全部分かるが、台所に立つと最初の一行で止まる
+ 勉強会の申し込みフォームを AI に 1 行で頼んで公開するまで — MulmoTerminal の共有アプリの実例
```

**変更の起点**: LLM の判断（タイトルから何の記事か分からない。chaff はタイトルの意味は見ない）

何の記事かが 1 行目で分かるようになりました。SEO 的にも検索キーワード（「申し込みフォーム」「AI」「MulmoTerminal」）が含まれています。

### 2. 冒頭 1 行目

```diff
- レシピを読んでいるあいだは、全部分かります。
+ 来月、30 名を集めて勉強会をやる予定があるとします。
```

**変更の起点**: LLM の判断（抽象的な比喩が強すぎる。chaff は比喩の良し悪しを見ない）

抽象的な比喩を、具体的なシナリオに差し替えました。読者が自分ごととして読み始められます。

### 3. 冒頭 2 行目（問題提起）

```diff
- 玉ねぎをみじん切りにして、しんなりするまで炒める。読めば分かりますし、想像もできます。作れそうな気もします。
- 台所に立つと、最初の一行で止まります。玉ねぎを買っていません。
+ 誰が来るのかを把握しておきたい。ただ、いざ「申し込みページを作る」の段になると手が止まります。Google Forms に流せばいいのは分かっているのですが、定員 30 名で埋まったらキャンセル待ちに回す、くらいの要件になった途端に、どこで動かすか、データをどう預かるかで悩み始める。
```

**変更の起点**: LLM の判断（比喩に逃げず、読者が実際に抱える具体的な悩みを書く）

比喩を剥がして、実在する悩みに置き換えました。「Google Forms に流せばいい」など、読者が実際に考えていそうな思考を書くことで、共感を得やすくなります。

### 4. chaffjs が指摘した「作るもの」の箇条書き

**変更の起点**: chaff ルール `list-item-form-mix` (info)

Pass 2 で初稿を書いた直後、chaffjs がこう指摘しました。

```text
22:3    info    「名前・メール・録画希望の 3 項目のフォーム」は名詞で終わっています。
                この箇条書きのほかの項目は文で終わります（4 項目のうち 1 項目）
                list-item-form-mix
```

初稿：

```markdown
- 名前・メール・録画希望の 3 項目のフォーム      ← 名詞で終わる
- 定員 30 席、超えたら自動でキャンセル待ちに回る  ← 文で終わる
- 主催者は全申込を一覧で見られる                ← 文で終わる
- 申し込んだ人は自分の予約状況だけ見える         ← 文で終わる
```

LLM に指摘内容を渡して修正：

```diff
- 名前・メール・録画希望の 3 項目のフォーム
+ 名前・メール・録画希望の 3 項目を聞く入力フォームを置く
```

4 項目すべてが動詞終わりで揃いました。この種の統一感は人間の目では見逃しがちですが、chaff は確実に拾います。

### 5. セクション見出し「三つの住所」の意味不明さ

```diff
- ## 三つの住所ができる
+ ## 3 つの入口ができている
```

**変更の起点**: LLM の判断（「住所」の比喩が「URL」を指す意味の飛躍が大きい）

「住所」は比喩で、「URL/エンドポイント」を指していましたが、意味の飛躍が大きすぎます。「入口」なら比喩としても最小限で、推測が要りません。これは chaff には引っ掛からない、LLM 側の判断です。

### 6. 役割を示す表の語彙

```diff
- | リンクを送られた人 | フォーム。送ると12番の席が取れましたか、キャンセル待ち3番です |
- | あなた              | 全部の行。人数。待っている人                              |
- | 申し込んだ人が水曜に来たとき | 自分の行だけ                                       |
+ | リンクを受け取った参加者 | フォーム。送信すると「12 番の席が取れました」 or「キャンセル待ち 3 番です」 |
+ | あなた（主催者）         | 全申込一覧、人数、キャンセル待ちの行列                            |
+ | 申し込んだ人が後日開き直したとき | 自分の予約だけ                                        |
```

**変更の起点**: LLM の判断（読者の役割が曖昧。表の記述が汎用性に欠ける）

「あなた」→「あなた（主催者）」、「水曜に来たとき」→「後日開き直したとき」。前者は役割の明示、後者はシナリオの汎化。読者がどの立場かで混乱しない書き方になりました。

### 7. race condition の説明

```diff
- 自分でフォームを作ると、三十一人目が入ります。今何件あるか数えて三十件未満なら受け付けるという作りだと、二人が同時に押したときに両方が二十九件を見るからです。
+ この手の仕組みを自分で素直に実装すると、「31 人目が入ってしまう」という落とし穴にはまります。
+
+ 「現在の件数を数えて、30 件未満なら受け付ける」という書き方をした場合、ほぼ同時に 2 人が送信ボタンを押すと、どちらも「現在 29 件」を見てしまい、両方とも通ってしまう。いわゆる競合状態 (race condition) です。
```

**変更の起点**: LLM の判断（技術用語の正式名を補足。説明順を現象→原因に）

2 つの改善：
1. 「落とし穴にはまる」で、現象→原因の順序を明示
2. 「競合状態 (race condition)」という正式名を補足。日本語読者で技術者にも通じる書き方に

### 8. 料理メタファーの最後の名残

```diff
- 料理の味見にあたる段です。出す前に一口食べます。
+ 4 つを一周見るのに 5 分もかかりません。公開してから気付くより、ここで一度自分の目で通した方がずっと早いです。
```

**変更の起点**: LLM の判断（比喩を剥がし、実用的な数値に置き換える）

比喩を削除して、実用的な工数見積もり（5 分）に置換しました。読者が「じゃあやろう」と判断できる情報に変わっています。

### 9. 見出しの許可明示化 — ノートを閉じる節

```diff
- ## ノートを閉じる
+ ## 告知したらノートを閉じていい
```

**変更の起点**: LLM の判断（見出しが単なる動作ではなく、読者の不安への回答になる）

「〜していい」で**何をしてよいかの許可**を明示しました。読者が持っていた不安（「寝ているあいだも動くの？」）に先回りして答える見出しです。

### 10. 配信インフラの誤解

```diff
- アプリは自分のパソコンが配信しているのではなく、公開済みのものが動いているので、寝ているあいだも番号が配られます。
+ よくある誤解を 1 つ。これは「自分のパソコンがサーバーになっている」話ではありません。公開ボタンを押した時点で、配信は MulmoTerminal 側のインフラに移っています。自分が寝ているあいだも 24 時間、申し込みは入り続けます。
```

**変更の起点**: LLM の判断（読者が持つ誤解を先回りして打ち消す構造にする）

「よくある誤解を 1 つ」で、読者が持ちやすい誤解を明示的に取り上げる構造に。情報密度は変わっていませんが、**なぜ心配しなくていいか**が読者に届きます。

### 11. 単位の違和感 — 八手という数え方

```diff
- 八手あるうち、キーボードを打つのは最初と最後だけです。残りは確かめる作業と、押す作業になります。
+ 全体で 8 ステップ。実際にキーボードを打つのは最初（依頼）と最後（公開指示）の 2 回だけで、残りはすべて「中身を確かめる」か「ボタンを押す」で済んでいます。
```

**変更の起点**: LLM の判断（「八手」は囲碁・将棋以外でほぼ使わない語彙）

「八手」は囲碁・将棋以外ではあまり使わない数え方。「ステップ」で現代的な語彙に。括弧補足で「依頼」「公開指示」と具体化しました。

### 12. 文末「位置づけです」の硬さ

```diff
- フォルダは、それを編集するための原本として手元に残ります。
+ 手元に残っているフォルダは、設計を次に編集するための原本として置いておく、くらいの扱いで構いません。
```

**変更の起点**: LLM の判断（事務的な語彙を柔らかい文末に差し替える）

「〜という位置づけです」のような事務的な締めくくりを、「〜くらいの扱いで構いません」で読み手に判断を預ける書き方に差し替えました。

### 13. 文末のフラグメント — 名前は何でも。

```diff
- 空のフォルダを 1 つ作ります。デスクトップで構いません。名前は何でも。
+ 空のフォルダを 1 つ作ります。デスクトップで構いません。名前は何でも大丈夫です。
```

**変更の起点**: LLM の判断（chaff ルール `taigen-dome-in-prose` を予防的に回避）

体言止めで終わる 3 連続は、chaff の `taigen-dome-in-prose` ルール（本文中の体言止めが 4 文を超えると info 指摘）に引っかかりやすくなります。LLM 側で先に自然な文末形式に揃えました。chaff の指摘を待たずに、ルールを知った LLM が予防的に修正した例です。

### 14. 動詞の反復 — 頼みますの繰り返し

```diff
- やめるときは、同じマスで「このアプリの公開をやめて」と頼みます。データを全部消すなら「レコードを全部消して」ですが、消すと戻らないので、画面で中身を見て、必要なら書き出してから頼んでください。
+ やめるときは、同じマスで「このアプリの公開をやめて」と伝えます。データ自体を全部消したい場合は「レコードを全部消して」です。消すと戻せないので、先に画面で中身を確認し、必要なら書き出してから依頼するのが安全です。
```

**変更の起点**: LLM の判断（同語の反復。chaff には動詞反復のルールがない）

同じ段落で「頼みます」が 2 回連続。LLM が「伝えます」「依頼する」で表現を散らしました。chaff は同じ動詞の繰り返しを明示的に検出しない（単語レベルの反復チェックはあるが、文中の同義語リライトまで含めると過剰なので、ルール化されていない）ので、ここは LLM の守備範囲です。

### 15. 助詞の不自然さ — AI 側でという表現

```diff
- AI 側で「じゃあ 30 席、超えたらキャンセル待ち」と判断してくれます。
+ あとは AI が勝手に「30 席、超えたらキャンセル待ちで」と解釈してくれます。
```

**変更の起点**: LLM の判断（「〜側で」は責任主体をぼかす日本語表現）

「〜側で」は責任主体をぼかす日本語の悪癖。「AI が勝手に」の方が主語がはっきりして、ユーモアも出ます。

### 16. まとめの終わり方

```diff
- その 1 工程さえ飛ばさなければ、イベント運営者がやる作業は、キーボード入力 2 回とボタン数回で済みます。
+ その 1 工程を飛ばさないでいる限り、イベント運営者が実際に手を動かすのは、キーボード入力 2 回とボタン操作数回で済みます。残りの時間は、来てくれる人に何を話すかを考えることに回せます。
```

**変更の起点**: LLM の判断（記事全体の目的意識を最後に明示する）

技術的な結論（「操作が少ない」）だけで終わらず、**その余った時間で何をするか**まで書くことで、記事全体の目的意識が最後に収束します。

## chaffjs が指摘するもの vs LLM が気づくもの

5 pass を通じての観察：

| 気づけるもの | chaffjs | LLM |
|---|---|---|
| 一文の長さ超過 | ◎（100 字で警告） | △ |
| 太字密度 | ◎（1000字 20 箇所超で警告） | × |
| 体言止めの連続 | ◎（4 文超で警告） | △ |
| 「の」3 連続 | ◎ | ○ |
| 箇条書きの文体不統一 | ◎ | △ |
| 比喩が強すぎる | × | ◎ |
| 読者視点の欠落 | × | ◎ |
| 専門用語の過不足 | × | ◎ |
| 誤解を招く見出し | × | ◎ |
| ユーモアと真面目の塩梅 | × | ◎ |

**chaffjs は「形式」を、LLM は「意味」を担当する**という分業が自然に成立しました。片方だけで仕上げると、同じ記事を何周ブラッシュアップしても「人間らしさ」には届かない、というのが 5 pass を回しての実感です。

## 5 pass の総括

| Pass | 焦点 | 変化行数 |
|---|---|---|
| 1 | タイトル差し替え、料理メタファーの大幅削減 | +98 / -90 |
| 2 | 文の硬さを薄め、残っていた比喩を更に削減 | +26 / -26 |
| 3 | 各節の出だしを緩め、読者視点に書き換え | +17 / -17 |
| 4 | 細部の違和感と文末の反復を解消 | +8 / -8 |
| 5 | 冒頭・結びの印象を調整（最終） | +6 / -6 |

**pass を重ねるごとに変化行数が減っていく**のが興味深いところです。1 周目で大きく書き換え、2〜4 周目で中規模の違和感、5 周目で最後の仕上げ、という減衰カーブが自然に出ました。「もう直す所がない」と判断する境界線は、chaffjs の指摘が 0 件になり、かつ LLM に追加 pass を投げても「大きな違和感なし」と返ってくるあたりに置くと、ちょうどよさそうです。

## 教訓

5 pass を通じて得た示唆を 3 つに絞ります。

- **chaff の指摘 0 件は、文章の完成を意味しない**。chaff は決定論的な部分しか見ないので、「違和感はあるが文法的には正しい」という文はそのまま素通りします
- **LLM での違和感直しも、1 周では足りない**。1 pass で大きな違和感、2〜3 pass で中規模、4〜5 pass で細部、というレイヤーが自然に分かれていきます
- **chaff と LLM は交互に使う**。LLM で書き換え → chaff で機械チェック → LLM で指摘対応 → chaff で再確認、を回します。両者の守備範囲が重ならないので、交互に挟むと穴が順に消えていきます

AI 生成文章の品質問題は、「文法を直す」だけでは解決しません。「人間の読み手にとっての自然さ」という曖昧な領域を、確率的な LLM と決定論的な chaff で挟み撃ちする — これが 2026 年現在、わりと素直に辿り着く解法のひとつだと感じています。
