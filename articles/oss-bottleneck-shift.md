自分が作っている [MulmoTerminal](https://github.com/receptron/mulmoterminal) はオープンソースです。ソースは全部公開しています。

でも、**プルリクエストは受け付けていません。** 外部からの PR は、規模によらず自動でクローズされます。issue だけ立ててもらって、実装はこちらでやる。そういう運用にしています。

矛盾しているように見えると思います。でも、この2つは矛盾していません。**オープンソースで足りないものが、入れ替わったからです。**

## 昔のオープンソースは「手が足りない」に尽きた

ずっと足りなかったのは人手でした。

あれも作りたい、これも作りたい、そっちも試してみたい。アイデアはいくらでもある。でも簡単な変更なら少人数でも回せても、大きな機能や QA には人手がかかります。

そして何より、**リスクのある変更に時間をかけられませんでした。**

かなり難しくて、成功するかどうかも分からない変更に3ヶ月かける。ひょっとしたらブレークスルーするかもしれないけれど、何も残らないかもしれない。その賭けに人手を割く余裕は、なかなかありません。

だからトリアージが重要でした。限られた手をどこに配分し、何を捨てるか。

そして、**手が早い人、なんでも手伝ってくれる人がとにかく重要でした。** オープンソースのコミュニティが機能していたのは、この「手」を持ち寄る仕組みだったからです。

## vibe coding で、その制約が消えた

いま、その制約がありません。

どんなアイデアでも、出せばすぐ機能になります。大きな機能も1日あれば形になる。リスクの高い変更も、**とりあえず作ってみて、駄目なら捨てる**ことが現実的な選択肢になりました。

3ヶ月かけるか迷っていたものが、1日で試せる。捨てるコストも同時に下がったので、「まず作る」という判断が普通にできます。

実装の速度も、手の数も、テストも、もうボトルネックではありません。

## 代わりに、コードレビューが壊れた

ところが、まったく同じ理由で別のものが壊れました。

**大きな PR が大量に来ると、読めないのです。**

書く側が AI で加速した分、読む側は加速していません。しかも生成されたコードは一見きれいなので、**問題を見つけにくくなっています。** 人間が手で書いたコードなら「ここは怪しい」と匂いで気づけたところが、均質な見た目に埋もれる。

そうすると、間違ったコードを、あるいは悪意のあるコードを、取り込んでしまうリスクが出てきます。

MulmoTerminal は**ユーザーの実機とリポジトリに対してコーディングエージェントを走らせる**ソフトウェアです。監査しきれないものをマージするわけにはいきません。

だから受け付けないことにしました。

:::message
これは「AI が書いたコードを排除する」ルールではありません。PR を書くメンテナ自身もエージェントを使っています。合意するのは**プラン**で、出来上がったコードは**それを着地させた人が持つ**。境界をそこに引いた、というだけです。
:::

## では、なぜオープンソースなのか

実装が足りていて、コードも受け取らないなら、公開する意味はどこにあるのか。

**いま足りないのは、利用者の目の数とアイデアだからです。**

開発側では見つけられないバグがあります。思いつかない使い方があります。それは実際に使っている人からしか出てきません。

数字があります。MulmoTerminal に外部から届いた issue のうち、**17パーセントが Windows 固有の問題**でした。しかも報告者は**全員それぞれ別の人**です。

- claude が spawn できない（File not found）
- `--settings` の JSON が壊れて届く
- 2つ目のインスタンスが、起動中のインスタンスの状態を消す
- 日本語名のディレクトリを選ぶと、デフォルトパスで起動してしまう

こちらは Mac で開発しています。**これらは絶対に自分たちでは見つけられませんでした。** 「Windows で日本語のフォルダ名を使っている人」にしか踏めないバグを、Mac の上で想像するのは無理です。

コードをもらえなくても、この報告には価値があります。むしろ**いまはこちらのほうが希少です。**

## だから、参加のハードルを下げる

そう考えると、やることははっきりします。

導入しやすくする。機能を見つけやすくする。コミュニティに参加しやすくする。

使ってくれている人に、**開発チームの1人になってもらう。** コードを書いてもらうという意味ではなく、「気づいたことを言ってもらう」という意味で。

そのためには、まず使ってもらえないといけないし、使ったときに機能に気づいてもらえないといけないし、気づいたことを言う場所がないといけません。オープンソースであることは、その全部の前提になっています。

## そして、これは企業には難しい

ここが一番言いたいところです。

この動き方は、会社だとなかなかできません。理由は**判断の速度**です。

コミュニティやオープンソースなら、1つ1つの判断がすぐにできます。issue が来て、その日のうちに実装して出す。それが普通にできる。外資のスタートアップならできるかもしれません。

でも、判断が遅い企業にはできません。

権限がどこまで委譲されているか。判断までに何人の承認が要るか。それが致命的に効いてきます。

**実装が1日で終わる世界では、判断に1週間かかることのコストが跳ね上がる**からです。実装3ヶ月に対する判断1週間は誤差でした。でも実装1日に対する判断1週間は、それ自体がボトルネックです。比率が変わったのに、承認プロセスだけが昔のままなら、そこが全体の速度を決めます。

だからこれから、コミュニティやオープンソースがますます重要になっていくと思っています。

**手を集めるためではなく、目とアイデアを集めるために。** そして、集まったものにすぐ応えられる速度を持つために。
