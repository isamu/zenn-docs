自分が作っている [MulmoTerminal](https://github.com/receptron/mulmoterminal) はオープンソースです。ソースは全部公開しています。

でも、**プルリクエストは受け付けていません。** 外部からの PR は、規模によらず自動でクローズされます。issue だけ立ててもらって、実装はこちらでやる。そういう運用にしています。

矛盾しているように見えると思います。でも、この2つは矛盾していません。**オープンソースで足りないものが、入れ替わったからです。**

## 昔のオープンソースは「手が足りない」に尽きた

ずっと足りなかったのは人手でした。

あれも作りたい、これも作りたい、そっちも試してみたい。アイデアはいくらでもある。でも簡単な変更なら少人数でも回せても、大きな機能や QA には人手がかかります。

そして何より、**リスクのある変更に時間をかけられませんでした。**

かなり難しくて、成功するかどうかも分からない変更に3ヶ月かける。ひょっとしたらブレークスルーするかもしれないけれど、何も残らないかもしれない。その賭けに人手を割く余裕は、なかなかありません。

だからトリアージが重要でした。限られた手をどこに配分し、何を捨てるか。

そして、**手が早い人、なんでも手伝ってくれる人がとにかく重要でした。** オープンソースのコミュニティが機能していたのは、この「手」を持ち寄る仕組みだったからです。

## vibe coding で、その制約が消えた

いま、その制約がありません。

どんなアイデアでも、出せばすぐ機能になります。大きな機能も1日あれば形になる。リスクの高い変更も、**とりあえず作ってみて、駄目なら捨てる**ことが現実的な選択肢になりました。

3ヶ月かけるか迷っていたものが、1日で試せる。捨てるコストも同時に下がったので、「まず作る」という判断が普通にできます。

実装の速度も、手の数も、テストも、もうボトルネックではありません。

## 代わりに、コードレビューが壊れた

ところが、まったく同じ理由で別のものが壊れました。

**大きな PR が大量に来ると、読めないのです。**

書く側が AI で加速した分、読む側は加速していません。しかも生成されたコードは一見きれいなので、**問題を見つけにくくなっています。** 人間が手で書いたコードなら「ここは怪しい」と匂いで気づけたところが、均質な見た目に埋もれる。

そうすると、間違ったコードを、あるいは悪意のあるコードを、取り込んでしまうリスクが出てきます。

MulmoTerminal は**ユーザーの実機とリポジトリに対してコーディングエージェントを走らせる**ソフトウェアです。監査しきれないものをマージするわけにはいきません。

だから受け付けないことにしました。

:::message
誤解されそうなので書いておくと、これは「AI が書いたコードを排除する」ルールではありません。**こちらが書く PR も、中身はエージェントが書いています。**

違うのは責任の所在です。マージした人がそのコードの責任を持つ以上、**中身を理解していないコードは入れられません。** 自分（とエージェント）で書いたものなら、設計の意図が分かっているので、どこを疑えばいいかも分かります。外から来た大きな diff にはそれがありません。

だから、外部の方とは「何をどう直すか」を issue で合意するところまでやって、**実装はこちらが引き取る**、という形にしています。
:::

## では、なぜオープンソースなのか

実装が足りていて、コードも受け取らないなら、公開する意味はどこにあるのか。

**いま足りないのは、利用者の目の数とアイデアだからです。**

開発側では見つけられないバグがあります。思いつかない使い方があります。それは実際に使っている人からしか出てきません。

数字があります。MulmoTerminal に外部から届いた issue のうち、**17パーセントが Windows 固有の問題**でした。しかも報告者は**全員それぞれ別の人**です。

- claude が spawn できない（File not found）
- `--settings` の JSON が壊れて届く
- 2つ目のインスタンスが、起動中のインスタンスの状態を消す
- 日本語名のディレクトリを選ぶと、デフォルトパスで起動してしまう

こちらは Mac で開発しています。**これらは絶対に自分たちでは見つけられませんでした。** 「Windows で日本語のフォルダ名を使っている人」にしか踏めないバグを、Mac の上で想像するのは無理です。

コードをもらえなくても、この報告には価値があります。むしろ**いまはこちらのほうが希少です。**

## 「調べてもらう」ができる

そして、見つけてもらって終わりではありません。

**こちらで再現できない問題は、直しようがない**からです。上の Windows の件も、手元では一度も再現しませんでした。再現しないバグを直すのは、目をつぶって手術するようなものです。

ソースが公開されていると、ここから先を**ユーザーにお願いできます。**

「この行にログを足したビルドで試してもらえますか」「この関数が何を返しているか見てもらえますか」「この修正を当てたブランチで直っていますか」——これが成立する。相手はコードを読めるし、手元でビルドして動かせるからです。

クローズドだとこうはいきません。こちらが推測でパッチを当て、リリースし、「まだ直りません」と言われ、また推測する。1往復に何日もかかります。

**再現環境を持っている人が、同時にコードも読める。** これはオープンソースでしか作れない状況です。バグ報告が「報告」で止まらず、**調査そのものを分担できる。**

## MulmoTerminal の場合は、もう一段ある

そしてこのツールには、特殊な事情があります。

**MulmoTerminal は、Claude Code を使うためのツールです。**

つまり、使っている人の目の前には**すでにコーディングエージェントが立ち上がっています。** しかもそれが動いているのは、たいていそのユーザーのマシン、つまり**バグが再現している当の環境**です。

だから「ログを足したビルドで試してください」が、その人にとっては**エージェントに一言頼むだけ**の作業になります。ソースを読むのも、原因を絞り込むのも、直して確かめるのも。

丸投げに聞こえるかもしれないので補足すると、**道具のほうを用意しています。**

MulmoTerminal には `/mulmoterminal-bug-report` というスキルが同梱されていて、打つとユーザーの手元のエージェントが**実際の設定とバージョンを読み**、それが仕様なのか設定ミスなのかを先に確かめ、既知の issue を検索し、それでも説明がつかないものだけを報告にまとめます。環境情報は自動で集め、パスや鍵はマスクされます。

ユーザーに調査を押しつけているのではなく、**診断のやり方をこちらが用意している**、というのが近いです。

そして、これは他のツールでも同じことが言えます。

エージェントは、もう誰の手元にもあります。**あとは、それが何を見ればいいかを製品側が用意できているかどうかです。** これからのソフトウェアは、**ユーザー自身が診断できるように整えておくこと**が効いてくると思っています。

## だから、参加のハードルを下げる

そう考えると、やることははっきりします。

導入しやすくする。機能を見つけやすくする。コミュニティに参加しやすくする。

使ってくれている人に、**開発チームの1人になってもらう。** コードを書いてもらうという意味ではなく、「気づいたことを言ってもらう」という意味で。

そのためには、まず使ってもらえないといけないし、使ったときに機能に気づいてもらえないといけないし、気づいたことを言う場所がないといけません。オープンソースであることは、その全部の前提になっています。

## 効いてくるのは、判断の速度

もう1つあります。**判断の速度**です。

コミュニティやオープンソースなら、1つ1つの判断がすぐにできます。issue が来て、その日のうちに実装して出す。それが普通にできる。

でも、判断が遅い組織にはこれができません。権限がどこまで委譲されているか。判断までに何人の承認が要るか。それが致命的に効いてきます。

**実装が1日で終わる世界では、判断に1週間かかることのコストが跳ね上がる**からです。

実装3ヶ月に対する判断1週間は、誤差でした。でも実装1日に対する判断1週間は、それ自体がボトルネックです。**比率が変わったのに承認プロセスだけが昔のままなら、そこが全体の速度を決めてしまいます。**

## これは、オープンソースだけの話ではない

ここまでオープンソースの話として書いてきました。でも、**この構造はソースを公開しているかどうかとは関係ありません。**

クローズドソースでも同じです。スタートアップでも、社内向けのサービスでも同じです。

実装がボトルネックでなくなり、代わりに「使っている人が何に困っているか」がボトルネックになる。この入れ替わりは、ソフトウェアやサービスを作っているかぎり、どこでも起きます。

違うのは**経路が最初からあるかどうか**だけです。オープンソースには issue という経路が、たまたま最初からありました。無いなら、作らないといけない。

そして経路を作っても、届いたものに応える速度が無ければ意味がありません。「ご意見ありがとうございます」で終わり、次のリリースは3ヶ月後。それでは誰も2度目を言ってくれません。**声が届くことと、その日のうちに返ってくることは、セットで初めて機能します。**

だからこれは、これからのソフトウェアやサービスの作り方そのものの話だと思っています。

- **ユーザーの目とアイデアが、いちばん希少な資源だと認める**
- **それが届く経路を持つ**
- **ユーザー自身が診断できるように整える**
- **届いたものに、その日のうちに応えられる速度を持つ**

オープンソースは、この4つをやりやすい形です。issue という経路が最初からあり、コードが見えているから調査も分担でき、判断する人と実装する人が同じなので速い。

でも、**やらなければいけないのはオープンソースだけではありません。**

3つ目はとくにそうです。ソースが公開されていなくても、**何が起きているかをユーザー自身が確かめられる状態**は用意できます。ログの出し方、状態の見せ方、診断コマンド。エージェントが誰の手元にもある以上、**「読める材料をどれだけ product 側に置けるか」がそのまま調査の速度になります。**

クローズドなプロダクトでも、この4つを意図的に作れるかどうかが、これから効いてくると思っています。

手を集めるためではなく、**目とアイデアを集めるために。** そして、集まったものにすぐ応えられる速度を持つために。

## 最後に、お願い

MulmoTerminal について X で書かれているものも、**できるかぎり探して拾っています。** 「ここが使いにくい」「これが動かない」——見つけたら対応します。実際、そうやって直したものもあります。

ただ、**できれば [issue](https://github.com/receptron/mulmoterminal/issues) を立ててほしいです。**

X の投稿は流れていきます。検索のタイミングを外せば見つかりませんし、後から「同じことを言っている人が他にもいたか」を確かめる手段もありません。issue なら残ります。検索できます。同じ問題を踏んだ次の人が、たどり着けます。

そして何より、**issue には返事が来ます。**

コードは要りません。「これが動かない」の一行で十分です。それが、いまいちばん足りていないものです。
