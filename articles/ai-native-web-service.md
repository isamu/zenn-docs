## 作れるようになった。でも、出せない

**vibe coding で、アプリが作れるようになりました。**

AI に話しかけていたら動くものができた、という経験をした人が、この1年で一気に増えました。

そして、たいていの人が次にこう思います。

> **これ、人に使ってもらいたいな**

ところが、そこで止まります。**作れたのに、出せない。**

止めているものが2つあります。

### ① セキュリティが怖い

人に使ってもらうには、インターネットに出すことになります。
そして、**データの置き場もインターネットに向きます**。

設定をひとつ間違えると、中身が誰にでも読めます。
「その機能は画面に作っていないから大丈夫」は、**まったく通じません**。

実際、この種の事故はよく起きています。
（この話だけで1本あります → [vibe coding で、安易にクラウドを使うな](https://zenn.dev/singularity/articles/vibe-coding-deploy-and-security)）

### ② AI の料金に、上限が無い

そして、こちらのほうが厄介かもしれません。

AI は**1回の応答ごとにお金がかかります**。使われた分だけ、**作った人に請求が来ます**。

サーバー代なら、だいたい見当がつきます。使われすぎたら遅くなるか、止まるだけです。
**AI は止まりません。動いた分だけ、増えます。**

だから、こう考えてしまいます。

> もしバズったら、いくら請求が来るんだろう

**正直に言うと、そんなことはほとんど起きません。** 作ったものは、たいていバズりません。
**それは自分でも分かっています。**

でも、**その「もしも」だけで、公開をやめるには十分**なんです。

上限のわからない支払いに、自分の名前でサインする。
**その怖さは、まったく正しい。**

### 止めているのは、請求ではなく、請求の可能性

ここが、この問題のいちばん厄介なところです。

**実際には、ほとんどの人に大きな請求は来ません。** それでも公開されません。
**来るかもしれない**、で十分だからです。

だから「大丈夫ですよ、たぶんバズりませんから」と言っても、何も解決しません。
**上限が無いという構造そのもの**を変えないと、この手は止まったままです。

以下は、**その構造を変える話**です。

## 「使う人に払ってもらえばいい」は、うまくいかない

ここで、たいてい思いつく方法があります。

> **使う人の API キーを預かって、それで動かせばいい**

**API キー**というのは、AI を使うための文字列です。
「**この文字列を持っている人が使ったぶんは、私に請求してください**」という
許可証だと思ってください。ChatGPT や Claude の設定画面で発行できます。

これを利用者から預かって使えば、料金は**利用者に**請求されます。
作った人は払いません。

実際、そういう作りのツールはあります。**でも、たいてい広まりません。**

### 今度は、使う人が怖い

**API キーを預ける側**から見ると、こうです。

```
知らない人が作ったサービスに、
自分のお金を使える文字列を渡す
```

- **何に使われたか、見えません。** 明細には合計しか出ません
- **止めるには、自分で気づいて無効にするしかありません**
- そして**請求が来るまで、気づきません**
- **API キーが漏れたら、まったく知らない人が自分のお金で使います**

上限を決められる場合もあります。でもそれは「**上限まで使われても文句は言えない**」
という話でもあります。

そもそも、**初めて使うサービスに API キーを貼り付ける**という行為自体が、
かなりの信頼を要求します。**だいたいの人は、そこで閉じます。**

### 怖さが引っ越しただけ

整理すると、こうなります。

| | 誰が怖いか |
|---|---|
| サービスが AI を持つ | **作った人**が怖い（上限の無い請求） |
| 利用者の API キーを預かる | **使う人**が怖い（財布を渡す） |

**どちらも、誰かが怖い。** だから片方は公開をやめ、もう片方は使うのをやめます。

**必要なのは、どちらも怖くない形**です。

そのためには、**API キーを渡さないまま、使う人の AI を使う**必要があります。
できるでしょうか。

## 考え方を1つ変える

**AI の部分だけを、使う人の側に移します。**

使う人は、たいてい**もう AI に月額を払っています**。ChatGPT なり Claude なり。
その枠が余っています。

```
いままで：  サービスが AI を持つ  →  サービスが払う  →  無料にできない
これから：  使う人が AI を持つ    →  本人が払う      →  サービスは無料でも出せる
```

**払っている人が、自分の分を使う。** それだけのことです。

## サービスが用意するもの（4つ）

### ① データの置き場

予約の記録、名簿、在庫。**誰のものか、誰が見ていいか**を管理します。
ここは今までどおりで、変わりません。

### ② 人が見るための画面

普通の Web サイトです。ブラウザで開けば誰でも見られる、あの画面です。

ただし**最低限に留めます**。理由は次の節で書きます。

### ③ AI が操作するための窓口

**人が画面のボタンを押すのと同じことを、プログラムから頼める入口**です。
**Web API** と呼ばれます。

```
「9月25日の10時の枠を、山田さんで予約」
→ 窓口に頼む → 予約が入る
```

画面のボタンが裏でやっていることを、**直接頼めるようにしたもの**だと思ってください。

**ここが大事なところです。これは、たいてい既にあります。**

画面自体がこの窓口を使って動いていることがほとんどだからです。
**新しく作るというより、外からも使えるようにする**という話になります。

（**MCP** という、AI に道具を使わせるための新しい決まりごともあります。
どちらでも構いません。**外から頼める入口がある**ことが大事です）

### ④ AI への説明書 ← ここが新しい

窓口があっても、**何をどう頼めるのかが分からなければ使えません。**

人間向けのヘルプページの、AI 版だと思ってください。

```
予約を取るには：日付と時間と人数を送ってください
予約を取り消すには：予約番号を送ってください
   ※ 取り消せるのは自分の予約だけです
```

**これを置くだけで、利用者の AI がそのサービスを操作できるようになります。**

サービス側は AI を1つも動かしません。**説明書を置いただけ**です。

### まとめると

| | いま持っているか |
|---|---|
| ① データの置き場 | 持っている |
| ② 人が見る画面 | 持っている |
| ③ AI が操作する窓口 | **たいてい持っている**（外に開くかは別） |
| ④ AI への説明書 | **これが無い** |

**新しく要るのは、実質④だけ**ということが多いはずです。

## 使う人は、どうするか

先に、いちばん大事なことを書きます。

### Web は、最低限を引き受けます

**AI を持っていない人も、普通に使えます。**

ブラウザを開いて、カレンダーで空いている枠を見て、クリックして予約する。
予約を変える。取り消す。**これは誰でもできます。**

```
AI が無いと使えないサービス、ではありません。
```

ただし、**Web 側は「最低限」に留めます。** ここは意図してそうします。

- 空きを見る
- 予約する
- 変える、取り消す

**それ以上は、作りません。**

「先月と比べたい」「この条件のときだけ通知してほしい」「複数の条件を組み合わせたい」
——**そういうものを全部載せにいかない**、ということです。

### なぜ、わざと最低限にするのか

**全部載せるのは、そもそも無理だからです。**

聞きたいことは人によって違います。ひとりで作っている先生が、
生徒50人ぶんの「あったらいいな」を全部作ることはできません。

**今までは、そこで詰んでいました。** 作れないものは、諦めてもらうしかなかった。

この形が変えるのは、そこです。**最低限より先は、欲しい人が自分で埋められます。**

だから Web 側は、**誰にとっても要るものだけ**を、きちんと作ればいい。
残りを抱え込まなくて済みます。

### そのうえで、AI を持っている人は

ここからが追加分です。**同じサービスが、こんなふうにも使えます。**

**自分の都合を、そのまま言える**

```
「来週ヨガ行きたい。私の予定と被らない日で取っといて」
```

画面を開かずに済みます。**空き枠と自分の予定を突き合わせる作業**が、
自分の AI の仕事になります。

**言葉にしにくい条件も、通る**

```
「木曜は無理だけど、第3週だけは大丈夫。それ込みで探して」
```

画面のカレンダーには「第3週だけ木曜OK」なんて入力欄はありません。
**でも自分の AI になら、そのまま言えます。**

**自分の見たい形で見られる**

```
「今月何回行ったか、去年の同じ月と比べてグラフにして」
```

サービスの画面にその機能が無くても構いません。
**データを取ってきて、手元で描きます。**

**別の入口からも使える**

誰かが「LINE から予約できる AI」を作っていれば、LINE で

```
「来週振替できる？」
```

と打つだけで済みます。**教室側は LINE 対応を作っていません。**

### つまり

| | できること |
|---|---|
| **AI を持っていない人** | 今までどおり全部。予約も変更も取り消しも |
| **AI を持っている人** | それに加えて、話しかけて済ませられる。自分の都合込みで |

**下の段が減るのではなく、上に段が増えるだけ**です。

## いちばん大事なところ：本人確認と、権限

先に、ここを書きます。**この形で一番大事なのは、ここです。**

言葉を2つだけ。

- **本人確認** — 頼んできたのが、本当にその人かを確かめること
- **権限** — その人が、何をしてよいかを決めること

「山田さんが予約を取り消そうとしている」とき、本当に山田さんか（本人確認）、
そして**山田さんが取り消せるのは山田さんの予約だけ**（権限）。この2つです。

### なぜ、この形だとより大事になるのか

**今までは、頼みごとがサービスの画面からしか来ませんでした。**

だから「他の人の予約を取り消すボタンは画面に付けない」で、なんとなく防げている
気がしていました。

**この形では、頼みごとがいろいろな場所から来ます。** 利用者の AI から、別の会社が
作ったサービスから。**画面にボタンを付けなかった、は通じません。**

### 実は、今までも同じでした

ここは誤解されやすいところなので、はっきり書きます。

**画面にボタンを付けなかったからといって、守られてはいませんでした。**

データの置き場と画面は別のものです。画面に「他人の予約を見る機能」が無くても、
**データの置き場に直接聞けば、答えてしまいます**。設定が甘ければ。

実際、この種の事故はよく起きています。**画面は、鍵ではありません。**

つまり本人確認と権限は、**この形で新しく必要になったのではなく、今までも本当は
必要だった**ものです。この形は、それを**ごまかせなくする**だけです。

### 良い知らせ

**この部分を手で書かなくて済む形があります。**

「誰が何を見ていいか」を宣言として書いておくと、**細かい設定は自動で作られます**。
そして、危ない形になっていたら**公開そのものを止めます**。

一番事故が多いところを、人間の手作業から外す。これが効きます。

## 具体例：ひとりで教室をやっている先生

### 困っていたこと

ヨガ教室を1人でやっている先生が、予約サイトを作りたい。

生徒から「来週の振替できますか」と LINE が来るたびに、手で確認して返信しています。
**AI が答えてくれたらいいのに**と思うけれど、生徒が50人いて毎日問い合わせが来たら、
**AI の料金を先生が全部払う**ことになります。**それでは続きません。**

### 先生が用意するもの

1. **予約の記録**（誰がいつ予約したか）
2. **予約状況が見られる画面**（生徒が開いて空きを確認し、そのまま予約できる）
3. **外から頼める窓口**（予約サイトを作った時点で、たいてい既にあります）
4. **AI への説明書**（「空きの調べ方」「予約の取り方」「取り消し方」）

そして **誰が何をしてよいか**を決めておきます。

```
空き枠を見る       → 生徒なら誰でも
予約を取る         → 生徒なら誰でも
予約を取り消す     → 自分の予約だけ
生徒の一覧を見る   → 先生だけ
```

**先生は AI を1つも動かしません。** 料金は発生しません。

### 生徒の使い方は、3通りあります

**① 画面で予約する（今までどおり）**

ブラウザを開いて、空いている枠をクリックして予約。**これで足りる人が大半です。**
何も新しくありません。

**② 自分の AI に頼む**

```
「来週、ヨガの振替を取りたい。私の予定と被らない日で」
```

生徒の AI が空いている日を調べて、教室の空き枠と突き合わせて、予約します。

**ここが大事なところです。教室が渡すのは、空き枠の一覧だけ。**

判断は、生徒の側でしています。しかも**カレンダーだけを見ているのではありません。**

```
火曜は仕事帰りに寄りやすい
木曜は子どもの迎えがあるから無理
でも9月の第3週だけは、夫が休みだから木曜でもいい
去年の冬は、朝のクラスに変えたら続かなかった
```

**こういうことを、自分の AI は知っています。**

カレンダーに書いてある「予定」ではありません。**予定になっていない事情**です。
曜日の癖、家族の都合、過去に続かなかった理由。**一番言葉にしにくくて、一番
効いてくるもの**です。

いまのサービスで同じ精度の提案をしてもらおうとすると、**これを全部、教室側の
AI に話すことになります。** ヨガの予約のために、仕事の帰り時間も、子どもの
迎えの話も、夫の休みも。

**この形なら、話さずに済みます。** 教室に届くのは「この枠を取ってください」
という1つの頼みだけです。

**③ LINE から**

もし「LINE と Web サービスをつなぐ AI」を誰かが作っていれば、生徒は LINE で

```
「来週振替できる？」
```

と打つだけで済みます。そのサービスが先生の説明書を読んで、空きを調べて、予約まで
済ませます。

**先生は LINE 対応を作っていません。** 説明書を置いただけです。

### 入口が増えるほど、本人確認と権限が効きます

画面から、生徒の AI から、LINE のサービスから。**頼みごとの入口が3つになりました。**

どこから来ても、**山田さんが取り消せるのは山田さんの予約だけ**。
**生徒の一覧を見られるのは先生だけ**。

ここさえ決まっていれば、**入口はいくつ増えても構いません。**
むしろ、増えるほど便利になります。

### さらに

ある生徒が「通った回数を月ごとにグラフで見たい」と思ったとします。

**先生がその機能を作る必要はありません。** その生徒が自分の AI に言えば、
データを取ってきて手元でグラフにします。

**「その機能を付けてください」という要望が、要望で終わらなくなります。**

## もうひとつの例：データを出さずに、分析してもらう

ヨガの例は「**自分の事情をサービスに渡さない**」話でした。
逆向きの例も書きます。「**扱うデータを AI に渡さない**」ほうです。

### 困っていたこと

地図と店舗のデータを持っている分析サービスがあるとします。
使っている会社は、新しい店をどこに出すか決めたい。

聞きたいことは、こういうことです。

```
競合の店から500メートル以上離れていて、
最寄り駅の乗降客数が1万人以上で、
うちの既存店とお客さんが取り合いにならない場所は、どこか
```

**そんな機能は、サービスに付いていません。** 会社ごとに聞きたいことが違うので、
**全部作るのは無理**です。

そして会社の側にも事情があります。**自社の売上データを外に出したくない。**
分析には要るのに、渡したくない。

### どうするか

**① 偽のデータで、手順を作る**

まず、**本物そっくりの形をした偽のデータ**を用意します。
中身はでたらめでいい。列の並びと形だけ本物と同じにします。

それを使って、手元の AI と相談しながら分析の手順を組み立てます。

```
「まず競合店から500m の円を描いて、そこを除外して」
「次に駅の乗降客数で絞って」
「あ、既存店の商圏と重なる分も外して」
```

**試行錯誤は全部、手元で終わります。** 何度やり直しても、見ているのは偽物です。

**② できた手順だけを、サービスに渡す**

手順が固まったら、**手順だけ**をサービスに送ります。データは送りません。

サービス側が、**本物のデータに、その手順を適用**します。
結果はブラウザで見られます。

### 何が起きたか

**本物のデータは、一度も外に出ていません。**
サーバーの中にあったものが、サーバーの中で処理されただけです。

**AI は、本物のデータを一度も見ていません。**
見たのは、形だけ同じ偽物です。

そして会社は、**サービスに付いていない分析**ができました。

### これが効く場面

- **顧客名簿**を使った分析。名簿は渡せないが、分析はしたい
- **患者の記録**、**従業員の給与**。持ち出しが禁止されているもの
- 契約で「**外部に送信しない**」と決まっているデータ

「**データは動かさない。手順だけ動かす**」という形です。

## 運営する人のメリット

**① AI の料金を払わなくていい**

一番大きいところです。**個人でも、無料でも公開できます。**
「使われるほど赤字」が無くなります。

**② 画面を全部作り込まなくていい**

「こういう表示が欲しい」は、**欲しい人が自分で解決できます**。
要望を全部実装する必要がありません。

**③ 余計な個人情報を預からなくて済む**

生徒のカレンダーも、生徒が AI に何を相談したかも、**教室には届きません**。
**預からなければ、漏らしようがありません。**

そして「入口が増えても、決めたことさえ守られていればいい」ので、
**入口ごとに作り込む必要もありません。**

## 使う人のメリット

**① 自分の AI を使える**

好きなものを選べます。すでに払っているものを使えます。
自分のパソコンの中だけで動く AI を使うこともできます。

**② 自分の情報を、サービスに渡さなくていい**

ここが、思っているより大きいところです。

いまのサービスで AI に相談すると、**相談内容はサービス側の AI に読まれます**。

```
健康記録のアプリ：
   「最近どうも調子が悪くて、去年から飲んでいる薬を変えてから…」
   → この文章は、サービスの AI に送られます
```

この形なら、**読むのは自分の手元の AI だけ**です。
サービスは「こう操作してください」という説明書を出しているだけで、
**相談内容を見ていません。**

**自分の事情、自分の文脈、自分の言い回し。渡さずに済みます。**

**③ 用意された画面に縛られない**

見たい形が無ければ、自分で作らせればいい。

## よくある疑問

**Q. サーバー代はかからないんですか？**

かかります。**そこは消えません。**

ただ、AI を使ったサービスを出せずにいる人がつまずいているのは、
**サーバー代ではなく AI の料金**のほうです。使われるほど増えるのはこちらです。

**Q. AI を持っていない人は使えないんですか？**

**画面で見る・操作するぶんには、今までどおり使えます。**
AI がある人は、それに加えて自分の AI からも操作できる、というだけです。

**Q. 勝手に操作されたりしませんか？**

**誰が何をしてよいかを決めるのは、サービス側のままです。**
利用者の AI は、あくまで利用者の代わりに頼んでいるだけで、
**本人ができないことは、AI にもできません。**

## いまは、開発者だけの話です

正直に書きます。**ここまでの話が普通にできるのは、いまのところ開発者だけです。**

「手元に AI がある」という前提が、まだ全員には当てはまりません。
パソコンに何かを入れて、設定して、という段階を越えられる人は限られます。

ただ、**これは終着点ではなく、途中の景色**だと思っています。

## 必要なものは、2つだけ

この形が普通になるために足りていないものは、実は2つしかありません。

**① 説明書の形が決まること**

いまは「AI への説明書」の書き方が、サービスごとにバラバラです。
**共通の書き方が決まれば**、どの AI でも、どのサービスの説明書でも読めるようになります。

**② 手元に AI があること**

これが、いまは「自分でパソコンに入れた人」だけです。

## ②は、ブラウザに入り始めています

**ブラウザ自身が AI を持つ**動きが、すでに始まっています。
何もインストールせずに、**ブラウザの中だけで動く AI**です。

ここが揃うと、話がまるごと変わります。

```
ブラウザがサービスの説明書を読む
       ↓
ブラウザの中の AI が、それを使えるようになる
       ↓
利用者は、何も入れていない
```

**「AI を入れている人」という条件が消えます。**

## そうなると、スマホでも

そして、これがいちばん効いてくるのはスマホだと思っています。

スマホには、**アプリを入れてもらう**という高い壁があります。
予約のためだけに、教室のアプリをインストールする人は多くありません。

ブラウザで済むなら、その壁がありません。

```
スマホのブラウザで教室のページを開く
   ↓
「来週の木曜、振替できる？」と話しかける
   ↓
終わり
```

**アプリも要らない。画面の操作も要らない。** 話しかけるだけになります。

## そのとき、これは「特典」ではなくなる

いまの段階では、AI を使った操作は「**AI を持っている人の特典**」です。
持っていない人は、画面を使います。

ブラウザに入ってしまえば、**その区別が消えます。**
誰でも、話しかけて使える。**画面は、そうしたい人のための選択肢になります。**

**そこまで行って、ようやく「AI native」と呼べるのだと思います。**

いまはその手前です。ただ、**足りない2つがどちらも動いている**のは確かで、
**どちらへ向かっているかは、もうかなりはっきりしている**と思っています。

## 部品は、もう揃っています

さっき「説明書の形が決まること」と書きました。ここをもう少し具体的に書きます。

**必要なものは、だいたい既にあります。**

- **MCP** — AI に道具を使わせるための決まりごと
- **OpenAPI** — サービスの窓口を機械が読める形で書く決まりごと
- **llms.txt** — このサイトは何なのかを AI 向けに置いておく書き方

どれも既にあって、使われています。

**決まっていないのは、その組み合わせ方だけです。**

> **Web サービスが、自分の説明書を、誰にでも読める形でどう置くか**

ホームページに `favicon` を置くのと同じくらい、当たり前の置き方。
そこがまだ、ばらばらです。

### つまり、今日でも作れます

**部品が揃っているということは、組み合わせれば動く**ということです。
新しい発明を待つ必要はありません。

そして**決まった形が無い**ということは、**誰の許可も要らない**ということでもあります。

- 自分のサービスに、説明書を1枚置いてみる
- 自分の AI に読ませて、操作させてみる
- うまくいかなかったところを直す

これだけです。**大げさな仕様の会議は要りません。**

### 試して、出してみる

そして、**うまくいった形を外に出す**。

決まりごとは、誰かが決めて降ってくるものではありません。
**何人かが別々に同じことをやって、似た形に落ち着いたときに決まります。**
`favicon` も `robots.txt` も、そうやって決まりました。

だから、いま要るのは合意ではなく、**試した数**です。

**やってみて、うまくいったら出す。** それを何人かが繰り返せば、形は勝手に決まります。

## おわりに

**作れるようになったのに、出せない。** ここで止まっている人が、たぶんたくさんいます。

止めているのは、セキュリティと、上限の無い料金でした。
どちらも「気をつけましょう」で解決する種類のものではありません。**構造の問題**だからです。

**賢い部分を、使う人の側に置く。**

そうすると、料金は払っている人が自分のぶんを使うだけになり、
サービスは**持つ・共有する・誰が何をしてよいか決める**という、
サーバーにしかできない仕事だけを引き受けます。

そして副産物として、**渡さなくていいものを渡さずに済むようになります。**
自分の事情も、扱うデータも。

残っているのは、**どう配るかを揃えること**だけです。
部品はもうあるので、**やってみることはできます。**

**それが揃った日に、これは「AI を持っている人の特典」ではなくなります。**
