Mac が落ちました。

ファイルまわりの負荷がじわじわ溜まって、最後は反応しなくなって、落ちた。そこまではまあ、たまにあります。問題はそのあとでした。

**起動しないのです。**

電源を入れて、FileVault のパスワードを入れる。進捗バーが出る。2割くらいまで進む。そこで止まる。5分待っても、10分待っても動かない。

**Mac が壊れた、と思いました。**

電源ボタンを長押しして、強制的に切りました。

しばらくしてから、もう一度だけ電源を入れました。また2割で止まります。今度は何もせず待つことにしました。祈りながら待ちました。20分ほどたって、ようやくバーが進み、デスクトップが出てきました。

よかった。本当によかった。

でも、**こういうのは3回目**です。

## 買い替えれば直る？

使っている Mac も、もう新しくはありません。そろそろ寿命なのかもしれない。買い替えようか。

でも、今と同じくらいの構成で買い直すと、

**200万円近くかかります。**

買えません。

そこで、買い替える前に調べることにしました。起動が止まるのはなぜか。普段から重いのはなぜか。買い替えるなら、メモリはどれだけ要るのか。

調べたのは Claude Code です。条件を一つだけ付けました。**読み取りだけで診断すること。** 設定を変えない、ファイルを消さない、プロセスを止めない、再起動しない。対処は提案までで、実行は僕が判断する。壊れかけ（かもしれない）のマシンで、AI に修復操作を勝手にされるのは怖いからです。

## 最初の壁：ログが1行もない

起動が遅いなら、起動時のログを見ればいい。そう思ってのぞいてみると、**止まっていた約18分間のログが1行もありません。**

時刻を並べるとこうなっていました。

| 時刻 | できごと |
|---|---|
| 02:44:31 | カーネル起動（`sysctl kern.boottime`） |
| 〜02:45:18 | FileVault の解除画面。パスワードを入れたのはここ |
| 約18分 | 何も記録されていない |
| 03:03:39 | 通常の起動処理が始まる |

Apple Silicon の FileVault 起動では、まず小さな解除用の環境が立ち上がり、パスワードで解除したあとに本来の macOS の起動が始まります。進捗バーが2割で止まっていたのは、その本来の起動の**ごく初期**です。この段階ではログを記録する `logd` がまだ動いていません。だからログがない。

しかも、起動直後のカーネルログもほぼ残っていませんでした。理由はあとで書きますが、別のログが大量に流れて、古いものを押し出していたのです。

## 手がかりは「強制リセット」の診断ファイル

行き詰まりかけたところで、Claude Code が `/Library/Logs/DiagnosticReports` に気になるファイルを見つけました。

```
forceReset-full-2026-10-19-030340.0002.diag
ResetCounter-2026-10-19-030342.diag
```

中には `panic: btn_rst`、`Boot faults: force_off` とあります。**僕が電源ボタンを長押ししたときの記録**です。

電源ボタンの長押しで強制終了されると、macOS はその瞬間のシステムの状態をこういう診断ファイルに残すことがあります。今回のファイルには、**「起動が止まっていたあいだ、Mac の中で何が起きていたか」のスナップショット**が入っていました。ログが取れない時間帯について、残っている記録はこれくらいしかありません。

スナップショットの中身はこうでした。

- 存在したプロセスは3つだけ：`kernel_task`、`launchd`、`dirhelper`
- `launchd`（PID 1）が `dirhelper` の完了を待っている
- `dirhelper` がさらに子の `dirhelper` を待っていて、**動いているのはその子だけ**
- その子は、カーネル内で150秒以上の CPU 時間を使い、500MBほどのメモリを抱えていた
- メモリ不足の兆候はなし

`dirhelper` は、起動時に**一時ファイルを片付ける**ためのプログラムです。カーネル内でばかり時間を使っているのは、ファイルを大量に削除しているときの典型的な姿です。

つまり、**起動が止まっていたのではなく、一時ファイルを消し終わるのを待っていた**、と読めます。その削除が終わるまで、macOS は次の段階に進めない。

ただし、スナップショットには `dirhelper` が**どのパスを**消していたかまでは残っていません。ここから先の「何を消していたか」は、状況からの推定です。

## 何を消していたのか

macOS は起動時に `/private/tmp`（`/tmp` の実体）の中身を消します。実際、今回の起動後の `/private/tmp` を見ると、中身はすべて起動処理が始まった 03:03:40 以降に作られたものでした。起動前のものは全部消えていた、ということです。

では、普段の `/private/tmp` にはどれだけファイルがあるのか。起動から9時間半たった時点で数えてみました。

**約99万ファイル。**

ほぼすべてが、Claude Code の作業用ディレクトリでした。

## Claude Code の作業用ディレクトリ

Claude Code は、一時ファイルを置くための作業用ディレクトリ（scratchpad）をセッションに用意します。僕の環境では `/private/tmp/claude-<UID>/` の下にあり、プロジェクトごと、セッションごとに分かれていました。

ここに何が入るかは使い方しだいです。僕の場合は、ここに**リポジトリを丸ごと clone して `yarn install` する**のが日常でした。

理由があります。依存パッケージの定期更新を AI に任せるとき、手元の作業コピーを汚されたくない。だから「更新作業は origin から作業用ディレクトリへ新しく clone してやる」というルールにしていたのです。安全のためのルールでした。

その結果、プロジェクトごとの作業用ディレクトリの中身はこうなっていました。

| 作業用ディレクトリ | ファイル数 |
|---|---|
| プロジェクト A | 約47万 |
| プロジェクト B | 約27万 |
| プロジェクト C | 約20万 |

中身のほとんどは `node_modules` です。JavaScript のリポジトリを clone して install すれば、それだけで数万ファイルを超えることがよくあります。それを毎日のように、何セッションも並べて回していました。

**9時間半で約99万。** 前回の再起動までは、6週間連続で動かしていました。単純にかけ算はできませんが、数百万ファイル以上が溜まっていてもおかしくありません（これは推定です）。それを起動時に1本の処理で消していたのだとすれば、20分かかるのも納得できます。

ちなみに、システムの一時ディレクトリ（`$TMPDIR`、`/var/folders/...` の下）にも、最上位だけで1万ほどの項目が残っていました。テストが作った一時ディレクトリや、パッケージマネージャの一時ファイルなどです。ただ、こちらは中身が少ないので、主役ではなさそうです。

## 強制リセットは逆効果だった

ここまで分かると、あの夜の出来事の意味が変わります。

- 1回目の起動：12分ほど待ったところで、僕が電源ボタンを長押しした
- 2回目の起動：約18分かかって、ようやく起動した

1回目は**壊れていたのではなく、削除の途中だった**と考えられます。僕はそれを途中で止めて、残りを2回目の起動で消させていた。「壊れた」と思って押した長押しは、少なくとも起動を早めてはくれませんでした。

## ついでに分かった、普段の重さ

起動の件とは別に、普段の重さも見てもらいました。

### メモリは足りていた

起動から9時間半、テストを並列で回している時間帯も含めて、**メモリの圧縮もスワップも一度も起きていません**でした。アプリが使っていたメモリは47GBほどです。

積んでいるメモリには、まだかなり余裕がありました。

### SSD も減っていなかった

SSD の消耗も見てもらいました。これも読み取りだけで分かります（`brew install smartmontools` が要ります）。

```bash
smartctl -a /dev/disk0 | grep -iE 'percentage used|data units written|power on hours'
```

| 項目 | 値 |
|---|---|
| 消耗の表示 | 6% |
| 書き込み総量 | 251TB |
| 通電時間 | 9,859時間 |
| 予備領域 | 100%（しきい値は99%） |
| データの異常 | 0件 |

通電410日ほどで6%なので、この調子で進むなら、残りを使い切るのに十数年かかります。予備領域はまだ一つも使われておらず、データの異常も記録されていません。買い替えを考える理由が SSD の寿命なら、その理由はありませんでした。

ただ、1日あたりに直すと約600GB書いています。一般的な使い方では1日に数十GBと言われるので、かなり多いほうです。心当たりはあります。毎日のようにリポジトリを clone して install して、テストを並列で回していました。起動時に時間を取られるのはファイルの数ですが、SSD に積まれるのは中身の量です。同じ習慣が、別の形で出ていたことになります。

ついでに、安全でない終了が32回記録されていました。クラッシュも含んだ数ですが、あの夜の長押しもこの中の1つです。

### 重さの正体は CPU

重いときのロードアベレージは26〜28で、コア数を上回っていました。**CPU が埋まりきっています。** テストや解析のプロセスがそれぞれ1コア以上を使って並び、そこにブラウザの描画処理が重なっていました。

### node が毎分数千回起動されていた

カーネルログを押し出していたのは、node が起動されるたびに出るメッセージでした。

```
ASP: Unable to apply provenance sandbox ... /bin/node
```

これがカーネルログに554万行。セキュリティの審査をする `syspolicyd` のログも1400万行ありました。数えると、**システム全体で node が毎分1100〜4500回起動されて**いました。

短い時間で終わるプロセスは `ps` では捕まりません。そこで Claude Code は、プロセス一覧を高速に取り続ける小さな C のプログラムを書いて、新しく現れたプロセスと親を記録しました。すると、ある開発用サーバーが**11秒で約1800個の子プロセス**を起動している時間帯がありました。子プロセスの名前はほとんど node で、それぞれが何を実行していたのかはまだ分かっていません。同じ時間帯には、`git` も200回以上起動されていました（`git status --porcelain` など）。

ただ、時間を置いて測り直すと、同じサーバーの子プロセスは10秒で33個でした。どういう条件で増えるのかは、まだ突き止められていません。

### Spotlight が node_modules を索引していた

`node_modules` を索引の対象から外すつもりで、開発用のディレクトリに `.metadata_never_index` を置いていました。**効いていませんでした。** 最近の macOS では、このファイルはボリュームの直下に置いたときしか効かないようです。

索引されている `package.json` 約18万件のうち、ほぼすべてが `node_modules` の中でした。`.js` ファイルは約237万件が索引されていました。

## AI の調査も間違える

一つ書いておきたいことがあります。最初の報告には誤りがありました。

「開発用サーバーが、セッションごとに tmux のコマンドを繰り返し起動している」という報告でした。実際には、それは**セッションごとに1つずつ常駐している**プロセスで、プロセス一覧を取るたびに同じものを数えていただけでした。ソースコードを読み直して分かりました。

調査を AI に任せるのは便利です。でも、**報告は主張であって、事実ではありません。** 「確認できた事実」と「原因の仮説」を分けて書いてもらい、仮説のほうは自分で裏を取る。今回はその分け方に助けられました。

## まだ確かめていないこと

ここまでは、状況証拠をつないだ推定です。確度は高いと思っていますが、まだ検証はしていません。

- 止まっていた間に `dirhelper` が消していた**具体的なパス**は、スナップショットに残っていません。`/private/tmp` だというのは、ファイル数と状況からの推定です
- 「片付けてから再起動すれば止まらない」ことは、まだ試していません

次の再起動の前に件数を記録し、片付けてから再起動して、止まる時間がどう変わるかを測るつもりです。

## 同じ目にあわないために

Claude Code をたくさん回している人向けに、分かったことをまとめます。

1. **`/private/tmp` の中身を時々見る。** `find /private/tmp -xdev | wc -l` で数えられます（数が多いと、これ自体に時間がかかります）。`/private/tmp/claude-<UID>/` の下を見れば、どのプロジェクトが溜めているか分かります
2. **終わったセッションの作業用ディレクトリは消す。** ただし、動いているセッションのものを消すと、そのセッションが壊れます。どのセッションのものか確実に分からないものは消さないでください。全部のセッションを終えて作業を保存してから、消すか再起動するのが安全です
3. **長く再起動しないと、次の再起動が重くなりやすい。** 作業用ディレクトリは放置すると溜まり続けます。今回も、6週間ぶりの再起動で止まりました
4. **心当たりがあるなら、進捗バーが止まっても電源ボタンは押さずに待つ。** 削除が途中で止まり、残りを次の起動でまた消すことになるとみられます。ただし、何時間たっても進まないなら、別の問題を疑ってください
5. **強制リセットしてしまったら、`/Library/Logs/DiagnosticReports` の `forceReset-*` を見る。** ログが取れない時間帯の、数少ない手がかりです

## 結局、買い替えは要るのか

- **今の使い方なら、メモリは今より少なくても足りる見込みです。** 使っていたのは47GBほどで、圧縮もスワップもゼロでした。重いときの上乗せを見込んでも、ファイルキャッシュに十分な余裕が残ります
- **効くのは CPU のコア数です。** 普段の重さの正体は CPU が埋まっていることでした
- **SSD を速くしても、起動の停止はあまり縮まらないと見ています。** ファイルの削除は数がものを言います。速いディスクに替えるより、ファイル数を減らすほうが確実です

起動に20分かかっていた原因は、Mac の故障でも、古さでもなさそうです。いちばん怪しいのは、**僕が AI に、安全のために毎日のように clone させていたリポジトリの残骸**でした。

200万円は、もう少し先送りできそうです。

## 補足：どういう使い方をしているのか

これだけの数が出る使い方も書いておきます。作っているのは [MulmoTerminal](https://github.com/receptron/mulmoterminal)、[MulmoClaude](https://github.com/receptron/mulmoclaude)、[chaffjs](https://www.npmjs.com/package/chaffjs) を含めて10個ほどの製品で、どれも並行して開発しています。

その開発自体も MulmoTerminal の上でやっています。ブラウザに複数のセッションを並べて、製品ごとに担当させる形です。どれかが考えている間に別のどれかが動いているので、手が止まる時間がほとんどありません。

つまり、どのセッションも同時にファイルを作り続けています。作業用ディレクトリはセッションごとに作られるので、溜まり方も製品の数ではなくセッションの数に比例します。9時間半で約99万という数は、そういう使い方の結果です。
