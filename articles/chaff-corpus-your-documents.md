## プログラミングは、確かめる工程ごと自動になった

プログラミングでは、作る工程の自動化が一気に進みました。
AI がコードを書き、それを確かめる工程も機械が受け持ちます。

- **リンター**: コードが決まりに沿って書かれているかを確かめる
- **ユニットテスト**: コードを変えるたびに、想定どおりに動くかを確かめる
- **AI によるレビュー**: 変更の意図と中身が合っているかを読む

この三つが変更のたびに自動で回るので、人が一行ずつ確かめなくても、本番に出せるコードがとても速くできるようになりました。
プログラミングの仕事の 9 割以上は、もう自動にできます。
Anthropic は自社のブログで、社内のコードの大半を AI が書くようになったことを書いています。
Uber をはじめとする先端の企業や、AI を使いこなすスタートアップでも、それが普通の働き方になりつつあります。

## 文書の仕事は、まだそこまで来ていない

一方で、文書を中心に仕事をする人たち — 契約書を作る、報告書をまとめる、規程を直す、議事録を残す — の仕事は、まだそこまで来ていません。
法務、経理、行政など、分野ごとに道具やスタートアップは出てきていますが、どこもまだ手探りです。

理由の一つは、文書が**決まった形をしていない**ことです。
コードは、コンパイラが読める形で書かれているので、機械で確かめる仕組みを作りやすい。
文書は人が読むために書かれていて、書き方も分野ごとに違います。だから自動にしにくいのです。

でも、プログラミングが速くなったのは、AI が書けるようになったからだけではありません。
**書いたものを機械が確かめる仕組みが先にあった**から、AI に任せても大丈夫になったのです。
確かめる仕組みがなければ、AI が速く書いた分だけ、人が読んで確かめる仕事が増えます。

文書の仕事を同じように速くするには、**文書のためのリンターとテストとレビュー**が要ります。

## chaff ってなに？

[chaff](https://isamu.github.io/lab/)（npm では `chaffjs`）は、私たちが作っている、**文書を機械で確かめる道具**です。
プログラミングのリンターとユニットテストを、ふつうの文章のために作り直したものです。
契約書、報告書、社内規程、マニュアル、議事録、ブログなど、日本語と英語の文書をそのまま読みます。

文章のリンター自体は、これまでもありました。たとえば textlint は、技術文書の表記をそろえるのに広く使われています。
chaff が目指しているのは、それを**AI と一緒に使う前提で作り直す**ことです。

- **毎回同じ結果を返す。** 判定に AI を使っていないので、同じ文章なら何度かけても同じ結果になります。AI が書き直すたびにかけて、前と比べられます。
- **なぜ、どう直すかまで返す。** 指摘ごとに、なぜ読みにくいかと、直す方向を返します。`npx chaffjs fix-plan` は、それをルールごとにまとめた「直す計画」を JSON でも出すので、そのまま AI に渡して書き直させられます。
- **書き直しで落ちたものを見つける。** `npx chaffjs compare 前.md 後.md` は、AI の書き直しで数字・日付・URL・名前が落ちたり足されたりしていないかを確かめます。
- **見ていないことを隠さない。** 「指摘なし」を「全部見て問題なし」と取り違えないよう、今回動かなかったルールを理由付きで一覧にします。
- **意味の判断が要るところだけ AI に回す。** 意味を読まないと決められない検査は `chaff test` に分けてあり、何を送るかを先に見せてから、判断が要る箇所だけを送ります。
- **CI に入れられる。** 終了コードを返し、指摘を SARIF でも書き出せるので、プログラムと同じく変更のたびに回せます。

chaff は文章を書き換えません。直すのは書いた人、またはその人が頼んだ AI です。

確かめることの例を挙げます。

| 種類 | 例 |
| --- | --- |
| 読みやすさ | 一文が長すぎないか、同じ語を二通りに書いていないか |
| 構造 | 条や番号が飛んでいないか、同じ用語を二度定義していないか、定義する前に使っていないか |
| 食い違い | 日付の順番や曜日が正しいか、合計と内訳が合っているか |
| 書き直しの前後 | 書き直したときに、数字や日付が落ちていないか、引用が原文にあるか |

## なぜ AI ではなく機械で確かめるのか

AI の書いた文書には、AI らしい間違いが混ざります。書き直したら数字が一つ落ちていた。同じものを途中から別の呼び方で書いていた。
引用のつもりが、原文にない言い回しになっていた。

こうした間違いを、別の AI に読ませて確かめることもできます。
けれども、AI が AI の文章を確かめると、同じ思い込みを共有したまま「問題なし」と言いがちです。答えも毎回少しずつ変わります。

一方、こうした間違いの多くは、**意味を読まなくても機械で確かめられます**。
数字が書き直しの前後でそろっているか、用語が一通りに書かれているか、第4条の次が第5条か。
これらは決まった手順で判定でき、判定すれば毎回同じ答えになります。

そこで、**機械で確かめられることは機械に任せ、意味を読まないと分からないことだけを人や AI に残す**ことにしました。
chaff はその「機械の半分」です。プログラミングでリンターとテストが AI の書いたコードを支えているように、AI の書いた文書を機械で支えるための道具です。

## どう使うの？

Node.js 24 以上があれば、インストールも設定ファイルも要りません。

```bash
npx chaffjs article.md
```

たとえば、次の `article.md` にかけると、

```markdown
# キャッシュを使う

## キャッシュの仕組み

キャッシュの仕組みについて説明します。一度読んだデータを手元に置き、二度目からはそこから返します。
```

画面にはこう出ます（出力の前半です）。

```text
article.md   blog/tech · 日本語   ジャンルは既定から

─── 5 行目 ───────────────────────────────────────────────────

    キャッシュの仕組みについて説明します。

  ·  見出しの繰り返し

     見出し「キャッシュの仕組み」を直後の文がほぼそのまま繰り返しています
     見出しで言ったことを次の文が繰り返すと、読者はそこで何も受け取れません。

     → 見出しが約束したことの中身から書き始めてください。

     このルールをゆるめる:  npx chaffjs relax heading-echo
```

指摘された文、何が起きているか、なぜ読みにくいか、どう直すか（`→` の行）が並びます。
最後の行は、この指摘がチームの方針に合わないときに、ルールのほうをゆるめるコマンドです。

文書の種類（ジャンル）を指定すると、その種類の書き方に合わせて見ます。
契約書と議事録とブログでは、よい書き方が違うからです。

```bash
npx chaffjs --genre legal/contract 契約書.md    契約書として見る
npx chaffjs genres                              ジャンルの一覧
npx chaffjs init                                設定ファイル chaff.yaml を作る
```

インストールせずに試すなら、[プレイグラウンド](https://isamu.github.io/lab/ja/playground/)に文章を貼るだけで動きます。

## この記事で伝えたいこと

ここから先は、二つのことを書きます。

1. **自分たちの決まりを chaff に書いて、自分の文書がよくなるのを実感する**使い方
2. chaff が外れたときに、**その文書を [chaff-corpus](https://github.com/isamu/chaff-corpus) にプルリクエスト（PR）で送ってもらう**方法と、
   なぜそれをお願いしているのか

文章チェックの道具は、使い始めはよく効いても、しばらくすると外れが目に付いてきます。
正しい書き方なのに指摘される。見つけてほしい誤りを素通りする。そのうち指摘を読まなくなり、やがて外されます。
chaff は、使う人から届く「外れた実例」で直していく前提で作っています。二つ目が、この記事の本題です。

## 自分たちの決まりを書くと、効き目が見える

<!-- stet: katakana-long-vowel — 表記の揺れそのものを例に挙げている -->
既定のルールだけでも動きますが、chaff が一番効くのは、**チームの決まりを書いたとき**です。
「サーバ」と「サーバー」のどちらに寄せるか、未定のまま出してはいけない書き方は何か — こうした決まりはチームごとに違うので、
chaff は既定では何も言いません。リポジトリの一番上に置く `chaff.yaml` に書きます。

```yaml
# chaff.yaml
genre: business/report        # 報告書として見る

prefer:                       # 左を見つけたら右を勧める
  サーバ: サーバー
  ユーザ: ユーザー

custom_rules:                 # チーム独自のルール（コードは要らない）
  - id: team-no-tbd
    type: pattern
    pattern: 'TBD|未定'
    level: error
    name: 未定のまま
    why: 未定のまま出すと、読む人が決まったことと取り違えます。
    how_to_fix: 決まっていることを書くか、決める人と期日を書いてください。
    example: { before: 締切は TBD です。, after: 締切は 10 月 5 日です。 }
```

この設定で、次の報告書にかけてみます。

```markdown
# 第3四半期の進捗報告

## 概要

今期はサーバの移行を進めました。移行の完了日はTBDです。
```

出力の一部です（chaffjs 0.36.0）。

```text
報告.md   business/report · 日本語   ジャンルは chaff.yaml から

─── 5 行目 ───────────────────────────────────────────────────

    今期はサーバの移行を進めました。

  ⚠  チームの表記と違う

     「サーバ」は「サーバー」と書きます
     …
     → 「サーバー」に直してください。固有名詞など、そのままにすべき箇所なら stet で理由を添えて黙らせます。

─── 5 行目 ───────────────────────────────────────────────────

    移行の完了日はTBDです。

  ✖  未定のまま

     未定のまま:「TBD」
     未定のまま出すと、読む人が決まったことと取り違えます。

     → 決まっていることを書くか、決める人と期日を書いてください。
```

ジャンルを `business/report` にしたので、指摘の前に「報告書の指針」も出ます。
冒頭で結論を述べているか、次の行動を担当と期限付きで書いているか、といった問いの一覧です。

直してもう一度かければ、指摘は消えます。**自分たちで決めたことが、毎回同じように守られる**。
これが chaff を使って最初に感じる手応えだと思います。

指摘に納得できないときの応じ方は三つあります。

| 場合 | 応じ方 |
| --- | --- |
| 指摘がもっとも | 文章を直す |
| 指摘は正しいが、そこは意図して書いた | その箇所に `<!-- stet: rule-id — 理由 -->` を書いて黙らせる |
| チームの方針に合わない | `npx chaffjs relax rule-id --why "理由"` でルールのほうをゆるめる |

ここまでは、自分の手元で完結する話です。

## それでも chaff が外れるとき

困るのは四つ目の場合です。**指摘そのものが誤っている**（誤検出）、あるいは**出るべき指摘が出ない**（見逃し）。

`relax` や `stet` で黙らせることはできますが、それでは chaff は直りません。
同じ書き方をしている別の文書でも、同じ外れ方をし続けます。

chaff は決まった手順で判定する機械なので、外れ方には必ず形があります。
「見出しを文として読んだ」「定義語が別紙で定義されているのを見ていない」「箇条書きの各行を一続きの文として読んだ」 —
一つの外れを直すと、同じ形をしたほかの文書の外れもまとめて直ります。
だから、**外れた実例をいただけること**が、chaff にとって一番ありがたい報告になります。

## 報告の道は二つ

### 手軽な道: `chaff feedback` で下書きを作る

```bash
npx chaffjs feedback 報告.md --rule preferred-term --line 5
```

その指摘の前後の行だけを抜き出した報告の下書きを `.chaff-feedback.md` に書き、送るためのコマンドを表示します。
chaff 自身は何も送りません。読み直して、共有したくない部分を消してから送ります。

```text
  Wrote a draft report to .chaff-feedback.md. From the document it includes only the lines around 5.
  Read it before sending, and delete anything you do not want to share.

  To send it (either):
    gh issue create -R isamu/lab --title 'False positive: preferred-term — …' --body-file .chaff-feedback.md
  …
  chaff has not sent anything.
```

見逃しは `--missed --line N` で同じように下書きできます。

### 一番効く道: 文書ごと chaff-corpus に PR する

もう一つが、**文書を丸ごと、判定付きで** [isamu/chaff-corpus](https://github.com/isamu/chaff-corpus) に送る道です。
chaff-corpus は、実在の文書と、chaff がその文書に出す指摘一つ一つの判定を組にして置くリポジトリです。
行政の案内、法令、契約のひな形、議事録、有価証券報告書、社内ハンドブック、プレスリリースなど、
日本語と英語の文書が数百本入っていて、いまも増えています。

指摘一つ一つには、次のどれかの判定が付いています。

| 判定 | 意味 | chaff が変わって結果が動いたとき |
| --- | --- | --- |
| `correct` | 正しい指摘で、出続けるべき | 消えたら **CI が失敗**（後退） |
| `false-positive` | 誤った指摘で、消えるべき | 消えたら改善として報告 |
| `missed` | 出るべきなのに出ない | 出るようになったら「見つかった」と報告 |
| `unjudged` | まだ誰も判定していない | 判定待ちとして列挙 |

前後の数行だけの報告と違い、ここに置いた文書は**chaff の修正をそのまま試す材料**になり、そのあとも残り続けます。

## 文書を送る手順

chaff-corpus の [CONTRIBUTING.ja.md](https://github.com/isamu/chaff-corpus/blob/main/CONTRIBUTING.ja.md) に詳しく書いてあります。
流れは次のとおりです。必要なのは Node 24 と Yarn 1 です。

### 1. 共有してよい文書か確かめる

- 再配布を認めるライセンス（パブリックドメイン、CC0、CC BY、公共データ利用規約、政府標準利用規約など）の文書なら、本文ごと置けます。
- 公開されているが複製を認めていない文書は、本文を置かずに、出典の URL と本文のハッシュだけを置きます（`redistribute: false`）。
  本文は CI が実行時に取りに行き、ハッシュが一致したときだけ使います。
- 自分で書いた文章は、CC0 や CC BY 4.0 などのライセンスを付ければ使えます。
- **社外秘の文書は、抜粋も含めて送れません。** 同じ外れ方をする短い文章を自分で書いて、それを送ってください。
  外れの「形」さえ再現できれば、chaff は直せます。
- 私人の名前・メールアドレス・電話番号は含めません。

### 2. 文書を置く

```text
docs/<lang>/<genre>/<id>.md     本文
docs/<lang>/<genre>/<id>.yaml   出典、ライセンス、言語、ジャンル、本文の sha256
```

`<genre>` は `npx chaffjs genres` の一覧から選びます（`business/report`、`legal/contract`、`docs/faq` など）。

```yaml
id: q3-report
title: 第3四半期報告
language: ja
genre: business/report
source:
  url: https://example.go.jp/reports/q3
  fetched: 2026-10-14
license:
  name: CC-BY-4.0
  url: https://creativecommons.org/licenses/by/4.0/
  note: 出典: 〇〇省ホームページ（…）を加工して作成
redistribute: true
sha256: 3f5a…            # shasum -a 256 docs/ja/business/report/q3-report.md
```

### 3. chaff の指摘を書き出す

```bash
yarn install
yarn validate                          # メタデータ、ライセンス、個人情報、サイズ
yarn run-corpus --update --only q3-report
```

chaff が出す指摘がすべて `unjudged` として `expected/q3-report.yaml` に書かれます。

### 4. 外れに印を付ける

誤った指摘は `verdict` を `false-positive` にして、理由を一行の `note` に書きます。
出なかった指摘は、`rule`、`line`、`what`、`verdict: missed` の項目を足します。

```yaml
id: q3-report
chaff: 0.36.0
findings:
  - rule: undefined-term
    line: 12
    text: 本サービス
    verdict: false-positive
    note: 定義は第1条にあり、見出しの書き方のせいで chaff が結び付けられていない
  - rule: numbering-gap
    line: 40
    what: 第4条の次が第6条
    verdict: missed
```

`note` には、**どういう形の外れか**を自分の言葉で書いてください。この一行が、そのまま chaff の修正の出発点になります。
`rule`、`line`、`text` は変えません。実行時に同じ指摘を見つけ直すための手がかりです。

ほかの指摘は、判定できるものだけ `correct` か `false-positive` にして、自信のないものは `unjudged` のままでかまいません。

### 5. PR を出す

PR のテンプレートに、ライセンス、個人情報、判定の確認項目が並んでいます。
最後に「chaff が何を間違えたか」を一、二文で書いてください。

## PR を出したあと、何が起きるか

1. **CI は事例を受け入れます。** `false-positive` と `missed` は未解決の事例として残課題に載りますが、CI は落ちません。
   PR には、公開前の chaff（isamu/lab の main）で同じ文書を回した結果も出ます。すでに直っていて、まだ公開されていないだけかどうかが分かります。
2. **chaff 側に課題が開きます。** 事例が chaff-corpus に入ると、chaff の開発リポジトリ（isamu/lab）に
   `corpus-case` ラベルの課題が文書ごとに自動で開きます。
3. **chaff の修正は、その文書に対して試されます。** 修正の PR は chaff-corpus 全体に対して実行され、どの事例を解決するか、
   正しい指摘を一つも落としていないかが報告されます。
4. **新しい chaff が出ると、自動で閉じます。** npm に新しい chaffjs が出ると、chaff-corpus で毎日動く仕組みが版を上げ、
   消えた誤検出を取り除き、見つかった見逃しを `correct` に変える PR を開きます。
   それが入ると、chaff 側の課題も閉じます。

送った文書はそのあとも chaff-corpus に残ります。
**一度直った外れが、将来の変更で戻ってきたら、CI がそこで気づきます。**

## なぜ PR でお願いしているのか

報告を受ける形はいろいろありえます。それでも「文書ごと、判定付きで」をお願いしているのには理由があります。

**一つ目は、直したことを実物で確かめられるからです。** 前後数行の抜粋で直すと、その数行では直っても、文書全体ではほかの指摘が動くことがあります。
文書全体があれば、直した chaff を同じ文書にかけて、外れが消えたこと、ほかの正しい指摘が消えていないことを、機械で確かめられます。

**二つ目は、直ったものが戻らないからです。** 判定は消えずに残ります。`correct` と判定した指摘が消えれば CI が失敗するので、
誰かの別の修正が、あなたの文書で直したことを黙って壊すことはありません。

**三つ目は、あなたの判定が、同じ種類の文書の既定を変えるからです。** chaff は、ルールとジャンルの組ごとに、
chaff-corpus での判定から精度を測っています。外れの多い組は、そのジャンルの既定でルールを止めます。
議事録で外れてばかりのルールがあれば、議事録の判定が集まるほど、議事録では最初から動かなくなります。
あなたの判定は、あなたと同じ種類の文書を書く人全員の既定になります。

**四つ目は、chaff を直しているのが AI だからです。** chaff のルールの修正は、実際には AI が行っています。
chaff-corpus の誤検出を読んで外れの形を見つけ、最小の抜粋でテストを書いて失敗を確かめてから直します。
そのあと、コーパス全体で何も後退していないことを確かめます。この繰り返しです。
AI は直すのが速い一方で、**何が外れなのかは、その文書を書いている人にしか判定できません。**
その判定が人から届く限り、chaff は直り続けます。
chaff が「AI の間違いを機械で捕まえる道具」であるためにも、その機械の判断基準は人の判定に置いておきたいのです。

## まとめ

- まず `chaff.yaml` に、チームの表記と独自のルールを書いて、自分の文書にかけてください。決めたことが毎回同じように守られます。
- 指摘に納得できなければ、文章を直すか、`stet` で黙らせるか、`relax` でルールをゆるめます。
- chaff そのものが外れていたら、`npx chaffjs feedback` で下書きを作るか、
  文書を判定付きで [chaff-corpus](https://github.com/isamu/chaff-corpus) に PR してください。
- 送られた文書で chaff が直り、直ったことはそのあとも守られ、同じ種類の文書を書く人全員の既定がよくなります。

外れた文書を、お待ちしています。
