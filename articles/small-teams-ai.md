## できるかどうかも、欲しいかどうかも分からないものの仕様書は書けない

MulmoTerminal の起点は、**ブラウザでターミナルが動くかどうかの実験**でした。動いたので、単純にグリッドに広げてみた。あとは触りながら、欲しい機能を足していった。それだけです。

このとき、仕様書を書く余地はどこにもありませんでした。

- **できるかどうか分からない**（ブラウザに本物の pty を9枚並べて実用になるのか）
- **欲しい機能かどうか分からない**（並べたところで嬉しいのか、自分でも分からない）

**この2つが未知のまま、何を書けというのか。** 書けるとしたら、それは仕様書ではなく願望です。

一方で、仕様書が有効に機能する場面は明確にあります。Amazon のクローンを作る。UIにこだわらない業務システムを作る。**このとき仕様書が書けるのは、対象がすでに世の中に存在するからです。**

> **仕様書は「すでにある知識の圧縮」であって、「まだ無いものの発見」ではない。**

圧縮する対象がないものを、圧縮することはできません。

## ウォーターフォールが失敗したのは、実装が遅かったからではない

ここで思い出してほしいことがあります。

**人間だけで作っていた時代も、仕様書は間違っていました。**

仕様を書いて、開発に渡して、SWEから「これ、こうなってますけど成立しません」と何度も戻ってくる。実際に動くものを触って初めて「あ、これじゃない」と気づく。**あの往復は、実装が遅いから起きていたわけではありません。**

**仕様が間違っていて、触るまで誰も分からなかったから起きていました。**

そして今、AIが速くしたのは**実装のほう**です。

```
遅かったもの     実装        → 速くなった
間違っていたもの  仕様        → 何も変わっていない
```

**失敗の原因は、1ミリも解決していません。** それどころか悪化します。**間違った仕様が、より速く、より大量に実体化する**ようになったからです。

## アジャイルにしても同じことが起きる

「だからアジャイルでやっている」という反論はあると思います。でも、それでも足りません。

**プロダクトのオーナーとチームが分離していると、意思決定が遅れます。** そして最悪の場合、**コードレベルの意思決定が反映できず、クソシステムになります。**

本当の変数は、ウォーターフォールかアジャイルかではありません。

> **意思決定する人と、コードの距離。**

```
仕様駆動           決める人がコードから最も遠い。一度だけ、最も遠くで決める
アジャイル(分離型)   決める人は会議にいる。キーボードにはいない
                   → スプリントの粒度でしか決められない
並走               決める人がキーボードにいる
```

アジャイルは距離を縮めました。でも**ゼロにはしていません。** そして、**ゼロでないと届かない決定がある**というのが、この記事で一番言いたいことです。

## コードレベルでしか出てこない決定の実例

MulmoTerminal の README に、こういう一行があります。

> the one-session-per-worktree limit applies to **agents only**, and a shell or a `yarn dev` launcher can sit in the same worktree an agent is working in

**「1 worktree につき1セッション。ただしエージェントにだけ適用する」**

これは製品ルールですが、**実装の事実から出てきたもの**です。「どのセルも本物の pty で、エージェントはそこで走らせるものの1つでしかない」と分かって初めて言えます。

**PO はこれを書けません。** 書くとしたら「1 worktree につき1セッション」で、**それは間違いです。** dev サーバも `htop` も締め出してしまう。しかも**エージェントが作業している worktree こそ、dev サーバを動かしたい場所**です。

**製品の中心にある差別化が、コードレベルの発見から生まれています。** 仕様書からは到達できない場所です。

もう1つ、開発ログに残っている判断を引用します。

> 検査は多数の重複を指摘していますが、「読み込む→見つからなければエラー→例外を捕まえる」という構造上の反復であり、**各処理が自己完結しているからこそ読みやすい**、という理由です。まとめると2700行の巨大ファイルを広範囲に書き換えることになり、**読みやすさがむしろ下がる**と判断しました。

**機械が「直せ」と言ったのに、従わなかった。** この判断は、そのコードを読んでいる人にしかできません。チケットにも、仕様書にも、スプリントレビューにも乗りません。

## AIは距離を縮めない

ここが一番大事なところだと思います。

**AIが上げたのは「キーボードにいる人」の生産性です。** 決定権がキーボードから遠いところにあるなら、その高速化は届きません。

```
決定権がキーボードにある   →  速く、正しく作れる
決定権が遠いまま           →  遠いまま速く作れる
                            ＝ クソシステムが速く完成する
```

**多くの組織が、同じ道具を入れても同じ速度になりません。** 道具の問題ではなく、意思決定がキーボードから遠いからです。**そしてAIは、その距離には何もしません。**

## 症状：「大きなコードができてレビューできない」

最近こういう相談を受けました。

> 大規模なコードができてしまってレビューできない。どうすればいいですか。

**これは質問ではなく、すでに詰んでいる状態の報告です。**

そして「AIにレビューさせればいい」は答えになりません。**人間が読めないものは、AIも読めません。**

コンテキストサイズは有限です。**でかい差分は、そもそもコードレビューできない。** 入ったとしても、全体に注意が行き渡るわけでもありません。

```
仕様書を全部書く → 一気に生成 → 巨大な差分 → 誰もレビューできない
                                          ↑ 人もAIも
```

**「最後はAIがレビューしてくれる」を前提にした設計は、ここで詰みます。**

## 機械が測れるものを全部クリアしても、残るものがある

余談に見えるかもしれませんが、これは同じ話です。

2026年4月、mulmoclaude で `handleTableClick` という関数が**143行、認知的複雑度163**ありました。`.vue` をESLintの対象に入れた瞬間に浮上したものです。分割してユニットテストを足し、閾値以下に戻しました。

それから3ヶ月後、同じリポジトリを測るとこうなっています。

```
CollectionView.vue      2,945行  関数187個  最長 61行
server/index.ts（別repo） 3,020行  関数212個  最長 82行  中央値 6行

```

**関数の肥大は、実際に解決されました。誰も違反していません。** それなのに**ファイルは3,000行**あります。

「機械に通ったから大丈夫」が成立しないのは、レビューでも、設計でも、同じです。

## では、実際どうやって作っているのか

冒頭の数字の内訳です。全部実測です。

```

  中央値       1.6 時間
  6時間以内     77%
  24時間以内    92%

  中央値       286 行
  300行未満     51%
  変更ファイル   中央値 7個
```

**issueが1.6時間で閉じるということは、それは仕様書ではありません。**「いま気づいたこと」の記録です。それを53日で400件以上やって、64回リリースしています。

そして、**巨大な差分にならない状態を先に作っています。** 「レビューできないコードをどうするか」ではなく、**そこに入らない。**

### 仕様書は書いています。351本。

誤解のないように言うと、計画を書かないわけではありません。

自分たちのワークフローが、そのまま主張の証拠になっていました。仕様駆動を否定しているのではなく、**仕様書が書ける条件を守っているだけ**です。

## 並列できる数は、道具ではなく自分で決まる

ここから人数の話になります。

自分が実際に何個並列できるかを、正直に書きます。

```
1つのプロジェクト内
  ざっと流して判断するだけ     6個以上いける
  仕様を考えながら             5個が限界

プロジェクトをまたぐ
  脳の負荷が低い作業           3〜4プロジェクト
  依存がある・仕様を考える・
  再現しながら追う             並列できない（1個）
```

**ツールは9個並べられます。並べられないのは自分のほうです。**

これには名前がついていて、**アムダールの法則**そのものです。全体のうち直列にしか進まない部分の割合を s とすると、どれだけ並列にしても速度向上は 1/s で頭打ちになります。

```
直列部分（自分が考えないと進まない割合）
   30%  →  最大 3.3個
   20%  →  最大 5個      ← 実測（3〜6個）はここ
   10%  →  最大 10個
```

**いま3〜4個で止まっているのは、道具の限界ではなく、直列部分が2〜3割あるからです。**

だとすれば打ち手は「エージェントを増やす」ではなく、**「自分が考えないと進まない部分を減らす」**です。仕様を先に決める、再現手順を先に作る、依存を先に切る。ボトルネックだけを切り出す。

ただし**切り出す作業そのものも直列**なので、ゼロにはなりません。1/3を1/6にできれば3個が6個になる、という程度です。それと、**自分の稼働率が8割を超えたあたりから待ち行列が伸びます。** 「あと1個いけそう」で足すと、全体が遅くなります。

## だからチームも同じだ

ここが結論です。

**人数を決めるべき変数は、実装量ではありません。判断の帯域です。**

実装量で人数を決めていた時代は終わりました。実装は人数に比例しなくなったからです。**残ったのは判断で、判断は分割できません。**

だから、**AIを使うほどチームは小さくなるべきです。**

> **1つのプロダクトにつき1〜3人。**
> プロダクトのオーナー自身か、それを支えられる人が、実装する。

それより多い人数でAIを使って開発しているなら、**根本的に何かが間違っています。**

### ピザ理論は、もう会議の話ではない

ベゾスの2ピザルールは**会議**の話でした。コミュニケーションのコストへの歯止めです。当時は実装に人数が必要だったので、会議だけを絞るのが合理的でした。

**いまは実装が人数に比例しません。** 残っているのは判断だけで、判断こそコミュニケーションのコストを一番食います。

```
かつて  会議が2ピザ
いま    開発そのものが2ピザ
```

### 減らすのは人ではなく、プロダクトあたりの人数

ここは誤解されやすいので明確にしておきます。**「8人を2人にしろ」ではありません。**

```
✗  8人を2人にする
✓  8人を1つのプロダクトに置くのをやめる
   → 2人 × 4プロダクト
```

1人が3〜4プロジェクトを並列できるなら、2人で6〜8プロダクトです。**人を減らすのではなく、プロダクトあたりの人数を減らす。**

そして、これは思いつきではありません。**11年やってきた結果です。**

```
2015  VideoShader    iOS/OpenGL の GPU 動画処理
2015  Swipe          漫画をスマホで動かすランタイム
2020  おもちかえり.com  コロナ禍の飲食店テイクアウト支援
2023  SlashGPT
2024  GraphAI
2025  MulmoCast
2026  MulmoTerminal
```

**7プロダクト、4領域、ずっと同じ2人です。** 全部オープンソースがコアにあって、全部いまもGitHubにあります。

## 例外はある

最後に、この主張が当てはまらない場所を書いておきます。ここを曖昧にすると、ただのスローガンになるので。

- **専門領域が必要なもの** — セキュリティ、ML、ハードウェア、規制対応。ここは人数ではなく知識の問題です
- **24時間運用が要るもの** — 人間の睡眠は分割できません
- **職務分離が法的に必須な業界** — 金融や医療で「作った人がレビューする」は選べません
- **プロダクトの数が多い場合** — 1プロダクト1〜3人であって、会社が3人という意味ではありません

これらに当てはまらないのに8人いるなら、**なぜ8人なのかを一度考えてみる価値はあると思います。**

## まとめ

- **できるかどうかも、欲しいかどうかも分からないものの仕様書は書けない**
- 問題はウォーターフォールでもアジャイルでもない。**意思決定とコードの距離**
- **AIが速くしたのは実装だけ。** 仕様が間違う問題も、距離も、何も解決していない
- 距離が遠いまま速く作れるようになった結果、**クソシステムが速く完成する**
- 「大きすぎてレビューできない」は質問ではなく、**すでに詰んでいる状態の報告**。人が読めないものはAIも読めない
- 並列数もチームサイズも、決めているのは道具ではなく**判断の帯域**
- だから **1プロダクト1〜3人**。ピザ理論は、もう会議ではなく開発そのものに効く

ベースだけざっと作って、あとは並走する。**それは「雑にやる」という意味ではありません。判断の回数を増やす、という意味です。**

そして判断の回数を増やせるのは、**キーボードの前に座っている人だけ**です。
