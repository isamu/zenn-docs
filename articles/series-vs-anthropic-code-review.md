2026 年 10 月、Anthropic の Claude Code チームが、自分たちのコードレビューの仕組みを公開しました。人間が 1 行ずつ読むのをやめ、読む作業のほとんどを機械に移したという内容です。

私たちも、1 日 500 コミットの開発を続けるなかで、同じ方向に進んできました。その記録は「1日500コミット」シリーズとして書いてきました。この記事では、二つを項目ごとに突き合わせ、どこが同じで、どこに抜けがあるかを表で評価します。

材料にしたのは 3 つだけです。1 つ目は Anthropic の記事 [How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/) です。Addy Osmani、Morgan Westlee Lunt、Qing Wang の 3 人が 2026 年 10 月 15 日に公開し、レビューの層の構成と、その効果の数値を書いています。2 つ目は、私たちが MulmoTerminal の開発で実際にやっていることを書いた「1日500コミット」シリーズの 9 本です（一覧は末尾）。3 つ目は、[receptron/mulmoterminal](https://github.com/receptron/mulmoterminal) のマージ済み PR の記録で、回帰がどれだけ起きたかをここから数えました。

評価は、記事や記録に書いてあるかどうかだけで決めています。筆者の意見は、最後の節に分けて書きます。

## Anthropic の仕組み

Anthropic の記事は、方針を次のように書いています。

> We didn't remove review. But we did move most of the reading to machines, optimized for human time and attention, and invested heavily in making it fast and easy to undo mistakes.

「レビューはなくしていないが、読む作業のほとんどを機械に移し、間違いを速く簡単に取り消せるようにした」という意味です。仕組みは、次の層の重ね合わせです。

| 層 | 中身 |
|---|---|
| PR を出す前 | Claude 自身がテスト・ビルド・スクリーンショットで確かめる。別のエージェントが新しい文脈で差分を読む。`CLAUDE.md` と `REVIEW.md` に規約と「何を指摘しないか」を書く |
| AI レビュー | すべての PR に Claude のレビューが付く。複数のエージェントが並列に探し、別のエージェント群が投票して、合意したものだけを載せる。指摘は重要・細かい・既存の 3 種類に分ける |
| セキュリティ | 自動のセキュリティレビュー。未解決の指摘があるとマージできない |
| 自動チェック | lint・型・全プラットフォームのテスト・ビルドが必須 |
| 人間の承認 | 変更のリスクで人数が決まる（下の表） |
| マージとリリース | マージキュー、フィーチャーフラグ、社内での先行利用、段階リリース、週替わりのオンコール |
| 事後 | 障害のあと「どの層なら止められたか」を振り返る |

人間の承認は、変更のリスクで 3 段階に分かれています。

| リスク | 例 | 必要な人間の承認 |
|---|---|---|
| 低 | 文書、文言、社内向けの機能、フラグの裏に置いた追加 | 自動レビューとセキュリティチェックが通れば 0 人 |
| 中 | 普通の機能変更、キャッシュ・自動更新・システムプロンプトのような繊細な箇所 | 1 人 |
| 高 | もっともリスクの高いコードと、常に 2 人が要る一部のパス | 2 人 |

効果として、記事には次の数値が載っています。

- 6 月から 9 月で、マージされた PR は 2 倍を超え、取り消し（revert）の割合は 40% 以上下がった
- 中身のある指摘が付く PR の割合は、16% から 54% に上がった
- 往復を収束させる工夫（3 往復で方針の見直しを促す、など）のあと、合格までのレビュー回数の平均は 2.08 から 1.32 に下がった
- レビューが繰り返し指摘していたものを `git blame` で調べると、約 59% は PR が入れたものではなく、もともとあったコードだった

## 私たちの運用の前提

シリーズで書いてきた運用を、人間がどこで関わるかの観点でまとめると、次のようになります。

- issue を渡す段階で、必要なら人間が確認する
- 実装中に AI が迷ったところ（コードから決められない判断）は、人間に聞く
- 動作確認が要るものは、人間が動かして確かめる。人間はコミットを積まない
- それ以外は、AI のクロスレビュー（Claude Code が書き、Codex と CodeRabbit が読む）と CI を通れば、自動でマージする
- マージまで AI が見守り、`main` を取り込むときの衝突も AI が直す
- gitleaks で秘密情報の混入を検出する。そもそもリポジトリで秘密情報を扱わない
- 不具合は、戻すのではなく、その日のうちに直して前に進む

## 突き合わせの表

Anthropic の記事の項目ごとに、シリーズでの扱いを評価しました。

表の記号は、○がやっていると書いてあるもの、△が一部または別の形でやっているもの、×がやっていないものです。

| 層 | 項目 | 評価 | シリーズでの根拠 |
|---|---|---|---|
| PR を出す前 | `CLAUDE.md` に規約を書く | ○ | [レビューをやめた話](https://zenn.dev/singularity/articles/stopped-reviewing-my-code)、[きれいなコードの守り方](https://zenn.dev/singularity/articles/clean-code-ci-for-ai-era) |
| | 書いたのとは別の AI に読ませる | ○ | 「実装したのと別の AI にレビューさせる。」（レビューをやめた話） |
| | AI 自身がテストやビルドで確かめる | △ | 型チェックやテストを回すよう `CLAUDE.md` で指示している |
| | `REVIEW.md`（何を指摘しないか） | × | — |
| AI レビュー | すべての PR にかける | ○ | 「Auto-fire on EVERY PR」（レビューをやめた話） |
| | 全指摘に応答する | ○ | 「何を直して何を意図的に飛ばしたかを PR にコメントする」（同） |
| | 往復の上限 | ○ | 「最大5イテレーション」（同）。Anthropic は 3 往復 |
| | 複数エージェントの投票 | △ | 種類の違う 2 つのレビュアーを併用。投票はしていない |
| | 指摘の重大度を分ける | △ | 受け取る側で「本物の修正・妥当な細かい指摘・誤検知」に分けている |
| セキュリティ | 自動化してマージを止める | △ | ESLint のセキュリティルールと gitleaks。レビューとしての独立した関門はない |
| 自動チェック | lint・型・テスト・ビルドが必須 | ○ | 3 OS の CI。[「入れたつもり」を数える](https://zenn.dev/singularity/articles/what-else-was-off) |
| 人間の承認 | リスクで人数を変える | △ | 「人間が要るものだけ止める」の 2 段階。決めるのは変更内容ではなく、実装する AI の迷い |
| | 高リスクのパスは常に人間 | × | パスによる指定はない |
| マージ | マージキュー | △ | `main` の取り込みと確認を AI が行う。GitHub の設定による強制はない |
| リリース | フラグ・段階リリース・オンコール | × | 「その日のうちに直す」で代えている（[中央値1.2時間](https://zenn.dev/singularity/articles/issue-median-one-hour)） |
| | 取り消し（ロールバック） | × | 戻さずに直して進む方針 |
| 改善の仕組み | 既存コード由来の指摘を分ける | ○ | 「古いコードは免除、新しいコードは初日から全ルール適用」（[ever-better](https://zenn.dev/singularity/articles/ever-better-pm2)）。lint の側の話 |
| | 過去の障害でレビューの精度を測る | × | lint の誤検知は数えているが、AI レビューの見逃しは測っていない |
| 指標 | 回帰の割合を追う | × → 本記事で実測 | 次の節 |

## 違いは二つ

表の×と△を見ていくと、違いは二つにまとまります。

### 人間を呼ぶ条件

Anthropic は「**間違えると痛いか**」で人間を呼びます。キャッシュ、自動更新、システムプロンプト、決まったパスは、変更が小さくても人間が見ます。判定するのは著者ではなく、変更の中身です。

私たちは「**AI が迷ったか**」「**動かして確かめる必要があるか**」で人間を呼びます。判定するのは、実装している AI と、issue を渡す人間です。

### 事故への備え

Anthropic は「**すぐ戻せる**」ことに投資しています。記事には「Flags, reverts and staged releases undo most mistakes in minutes.」とあり、だからこそ低リスクの変更を人間の承認 0 人で通せる、という組み立てです。

私たちは「**起きないようにする**」と「**起きたらすぐ直す**」に投資しています。秘密情報は扱わず、gitleaks で混入を止めます。不具合は、その日のうちに直して前に進みます。

## 回帰の実測

この運用で、実際にどれだけ回帰が起きたかを MulmoTerminal の記録から数えました。

**数え方**

1. 2026 年 6 月 15 日から 10 月 22 日までにマージされた PR を、すべて取得した（2,027 件）
2. タイトルが `fix` か `revert` で始まり、本文で「regression」「回帰」「退行」「introduced by」などの語と一緒に、原因になった以前の番号を名指ししている PR を抜き出した
3. 抜き出したものを 1 件ずつ読み、自分たちの変更が原因の回帰かどうかを判定した

**結果**

| 修正した PR | 日付 | 原因 | 中身 |
|---|---|---|---|
| #23 | 6/17 | #17（サーバーの TypeScript 化） | ファイル名の変更で、子プロセスの起動先が古いままだった |
| #78（取り消し） | 6/21 | コミット 744a777 | グリッドの拡大表示が崩れた |
| #214、#215 | 7/5 | #197（tmux によるセッションの永続化） | ホイールでのスクロールと、クリップボードへのコピーが効かなくなった |
| #738 | 7/24 | #729、#730（マウス報告の修正） | ホイールが入力履歴を回すようになった |
| #758（取り消し） | 7/24 | #724（再開ピッカーの絞り込み） | 通常の端末で始めたセッションが一覧から消え、利用者には「消えた」ように見えた |

除外したものもあります。外の変化が原因のもの（新しいモデルの追加漏れ、tmux 3.7 側の回帰）、マージした PR へのレビュー指摘の追い対応、起こりうる退行をテストで防いだという記述は、数えていません。

自分たちの変更が原因の回帰は、**原因になった変更で 5 件、修正の PR で 6 件**でした。マージ 2,027 件に対して、原因の数で約 0.25% です。5 件はすべて 6 月と 7 月の立ち上げ期に集中していて、**7 月 24 日より後にマージされた 1,452 件では、自分たちの変更が原因の回帰は見つかっていません**。

**この数え方の限界**

本文で原因を名指ししていない修正は拾えていないので、この数は下限です。確実にするには、`fix` で始まる PR をすべて読む必要があります。

## シリーズにあって、Anthropic の記事にないもの

逆に、Anthropic の記事には書かれていない実践が、シリーズにはあります。

| 実践 | 記事 |
|---|---|
| 違反数を凍結し、ゼロにしてから error に上げていく手順 | [ever-better](https://zenn.dev/singularity/articles/ever-better-pm2)、[レビューをやめた話](https://zenn.dev/singularity/articles/stopped-reviewing-my-code) |
| 重複コードと未使用コードの検出 | [jscpd](https://zenn.dev/singularity/articles/jscpd-dry-detection-mono)、[きれいなコードの守り方](https://zenn.dev/singularity/articles/clean-code-ci-for-ai-era) |
| 型だけの変更が挙動を変えていないことを、コンパイル後の JS の比較で確かめる | [ever-better](https://zenn.dev/singularity/articles/ever-better-pm2) |
| 設定が本当に効いているかを、わざと壊して確かめる | [「入れたつもり」を数える](https://zenn.dev/singularity/articles/what-else-was-off) |
| 並列に動くエージェントの状態を、人間が一目で見られるようにする | [ターミナルを自作した話](https://zenn.dev/singularity/articles/diy-terminal-500-commits) |
| マシンの負荷を見てから作業を足す | [Macが熱で落ちる話](https://zenn.dev/singularity/articles/bottleneck-descends) |
| 仕事を判断の最小単位まで小さく切る | [宝くじの話](https://zenn.dev/singularity/articles/small-teams-ai) |

今回読んだ範囲では、Anthropic の記事は lint を必須にしていると書くだけで、どう締めていくかには触れていません。シリーズが厚いのは、この「マージ前の機械の層をどう育てるか」です。

## 筆者の見解

ここからは事実ではなく、筆者の考えです。

二つは、同じ目的を別の手段で達成していると考えます。Anthropic は「戻せるから通す」、私たちは「起きないから通す、起きたらその日に直す」です。回帰の実測を見る限り、私たちの手段でも、少なくとも MulmoTerminal の規模では成り立っています。

Anthropic の仕組みのうち、フラグや段階リリース、オンコールは、利用者の数と、チームの人数の多さに見合った投資だと思います。私たちの規模では、それよりも、マージ前の機械の層を厚くするほうが効いています。

一方で、取り入れる価値があると思うものが二つあります。

一つは、パスで人間を呼ぶ層を一枚足すことです。AI が迷わずに書き換えた変更でも、CI やデプロイの設定のような場所に触れたら人間に回します。AI の迷いとは別の軸なので、今の運用にそのまま重ねられます。

もう一つは、回帰の割合を、後から数えるのではなく続けて測ることです。今回は手で数えましたが、Anthropic はこれを日々の指標にしています。続けて測れば、「回帰はほぼない」が主張ではなく、いつでも確かめられる事実になります。
