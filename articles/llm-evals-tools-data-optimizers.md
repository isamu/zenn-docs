1. **どのツールで回すか**

## 先に結論

- **自動改善のツールが自動でやるのは「添削」だけです。** 練習問題と採点は人が用意します。評価の仕組みが先にあり、改善の手法はその上に載ります。
- **ツールは「回す道具」と「記録する基盤」の 2 種類です。** 小さく始めるなら Promptfoo、本番の記録からデータを育てるなら Langfuse、という組み合わせが入りやすいと考えます。
- **練習問題の「入力」は簡単に増やせますが、採点基準は人が出力を見て直す工程を省けません。** 生成した問題は本物より易しく、模擬の利用者は本物より素直です。
- **プロンプトの自動改善でいま中心にあるのは GEPA です。** 効き目は、採点関数が返す**理由の文章（赤ペン）の質**で決まります。
- **最大の落とし穴は、評価用データへの過剰適合です。** データを 3 つに分け、平均点の裏で「解けなくなった問題」がないかを問題ごとに見ます。

## 1. 全体像：新人の手引き書を、答案を添削しながら直す

自動改善の仕組みは、どのツールでも次のたとえで説明できます。

> 新人（AI）に手引き書（プロンプト）を渡して、練習問題を解かせる。先輩（採点）が答案に点と赤ペンを入れる。添削係（もう 1 つの LLM）が赤ペンを読んで手引き書を書き直す。新しい手引き書で解かせて、点が上がっていれば採用する。

| 用意するもの | たとえ | 問い合わせ AI では | 誰が用意するか |
|---|---|---|---|
| 直す文章 | 手引き書 | システムプロンプト、道具の説明文、スキル文書 | 人 |
| 練習問題 | 練習問題 | 過去の問い合わせと、そのときの正しい対応 | 人（一部は AI で増やせる → 4 章） |
| 採点 | 先輩の点と赤ペン | 注文番号を引用したか、勝手に返金を約束していないか | 人（AI の採点は人と比べてから → 3 章） |
| 書き直し | 添削係 | 赤ペンを読んでプロンプトを直す | **ツール**（→ 5 章） |

返金の方針のように変えたくない文章は、**直す対象に入れなければ守られます**。何を直してよいかを決めるのも人です。

## 2. ツールの役割分担

評価のツールは 2 種類に分かれます。

```
本番の実行記録 ──(拾う)──> 評価用データ ──> 実験（プロンプト・モデルを変えて回す）
      ▲                                              │
      └──────────── 採点結果を見て直す ◀─────────────┘
   Langfuse などが担う範囲            Promptfoo / Inspect AI などが担う範囲
```

| 種類 | ツール | 向いている用途 | 調べて分かった注意点 |
|---|---|---|---|
| 回す道具 | Promptfoo | プロンプトやモデルの比較、CI での退行検知 | 2026 年 3 月に OpenAI が買収を発表。オープンソースは続けると表明 |
| 回す道具 | Inspect AI | 厳密な実験、エージェントの評価 | Python で書く。覚えることはやや多め |
| 回す道具 | DeepEval | 既製の指標をすぐ使いたいとき | 採点用の指示文は英語。日本語では人の判定と比べて確かめる |
| 記録の基盤 | Langfuse | 実行記録・データセット・実験の比較・人の注釈 | 2026 年 1 月に ClickHouse が買収。自前運用は続けると表明。日本リージョンあり |
| 記録の基盤 | Braintrust / LangSmith / Phoenix | 実験同士の差分の画面、LangChain との連携、手元での起動 | 商用か、機能が Langfuse と重なる |

ふつうは両方を使います。最初は回す道具だけで始め、データが増えてきたら記録の基盤を足す、という順番が入りやすいと考えています。

**評価しやすいかどうかは、ツールよりも「正解をどう決められるか」でほぼ決まります。** 元記事では 3 つの業務で比べました。

| | EC の問い合わせ | 社内の法務チェック | 社内規程の問い合わせ |
|---|---|---|---|
| 機械で判定できる部分 | 多い（分類、注文番号、禁止表現） | 中（見落とし、引用の正しさ） | 中（検索、「分からない」と言えたか） |
| 正解データの入手 | 容易（過去の返信） | 難しい（専門家の時間が要る） | 中（担当者の確認が要る） |
| 失敗したときの重さ | 中 | 高い | 中 |

法務チェックのように失敗が重い業務では、**平均点とは別に、重大な見落としの件数を必ず出します**。平均点が上がった陰で重い見落としが 1 件増えた、という状態がいちばん危ないからです。

## 3. 採点関数の作り方

自動改善でもふつうの評価でも、中心になるのは採点関数です。元記事では DSPy と gepa のソースと文書、Anthropic の評価の手引きを読んで、作り方を 6 つの手順にまとめました。

### 観点に分け、機械で判定できるものは機械で

採点を 1 つの大きな判定にせず、**観点ごとの小さな判定の集まり**にします。判定方法は、速く確実なものから選びます（Anthropic の手引きの考え方です）。

| 観点 | 判定方法 | 扱い |
|---|---|---|
| 方針にない返金を約束していないか | 機械（禁止表現・正規表現）＋ AI（言い換えの検出） | **足切り**（違反なら 0 点） |
| 出力が決めた JSON の形になっているか | 機械（`jsonschema`） | 足切り |
| 注文番号を引用したか | 機械（全角・半角をそろえてから部分一致） | 点数に入れる |
| 配送予定日が注文データと合っているか | 機械（日付を抜き出して値で比べる） | 点数に入れる |
| 客の要望（期限など）に答えたか | AI | 点数に入れる |

**足切り**は、平均点で埋め合わせてはいけない失敗に使います。勝手な返金の約束がその例です。

判定したい値は、できるだけ**出力の JSON の欄として書かせます**。返信文の中から日付を探すより、`category` や `escalate` の欄を別に出させて `==` で比べるほうが確実です。

### AI に判定させるときの決まりごと

- 「丁寧か」ではなく、**満たす例と満たさない例**を添えた具体的な基準を書く
- 答えは観点ごとの **2 値（満たす / 満たさない）**にし、**根拠を先に書かせてから**判定させる
- 答えを作ったモデルとは**別のモデル**に採点させる（採点役には位置・長さ・自分びいきの偏りがあると [Zheng ほか](https://arxiv.org/abs/2306.05685) が報告しています）
- 採点役は**自動改善で直す対象の外に置く**。採点役まで直されると、点数の意味が変わります
- 一部の問題に担当者が判定を付け、**採点役と人の一致を観点ごとに測ってから**使う。一致しない観点は分け直すか、点数から外す

### 部分点と赤ペンを返す

採点関数は**点数と理由の文章の両方**を返します。DSPy の GEPA では、次の形です（元記事のコードを短くしたものです。`refund_promised` と `normalize` の中身は元記事にあります。`WEIGHTS` は観点ごとの重みで、合計を 1 にします）。

```python
def metric(gold, pred, trace=None, pred_name=None, pred_trace=None):
    if refund_promised(pred.reply) and not gold.refund_allowed:
        return dspy.Prediction(score=0.0,
            feedback="方針で認められていない返金を約束している。返金は方針を確認してから案内する")

    problems, passed = [], {}
    passed["注文番号"] = gold.order_id in normalize(pred.reply)
    if not passed["注文番号"]:
        problems.append(f"注文番号 {gold.order_id} を引用していない")
    passed["分類"] = pred.category == gold.category
    if not passed["分類"]:
        problems.append(f"{gold.category} の問い合わせを {pred.category} に分類した")

    score = sum(WEIGHTS[name] for name, ok in passed.items() if ok)
    return dspy.Prediction(score=score, feedback="。".join(problems) or "問題なし")
```

点数が 0 と 1 だけだと、候補同士に差がつかず引き分けばかりになります。観点ごとの**部分点**があれば、「分類は直ったが、要望への答えはまだ」という小さな前進を拾えます。

赤ペンには「**何が、どこで、本来はどうあるべきか**」を入れます。「不正解」ではなく「注文番号 A-1029 を引用していない」です。ただし、その問題だけの事情（「この客は常連なので」）を書くと、それが手引き書に書き込まれて例外だらけになります。

## 4. 練習問題は、どこまで自動で作れるか

元記事では、promptfoo、DeepEval、Ragas、Giskard、NeMo Data Designer、Opik、LangSmith などの公式文書を確認し、難しさの順に 5 段階に分けました。

| 段階 | 作るもの | 自動化のしやすさ | 主なツール |
|---|---|---|---|
| 1 | 入力（問い合わせ文）を増やす | 簡単。コマンド 1 つか画面のボタン 1 つ | promptfoo の `generate dataset`、NeMo Data Designer、DeepEval、Opik |
| 2 | 文書から問題と参照回答を作る | 簡単〜中 | DeepEval の `Synthesizer`、Ragas |
| 3 | 採点基準を作る | 中。**人の確認が必須** | promptfoo の `generate assertions`、LangSmith |
| 4 | 会話や道具を使う作業を模擬する | 中〜難 | DeepEval、Opik、IntellAgent |
| 5 | 正解を機械で確かめられる課題を作る | 難。コードでは実用段階 | SWE-smith |

### 論文から分かる落とし穴

- **多様性は、指定しないと出ない。** 1 問ずつ作ると、全体として現実の利用者の幅を覆えません。「どの種類の客の、どの種類の問い合わせを何割」を自分で決めて指定するのが、段階 1 でいちばん大事な作業です。
- **生成した問題は易しくなる。** 人が作った読解の問題集を LLM に作り直させた研究（[What Has Been Lost with Synthetic Evaluation?](https://arxiv.org/abs/2505.22830)）では、生成した問題は妥当なものが多かったものの、元の問題より易しくなりました。本番の記録と、人が作った難問を必ず混ぜます。
- **採点基準は、出力を見ないと決まらない。** EvalGen の研究（[Who Validates the Validators?](https://arxiv.org/abs/2404.12272)）では、出力を採点していくうちに基準そのものが定まっていきました。基準を先に全部決めてから問題を作る、という順序は成り立ちません。
- **模擬の利用者は本物より素直。** 実際のチャットと模擬の会話を比べた研究（[Synthetic Users, Real Differences](https://arxiv.org/abs/2605.02624)）では、模擬は本物の行き違いを再現できず、評価が楽観的になりました。一方、銀行 Nubank の事例（[Screen Before You Serve](https://arxiv.org/abs/2609.30137)）では、模擬での版ごとの評価が本番の評価と強く相関しました。ここから、模擬は**「どちらの版が良いか」の比較には使えるが、「本番で通用するか」の判定には甘い**と私たちは読んでいます。

### いちばん効くのは「正解を先に決めてから問題を作る」形

[SWE-smith](https://arxiv.org/abs/2504.21798) は、リポジトリにバグを仕込み、**既存のテストが落ちるようになったものだけ**を課題にします。正解（どこが壊れているか）が先に分かっているので、採点は機械でできます。

コード以外でも同じ発想が使えます。法務チェックなら、**問題のある条項をわざと埋め込んだ契約書**を作れば、見落としを機械で数えられます。自動生成でいちばん効くのは、この形に持ち込めるかどうかだと考えています。

## 5. プロンプトの自動改善は、中で何をしているのか

### 骨格はどの手法も同じ

候補を作り、練習問題で採点し、良ければ採用する。この繰り返しです。違うのは「候補の作り方」と「どの候補を残すか」だけです。

文章の直し方は 3 つに分けられます。

| 直し方 | 何が新しい文章を作るか | 例 |
|---|---|---|
| A. AI に書き直させる | LLM が書く | 失敗と理由を読んで直す（GEPA）、点数の推移を見て書く（OPRO）、2 案を掛け合わせる（EvoPrompt） |
| B. 組み合わせで直す | 既にある部品を選んで並べる | 指示文の案 × お手本のセットから最良を探す（MIPROv2） |
| C. 機械的な規則で直す | 決まった操作（LLM を使わない） | 句の削除・入れ替え（GrIPS）、書式の入れ替え、1 文ずつ消して効かない文を外す |

### 主な 3 つのツールの違い

元記事では DSPy、gepa、TextGrad のソースを読みました。

| | 添削係が読むもの | 直し方 | 準備の重さ |
|---|---|---|---|
| MIPROv2（DSPy） | 点数だけ | 書き方のヒントを変えて指示文の案を作り、お手本との組み合わせをベイズ最適化で探す | 軽い（点数を返すだけ） |
| GEPA（DSPy / gepa） | 点数＋赤ペン＋実行の記録 | 失敗を読んで 1 つずつ書き直す | 中（赤ペンを書く採点が要る） |
| TextGrad | 文章の批評 | 批評を逆向きに伝えて書き直す（PyTorch 風の書き方） | 中 |

GEPA の 1 回の改善は、ソースを読むと次の流れです。

1. これまでの候補から土台を 1 つ選ぶ。**どれか 1 問で最高点を取った候補をすべて残しておき**、その中から選ぶ（平均だけで選ぶと「返品だけは得意」な候補が消えるため）
2. 直す部品を選ぶ（既定では部品を 1 つずつ順番に）
3. 練習問題を数問解かせ、答え・点数・実行の記録を取る
4. 添削係が「いまの手引き書」と「問題・答え・赤ペン」を読んで書き直す
5. 同じ数問で点が上がれば、検証用の問題全体でも採点して候補に加える

[GEPA の論文](https://arxiv.org/abs/2507.19457)（ICLR 2026 口頭発表）は、強化学習や MIPROv2 を上回り、試行回数も大きく減ったと報告しています。

### 2026 年は、スキル文書も直す対象になった

Claude Code などのスキル（`SKILL.md`）を最適化する研究が 2026 年に急に増えました。共通する作法は、**1 回の編集量に上限を設け、検証用データで良くなったときだけ採用し、却下した編集も記録して繰り返さない**ことです（[SkillOpt](https://arxiv.org/abs/2605.23904) など）。

ここでも難しいのは書き直しではなく採点です。gepa に同梱の gskill は、SWE-smith で答え合わせのできる課題を作るところから含めてスキルを育てています。

## 6. 落とし穴と、その避け方

4 本の記事に繰り返し出てきたものを集めます。

| 落とし穴 | 何が起きるか | 避け方 |
|---|---|---|
| 評価用データへの過剰適合 | 練習問題の癖を覚えたプロンプトになる | 学習用・検証用・試験用の 3 つに分け、試験用の赤ペンは添削係に見せない |
| 手引き書が膨らむ | 例外を詰め込んだ冗長なプロンプトになり、汎化しない（[Decagon の報告](https://decagon.ai/blog/optimizing-gepa-for-production)） | 文字数の上限、「方針の文は変えない」などの追記方針。DSPy の `InstructionProposer` で設定できる |
| 全体の書き直しで細部が消える | 書き直すたびに要約され、業務に固有の知見が落ちる（[ACE](https://arxiv.org/abs/2510.04618) の「文脈の崩壊」） | 全体を書き直さず、項目単位や部分単位で直す |
| 平均点の裏の入れ替わり | 平均が少し上がる裏で、正解→不正解が大量に起きている（[RFDPO](https://arxiv.org/abs/2610.19084)） | 結果を**問題ごとに**残し、新たに解けなくなった問題を添削係に伝える |
| 差がつかない問題ばかり | どのプロンプトでも同じ点になり、最適化が効かない（[p1](https://arxiv.org/abs/2604.08801)） | プロンプトの良し悪しで点が変わる問題を選んで使う |
| 採点の甘いところを突かれる | 採点役が見逃す書き方へ寄っていく | 採点役と人の一致を定期的に測り、改善後の答えを人が読む |

## 7. 今日からできる順番

元記事の内容から、手を付ける順番をまとめます。順番は私たちの提案です。

1. **直す準備をする（ツールなしでできる）**
   - プロンプトを「役割」「業務の知識」「方針・禁止事項」「出力形式」に分け、自動で直してよい部品と人が管理する部品を決める
   - 採点に**理由を返させる**
   - 結果を**問題ごとに**残す
   - データを 3 つに分ける
2. **手で 1 周回す**
   - 失敗した問題の「問題・答え・理由」を集め、Claude などに**失敗を種類ごとに分類**させる（[ETGPO](https://arxiv.org/abs/2602.00997) の方法）
   - いちばん多い種類について、該当する部品だけを直させる（[SAPO](https://arxiv.org/abs/2608.11219) の方法）
   - もう一度解かせて、**新たに解けた問題と解けなくなった問題の両方**を確かめる
3. **既製のツールに任せる**
   - DSPy で書いているなら `dspy.GEPA`、そうでなければ gepa の `optimize_anything`
   - 添削係には文字数の上限と「方針・禁止事項は変えない」を必ず付ける
4. **練習問題を増やす**
   - 種類の割合を本番に合わせて指定して入力を増やし、本番の記録と人の難問を混ぜる

1 周手で回すと、採点の甘いところや練習問題の偏りがかならず見つかります。自動化は、この手作業が回るようになってからで十分だと考えています。

---

## まとめ

- 自動改善のツールがやるのは添削だけです。**何を直すか、どう採点するかは自分たちで決めます。**
- 採点関数は観点ごとの判定の集まりとして作り、機械で判定できるものは機械で、判断が要るものだけ AI に任せます。足切り、部分点、赤ペンを返します。
- 練習問題は入力までなら簡単に増やせます。ただ、生成した問題は易しく、模擬の利用者は素直で、採点基準は出力を見ないと決まりません。
- いちばん効くのは、**正解を先に決めてから問題を作る**形です。
- 始めるなら、ツールより先に**採点に理由を返させ、結果を問題ごとに残す**ことです。

前回の記事の最後に「最初に作るべきものはプロンプトではなく、それを測るベンチマークかもしれない」と書きました。今回調べて分かったのは、その先の自動改善も、**測る仕組みの質で効き目が決まる**ということでした。
