自分の作った OSS を使ってくれている方6人から、話を聞いたり記事を書いてもらったりしました。インタビュー4人と、こちらが依頼していない自発的な記事が2本です。

並べてみたら、**痛みが3つに収束していました**。そして、そのうち1つは**自分がまったく認識していなかったもの**でした。

この記事は製品の宣伝ではなく、**AIエージェントを並列で回すと人間に何が起きるのか**の観察です。ツールが何であれ同じことが起きると思うので、書いておきます。

## 前提：みんな何体くらい回しているのか

まずここが意外でした。

| | 並列数 |
|---|---|
| Aさん | 3〜5（最大8まで行ったが戻した） |
| Bさん | 5〜6 |
| Cさん | 4〜6 |
| Dさん | **1〜3**（最大5） |
| 記事①の方 | 6〜8 |
| 記事②の方 | 6 |

**1〜10。中央値は5あたり**です。「並列」といっても、20体も30体も回している人はいませんでした。

そして重要なのは、**「もっとたくさん回したい」と言った人が1人もいなかった**ことです。全員が言っていたのは「**いまの数を、楽に扱いたい**」でした。

これは僕にとって、かなりの発見でした。自分は「並列数の天井を上げる道具」を作っているつもりだったからです。

## 痛み①：メモリが先に死ぬ

一番多かったのがこれです。6人中3人。

> Cursor の Window をたくさん開いていてメモリ枯渇しがちだった

> メモリの枯渇（特に VS Code の IDE の場合）

> **メモリー圧迫しないの最高すぎる。64Gのvaio君がカクカクなっていたけど、今のところサクサク動いている。**

構造はシンプルです。**エージェントを分けるために、IDE のウィンドウを分ける**。すると、エディタ本体・言語サーバー・拡張機能・ファイルウォッチャーが、エージェントの数だけ立ち上がります。

64GB のマシンでも足りない、という報告が出てくるのはそのためです。エージェントは1体増えるごとに1プロセスですが、IDE は1体増えるごとに**一式**増えます。

## 痛み②：どれがどれだか分からなくなる

これも3人。ただし、言い方が全員違いました。

> 別タブへの返信のつもりが、間違えて違うタブに入れてごちゃごちゃになることがあった

> **複数のウインドウを開いていると、ぱっと見た時の見た目がどの画面も同じなので、画面の切り替えの時に何を見ているか分からなくなり、識別に地味に時間を取られる。今何をやっているのか、思い出すのにも時間がかかる**

> ターミナルで複数の違うプロジェクトのディレクトリで作業をしている場合、どの作業がどこまで進んでいるかを並列で記憶しておくのが大変だった

3人とも、**別々の言葉で同じことを言っています**。

これは処理能力の問題ではありません。**人間の作業記憶の問題**です。同じ見た目のペインがN枚あると、「どれが何か」を頭の中に持ち続けなければならず、その保持コストがN に比例して増えていく。

そして限界を超えると、**別のエージェントのターミナルに返事を打ち込む**という事故が起きます。

## 痛み③：並列と精読はトレードオフだと思われている

これが、**自分ではまったく認識していなかった**ものです。

記事にこう書かれていました。

> ターミナルを6分割すると、1つ1つのペインが小さすぎる。4000字の出力を読むのに、スクロールとリサイズが必要になる

> **「複数のAIエージェントを並列に走らせる」と「ひとつの出力を大きく読んで判断する」が、同時に実現できる**

読んで、ああ、と思いました。

**「並べる」と「読む」は、画面の面積を奪い合う**。6分割すれば1つあたりは6分の1になるので、当然です。だから人は、並列数を増やすたびに「読みにくさ」を我慢していた。

僕は「グリッドと拡大を行き来できる」という機能を、**便利機能**だと思っていました。実際には、**この我慢を解消するもの**だった。使っている人のほうが、価値を正確に言語化していました。

## 3つを並べて分かること

改めて並べます。

1. **メモリ** — エージェントを分けるためにウィンドウを分けると、マシンが先に音を上げる
2. **識別** — 同じ見た目のペインが増えると、頭の中の保持コストが増える
3. **並列と精読の衝突** — 並べるほど1つ1つが読めなくなる

**3つとも「たくさん回せない」という話ではありません。** 全部、**「回した後に人間が壊れる」**という話です。

エージェントを起動するのは簡単です。`claude` と打つだけ。難しいのは、起動した後に**それらを人間が把握し続けること**でした。

## だから僕は、売り文句を間違えていた

自分の作ったツールを、僕はずっとこう説明していました。

> 6体が限界だった。道具で天井が上がった。

でも6人に聞いた結果は、**誰もそう言っていません**。天井が上がった人はいなかった。1〜3体しか回していないのに乗り換えた人すらいました。

正しくはこうでした。

> 同じ数を、見失わずに扱えるようになった。

**約束すべきは「もっと多く」ではなく「もう見失わない」**だった。作った本人が、6人に言われるまで気づいていませんでした。

## 作り手には、初回起動の画面が見えない

もう1つ、痛かった発見があります。

まだ乗り換えていない方が、こう答えました。

> 単一パネルと複数パネルが分かれて表示されていたため、最初、単一パネル側でショートカットでターミナルのように分割できると思ったら、そうではないことが分かり、**どこから進めればよいかが分からずつまずきました**

> まだ私が使いこなせていないからだと思うのですが、**これだと思った瞬間は来ていません**

**自分を責めています。** 導線が悪いだけなのに。

僕は毎日このアプリを使っています。だから**初回起動の画面を、まっさらな気持ちで見ることが二度とできません**。これは1人だから狭いという話ではなく、**作っている側は全員そうなる**という話です。人数を増やしても、増えるのは「使い慣れた人の目」だけでした。

（この方は、その後この点を直したら記事まで書いてくれました。順番が逆で、**言ったものが入るから次も言ってもらえる**のだと思います）

## で、あなたのツールでも同じことが起きているはず

MulmoTerminal の話として書きましたが、**この3つはツールに依存しません**。

- IDE を複数開いて並列運用しているなら、①が起きます
- ターミナルを分割して並列運用しているなら、②と③が起きます
- そして**どのツールを使っていても、作り手には初回起動の画面が見えません**

もし並列でエージェントを回していて「なんか疲れる」と感じているなら、それは**あなたの集中力の問題ではなく、たぶん上の3つのどれか**です。分けて考えると、対処が変わります。

- メモリなら → プロセスを減らす（ブラウザのタブは IDE より軽い）
- 識別なら → 色・名前・状態表示を付ける（並べるだけでは解決しない）
- 精読なら → 「並べる」と「読む」を**切り替え可能**にする（同時に成立させようとしない）

## おわりに

聞いてよかった、というのがいちばんの感想です。**6人に聞いて、売り文句が間違っていたことが分かりました。**

もし何か作っていて、まだユーザーに聞いていないなら、聞いてみることをおすすめします。たぶん自分が思っているのと違うことを言われます。そして、そのほうが正しい。
