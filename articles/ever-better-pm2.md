1日500コミットを日常にするために、環境を整えるツールを作りました。**これを使えば、だれでも500コミットは余裕です。**

[ターミナルを自作したら1日500コミットを超えた話](https://zenn.dev/singularity/articles/diy-terminal-500-commits)と、[だからコードレビューをやめた話](https://zenn.dev/singularity/articles/stopped-reviewing-my-code)を書きました。どちらも、読まなくても壊れない足回りがあって初めて成立します。そして、読んで「やってみたい」と思った人から、こう言われました。

> 記事を読めば簡単にできそうだと思った。でも実際にやると、手順も、細かいノウハウも分からない。

**そのとおりだと思います。** なので、その手順を全部ツールにしました。[**ever-better**](https://github.com/isamu/ever-better)（MIT・ランタイム依存ゼロ）です。

TS/JS のリポジトリなら、Claude Code にこう言うだけです。

```
https://github.com/isamu/ever-better  これやって
```

**判断や確認は挟まりますが、基本は自動で進みます。** 順に PR が飛んできます。

## 実際にできました

自分のリポジトリで試しても手心が加わるので、わざと**古くて・有名で・自分は中身を知らない**ものを選びました。[pm2](https://github.com/Unitech/pm2) です。★43,254、2013年から13年動き続けている Node.js のプロセスマネージャで、たぶんこれを読んでいる人の半分は使ったことがあります。

[フォークして](https://github.com/isamu/pm2)、「きれいにして」と言いました。

```
1時間    品質ツールを導入 → 違反 4,942件を凍結 → PR 6本マージ
4日      警告 3,689 → 741
```

途中で本物のバグも出ました。**13年間だれも報告していなかったものが2件**です。[本家に PR を出しています](https://github.com/Unitech/pm2/pull/6143)。`lib/` の `.js` 49本を `.ts` に**名前だけ**変えたら、型エラーが 2,641件。

**これが全部、指示を1行出したあとに起きたことです。** 僕が張り付いていたのは、判断のところだけでした。

もう1つ。**まったく同じ形のバグが、いま書かれている TypeScript のプロジェクトにも6件ありました。** 古いコードだけの話ではありません。しかも型システムは何も言いません。むしろ「そのコードは正しい」と保証してきます。

これを、あなたのリポジトリでもやれます。以下、何をする道具なのか、どういう順で進むのかを順番に書きます。

## なぜ作ったか：足回りが、最初から入っていたことがない

正直に書いておくと、僕はその足回りを、最初から入れられたことが一度もありません。

プロトタイプのつもりで始めるので、最初の設定はいつも適当です。動くものができてから、途中で入れて、少しずつ厳しくしていく。毎回そうなります。そして毎回「次こそ最初から入れよう」と誓って、次も入っていません。

しかも自分のものだけではありません。人のプロジェクトに入ることもあります。そこには当然、僕の足回りはありません。

つまりこの作業、毎回発生するんです。

```
自分の新しいリポジトリ    プロトで始めるので、途中から入れる
自分の古いリポジトリ      入っていなかった期間のぶんが溜まっている
人のプロジェクト          入っていない。しかも自分では最初から作れない
```

毎回、同じことを手でやっていました。もう苦労したくないので、道具にしました。

## キッカケ：記事では、たぶん再現できない

冒頭の一言について、もう少し書きます。

最初はプロトのプロト、というか、僕が毎回やっている手順を雑にスクリプトにしただけのものでした。それを [Singularity Society のブートキャンプ](https://zenn.dev/singularity/articles/singularity-society-feedback-loop)で見せたら、参加者から反響がありました。話を聞いてみると、**前の記事を読んで、自分で1つずつやっている人がいた**んです。そして「手順も細かいノウハウも分からない」と言われました。

これはそのとおりだと思いました。そして、僕の記事に限った話ではないと思っています。

いま出回っている記事 ── ハーネスの作り方、ループの回し方、エージェントの並列化 ── は、たいてい抽象論です。考え方は書いてあるけれど、動くものが付いていない。設定ファイルも、実際に打ったコマンドも、詰まったときにどう判断したかも載っていない。

だから読んだ人は、足りない部分を自分なりに解釈して埋めます。そしてその解釈が合っているかどうかは、誰も教えてくれません。

学術論文なら、それでいいのかもしれません。再現したい研究者が著者にメールを書いて、データを送ってもらって、時間をかけて確かめる。**それが成り立つ世界です。**

**でも、エンジニアリングは違います。** 読んだ人がやりたいのは、**いま目の前にある自分の問題を、今日直すこと**です。半年後に再現できても遅いし、「著者に聞けば分かる」も答えになっていません。**その場で動かせないなら、無いのとほぼ同じです。**

そして、もっと厄介なことがあります。

```
プログラム   間違っていれば、エラーになる
記事         間違って解釈しても、何も起きない
```

うまくいかないと「自分のやり方が悪いんだろう」と思って終わります。間違ったことにすら気づけない。

書き手が手を抜いているわけでもありません。**書けない理由が2つあります。**

1つは、具体的な部分がリポジトリごとに違うこと。僕の eslint 設定をそのまま載せても、あなたのリポジトリでは動きません。詳しく書けば書くほど、その repo でしか通じない話になっていきます。

もう1つは、**会社のプロジェクトだと、そのままでは出せない**こと。一番ノウハウが溜まっているのはたいてい仕事のコードなのに、それは貼れません。この記事だって、後半に出てくるプロジェクトは名前を伏せています。だからみんな、出せるところまで抽象度を上げて書くことになります。

ただ、ここは正直に書いておくと、**「出せない」の多くは「切り出す手間をかけていない」の言い換え**です。やりようはあります。

```
設定を整理して出す      機密を抜けば eslint.config.js はそのまま公開できる
モックとサンプルを作る  会社のコードを1行も含まずに、同じ問題を再現させる
ツールにする            どの repo でも動く形にする。一番手間がかかって、一番効く
```

**共通しているのは、その課題の具体的な部分だけを、動く形で切り出すこと**です。丸ごと出せないからといって、抽象論に逃げる必要はありません。設定ファイルは整理すれば出せるし、バグの再現もモックを1つ書けば済みます。

そこまでやっても repo ごとに違う部分が残る ── そこが道具の出番です。この記事で言えば、僕の `eslint.config.js` ではなく、**あなたのリポジトリを読んで設定を書く側**を配る、ということになります。

そして、ツールにすると効果がもう1つあります。**社内で配れる**ことです。

記事や口頭だと、同じ説明を毎回することになります。ツールなら渡すだけで、隣の人の repo でもそのまま動く。**自分の課題を解いたつもりが、チーム全体の課題を解いていた**ということが起きます。

さらにそれをオープンソースにすれば、**同じ課題を持っている人からフィードバックが来ます。** 自分の repo では起きなかった壊れ方、思いつかなかった構成、そもそも要らなかった機能 ── どれも外に出さないと分かりません。

**悪いことが1つも思いつきません。** なので、強くおすすめします。

> だからお願いなのですが、記事を書くなら、動くものを GitHub に置いてほしいです。設定ファイル1つでも、再現するモック1つでも、スクリプト1本でも構いません。

オープンソースで置いてあると、記事だけのときとは4つ変わります。

- **読めば分かる。** 解釈で埋める余地が減る。文章に書かれていないことは、ソースを見れば分かる
- **そのまま使える。** 写経しなくていい。clone して動かすところから始められる
- **良い案があれば PR が来る。** 読者が読者のままで終わらない
- **fork で亜種ができる。** 自分の環境に合わない部分は、その人が変えて持っていける

記事は一方通行ですが、リポジトリは往復します。

実際、この記事を書くために手元のプロジェクトを調べ直していたら、**ever-better 自身の穴が見つかりました。** 後半に出てくるバグを検出できる唯一のルールを、ブラウザ向けのリポジトリでだけ切っていたんです。「そのルールが見ているのはサーバ側の問題ばかりだから」と判断して外していたのですが、**それが間違いでした。** 直して PR を出しました。

**記事にしていなければ、その穴は残ったままです。** 書くために自分のコードを読み直す、というのが効きました。

僕自身、前の記事ではリポジトリを出していませんでした。なので今回は、記事より先に公開しています。

そのうえで、両方でやることにしました。

```
ツール（プログラム）   測る / 入れる / 凍結する / ゲートする
                      ← 決まりきっていて、間違えようがない部分

スキル（AI）           順番 / 詰まったときの判断 / 直し方 / issue の切り出し
                      ← 記事に書ききれない部分
```

CLI とプラグインの両方がある理由が、ここです。片方だけでは足りません。

気合で作りました（Claude Code が）。そして、わざと古いプロジェクトを探して実験しました。

## 課題：既存コードに linter を入れると、たいてい失敗する

linter（コードの書き方を機械的にチェックして、まずい書き方を指摘してくれるツール。JS/TS だと [ESLint](https://eslint.org/) が定番です）を、既にあるリポジトリに厳しめの設定で入れたことがある人は、これを知っていると思います。

```
strict（厳しい設定）を入れる
  ↓
エラーが4,000件出る
  ↓
「これは無理だ」
  ↓
全部 warn（警告どまり。CI は落ちない）にする、または revert
```

warn に落とすと、何も強制されません。そして件数は静かに増えていきます。入れる前より悪いとも言えます。「入れてある」という安心だけが残るので。

かといって4,000件を先に直すのは、始める前に終わっています。

### だから「天井」を凍結する

考え方は1行です。

> **今日ある違反を全部「天井」として記録して、そこから増やさない。**

具体的にどうなるか、時間を追って書きます。今日 4,000件出たとします。

```
今日    4,000件を記録して、ファイルに保存する
        → この4,000件については、以降まったく怒られない

明日    あなたが新しく書いたコードに1件でも違反があれば、CI が落ちる
        → 4,001件目は通らない

来週    100件直したら、天井を 3,900 に下げる
        → 二度と 4,000 には戻れない
```

つまり、**古いコードは免除、新しいコードは初日から全ルール適用**です。

「じゃあ古いコードは汚いままでは？」と思うかもしれません。**そのとおりです。** でも、**増えなくなります。** 減らすほうは、あとから好きなペースでやれます。逆に増え続けている状態では、どれだけ直しても追いつきません。

なお、この仕組み自体は **ESLint 本体に入っています**（`--suppress-all`）。ファイルごと・ルールごとに「いま何件あるか」を JSON に書き出して、その数だけ黙る。超えた分だけエラーにする。**ever-better はそれを使っているだけで、自前の発明ではありません。**

やっているのは、その手前と後ろです ── **どのルールを入れるべきか決めて、入れて、記録して、CI で守って、減ったぶんを反映する。**

## 道具：覚えるのは5つだけ

```bash
npx ever-better diagnose     # 読むだけ。何が足りないか、それぞれ何を意味するか
npx ever-better bootstrap    # 入れる。設定ファイルを生成する
npx ever-better freeze       # 今日の違反数を天井として固定
npx ever-better check        # CI（変更のたびに自動で検査する仕組み）のゲート
npx ever-better prune        # 直したぶん、天井を下げる
```

`freeze` が要です。ルールごとに現在の違反数を記録して、`.ever-better/state.json` というファイルに持ちます。`check` はそれと比べるだけ。1件でも増えていたら落とします。

実際には全部で11個あります（`status` `next` `migrate` `emit-diff` `catalog` `log` など）。ただ**この5つを順に打てば一周する**ので、最初はこれだけで足ります。

### Claude Code に渡すとどうなるか

さっき書いたとおり、README の URL を渡すところから始められます。

```
https://github.com/isamu/ever-better  これやって
```

ただし正直に書いておくと、URL を渡すのと、プラグインを入れるのは同じではありません。README に書いてあるのはコマンドの一覧までで、どの違反が本物のバグか、どこで止まって人に聞くか、何を issue にするか ── その判断はスキルのほうに入っています。何度も回すつもりなら、入れたほうが結果が安定します。

```
/plugin marketplace add isamu/ever-better
/plugin install ever-better
```

あとは話しかけるだけです。入口は2つあります。

```
「この repo の品質を上げたい」「lint を入れたい」「どこから手を付ける？」
   → まず診断して、何が足りないか・それぞれ何を意味するかを説明する

「きれいにして」「全部やっておいて」「品質上げといて」
   → 止まらずに最後まで回す
```

後者を選ぶと、この順で PR が飛んできます。**「無人」ではありません。** コードから決められないものは後述のとおり issue にして先へ進みますが、`.js` を捨てるかどうかのような大きい判断では、こちらに聞いてきます。

```
1  整形の PR（Prettier）
2  ツール導入の PR（ESLint / TypeScript / ゲート）
3  凍結の PR（天井を固定）
4  以降、ルール1本ずつの PR
```

4番目が本体です。1ルールずつ、違反を直して、直しやすくするために純粋な関数（外の状態に触らず、入力だけで結果が決まる関数。テストが書きやすい）を切り出して、テストを書いて、天井を下げます。

手つかずのリポジトリだと、これは数本では済みません。走らせる前に知っておいたほうがいいです。

### CLI だけでも、止血まではできる

エージェントを使いたくない場合でも、「これ以上増やさない」状態は CLI だけで作れます。

```
diagnose / bootstrap / freeze / check   →  CLI だけで完結する
違反を減らす                            →  ここから先はエージェントの仕事
```

`bootstrap` は依存の追加・設定生成・3プラットフォームの CI・`dependabot.yml` まで入れます。そこまで済ませて `freeze` すれば、その日から件数は増えません。

減らすほうは、コードを読んで直してテストを書く作業なので、CLI にはありません（`prune` は「直したあとに天井を下げる」だけです）。止血は CLI、治療はエージェント、と分かれています。

### 決めないことは、決めない

コードから決められることは全部決めます。そうでないものは issue を立てて先へ進みます。

- 挙動が曖昧なもの（ここは throw すべきか、retry か、log か）
- 公開している API の変更
- それ自体が別プロジェクトになる規模のリファクタ
- そのリポジトリでは、そのルールが単に間違っている場合

issue には選択肢と、自分ならどれを採るかを書きます。判断は人に返して、手は止めない。

## 実験：13年もののリポジトリに当ててみた

冒頭の話に戻ります。

自分のリポジトリで試しても、手心が加わるので意味がありません。条件を3つ決めました。**十分に古い。よく使われている。そして自分は中身を知らない。**

```
★43,254
2013年から13年
JavaScript
open issue 1,098件
```

[フォークして](https://github.com/isamu/pm2)、Claude Code に「きれいにして」と言いました。

最初の1時間がこれです。

```
09:09  導入計画と、エージェント向けの指示を追加
09:27  Prettier でツリー全体を整形
09:34  ESLint / TypeScript / 品質ゲートを導入
09:43  違反の天井を 4,942 件で凍結
09:56  ReferenceError を2件修正
09:58  macOS の CI ジョブを直す
10:14  PR 6本マージ完了
```

僕が張り付いていたのは、判断のところだけです。そのまま24時間、止めずに走らせました。大半は TypeScript 化まで進んで、いまはリファクタリングに入っています。

なおこの 4,942 件は「pm2 が悪い」という意味ではありません。2013年に書き始めたコードに、2026年のルールを当てているだけです。当時は正しかった書き方も混ざっています。天井を凍結する形にしたのは、まさにそれが理由でした。

### linter が最初に出したのは、バグでした

`no-undef`（存在しない変数を使っている、という一番基本的なルール）が、いきなり2件当てました。

1つめ。`pm2 monit` が、エラーのときに落ちる。

```js
// lib/API/Extra.js:703
that.exitCli(conf.ERROR_EXIT);
```

`conf` という変数は、このファイルに存在しません。他は全部 `cst.ERROR_EXIT` で、`cst` は8行目で読み込まれています。ここだけ違う。

2つめ。タブ補完のインストールが、エラーのときに落ちる。

```js
function readRc(completer, cb) {          // ← completer を受け取る
  ...
  if (err) return cb(new Error("... " + completer + " ..."));
}

function writeRc(content, cb) {           // ← 受け取っていない
  ...
  if (err) return cb(new Error("... " + completer + " ..."));
}                                                  ↑ 未定義
```

`readRc` からコピーして引数を1つ減らしたのに、本文の参照を消し忘れています。実際に動かして確かめました。

```
修正前  ReferenceError: completer is not defined
修正後  Error: No .zshrc file. You'll have to run instead: pm2 completion >> ~/.zshrc
```

2件とも、何かが既に失敗したあとにしか通らない場所です。だから13年見つかりませんでした。普通に動いているときは絶対に通りません。そして通ったときには、利用者は作者が書いたメッセージではなく、スタックトレースを見ることになります。

本家に PR を出しました → [Unitech/pm2#6143](https://github.com/Unitech/pm2/pull/6143)（差分4行）。

### 名前を `.ts` に変えただけで、型エラーが2,641件

linter は「無いものを使っている」までしか見ません。その先は型です。

`lib/` の `.js` 49本を、`git mv` で `.ts` に名前を変えただけにしました。ロジックは1行も書き換えていません。

```
                 改名前    改名後
eslint（未抑制）   3,130  →  1,875
型エラー           2,641  →    259
```

（259 は、代入だけされていたフィールド18個の宣言を足して、strict を掛ける対象を17ファイルに絞ったあとの数字です。残りはまだ緩い設定で逃がしてあります）

中身を見ていくと、そこに無いデータを読んでいるものばかりでした。フォークに issue を11件立てています。一番効いたのがこれです。

**プロトタイプが「見つかった」と答えてしまう。**

pm2 は、アプリ設定の `user` をユーザー表に引きにいきます。

```js
var users = passwd.getUsers();
var user_info = users[app.uid || app.user];
if (!user_info) { /* User ... cannot be found */ }
app.uid = parseInt(user_info.userId);
```

`getUsers()` が返すのは普通のオブジェクトです。JavaScript のオブジェクトは、自分が持っていないキーを聞かれると、プロトタイプ（すべてのオブジェクトが暗黙に継承している親。`toString` などが入っている）まで見にいきます。

```js
typeof users['constructor'];  // 'function' ← 誰も入れていないのに返ってくる
typeof users['toString'];     // 'function'
```

つまり `user` が `constructor` や `toString` だと、`!user_info` を素通りします。「User cannot be found」は出ません。そして `parseInt(undefined)` で `app.uid = NaN` になります。

そこに無いデータを読んだのに、JavaScript が答えてしまった。それだけです。

同じことが `pm2 ls --sort` でも起きていました。

```
$ pm2 ls --sort constructor
TypeError: propertyName.split is not a function
```

別の人が書いた、別のファイルで、独立に同じ間違いが起きています。個人のミスではなく、言語の性質です。

## 発見：「13年もののJSだから」ではなかった

ここまで読むと、古いコードの話に見えると思います。僕もそう思っていました。

同じことを、別の既存プロジェクトでもやっています。こちらは TypeScript で書かれた、新しいコードです（プロジェクト名は伏せます）。

そこで直したバグを、1つ具体的に書きます。

画面に、登録したツールがカードで並びます。カードには言語ごとのアイコンが出ます。表はこうです。

```ts
const ICONS: Record<string, string> = {
  python: "🐍",
  javascript: "📜",
  rust: "🦀",
};

const icon = ICONS[tool.language] ?? "🔧";   // tool.language は登録時に入力された文字列
```

`?? "🔧"` があるので、知らない言語なら 🔧 になる ── そのつもりで書かれています。実際そうなります。`ICONS["go"]` は `undefined` なので 🔧 です。

ところが、言語名に `constructor` と入れて登録すると違います。手元で動かした結果です。

```
go             string    🔧
constructor    function  function Object() { [native code] }
toString       function  function toString() { [native code] }
__proto__      object    [object Object]
```

`ICONS["constructor"]` は `undefined` を返しません。誰も入れていないのに、`Object` そのもの（関数）が返ってきます。プロトタイプが持っているからです。そして `??` が働くのは `undefined` と `null` のときだけなので、**フォールバックは素通りします。**

型も何も言いません。`Record<string, string>` は「どのキーにも string が入っている」と宣言しているので、`ICONS[tool.language]` は string として通ります。**コンパイラの側から見れば、このコードは完全に正しい。**

そのあとどう壊れるかは、その値がどこへ流れるかで変わります。両方とも確かめました。

```
React の子要素に渡した場合
  → 警告がコンソールに出て、そこには何も描画されない
     "Functions are not valid as a React child."
     つまり画面上は「アイコンが無いカード」に見えるだけで、エラーにならない

文字列に埋め込んだ場合
  → 画面に function Object() { [native code] } と出る
     '__proto__' なら [object Object]
```

**前者のほうが厄介です。** 何も起きていないように見えるので、誰も報告しません。

同じ形が、このプロジェクトに全部で6箇所ありました。

```
アイコンの表と色の表（4箇所）      'constructor' に対して関数が返る
エディタに渡す言語IDの表           Object のコンストラクタがエディタに渡される
モデルIDから表示名を引く表         画面に function Object() { [native code] } と出る
イベントの理由から説明文を引く表    説明欄に [object Object] と出る
```

pm2 で見つけたのと、まったく同じ形です。

```
pm2（13年もののJS）        users['constructor']   → プロトタイプが答える
別プロジェクト（新しいTS）   lookup['constructor']  → プロトタイプが答える
```

古いコードの問題ではありませんでした。13年前に書いても去年書いても、`{}` に外から来た文字列で引けば、同じことが起きます。

`Object.create(null)` を使う（プロトタイプを持たないオブジェクトを作る）か、`Object.hasOwn()` で自分が持っているか確かめるか、`Map` を使うか。どれか1つを決めておけば全部防げます。決めていないと、書く人が変わるたびに再発します。

そして**型では止まらないので、linter で見るしかありません。** これを見ているのは `security/detect-object-injection` という1つのルールだけです。

前半で「記事を書いていたら ever-better 自身の穴が見つかった」と書きましたが、それがこれでした。**このルールを、ブラウザ向けのリポジトリでだけ切っていたんです。** 「このプラグインが見るのはサーバ側の問題だから」と思って外していました。**6件はブラウザの UI で見つかったので、判断が間違っていました。**

### もう1つ、100件を超えた群れ

同じプロジェクトで、正規表現の計算量が爆発する箇所が大量に出ました。ルールは `sonarjs/super-linear-regex` です。

```
sonarjs/super-linear-regex    163  →  51    （PR 14本）
```

「計算量が爆発する」というのは、こういうことです。

```
入力が2倍になると、時間が4倍かかる（quadratic）
入力が2倍になると、時間が8倍かかる（cubic）
```

普通の入力では気づきません。長い文字列を1つ投げられた瞬間に固まります。外から来る文字列に当てているものは、実質的に攻撃経路です。実際に、検索でゼロ幅の正規表現を使ってタブが固まる、というのも出ました。

ここで1つ、やり方の話を書いておきます。**linter の指摘をそのまま信じませんでした。** 実際に文字列の長さを変えて時間を測るスキャナを書いて、本当に爆発するかを確かめてから直しています。

その結果はこうでした。

```
linter が指摘したが、実際には爆発しなかった      あった
linter が指摘しなかったが、実際には爆発した      あった（cubic のものまで）
```

**両方向に外れます。** ルールは当たりを付ける道具であって、答えではありません。ここは記事の前半に書いた「機械が見つけた」の限界でもあります ── 機械が指摘した場所を人が確かめる、までやって初めて数字になります。

これも古い/新しいの問題ではありません。「動いているから正しい」と「速い」が別物なだけです。

## 順番：簡単なところから始める

`any` と正規表現ばかり書きましたが、実際に出たものはもっと幅がありました。全部で5日、PR 207本です。


数で見ると `any` が圧倒的ですが、**先に手を付けたのは下のほうです。**

### 最初にやったのは「ゼロにできるルール」

キャンペーンの最初の1日は、こう進んでいます。

```
バックエンドに lint を通す（それまで一度も検査していなかった）
すでにゼロに近い8ルールを片付けて、error に固定
457 → 259。さらに3ルールを error に固定
259 → 230。3ルールを error に、1つは「このリポジトリでは違う」と却下
no-explicit-any を3段階に分ける
no-empty を error に。残り5ファイルだけ warn
sonarjs を丸ごと追加（warn で）
sonarjs のセキュリティルールを全部 on（warn で）
```

パターンが見えると思います。**「たくさん減らす」ではなく「ゼロにする」を狙っています。**

理由は1つです。**ゼロにしたルールだけが error に固定できる**から。

```
1,000件のルールを100件減らす   →  まだ error にできない。明日また増えうる
8件のルールを8件減らす         →  error に固定できる。二度と増えない
```

**減った数は前者のほうが多いのに、守れた線は後者だけです。** だから残り数件のルールから当たります。1日で「二度と戻らないルール」が10本以上できて、そのぶん検査が効くようになる。

そして固定できたら、**ルールセットのほうを広げます。** 上の最後の2行がそれです。片付けて、固定して、広げて、また片付ける。

### 順番の全体像

```
1  一度も検査していない場所に、まず検査を通す
2  残り数件のルールをゼロにして、error に固定する
3  固定できたら、ルールセットを広げる（新しい警告が出る）
4  2 と 3 を繰り返す
5  機械的に直るものを一気に潰す（整形、未使用、var）
6  最後に any。ここが一番大きい
```

ever-better の `next` が並べているのも、この 2 番の順番です。**件数の多いルールではなく、あと1〜2回の編集で1ファイルが片付くところ**を上に出します。

## ノウハウ：`any` の片付け方

ここからは、その同じプロジェクトで `any`（型を書かない、という指定。コンパイラのチェックがそこで止まります）を実際に片付けたときの話です。

かかったのは4日弱です。正確には3日22時間、PR が188本、コミットが528。上の表を測った2点の間隔です（キャンペーン全体では5日・PR 207本）。

内訳は `refactor(any)` が47本、`chore(eslint)` が22本、`refactor(warns)` が19本、`fix(regex)` が13本。

数字はこうなりました。同じコマンドで両端を測っています。

```
                        開始時    現在
警告の合計               3,689  →   741
うち no-explicit-any     2,515  →   476

経過                    3日22時間（PR 188本 / コミット 528）
```

1つ、測り方について書いておきます。開始時点の `no-explicit-any` は「多すぎて今は直せない」というコメントつきで、**ほとんどのディレクトリで off にしてありました。** なので当時そのまま lint を回しても、79件しか出ません。上の 3,689 は、そのスイッチを全部 on に戻して測り直した数です。

作業しながらルールのほうも厳しくしていったので、**当時の設定で出た数と、いまの設定で出る数を引き算しても、やった量にはなりません。** 同じ物差しで測らないと比較になりません。

そして、そもそもの話も書いておきます。**最初から教科書どおりに書いていれば、こんな数にはなりません。** ここに出てくる警告のほとんどは「知らなかった」ではなく「後で直すつもりだった」ものです。ネストした三項演算子も `any` も、書いた瞬間は速い。その速かったぶんが、全部あとに回っているだけです。

だから本当の解決は、後から片付ける道具ではなく、最初から入れておくことです。冒頭に書いたとおり、僕はそれが毎回できていません。**道具のほうは、順番としては敗者復活戦です。**

### ① `any` の多くは、型がもう書いてあった

一番多かったのがこれでした。使っているライブラリがちゃんと型を配っているのに、`any` で捨てていた。

- ORM（データベースを操作するライブラリ）が返す行の型
- LLM の SDK が持っているイベントの型
- UI ライブラリのコンポーネントが受け取る型

どれも書く必要がありません。`any` を消すだけで、コンパイラが元から知っていた型に戻ります。一番数が多くて、一番簡単なので、ここから当たるのがおすすめです。

### ② `catch (e: any)` が、単独で最大の群れだった

```ts
} catch (e: any) {
  console.error(e.message);   // ← e が .message を持つとは限らない
}
```

これが169箇所ありました。

TypeScript では `catch` で捕まえたものは `unknown`（何か分からないもの。使う前に確かめる必要がある）です。何が投げられるか分からないので。`any` にすると、そのチェックが消えます。

対処は簡単で、小さい関数を1本作って全部そこを通すだけです。

```ts
const errorMessage = (e: unknown): string =>
  e instanceof Error ? e.message : String(e);
```

169箇所が1本に集約できます。

### ③ たった1つの `any` が、広範囲を無効化する

これは驚きました。

> 1つのプライベートメソッドの `any` が、ルート1本まるごとの型を無効にしていた。

`any` は伝染します。`any` を返す関数の戻り値は `any`、それを渡した先も `any`。1箇所直すだけで、連鎖的に何十箇所も型がつくことがあります。

なので「数」で優先順位をつけないでください。上流にある1個のほうが、末端の20個より効きます。

### ④ 外すとバグが出る

`any` を消すと、コンパイラが今まで黙っていたことを言い始めます。実際に出たのがこれです。

- 存在しないカラムを指していた絞り込み条件
- 送信側が送っている6つのフィールドが、型に書かれていなかった（だから受け取る側が全員 `any` にしていた）
- 4つの実装が、どこにも書かれていない同じ形を前提にしていた
- 型の上ではありえない分岐が残っていた

「片付け」のつもりが、バグ探しになります。

### ⑤ ディレクトリ単位で「昇格」させる

ここが運用の肝です。

```
1  no-explicit-any（any を禁止するルール）を3段階に分ける
     off   … まだ手を付けていないところ
     warn  … 作業中
     error … 片付いたところ

2  ディレクトリを1つ片付ける
3  そのディレクトリだけ error に昇格させる
4  以降、そこに新しい any を書くと落ちる
```

片付いた場所から順に「二度と戻らない」状態にしていきます。前半に書いた天井と同じ考え方です。

### ⑥ 似たものはまとめて、バッチで刻む

同じ形の `any` が167箇所ありました。配列のコールバックの引数です。これを5回に分けました。1回18件、17件、11件……という具合に。

レビューするのは AI なので、167件を1本の PR にしても、読むこと自体はできます。断られません。問題はそこではなく、**数が増えるほど取りこぼす**ことです。全部それらしく見えるので、1つだけ形の違うものが紛れていても通ってしまいます。

刻むのは人のためではなく、レビューの精度のためです。1本15〜20件くらいまでに抑えると、指摘が具体的になります。

### ⑦ 残りを「見積もる」

途中で、残り109件について「それぞれ何が必要か」を書いた文書を作りました。

```
これは消すだけ
これはライブラリの型を import すれば済む
これは型を新しく書く必要がある
これは設計を変えないと無理 → 別issue
```

残り件数だけ見ていると終わりが見えません。中身で分けると、実は大半が消すだけだったと分かって進みます。

### ⑧ 変えていないことを、機械で確かめる

`any` を消す作業は、動きを変えてはいけません。なので出力がバイト単位で同じであることを確認しながら進めました。型を直したつもりで挙動を変えていた、が一番怖いので、ここは機械に確認させるべきです。

### まとめると

```
1  ライブラリが配っている型に戻す        ← 一番多い。一番簡単
2  catch (e: any) を1つの関数に集約
3  上流の any から潰す（1つで何十箇所も効く）
4  外すとバグが出る。それが目的でもある
5  ディレクトリ単位で error に昇格させる
6  同じ形はまとめて、バッチで刻む
7  残りを「何が必要か」で分類する
8  出力が変わっていないことを機械で確認する
```

### 順番の話 ── `any` は最初にやらない

なお、さらに別のプロジェクトでも同じことをやっていて、そちらは935ファイルに `any` が 1,413 箇所ありました。linter の設定には「多すぎて今は直せない」という趣旨のコメントとともに、`no-explicit-any` が off にしてあります。

これは正しい順番だと思っています。

最初から `any` を error にすると、他のルールの指摘が全部その下に埋まります。1,413件の中から「本当に直すべき10件」を見つけるのは無理です。だから最初は off にして、視界から外す。

そして整理が進んだところで、**これが本丸です。**

```
最初    any は off。ノイズになるので、いったん視界から外す
途中    軽いルールから潰す。整形、未使用、var、機械的に直るもの
仕上げ  片付いたところで any に戻る。ここでじっくり攻める
```

この記事で4日弱かけたのは、まさに3番目です。**最後に来るからこそ、まとまった数が減らせます。** 順番を逆にすると、たぶん最初の日に諦めます。

ただし、off のまま止まると、そこは誰も確かめていない場所として残り続けます。`any` は「型が分からない」ではなく、型を決める判断を書かずに済ませた場所です。**off は順番であって、終着点ではありません。**

## それでも、コードは汚れていきます

ここまで書いておいて何ですが、**この道具を入れても、放っておけばコードは汚れます。** むしろ AI に書かせる量が増えるぶん、汚れる速度は上がります。

linter が見ているのは「書き方」だけだからです。**設計がおかしいコードは、全部そのまま通ります。**

```
同じ処理が3箇所に散っている        警告は出ない
名前が実態と合っていない          警告は出ない
置き場所が間違っている            警告は出ない
そもそもその機能が要らない        警告は出ない
```

なので、これは要ります。

- **定期的に、人間が問題を指摘する。** 機械には見つけられない種類のものです。そして指摘したら、**そこを集中的に直す。** 気づくたびに1個ずつ直していると追いつきません
- **`CLAUDE.md` と、そこから参照する規約をメンテする。** ディレクトリ構成、命名、どこに何を置くか。**ここが古いと、AI は古い規約どおりに正しく書きます。** 一番静かに効いてくる負債です
- **そもそも、変なコードを書かせない。** 出てきたものを直すより、書かれる前に止まるほうが桁で安い

効き方はこの順です。

```
書かせない        規約が効いている限り、ずっと効く
規約をメンテする  1回書けば、以降の全部に効く
人が指摘して直す  そのときだけ効く
```

**この道具がやっているのは、一番下の、自動化できる部分だけです。** 上の2つは、いまのところ人にしかできません。ever-better に `prepare` というスキルを入れてあるのも、走らせる前に `CLAUDE.md` が実在してメンテされているかを確かめるためです。**そこが薄いと、走らせるたびに違う答えが出ます。**

## 正直に書いておくこと

数字を出す以上、都合の悪いほうも書きます。

pm2 の天井が 4,933 → 3,637 に下がりましたが、そのうち 1,292 件は「直した」のではありません。あるルールを `.js` ファイル全体で対象外にしたぶんです。CommonJS（`require` で読み込む古い方式）のパッケージで `.js` が `import` を使えない以上、そのルールは新しいファイルを全部止めるだけで、線を守っていませんでした。

範囲を狭めたのであって、良くしたわけではありません。ツールの出力にもそう記録してあります。実際に直したのは4件です。

こういうものを混ぜて「1,296件改善」と書くことはできます。でもそう書いた瞬間、他の数字も信用されなくなります。

## まとめ

- 1日500コミットには足回りが要る。でも僕は最初から入れられたことが一度もなく、毎回途中から入れている
- そこを埋める [ever-better](https://github.com/isamu/ever-better) を作った（MIT・依存ゼロ）。今日の違反数を天井として固定し、そこから増やさない
- TS/JS なら、Claude Code に「きれいにして」と言うだけ。整形 → 導入 → 凍結 → ルール1本ずつの PR、と進む
- ★43,254・13年ものの pm2 に当てたら、1時間で 4,942 件を凍結できた
- `no-undef` だけで本物のバグが2件。どちらもエラー処理の中で、13年見つかっていなかった → [本家に PR](https://github.com/Unitech/pm2/pull/6143)
- `.js` を `.ts` に名前を変えただけで、型エラーが2,641件
- 同じ形のバグが、新しい TypeScript のプロジェクトにも6件あった。古いコードの問題ではなかった
- `any` の片付けは、まずライブラリが配っている型に戻すところから。それが一番多くて一番簡単
- **ただし、これを入れても放っておけばコードは汚れる。** linter は書き方しか見ないので、定期的に人が問題を指摘して集中的に直すこと、`CLAUDE.md` と規約をメンテすること、そもそも変なコードを書かせないことのほうが効く

古いコードを責める話ではありません。13年動き続けているコードのほうが、たいていのコードより優秀です。

ただ、確かめていない場所は、確かめるまで分からない。それだけです。そして確かめるのは、いまは1時間でできます。
