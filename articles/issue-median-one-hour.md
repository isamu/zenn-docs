## まず、何が起きているか

実際の例を3つ。どれも**ユーザーからの声を issue にしたもの**です。

| issue | もとの声 | 閉じるまで |
|---|---|---|
| [#878](https://github.com/receptron/mulmoterminal/issues/878) | 「単一パネル側で分割できると思ったら違った。どこから進めればよいか分からず、つまずいた」 | **5時間49分** |
| [#873](https://github.com/receptron/mulmoterminal/issues/873) | 「通知音を Done と Waiting で分けてほしい」 | **9時間45分** |
| [#874](https://github.com/receptron/mulmoterminal/issues/874) | 「サブエージェントが終わっただけで通知が飛ぶのを止めてほしい」 | **9時間47分** |

いずれも夜に立てて、翌朝には入っています。ユーザーから見ると、**言ったら、寝て起きたら直っている**。

最速の10件はこうです。

```
  9分  fix(tmux): pre-fix の tmux サーバーが NODE_ENV を保持し続ける
 11分  fix: 狭いグリッドセルで git チップが潰れて「空のバッジ」に見える
 12分  feat: Shell / Command セルのヘッダーにも名前バッジを出す
 14分  fix(ci): Codex auto-review が timeout-minutes: 10 に当たる
 15分  fix: Shell / Command セルに .mulmoterminal.json の設定が効かない
```

## なぜ速いのか — 3つあります

### 1. 実装が速いのではなく、「確認」が速い

誤解されやすいのですが、**コードを書く時間はもともとボトルネックではありません**。

時間を食うのは、書いたあとです。動作確認して、レビューを待って、指摘を直して、また待つ。**待ち時間の合計**が、issue のリードタイムのほとんどを占めます。

前回の記事で書いたとおり、うちはそこを機械に移しました。

- 規約は [`CLAUDE.md`](https://github.com/isamu/claude) に置いてあり、エージェントが読む
- ESLint が関数の長さ・複雑さ・`any`・非 null アサーションを **error** で止める
- ルールは pure 関数に切り出して、3,000 を超えるテストがある
- CI は mac / Linux / Windows
- 実装は Claude Code、レビューは Codex と CodeRabbit。**書いた側と読む側が別のモデル**

**「人間がレビューのために止まる」工程が無い**ので、issue → PR → マージが一直線に流れます。

### 2. レビューが「待つもの」でなくなった

以前、レビューの主役は CodeRabbit でした。無料枠で使っていたので **1時間に1回しかレビューが回らない**。

レビューは1往復では終わりません。指摘をもらう → 直す → もう一度見てもらう。**1往復ごとに1時間待ち**です。3往復したら3時間。

この待ち時間を、僕とアメリカにいる共同開発者の2人で、黙って待っていました。時差の関係で普段は枠が分かれるのですが、たまたま作業時間が重なるとレビュー枠の**奪い合い**になります。間違ったコミットでトリガーしてしまうと、さらに1時間。

いまは CI の中で Codex が自動で回ります。**push したら勝手にレビューが始まって、戻ってきたら指摘が積まれている。**

レビューの価値は1回の指摘ではなく、**往復の回数**にあります。1往復のコストが下がると、**質のほうが上がる**。「待つのが面倒だから、この指摘は次でいいか」が始まらないからです。

### 3. リリースが軽い

同じ期間（7/25〜7/28 の4日間）に **13 回リリース**しています。v1.9 から v2.4 まで。

マージしてもリリースされないなら、「1時間で閉じた」は意味がありません。**閉じたものがすぐ出る**から、ユーザーから見て速い。

## 誠実に書いておくこと

数字を出した以上、注釈も出します。

- **「クローズ」は「マージ」であって「リリース」ではありません。** ただし上記のとおりリリース間隔が短いので、実質の差は小さいです
- **32件は3日間の切り取りです。** 母数として多くはありません
- **難しい issue は、そもそも issue になる前に時間がかかっています。** 「調査が必要」と判断したものは別扱いで、この32件には現れません
- **速さは正しさではありません。** 速く出して、速く直している面は確実にあります

## この速さが変えたこと

一番大きいのは、**ユーザーが黙らなくなった**ことでした。

先日、使ってくれている方々に「不便なところは？」と聞いて回りました。そのうちの1人は、最初つまずいていた人です。

> まだ私が使いこなせていないからだと思うのですが、これだと思った瞬間は来ていません
> 単一パネル側で……どこから進めればよいかが分からずつまずきました
> 実際に使いこなせている人の使っている動画や解説があると嬉しいです

この方の指摘をもとに直したところ、**ファンになってくれました**。それ以降、ファイルエクスプローラーをはじめ、いくつものアイデアをもらって実装しています。

順番が逆なのだと思います。「良い製品だからフィードバックが集まる」のではなく、**言ったものが実際に入るから、次も言ってもらえる**。

そして issue が増えるほど製品が良くなるので、**ループが回りはじめると勝手に加速します**。

## 「AI が書くと雑になる」への答え

前回の記事に、こういう反応がありました。

> こういう AI Slop を撒き散らすことを生産性向上とか言わないでほしい

これは正当な懸念で、実際そうなり得ます。ただ、**速さそのものは雑さの原因ではありません**。

雑さが生まれるのは、**壊れたことに気づけないとき**です。だから前回、赤くなる仕組みを積み上げました。そして今回、**壊れていると誰かに言われてから直るまでの時間**を測りました。

- 壊れたら赤くなる（前回）
- 言われたら1時間で直る（今回）

この2つが揃っていれば、速さは雑さになりません。むしろ、**遅いほうが雑になります**。指摘が溜まって、直らないまま忘れられるからです。

## まとめ

- issue のクローズまでの中央値は **1時間**、24時間以内が **100%**
- 速いのは実装ではなく、**人間が待つ工程を消したから**
- レビューを CI の中に入れると、レビューは「待つもの」から「流れてくるもの」になる
- ユーザーは、**言ったものが入ると次も言ってくれる**
