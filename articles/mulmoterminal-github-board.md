月曜の朝の定例で、カンバンのボードを画面に映します。

「進行中」の列に、三週間前から動いていないカードがあります。担当の人に聞くと、プルリクエストは先週マージ済みで、カードを動かし忘れていただけでした。その隣の「レビュー待ち」のカードは、実はまだ CI が落ちていて、誰もレビューを始めていません。定例の前半は、ボードを実際の状態に合わせる作業で終わります。

最近はそこに、AI のエージェントが加わりました。Claude Code を三つ四つ並べて、それぞれ別の issue を進めてもらいます。エージェントはカードを動かしませんし、人も追いつけません。どのターミナルがどの issue をやっていて、どれが自分の返事を待って止まっているのかは、ターミナルを一つずつ覗かないと分かりません。

そんな経験はないでしょうか。

## 二か所に書くと、いずれずれる

カンバンのボードがずれるのは、作業の状態を二か所に書いているからです。

本当の状態は、作業そのものの側にあります。ブランチを切ったか、プルリクエストを出したか、CI は通ったか、レビューで直しを求められたか。ボードのカードは、それを人が手で写したものです。写す手間がかかるうえに、写すのを忘れても作業は進むので、写しのほうが少しずつ古くなります。

データベースの設計で、同じ値を二つの表に持たないようにと教わるのと同じ話です。二か所に持てば、どちらが正しいのかを誰かが決め続けなければいけません。カンバンでは、その役目を毎朝の定例が担ってきました。

GitHub Projects や Trello にも、プルリクエストがマージされたらカードを「完了」に移す、といった自動化があります。ただ、それで動くのは始まりと終わりくらいです。そのあいだの「CI が落ちて手戻り中」や「レビューを待っている」は、人が動かすか、誰も動かさないかのどちらかでした。

## 作業が跡を残すようになった

この数年で変わったのは、作業のほとんどが、機械で読める跡を残すようになったことです。

AI のエージェントに issue を頼むと、エージェントはブランチを切り、コミットして、プルリクエストを出します。そこに CI が走り、レビューのボットがコメントを付けます。人が手を動かしていたころは、作業の途中は人の頭の中にありました。いまは途中の状態まで、GitHub とターミナルの中にあります。

そうなると、ボードを人が書く必要はなくなります。GitHub とターミナルを読んで、その結果を列に並べればよいからです。カードを動かす人がいなければ、動かし忘れることもありません。

## MulmoTerminal の GitHub ボード

[MulmoTerminal](https://github.com/receptron/mulmoterminal) は、Claude Code や Codex などの AI のコーディング道具を、ブラウザの中で何個も並べて動かすためのアプリです。自分のパソコンに入れて、ブラウザで開いて使います。MIT ライセンスの無料のソフトウェアです。

その中に、試験中の機能として GitHub ボードがあります。登録したリポジトリの issue とプルリクエストを読み、作業一つを一枚のカードにして、五つの列に並べます。列は、未着手、実装中、レビュー中、QA 待ち、マージ済みです。

![ボード。左から未着手・実装中・レビュー中・QA 待ち・マージ済みの列が並び、選んだカードの詳細が右に開いている](https://raw.githubusercontent.com/receptron/mulmoterminal/main/docs/guide/images/v11.4.0-board-ja.png)

一枚のカードには、issue と、それを閉じるプルリクエストと、そのブランチと、そのブランチで開いているターミナルが一緒に載ります。四つの別々の場所にあったものが、作業という単位でまとまります。

## 列はどう決まるか

カードをどの列に置くかは、GitHub に書かれていることだけで決めます。人がドラッグする操作はありません。

未着手は、まだプルリクエストもターミナルも付いていない、開いている issue です。

実装中は、作業する側に球があるものです。プルリクエストが下書きのとき、CI が落ちているとき、レビューで修正を求められたときがここに入ります。プルリクエストはまだ無いけれど、ターミナルがそのブランチで開いている場合も実装中です。

レビュー中は、作業する側の手を離れて待っているものです。CI がまだ走っている途中か、最新の push がまだ誰にもレビューされていないプルリクエストがここに入ります。

QA 待ちは、CI が通り、最新の push がレビュー済みか承認済みのものです。人が最後に目を通して、マージを決める段階です。

マージ済みは、最近マージされたプルリクエストです。

判定の順番にも意味があります。下書き、CI の失敗、修正の依頼のどれか一つでもあれば、ほかがどうでも実装中になります。作業する人がまず知りたいのは、自分が直さなければいけないものがあるかどうかだからです。

カードには「レビュー 2 回目」のような表示も出ます。レビューを受けた push の数を数えたもので、何往復したかの目安になります。

## issue とプルリクエストを結ぶ

一枚のカードにまとめるには、どのプルリクエストがどの issue のものかを知る必要があります。

いちばん確かなのは、プルリクエストの説明に `Closes #123` のように書いてある場合です。GitHub はこれを、そのプルリクエストが閉じる issue として覚えています。ボードはまずそれを使います。

書いていない場合は、ブランチの名前から探します。`issue/123-fix-login` のようなブランチなら、123 番が候補です。ただし、名前の中の数字はいつも issue の番号とは限りません。`release/2026-11` のような名前もあります。そこで、そのリポジトリに 123 番の開いている issue があるときだけ結び付けます。

## ターミナルがカードに乗る

ボードがほかのカンバンと違うのは、ターミナルまでカードに載ることです。

MulmoTerminal は、自分が開いているターミナルが、どのフォルダで動いているかを知っています。そのフォルダが git のどのリポジトリの、どのブランチにいるかも分かります。リポジトリとブランチが分かれば、どのカードに載せるかが決まります。

カードの上のターミナルには、作業中、確認待ち、待機中の状態が出ます。押すとそのターミナルに移れます。

`main` のようなデフォルトのブランチで開いているターミナルは、どのカードにも載せません。デフォルトのブランチは作業そのものではないからです。こうしたターミナルは、そのリポジトリの列の上に、ブランチごとにまとめて出ます。

設定に登録していないリポジトリでも、そのクローンでターミナルを開いていれば、「未登録」と付けてボードに出ます。最後のターミナルを閉じると消えます。

## カードから始める

未着手のカードには、開始のボタンがあります。

押すと、その issue のための worktree を作ります。worktree は、一つのリポジトリから作業ごとに別のフォルダを切り出す git の仕組みで、エージェントが何本並んでも作業が混ざりません。ブランチは `origin` の最新から切ります。そこでエージェントを起動し、issue の本文をすぐに送ります。

起動するエージェントは、Claude、Codex などから選べます。新しいターミナルはボードの裏のグリッドに加わり、カードは未着手から実装中に移ります。ボードの画面はそのままなので、続けて別の issue を始められます。

同じ issue をもう一度押しても、二本目の worktree は作りません。すでにあるものが開きます。

## 自分の番が目立つ

ボードを開いている間、カードの上のターミナルの状態は、その場で変わります。

エージェントが質問をしたり、許可を求めたりして止まると、そのカードは琥珀色の枠になり、「確認待ち」の印が付きます。何本ものエージェントを走らせているとき、いちばん知りたいのは、どれが自分の返事を待っているかです。それが一目で分かります。

GitHub のほうは、ボードが画面に出ている間、一分ごとに読み直します。加えて、どれかのターミナルで一ターンが終わると、その数秒後にも読み直します。エージェントが push した直後に、CI が走りはじめたことがカードに表れます。

読み直しに失敗しても、カードは消さずに残し、上にエラーを出します。

## ボードから答える

カードを押すと、右に詳細が開きます。プルリクエストのチェックとレビューと説明、issue のラベルと説明が出ます。そのカードのターミナルの画面も、ここで読めます。

ターミナルごとに、返信や次の指示を書く欄があります。書いて送ると、そのターミナルに一行を打ち込んで Enter を押します。確認待ちのターミナルに答えることも、待機中のエージェントに次の仕事を頼むこともできます。

Claude Code が選択肢つきの質問をしているときは、その選択肢がボタンで出ます（質問の表示をオンにしている場合）。

コマンドの実行の許可（1. Yes / 2. No）は、キーの操作が要るので、ボードからは答えません。ターミナルを開いて答えます。質問の画面が開いている最中に打ち込むと、意図しない選択肢を選んでしまうので、そのときの送信は断るようにしています。

## レビューの判定も載る

筆者は、プルリクエストを Codex にもう一度読ませるレビューを回しています。その結果は、`CODEX VERDICT: LGTM (head 1a2b3c4)` のような一行で始まるコメントとしてプルリクエストに残します。ボードはこのコメントを数えて、カードに「Codex 2 回: LGTM」や「Codex 1 回: 修正依頼」と出します。

![ボード。赤い「Codex 1 回: 修正依頼」のカード、緑の「Codex 2 回: LGTM」のカード、薄い「Codex 3 回: LGTM」に「前の push への判定」が添えられたカード](https://raw.githubusercontent.com/receptron/mulmoterminal/main/docs/guide/images/v11.5.0-board-codex-ja.png)

色が付くのは、その判定が、いまのブランチの先頭の push を名指ししているときだけです。LGTM のあとに直しを push すると、前の LGTM は古い push についての判定になります。時刻だけでは区別できないので、判定の行に push の番号を書いてもらい、それを照らし合わせています。古い判定は薄く描かれ、「前の push への判定」と添えられます。

数えるのは、リポジトリの持ち主とメンバーとコラボレーターのコメントだけです。公開リポジトリには誰でもコメントを書けるからです。

この判定のコメントを書くレビューの仕組みは、筆者の手元のもので、MulmoTerminal には入っていません。同じ形の一行を書く仕組みがあれば、ボードはそれを数えます。

## 開いている作業だけ

開いている issue がたくさんあるリポジトリでは、ボードが未着手のカードで埋まります。いま手を動かしているのは、そのうちの数枚です。

そこで、ボードの上の「ターミナルを開いている作業だけ」は、最初からオンにしてあります。オンの間は、ターミナルが載っているカードだけが出て、カードの無い列とリポジトリは隠れます。外すと、未着手の issue も含めて全部出ます。

マージ済みのカードでも、ターミナルが残っていれば出ます。終わった作業のターミナルを閉じ忘れていることに気づけます。

ターミナルを閉じると、そのカードからすぐに消えます。開くと、数秒で読み直されて現れます。

## 一日の流れ

使い方を一日の流れで書くと、こうなります。

朝、ボードの「ターミナルを開いている作業だけ」を外して、未着手の issue を眺めます。今日やるものを三つ選んで、それぞれ開始のボタンを押します。worktree が三つでき、エージェントが三本動きはじめ、カードが実装中に並びます。

しばらくすると、一枚のカードが琥珀色になります。詳細を開いてターミナルの画面を読むと、エージェントが設計の選択肢を二つ挙げて、どちらにするかを聞いています。ボタンで一つを選ぶと、エージェントは作業に戻ります。

昼ごろ、二枚のカードがレビュー中に移っています。エージェントがプルリクエストを出し、CI が走っているところです。一枚はそのまま QA 待ちに進み、もう一枚は CI が落ちて実装中に戻ってきます。戻ってきたほうのターミナルに、「CI のエラーを読んで直して」と送ります。

夕方、QA 待ちのカードを開いて、チェックとレビューを確かめてからマージします。カードはマージ済みに移ります。そのターミナルを閉じれば、ボードからも消えます。

このあいだ、カードを手で動かしたことは一度もありません。

## ほかの道具との違い

GitHub の issue とプルリクエストを並べるだけなら、ほかにも道具があります。GitHub Projects でも、プルリクエストがマージされたら移す、といった設定はできます。

違いは二つあります。

一つは、列を GitHub の状態から毎回決め直していることです。カードの位置という別の情報を持たないので、実際の状態とずれる余地がありません。CI の失敗や修正の依頼で実装中に戻るのも、読み直した結果です。

もう一つは、カードの上に作業をしているターミナルがあり、ボードからそこへ働きかけられることです。始める、状態を見る、答える、次を頼むが、同じ画面の上でできます。ボードを見る場所と、エージェントに指示する場所が分かれていません。

## 試してみる

必要なものは次のとおりです。

- Node.js 22.13 以上と git
- GitHub CLI（`gh`）と、それでの GitHub へのログイン
- Claude Code と、それを使うための Claude の有料プラン（無料プランでは Claude Code は使えません）。Codex を使う場合は、そのためのアカウント

ボードは裏で `gh` を実行して GitHub を読みます。MulmoTerminal 自身はトークンを持たず、`gh` のログインをそのまま使います。まだなら、ターミナル（Windows なら PowerShell、Mac ならターミナル）で `gh auth login` を実行しておきます。

次を実行し、ブラウザで `http://localhost:34567` を開きます。

```bash
npx mulmoterminal@latest
```

設定の「プルリクエストのリポジトリ」に、見たいリポジトリを `owner/repo` の形で追加します。すると、グリッドの上のツールバーに GitHub のマークが出ます。押すと issue とプルリクエストの一覧が開き、その上の「ボードを開く（実験的）」でボードが開きます。

開始のボタンで worktree を作るには、そのリポジトリのクローンが手元に要ります。クローンは、設定のディレクトリのプリセットに登録しておきます。同じリポジトリのクローンを複数持っているときは、初回だけどれを使うかを聞かれます。

## 気をつけること

ボードは試験的な機能です。画面や列の決め方は、これから変わることがあります。

対象は GitHub のリポジトリだけです。GitLab のリポジトリは、ボードでは読めません。

「レビュー 2 回目」の数え方は目安です。レビューを受けた push の数を数えているので、ボットのレビューも人のレビューも同じ一回になります。

ボードの開始のボタンは、どのエージェントでも issue の本文をすぐに送ります。issue とプルリクエストの一覧から始めたときは、Claude なら本文を入力欄に置くだけで、Enter は自分で押します。ボードではその一手を省いています。さらに、Claude と Codex 以外のエージェントは、ツールの使用も自動で承認されます。issue を書いた人と、それを走らせる人が違うことはよくあるので、知らない人が書いた issue を始めるときは、先に本文を読んでください。

ボードを開いている間は、一分ごとに GitHub を読みます。リポジトリをたくさん登録していると、そのぶん `gh` の呼び出しが増えます。

詳しい説明は [GitHub のガイド](https://www.mulmoterminal.com/guide/ja/github.html) にあります。

## まとめ

カンバンのボードがずれるのは、作業の状態を、作業の側とボードの側の二か所に書いていたからでした。カードを動かすのは人の仕事で、動かし忘れても作業は進みます。

いまは、作業の途中の状態まで GitHub とターミナルに残るようになりました。それならボードは、人が書かなくても、読んで並べるだけで作れます。MulmoTerminal の GitHub ボードは、issue、プルリクエスト、CI、レビュー、ターミナルの状態から、カードの位置を毎回決め直します。

エージェントを何本も走らせていると、人の仕事は、作業そのものより、どれが自分を待っているかを見つけることに寄っていきます。誰もカードを動かさないボードは、その仕事のための画面です。
