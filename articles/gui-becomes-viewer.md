あなたが配置に悩んだそのボタン、**たぶん誰も押していません。**

先日、自分の作っているアプリのユーザー6人に話を聞いて、それを思い知りました。返ってきたのがこれです。

> worktree は使っていない（**どうやって使うのか、よく分かっていない**）

> **どこから進めればよいかが分からず**つまずいた

> Codex と Claude を**どうやって切り替えるかが、未だに分かっていない**

**全部、実装済みの機能です。** ボタンもあります。README にも書いてあります。それでも、見つけられていない。

ボタンの位置が悪かったのだろうと最初は思いました。でも違いました。**機能が20個あれば、20個目のボタンは必ずどこかに埋もれます。** どれだけ整理しても、ユーザーが「そういう機能がある」と知らなければ探しません。**探さないものは、見つかりません。**

それで、諦めました。

いま自分のアプリから、**設定フォームを1つずつ消しています**。代わりに置いたのは、**その設定を書くスキルを起動するボタン1つ**です。押すとセッションが立ち上がって、会話しながら設定してくれる。フォームはありません。

手抜きに見えると思います。僕もそう思っていました。でも結果として、**フォームがあった頃より確実に設定されるようになりました。**

## きっかけは、Web UI を作りかけて捨てたこと

あるベンチマークツールを作っていました。最初は Claude Code の中だけで動かしていたものです。

「他の人にも使いやすいように」と思って Web UI を作り始めたのですが、途中で手が止まりました。

**GUI を作るより、Claude Code の Skill として実装したほうが、使う側が圧倒的に楽だった**からです。

自然言語で伝えれば、必要な処理はバックエンドで全部進む。Web 側に必要だったのは、操作画面ではなく——**結果を見るための Viewer だけ**でした。

## 実際にやったこと：設定画面をスキルに置き換える

抽象論だと伝わりにくいので、実装の話をします。

[MulmoTerminal](https://github.com/receptron/mulmoterminal) という、AI エージェントを並列で回すための道具を作っています。当然、設定項目があります。テーマ、ディレクトリごとの色、キーボードショートカット、通知音、使うモデル。

これを全部フォームで作ろうとすると、**それぞれに画面が要ります**。色は7つ、キーマップは9アクション、通知は6種類×鳴らす/鳴らさない×音の選択。組み合わせるとかなりの量です。

### 気づいた問題：フォームは「できないこと」を作る

作っている途中で、もっと厄介なことに気づきました。

**Settings は、コントロールを持っている設定しか表示できません。** つまり——

| 実際 | Settings の見え方 |
|---|---|
| `themes` に書けば独自テーマを追加できる | **4択のドロップダウンだけ**。追加できると分からない |
| `keymap` で9アクションに割り当てられる | **読み取り専用の一覧**。設定方法が書いていない |
| `.mulmoterminal.json` の書式ミスは黙って捨てられる | **キーが消えて表示されない**。直す導線もない |

**ファイルで設定できるものが、アプリにできないことのように見えていた。** これはフォームの構造的な限界です。全部の設定にコントロールを用意しない限り、必ずこうなります。

### 置き換えた結果

各セクションに、**その設定を書くスキルを起動するボタン**を1つ置きました。

| セクション | 起動するスキル |
|---|---|
| テーマ | `mulmoterminal-theme` |
| ディレクトリの見た目 | `mulmoterminal-dirs` |
| 通知音 | `mulmoterminal-notify` |
| キーボードショートカット | `mulmoterminal-keys` |
| 設定の監査 | `mulmoterminal-config` |

押すとセッションが立ち上がって、こう聞いてきます。

> どのプロジェクトの色を決めますか？ 最近使ったディレクトリはこれです。
> 暖色系 / 寒色系 / 鮮やか、どれから始めますか？

決めたら書き込んで、**実際のセルを見て**から微調整する。フォームだったら「色を選んで保存、画面に戻って確認、また開いて調整」だったところです。

## もっと分かりやすい例：Google フォーム

自分のアプリの話だと「そりゃ自分で作ったんだから」と思われるので、誰でも触ったことがあるもので。

**Google フォームでアンケートを作るの、面倒すぎませんか。**

質問を追加して、形式を選んで、選択肢を1つずつ打ち込んで、必須にするかのトグルを探して、分岐を設定して、公開範囲を決めて。**やりたいことは1文で言えるのに、画面を10回くらい行き来します。**

```
「参加者に、興味のあるセッションを複数選んでもらって、
 最後に自由記述で感想。社内の人だけが答えられるように」
```

これで終わっていいはずです。**JSON を組み立てて POST すれば作れる**わけで、その JSON を書くのは人間である必要がありません。

結果も同じです。スプレッドシートを開いて、行を眺めて、ピボットを作って——ではなく:

```
「昨日の回答、まとまった？　傾向と、気になる自由記述だけ教えて」
```

**生データを見たいわけではありません。** 知りたいのは傾向と例外です。

### で、これを実現するために足りないもの

技術的には全部あります。API はあるし、JSON も定義されている。**足りないのは「AI から使えるか」という視点だけ**です。

- **認証** — OAuth の同意画面は人間がブラウザで踏む前提。エージェントが持てる資格情報の形になっているか
- **スキーマ** — 「複数選択・必須・分岐あり」を自然言語から組み立てられるだけの、素直な構造になっているか
- **エラー** — 弾かれたとき、**AI が読んで直せる文言**になっているか（「エラーが発生しました」では直せません）
- **結果の取得** — 集計済みを返せるか、生データを全部読ませるのか

**Web の操作画面を磨くより、この4つを整えるほうが、これからの使われ方には効きます。** 画面は「作った結果を確認する Viewer」で足りる。

もうこれは、**操作画面を作ることが古い**という話だと思っています。20世紀の発想が残っている。

## なぜフォームより確実なのか

やってみて分かった理由が3つあります。

### 1. 聞き返してくれる

フォームは**入力を待つだけ**です。何を入れればいいか分からなければ、そこで止まります。

スキルは聞いてきます。「どのディレクトリですか」「今どういう配色にしていますか」「暗いテーマと明るいテーマ、どちらを使っていますか」。

**足りない情報を相手が取りに来る。** これは人に仕事を頼むときと同じ体験で、フォームには原理的にできません。

### 2. 現状を読んで、続きをやってくれる

`mulmoterminal-dirs` は、起動すると**既にある設定を全部読みます**。そして「この人はプロジェクトを暖色のグラデーションで塗っている」と判断して、**新しく clone したリポジトリに、その並びの続きの色を提案します**。

フォームでこれをやるには、「既存設定を解析して規則を推測する機能」を実装しないといけません。スキルなら、読んで判断するだけです。

### 3. 書式を覚えなくていい

`.mulmoterminal.json` には20近いキーがあります。`orderPriority` は小さいほど前、`fontSize` は8〜32でクランプ、`cwdPresets` は `{label, path}` の配列——**これを覚えている人はいません**。作った本人も忘れます。

## GUI が消えるわけではない。**役割が変わる**

ここが誤解されやすいところです。**GUI は要ります。** ただし置き場所が変わります。

```
ユーザーは対話する
      ↓
AI が処理を考える
      ↓
バックエンドが実行する
      ↓
GUI は結果を表示する    ← ここが GUI の担当
```

同じアプリで、**Viewer としての GUI はむしろ増やしています**。エージェントのツール呼び出しを、図・フォーム・画像・書類として描画するパネルがあります。エージェントはテキストを印字するだけでなく、**見るためのインターフェースを手渡してくる**。

操作の入口は対話、結果の出口は GUI。この分担にすると、**どちらも作るのが楽になります**。フォームは「入力の検証」「エラー表示」「状態の復元」を全部持たないといけませんが、Viewer は表示だけです。

## 起点が変わる

これが一番大きい変化かもしれません。

これまでの設計は「**どんな画面を作ろう**」から始まっていました。

これからは「**AI は最初に何を聞くべきか**」から始まります。

そこから対話を設計して、その結果を表示する Viewer を考える。**UI ではなく Conversation Design が主役**になります。

実際、`mulmoterminal-dirs` を作ったとき、最初に決めたのは画面ではなく**最初の質問**でした。「どのディレクトリ？」ではなく「**最近使ったディレクトリを出すので、チェックを付けてください**」。ここを変えただけで、使われ方がまったく変わりました。

## 想定される反論に、先に答えます

Zenn に書く以上、ここは正直に。

### 「全部対話にしたら遅いのでは？」

**その通りです。** 頻繁に変えるものは対話にすべきではありません。

うちも、フォントサイズのステッパーや通知の ON/OFF トグルは**フォームのまま残しています**。**1クリックで終わるものを会話にするのは退化**です。

対話に移すべきなのは、**選択肢が多く、書式があり、頻度が低いもの**。テーマ作成、キーマップ、色の設計はそちらです。判断基準はこれだけだと思っています。

### 「発見可能性が下がるのでは？」

これは**逆でした**。

冒頭に書いたとおり、**ボタンは見つけてもらえません**。これは作り手の怠慢ではなく、選択肢が増えれば必ず起きることです。

一方、対話には**「知らないものについて聞ける」**という性質があります。

> 「同じリポジトリで並行して作業したいんだけど」

と言えば、worktree の存在を知らなくても worktree にたどり着きます。**メニューの何段目にあるかを知らなくていい。**

そして前述のとおり、フォームは「コントロールがある設定」しか見せられないので、ファイルでしか設定できないものは**存在しないように見えていました**。ボタンを置いたことで「テーマは自分で作れる」「キーマップは変えられる」が初めて画面に現れています。

**発見可能性は、減ったのではなく増えました。**

### 「AI が使えない環境では？」

このアプリは Claude Code / Codex を動かすための道具なので、**AI が居ることが前提**です。そこは正直に前提として置いています。

汎用のアプリで同じことをやるなら、**フォームとスキルの両方を残す**のが現実的だと思います。実際うちも、既存のフォームは消さずにボタンを足しました。

## まだ画面から考えているなら

もし今でも「まず画面設計をしよう」「まずボタン配置を考えよう」となっているなら、一度 AI エージェントと本気で数日仕事をしてみてください。Claude Code でも Codex でも構いません。

そのうち、**GUI を操作すること自体が億劫になってきます**。「対話すれば終わるのに、なぜ自分でボタンを探しているんだろう」という感覚です。

PowerPoint も同じで、まだ自分でレイアウトを選んで図形を配置して文字サイズを調整しているなら、その作業は急速に移っていきます。人間は「何を伝えたいか」を考え、AI が形にする。そのほうが速いし、たいてい品質も高い。

## まとめ

- **GUI はなくならない。主役ではなくなる**
- 操作の入口は**対話**、結果の出口は **Viewer**
- フォームは「コントロールを持つ設定」しか見せられない。**ファイルで設定できるものが「できないこと」に見える**
- **1クリックで終わるものは対話にしない**。選択肢が多く・書式があり・頻度が低いものだけ移す
- **どれだけ考えて配置しても、ボタンは見つけてもらえない。** 対話には「知らないものについて聞ける」性質がある
- 設計の起点が「どんな画面を作ろう」から「**AI は最初に何を聞くべきか**」に変わる
- 外部サービスも同じ。**磨くべきは操作画面ではなく、認証・スキーマ・エラー文言・集計API**——つまり「AI から使えるか」

実装は全部 MIT で公開しています。設定スキルもアプリに同梱してあるので、動くものが見たい方はどうぞ。

```bash
npx mulmoterminal@latest
```

- [receptron/mulmoterminal](https://github.com/receptron/mulmoterminal)
