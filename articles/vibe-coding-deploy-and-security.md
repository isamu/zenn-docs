AI に話しかけるだけでアプリが動くようになりました。ここまでは、もう誰でもできます。

止まるのは次です。**「で、これどこに置けばいいの？」**

調べると Supabase、Vercel、Cloudflare といった名前が出てきます。ただ、この3つは役割が違いますし、**「誰に見せるか」によって選ぶものも設定も変わります**。そして厄介なことに、間違えても画面は普通に動きます。事故は静かに起きます。

この記事では、各社の公式ドキュメントで確認できた事実だけを書きます。とくに「**その機能、どのプランから使えるのか**」まで書きます。無料プランでは使えない機能を前提に設計してしまうのが、最初のつまずきポイントだからです。

先に結論を3つ。

- **「誰に見せるか」を決めないとデプロイ先は決まらない。** 技術の問題ではなく、先に決めるべき仕様です
- **PaaS / BaaS では「IP で絞る」が効かない場面が多い。** とくに Supabase では、IP 制限を設定しても**アプリが実際に使っている通り道は開いたまま**です
- **社外・不特定多数向けは、本当に難しい。** 難しい理由がはっきりしているので、それを分解します

## 1. デプロイ先より先に決めること：誰に見せるか

公開範囲を4つに分けます。この分類がこの記事の背骨です。

| | 見せる相手 | 例 | 難易度 |
|---|---|---|---|
| **A** | 自分だけ | 自分用の集計ツール、議事録整形 | 低 |
| **B** | 社内の複数人 | 部内の申請フォーム、在庫照会 | 中 |
| **C** | 社外の特定の人 | 取引先に見せる見積シミュレータ | 中〜高 |
| **D** | 社外の不特定多数 | 誰でも使える公開サービス | **高** |

A から D に向かって、必要な守りが増えていきます。**そして A〜C と D のあいだには、他より大きな段差があります。** そこは後半で扱います。

まず「自分が作ろうとしているのはどれか」を1文で書いてください。これが決まらないまま「とりあえずデプロイ」をすると、だいたい D のつもりがないのに D になります。

## 2. Vercel と Supabase は役割が違う——ドアは1つではない

ここが最初の、そして一番大きな誤解です。

- **Vercel / Cloudflare Pages** … **画面**を置くところ（ホスティング）
- **Supabase** … **データ**を置くところ（BaaS。データベース＋認証＋ファイル保管）

この2つは別のサービスで、**別のドメインで、別々にインターネットに向いています**。

```
                ┌──────────────────────┐
  ブラウザ ─────→│ Vercel（画面）        │
      │         └──────────────────────┘
      │
      │         ┌──────────────────────┐
      └────────→│ Supabase（データ）    │  ← 別のドア
                └──────────────────────┘
```

矢印が**2本ある**のがポイントです。ブラウザは画面を取りに行き、そのあと**データベースに直接**問い合わせます。途中に Vercel は挟まりません。

昔ながらの構成（Web サーバー → アプリサーバー → データベース）では、データベースはインターネットから見えない場所にいました。外からの入口は1つで、そこを固めればよかった。

**BaaS は、データベースが最初からインターネット側にいます。** これは欠陥ではなく設計です。だからこそブラウザから直接使えて、サーバーを書かずに済む。ただし前提が変わります。

> **画面に鍵をかけても、データのドアは別に開いている。**

この一文が、以降のすべての土台です。

## 3. 「IP 制限」が効かない、の正体

ここが本題のひとつです。

### 従来型（AWS など）でやっていたこと

社内向けシステムなら、送信元 IP アドレスで絞るのが定番でした。セキュリティグループやロードバランサの設定で「この会社のオフィスと VPN からだけ」と書けば、それ以外は届かない。データベースは VPC の中にいて、そもそも外から触れません。

**「どこから来たか」で守る**——境界防御です。シンプルで、強い。

### PaaS / BaaS ではどうなるか

公式ドキュメントで確認した結果です。

| サービス | IP で絞れるか | 条件 |
|---|---|---|
| **Vercel** | できる（Trusted IPs） | **Enterprise プランのみ** |
| **Cloudflare** | できる（WAF の IP Access Rules） | **全プランで利用可**（国単位のブロックのみ Enterprise） |
| **Supabase** | **部分的にしかできない** | 次項で詳述 |

[Vercel の Trusted IPs](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/trusted-ips) は Enterprise 限定です。つまり Hobby でも Pro でも、IP では絞れません。

[Cloudflare の IP Access Rules](https://developers.cloudflare.com/waf/tools/ip-access-rules/) は「すべてのお客様が利用可能」と明記されています。ここは Cloudflare が明確に強い部分です。

### Supabase の落とし穴——これが一番危ない

Supabase にも [Network Restrictions](https://supabase.com/docs/guides/platform/network-restrictions) という IP 制限機能があります。ダッシュボードから設定できます。

ただしドキュメントにこう書かれています。

> ネットワーク制限は、PostgREST、Storage、Auth といった HTTPS API や、supabase-js などのクライアントライブラリには適用されません。

読み替えます。**制限が効くのは、Postgres への直接接続と pooler だけ**。あなたのアプリが実際に使っている経路——`supabase-js` が叩く Data API——は**制限の対象外**です。

つまりこうなります。

```
IP 制限あり  ✕ ← DB クライアントからの直接接続（psql など）
IP 制限なし  ○ ← supabase-js / REST API ← ★アプリが使うのはこっち
```

**設定画面に「IP 制限: 有効」と表示されているのに、アプリの通り道は開いている。** 「対策した」という記憶だけが残るので、何もしていないより危険とも言えます。

### だから、守り方を変える

境界防御が使えないなら、発想を切り替えます。

> **「どこから来たか」で守るのをやめて、「誰が来たか」で守る。**

これがゼロトラスト、あるいは ID ベースのアクセス制御と呼ばれるものです。IP アドレスではなく、Google アカウントやメールアドレスで入口を判定します。

そして非エンジニアにとって朗報なのは、**こちらのほうが運用が簡単**だということです。「オフィスの固定 IP を情シスに聞く」「在宅の人はどうする」「VPN を通す」といった話が全部消えて、「この人を許可する／外す」だけになります。

## 4. パターン別：具体的にどう置くか

### A. 自分だけが使う

**まず、デプロイしないという選択肢があります。** ローカルで動かせば、そもそもインターネットに出ません。自分用の集計ツールなら、これで十分なことが多い。

スマホからも使いたいなど、どうしても置きたい場合は Cloudflare Access（後述）で自分のアカウントだけを許可するのが手軽です。

注意点はひとつだけ。**Supabase を使っているなら、A であっても RLS の確認は必要です**（セクション5）。画面を自分しか開かなくても、データのドアは別に開いているからです。

### B. 社内の複数人が使う

ここは **[Cloudflare Access](https://www.cloudflare.com/plans/zero-trust-services/) が本命**です。理由は3つあります。

1. **無料枠が 50 ユーザーまで。** 部やチーム単位なら、たいてい収まります
2. **Google Workspace / Microsoft Entra ID / GitHub / メール OTP に対応。** 会社が既に使っている ID をそのまま使えます
3. **ドメイン単位でポリシーが書ける。** 「`@yourcompany.co.jp` のメールアドレスなら通す」という書き方ができるので、人が増えるたびの作業が要りません

アプリの手前に立って、認証されていないアクセスは中に到達すらしません。**アプリ側にログイン機能を作らなくていい**、というのが非エンジニアにとって一番大きい点です。

Vercel を使っていて Pro プランなら、[Password Protection](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/password-protection) という選択肢もあります（**保護するプロジェクトごとに月額課金**、Hobby では使えません）。ただし性質が違います。

| | Cloudflare Access | パスワード保護 |
|---|---|---|
| 誰が入ったか | **分かる**（個人が特定できる） | 分からない |
| 人を外す | その人だけ外せる | **全員のパスワード変更が必要** |
| 共有されたら | 共有できない（本人の ID が要る） | **そのまま入られる** |
| 退職者 | ID 停止で自動的に締め出せる | **手作業で気づかないと入れる** |

パスワード保護は「ちょっと見せる」には便利ですが、**誰がアクセスしたか分からない**のが決定的です。社内システムで「誰が見たか」を答えられないのは、後々つらい。

### C. 社外の特定の人に見せる

意外に思われるかもしれませんが、**ここも Cloudflare Access が相性がいい**です。

メールアドレスを個別に指定して、**ワンタイムパスコード**で認証する方式が使えます。相手にアカウントを作ってもらう必要がありません。「メールアドレスを入力 → 届いた数字を入れる → 入れる」で終わります。取引先に「まずアカウント登録を」と言わずに済むのは、実務上かなり効きます。

やってはいけないのは、**「URL を知っている人だけ」で済ませること**です。これは認証ではありません。

- メールやチャットで転送されたら、そこで終わりです
- **誰がアクセスしたのか記録が残りません**
- 取引先の情シスに説明を求められたときに、説明できません

「推測できない長い URL だから大丈夫」は、鍵をかけていない家のドアを、草むらに隠しているのと同じです。

### D. 社外・不特定多数——ここが本当に難しい

正直に書きます。**非エンジニアが最初に取り組む対象としては、おすすめしません。** 理由を分解します。

**1. 入口で人を選べない。** A〜C は「入れる人を限定する」で解けました。D は**誰でも入れることが要件**なので、この一番強い手が最初から使えません。

**2. 認可をアプリの中に書かなければならない。** 「誰がどのデータを見ていいか」をコードとポリシーで表現する必要があります。ログインまでは作れても、**「A さんのデータを B さんが見られない」を保証するのは別の仕事**です。

**3. 入力をすべて疑う必要がある。** 悪意のある入力が来る前提で作ります。善意のユーザーだけを想定したコードは、ここで破られます。

**4. 止められない。** 社内向けなら「すみません、今日は止めます」で済みます。公開サービスを止めると障害対応になります。**問題が見つかってから直すまでの時間、穴が開いたまま**です。

**5. 個人情報が乗ると法令の話になる。** 技術で閉じなくなります。

D をやるなとは言いません。ただ、**A〜C で価値を出してから D に進む**ほうが、順番として圧倒的に安全です。「社内で毎日使われているツールを、外にも出す」なら、そのときには実績と、直すべき箇所の見当がついています。

## 5. BaaS 最大の罠：anon key と RLS

Supabase を使うなら、ここだけは読んでください。**vibe coding でいちばん多い事故がここ**です。

### key が公開されているのは仕様です

ブラウザで動かす以上、Supabase の `anon key`（現在の呼び名は publishable key）は**誰でも読めます**。開発者ツールを開けば出てきます。これはバグでも設定ミスでもなく、**そういう設計**です。

[公式ドキュメント](https://supabase.com/docs/guides/getting-started/api-keys)にこう書かれています。

> publishable key は公開しても安全です。**RLS が有効になっていれば。** 行へのアクセス権限が、アクセスポリシーとユーザーの JWT に対して検証されるためです。

太字にしたのは筆者ですが、この条件節がすべてです。

### RLS を切っていると、何が起きるか

**RLS**（Row Level Security）は、データベース側で「この行を誰に見せるか」を決める仕組みです。

- RLS を**有効**にすると、ポリシーを書くまで API 経由で**一切データが取れなくなります**
- RLS が**無効**だと、公開されている key で**テーブルの中身が全部読めます**

つまり、RLS を切ったまま公開すると、**画面にログイン機能があっても無関係に、データは誰でも取り出せます**。ログイン画面は画面の話であって、データのドアには何の関係もありません。セクション2の「矢印が2本ある」図を思い出してください。

### 自分で確かめる方法

怖い話をしたので、確認方法も書きます。**自分のプロジェクトに対して**やってください。

1. ブラウザの開発者ツールで、通信内容から Supabase の URL と key を拾う
2. その2つを使って、アプリを経由せずに直接データを取りに行ってみる
3. **ログインしていない状態で中身が返ってきたら、それは誰にでも返ってきます**

AI に「このテーブルの RLS ポリシーを確認して」と聞くこともできますが、**最終的には実際に叩いて確かめるのが確実**です。設定画面の表示と実際の挙動がずれることは、セクション3の Supabase の IP 制限で見たとおりです。

RLS のポリシー設計に自信がないなら、**そこだけエンジニアに見てもらう**のが費用対効果として最良です。全部を見てもらう必要はありません。「RLS が有効か」「ポリシーが意図どおりか」の2点です。

## 6. まとめ表

| 公開範囲 | 現実的な構成 | 費用感 | 一番の落とし穴 |
|---|---|---|---|
| **A. 自分だけ** | ローカル実行／Cloudflare Access で自分のみ許可 | ほぼ無料 | Supabase を使うなら RLS は必要 |
| **B. 社内・複数人** | Cloudflare Access（ドメイン単位のポリシー） | 50 ユーザーまで無料枠 | パスワード共有で済ませると、誰が入ったか分からない |
| **C. 社外・特定の人** | Cloudflare Access（メール指定＋ワンタイムパスコード） | 同上 | 「URL を知っている人だけ」は認証ではない |
| **D. 社外・多数** | 認証・認可・入力検証をアプリ側で設計 | 別の覚悟 | 入口で守れないので、全部アプリの責任になる |

**全パターン共通**: Supabase を使うなら RLS。IP 制限は Data API には効きません。

料金とプラン要件は変わります。最終的には一次情報（記事末尾のリンク）で確認してください。

## 7. で、何から始めるか

1. **「誰に見せるか」を1文で書く。** A / B / C / D のどれかを決める。ここが決まらないうちにデプロイしない
2. **A〜C なら、まず Cloudflare Access を検討する。** 無料枠で足りることが多く、アプリ側にログイン機能を作らなくて済む
3. **Supabase を使っているなら、RLS だけは確認する。** 自信がなければ、そこだけ人に見てもらう
4. **D は、A〜C で実績を作ってから。** 最初の一歩にしない

最後に、この記事でいちばん覚えて帰ってほしい一文を繰り返します。

> **画面に鍵をかけても、データのドアは別に開いている。**

vibe coding で作れるものの範囲は、これからも広がります。**作る力が先に手に入って、置く場所の判断だけが残る**——というのが、いまの状況だと思います。その判断は、技術というより「誰に見せるか」という業務の判断です。だとすれば、それを決められるのは作った本人です。
