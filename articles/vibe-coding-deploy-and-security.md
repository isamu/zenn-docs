AI に話しかけるだけでアプリが動くようになりました。ここまでは、もう誰でもできます。

止まるのは次です。**「で、これどこに置けばいいの？」**

調べると Supabase、Vercel、Cloudflare といった名前が出てきます。ただ、この3つは役割が違いますし、**「誰に見せるか」によって選ぶものも設定も変わります**。そして厄介なことに、間違えても画面は普通に動きます。事故は静かに起きます。

この記事では、各社の公式ドキュメントで確認できた事実だけを書きます。とくに「**その機能、どのプランから使えるのか**」まで書きます。無料プランでは使えない機能を前提に設計してしまうのが、最初のつまずきポイントだからです。

先に結論を3つ。

- **「誰に見せるか」を決めないとデプロイ先は決まらない。** 技術の問題ではなく、先に決めるべき仕様です
- **BaaS を使うと、データベースが世界中に公開されます。** Supabase も Firestore も同じです。設計しないと漏れます。この認識がすべての土台です
- **だから、出たら困るデータは、外から触れる場所に置かない。** ルールを正しく書く話の前に、置き場所を分ける話があります
- **そして、そもそも出さないという選択肢がある。** 社内向けなら、手元で動くツールや社内サーバーのほうが強いことがあります

## 1. デプロイ先より先に決めること：誰に見せるか

公開範囲を4つに分けます。この分類がこの記事の背骨です。

| | 見せる相手 | 例 | 難易度 |
|---|---|---|---|
| **A** | 自分だけ | 自分用の集計ツール、議事録整形 | 低 |
| **B** | 社内の複数人 | 部内の申請フォーム、在庫照会 | 中 |
| **C** | 社外の特定の人 | 取引先に見せる見積シミュレータ | 中〜高 |
| **D** | 社外の不特定多数 | 誰でも使える公開サービス | **高** |

A から D に向かって、必要な守りが増えていきます。**そして A〜C と D のあいだには、他より大きな段差があります。** そこは後半で扱います。

まず「自分が作ろうとしているのはどれか」を1文で書いてください。これが決まらないまま「とりあえずデプロイ」をすると、だいたい D のつもりがないのに D になります。

## 2. Vercel と Supabase は役割が違う——ドアは1つではない

ここが最初の、そして一番大きな誤解です。

- **Vercel / Cloudflare Pages** … **画面**を置くところ（ホスティング）
- **Supabase** … **データ**を置くところ（BaaS。データベース＋認証＋ファイル保管）

この2つは別のサービスで、**別のドメインで、別々にインターネットに向いています**。

```
                ┌──────────────────────┐
  ブラウザ ─────→│ Vercel（画面）        │
      │         └──────────────────────┘
      │
      │         ┌──────────────────────┐
      └────────→│ Supabase（データ）    │  ← 別のドア
                └──────────────────────┘
```

矢印が**2本ある**のがポイントです。ブラウザは画面を取りに行き、そのあと**データベースに直接**問い合わせます。途中に Vercel は挟まりません。

昔ながらの構成（Web サーバー → アプリサーバー → データベース）では、データベースはインターネットから見えない場所にいました。外からの入口は1つで、そこを固めればよかった。

**BaaS は、データベースが最初からインターネット側にいます。** これは欠陥ではなく設計です。だからこそブラウザから直接使えて、サーバーを書かずに済む。**Supabase も Firestore も同じ構造**です。ただし前提が変わります。

> **画面に鍵をかけても、データのドアは別に開いている。**

この一文が、以降のすべての土台です。

## 3. 「IP 制限」が効かない、の正体

ここが本題のひとつです。

### 従来型（AWS など）でやっていたこと

社内向けシステムなら、送信元 IP アドレスで絞るのが定番でした。セキュリティグループやロードバランサの設定で「この会社のオフィスと VPN からだけ」と書けば、それ以外は届かない。データベースは VPC の中にいて、そもそも外から触れません。

**「どこから来たか」で守る**——境界防御です。シンプルで、強い。

### PaaS / BaaS ではどうなるか

公式ドキュメントで確認した結果です。

| サービス | IP で絞れるか | 条件 |
|---|---|---|
| **Vercel** | できる（Trusted IPs） | **Enterprise プランのみ** |
| **Cloudflare** | できる（WAF の IP Access Rules） | **全プランで利用可**（国単位のブロックのみ Enterprise） |
| **Supabase** | **部分的にしかできない** | 次項で詳述 |

[Vercel の Trusted IPs](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/trusted-ips) は Enterprise 限定です。つまり Hobby でも Pro でも、IP では絞れません。

[Cloudflare の IP Access Rules](https://developers.cloudflare.com/waf/tools/ip-access-rules/) は「すべてのお客様が利用可能」と明記されています。ここは Cloudflare が明確に強い部分です。

### Supabase の落とし穴——これが一番危ない

Supabase にも [Network Restrictions](https://supabase.com/docs/guides/platform/network-restrictions) という IP 制限機能があります。ダッシュボードから設定できます。

ただしドキュメントにこう書かれています。

> ネットワーク制限は、PostgREST、Storage、Auth といった HTTPS API や、supabase-js などのクライアントライブラリには適用されません。

読み替えます。**制限が効くのは、Postgres への直接接続と pooler だけ**。あなたのアプリが実際に使っている経路——`supabase-js` が叩く Data API——は**制限の対象外**です。

つまりこうなります。

```
IP 制限あり  ✕ ← DB クライアントからの直接接続（psql など）
IP 制限なし  ○ ← supabase-js / REST API ← ★アプリが使うのはこっち
```

**設定画面に「IP 制限: 有効」と表示されているのに、アプリの通り道は開いている。** 「対策した」という記憶だけが残るので、何もしていないより危険とも言えます。

### だから、守り方を変える

境界防御が使えないなら、発想を切り替えます。

> **「どこから来たか」で守るのをやめて、「誰が来たか」で守る。**

これがゼロトラスト、あるいは ID ベースのアクセス制御と呼ばれるものです。IP アドレスではなく、Google アカウントやメールアドレスで入口を判定します。

そして非エンジニアにとって朗報なのは、**こちらのほうが運用が簡単**だということです。「オフィスの固定 IP を情シスに聞く」「在宅の人はどうする」「VPN を通す」といった話が全部消えて、「この人を許可する／外す」だけになります。

## 4. パターン別：具体的にどう置くか

### A. 自分だけが使う

**まず、デプロイしないという選択肢があります。** ローカルで動かせば、そもそもインターネットに出ません。自分用の集計ツールなら、これで十分なことが多い。

スマホからも使いたいなど、どうしても置きたい場合は Cloudflare Access（後述）で自分のアカウントだけを許可するのが手軽です。

注意点はひとつだけ。**Supabase や Firestore を使っているなら、A であってもルールの確認は必要です**（セクション5）。画面を自分しか開かなくても、データのドアは別に開いているからです。

手元で動かす選択肢については、セクション7でもう少し詳しく書きます。

### B. 社内の複数人が使う

ここには2つの道があります。**インターネットに出さない**（社内サーバー、あるいは各自の PC で動くツール）か、**出したうえで入口を守る**か。前者はセクション7で扱うので、ここでは後者を書きます。

出す場合は **[Cloudflare Access](https://www.cloudflare.com/plans/zero-trust-services/) が本命**です。理由は3つあります。

1. **無料枠が 50 ユーザーまで。** 部やチーム単位なら、たいてい収まります
2. **Google Workspace / Microsoft Entra ID / GitHub / メール OTP に対応。** 会社が既に使っている ID をそのまま使えます
3. **ドメイン単位でポリシーが書ける。** 「`@yourcompany.co.jp` のメールアドレスなら通す」という書き方ができるので、人が増えるたびの作業が要りません

アプリの手前に立って、認証されていないアクセスは中に到達すらしません。**アプリ側にログイン機能を作らなくていい**、というのが非エンジニアにとって一番大きい点です。

Vercel を使っていて Pro プランなら、[Password Protection](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/password-protection) という選択肢もあります（**保護するプロジェクトごとに月額課金**、Hobby では使えません）。ただし性質が違います。

| | Cloudflare Access | パスワード保護 |
|---|---|---|
| 誰が入ったか | **分かる**（個人が特定できる） | 分からない |
| 人を外す | その人だけ外せる | **全員のパスワード変更が必要** |
| 共有されたら | 共有できない（本人の ID が要る） | **そのまま入られる** |
| 退職者 | ID 停止で自動的に締め出せる | **手作業で気づかないと入れる** |

パスワード保護は「ちょっと見せる」には便利ですが、**誰がアクセスしたか分からない**のが決定的です。社内システムで「誰が見たか」を答えられないのは、後々つらい。

### C. 社外の特定の人に見せる

意外に思われるかもしれませんが、**ここも Cloudflare Access が相性がいい**です。

メールアドレスを個別に指定して、**ワンタイムパスコード**で認証する方式が使えます。相手にアカウントを作ってもらう必要がありません。「メールアドレスを入力 → 届いた数字を入れる → 入れる」で終わります。取引先に「まずアカウント登録を」と言わずに済むのは、実務上かなり効きます。

やってはいけないのは、**「URL を知っている人だけ」で済ませること**です。これは認証ではありません。

- メールやチャットで転送されたら、そこで終わりです
- **誰がアクセスしたのか記録が残りません**
- 取引先の情シスに説明を求められたときに、説明できません

「推測できない長い URL だから大丈夫」は、鍵をかけていない家のドアを、草むらに隠しているのと同じです。

### D. 社外・不特定多数——ここが本当に難しい

正直に書きます。**非エンジニアが最初に取り組む対象としては、おすすめしません。** 理由を分解します。

**1. 入口で人を選べない。** A〜C は「入れる人を限定する」で解けました。D は**誰でも入れることが要件**なので、この一番強い手が最初から使えません。

**2. 認可をアプリの中に書かなければならない。** 「誰がどのデータを見ていいか」をコードとポリシーで表現する必要があります。ログインまでは作れても、**「A さんのデータを B さんが見られない」を保証するのは別の仕事**です。

**3. 入力をすべて疑う必要がある。** 悪意のある入力が来る前提で作ります。善意のユーザーだけを想定したコードは、ここで破られます。

**4. 止められない。** 社内向けなら「すみません、今日は止めます」で済みます。公開サービスを止めると障害対応になります。**問題が見つかってから直すまでの時間、穴が開いたまま**です。

**5. 個人情報が乗ると法令の話になる。** 技術で閉じなくなります。

D をやるなとは言いません。ただ、**A〜C で価値を出してから D に進む**ほうが、順番として圧倒的に安全です。「社内で毎日使われているツールを、外にも出す」なら、そのときには実績と、直すべき箇所の見当がついています。

## 5. BaaS 最大の罠：DB が世界に公開されている

ここがこの記事でいちばん大事なところです。**vibe coding でいちばん多い事故がここ**です。

そして、これは Supabase に限った話ではありません。**BaaS と呼ばれるものに共通する構造**で、Firestore もまったく同じです。

### key が公開されているのは仕様です

ブラウザで動かす以上、接続に使う key は**誰でも読めます**。開発者ツールを開けば出てきます。バグでも設定ミスでもなく、そういう設計です。

両社とも、公式にそう明言しています。

[Supabase](https://supabase.com/docs/guides/getting-started/api-keys):

> publishable key は公開しても安全です。**RLS が有効になっていれば。**

[Firebase](https://firebase.google.com/docs/projects/api-keys):

> Firebase 用の API キーは、コードやチェックイン済みの設定ファイルに含めて問題ありません。（…）バックエンドリソースへのアクセス制御には使われません。それができるのは Firebase Security Rules だけです。

太字は筆者によるものですが、言っていることは同じです。**key は鍵ではなく、住所です。** 実際に守っているのは別のもの——ルールのほうです。

### 構造は完全に同じ

| | Supabase | Firestore |
|---|---|---|
| ブラウザに出る key | publishable key（旧 anon key） | Firebase API key |
| その key は秘密か | **秘密ではない**（仕様） | **秘密ではない**（公式に明記） |
| 実際に守っているもの | **RLS ポリシー** | **Security Rules** |
| 中身が全部見える状態 | RLS が無効 | `allow read, write: if true`（テストモード） |
| ルールを迂回する鍵 | `service_role` key | Admin SDK（サーバー用ライブラリ） |

Firestore の**テストモード**は要注意です。ドキュメントには、このルールは**本番で絶対に使ってはならない**、誰でもデータベース全体を上書きできる、と書かれています。それでも作成時に選べてしまいますし、その状態でも**アプリは普通に動きます**。動いているかどうかでは気づけません。

そして Firebase のサーバー用ライブラリ（Admin SDK）は、**Security Rules をすべて迂回します**。これも仕様で、信頼できるサーバー側で使う前提だからです。裏を返すと、**この鍵がブラウザ側に渡った時点で、ルールは存在しないのと同じ**になります。Supabase の `service_role` key もまったく同じ性質です。

### つまり、どういうことか

> **ルールを書かなければ、DB の中身は世界中から読める。**

「ログイン画面をつけたから大丈夫」は成り立ちません。ログイン画面は画面の話であって、データのドアには関係がない。セクション2の「矢印が2本ある」図を思い出してください。

- ルールを**有効**にすると、ポリシーを書くまで**一切データが取れなくなります**。これが正しい初期状態です
- ルールが**無効、または全許可**だと、公開されている key で**中身が全部読めます**

### 自分で確かめる方法

怖い話をしたので、確認方法も書きます。**自分のプロジェクトに対して**やってください。

1. ブラウザの開発者ツールで、通信内容から接続先の URL と key を拾う
2. その2つを使って、アプリを経由せずに直接データを取りに行ってみる
3. **ログインしていない状態で中身が返ってきたら、それは世界中の誰にでも返ってきます**

AI に「このテーブルのルールを確認して」と聞くこともできますが、**最終的には実際に叩いて確かめるのが確実**です。設定画面の表示と実際の挙動がずれることは、セクション3の Supabase の IP 制限で見たとおりです。

ルール設計に自信がないなら、**そこだけエンジニアに見てもらう**のが費用対効果として最良です。全部を見てもらう必要はありません。「ルールが有効か」「意図どおりか」の2点です。

## 6. 秘匿情報は外に置かない——境界線を自分で引き直す

ここまでは「ルールを正しく書きましょう」という話でした。ただ、それだけでは一点に寄りかかりすぎです。**ルールを1行間違えたら全部出る**、という構造は変わっていません。

もう一段強い考え方があります。

> **そもそも、出たら困るデータを、外から触れる場所に置かない。**

### テーブルごとに、1つだけ問う

置く前に、テーブルごとにこれを問います。

> **「この中身が、いま全部そのまま流出したら、困るか？」**

- **困らない** → 公開側に置いて、ルールで守る
- **困る** → **置かない。** 内側に置く

判断は「漏れる確率」ではなく「**漏れたときの被害**」でします。確率の見積もりは当たりませんが、被害の大きさは今わかるからです。

外から触れる場所に置いてはいけないものの例です。

- 外部サービスの API キーやシークレット（**これは論外**。ブラウザに渡した時点で公開されています）
- 他人の個人情報のマスタ
- 原価、利益率、値引きの上限
- 人事・給与
- 監査ログそのもの

### 「内側」とは何か

内側とは、**ブラウザから直接叩けない場所**のことです。具体的には、自分が書いたサーバー側のコードだけが触れる場所。

```
【公開側】ブラウザから直接触れる
   ブラウザ ──→ BaaS ──→ 公開してよいデータ
                （ルールで守る）

【内側】ブラウザからは触れない
   ブラウザ ──→ サーバー関数 ──→ 秘匿データ
                （ここで権限判定）  （外から直接は叩けない）
```

サーバー関数として使えるものは、Supabase Edge Functions、Vercel Functions、Cloudflare Workers あたりです。

ポイントは、**`service_role` key や Admin SDK を使っていいのはここだけ**ということです。ここに置けば、ブラウザには渡りません。

やっているのは、BaaS でいったん消えた三層構造（画面 → アプリ → DB）を、**必要なところだけ自分で作り直す**ことです。全部をサーバー経由にする必要はありません。**秘匿情報だけ**。どこに線を引くかが、設計判断そのものです。

### AI は、放っておくと公開側に書く

vibe coding に固有の注意点を1つ。

**AI に「◯◯できるようにして」と頼むと、いちばん短いコードが返ってきます。そして最短経路は、たいていブラウザから直接 DB を触る形です。** サーバー関数を1枚挟むのは手数が増えるので、頼まれなければやりません。

なので、指示のしかたが変わります。

- ✕「取引先ごとの原価を表示する画面を作って」
- ○「原価はブラウザから直接 DB を読まないで。**サーバー側の関数を経由して、必要な値だけ返す**形にして」

**境界線をどこに引くかは、AI ではなく人間が決める仕事です。** 何が秘匿情報なのかを知っているのは、作っている本人だけだからです。

## 7. そもそもインターネットに出さない——社内サーバーと手元で動くツール

ここまで散々「外に出すときの守り方」を書いてきましたが、いちばん強い手は別にあります。

> **出さない。**

社内向け（パターン A・B）なら、これが現実的な選択肢です。

### 選択肢は2つ

**1. 社内にサーバーを立てる。** 社内ネットワークの中だけで動かせば、インターネットからは届きません。境界を自分で作る必要がなく、**会社のネットワークが既に境界**です。セクション3で悩んだ IP 制限の話も要りません。そもそも届かないので。

**2. 手元の PC で動くツールにする。** こちらのほうが手軽です。データはその PC から出ません。サーバーもドメインも認証基盤も要りません。

2つ目は vibe coding との相性がとてもいい。Web アプリを作ってデプロイして守るより、**デスクトップで動くツールにしてしまうほうが、やることが少ない**ことがよくあります。筆者が作っている [MulmoClaude](https://github.com/receptron/mulmoclaude) や MulmoTerminal も、この形です。

### 何がなくなるか

| | Web にデプロイ | 手元で動かす |
|---|---|---|
| 認証 | 必要 | **不要**（OS のログインが済んでいる） |
| アクセス制御 | 必要 | **不要**（その PC の持ち主だけ） |
| DB のルール設計 | 必要 | **不要**（外から届かない） |
| 秘匿情報の置き場所 | 悩む | **手元でいい** |
| 配布 | URL を渡すだけ | インストールが必要 |
| 更新 | 即時、全員に反映 | **各自に更新してもらう必要がある** |

**トレードオフは配布と更新に集約されます。** 使う人が数人なら、こちらのほうが総コストは低いことが多い。

そして、**人数が増えたら、あるいはデータを共有する必要が出たら、そのときに Web へ移す**。その頃には実際の使われ方がわかっているので、何を守るべきかの判断もつきます。順番として、こちらのほうが安全です。

### 「手元で動かす」は妥協ではない

念のため書いておくと、これは逃げではありません。**扱うものが秘匿情報なら、手元で動かすほうが正しい設計**です。守りやすいところに置く、というのはセキュリティの基本です。

「せっかく作ったから Web で公開したい」という気持ちと、「このデータは外に出したくない」という要件は、切り離して考えてください。

## 8. まとめ表

| 公開範囲 | 現実的な構成 | 一番の落とし穴 |
|---|---|---|
| **A. 自分だけ** | 手元で動かす／ローカル実行 | 出す必要がないのに、出してしまう |
| **B. 社内・複数人** | 手元で動くツール、社内サーバー、Cloudflare Access | パスワード共有で済ませ、誰が入ったか分からなくなる |
| **C. 社外・特定の人** | Cloudflare Access（メール指定＋ワンタイムパスコード） | 「URL を知っている人だけ」は認証ではない |
| **D. 社外・多数** | 認証・認可・入力検証をアプリ側で設計 | 入口で守れないので、全部アプリの責任になる |

全パターン共通で、3つ。

1. **BaaS を使うなら、ルール（RLS / Security Rules）は必須。** 書かなければ世界中から読めます
2. **秘匿情報は、外から触れる場所に置かない。** ルールの正しさに全部を賭けない
3. **IP 制限は BaaS の Data API には効かない。** 設定画面の表示を信じない

料金とプラン要件は変わります。最終的には一次情報（記事末尾のリンク）で確認してください。

## 9. で、何から始めるか

1. **「誰に見せるか」を1文で書く。** A / B / C / D のどれかを決める。ここが決まらないうちにデプロイしない
2. **出さずに済むなら、出さない。** 社内向けなら、手元で動くツールや社内サーバーを先に検討する
3. **出すなら、A〜C は Cloudflare Access を検討する。** 無料枠で足りることが多く、アプリ側にログイン機能を作らなくて済む
4. **テーブルごとに「全部流出したら困るか」を問う。** 困るものは、外から触れる場所に置かない
5. **BaaS を使っているなら、ルールが有効かを実際に叩いて確認する。** 自信がなければ、そこだけ人に見てもらう
6. **D は、A〜C で実績を作ってから。** 最初の一歩にしない

最後に、この記事で覚えて帰ってほしいのは2行だけです。

> **画面に鍵をかけても、データのドアは別に開いている。**
>
> **出たら困るものは、そもそも外に置かない。**

vibe coding で作れるものの範囲は、これからも広がります。**作る力が先に手に入って、置く場所の判断だけが残る**——というのが、いまの状況だと思います。その判断は、技術というより「誰に見せるか」「何が外に出てはいけないか」という業務の判断です。だとすれば、それを決められるのは作った本人しかいません。
