AI に話しかけるだけでアプリが動くようになりました。ここまでは、もう誰でもできます。

止まるのは次です。**「で、これどこに置けばいいの？」**

調べると Supabase、Vercel、Cloudflare といった名前が出てきます。ただ、この3つは役割が違いますし、**「誰に見せるか」によって選ぶものも設定も変わります**。そして厄介なことに、間違えても画面は普通に動きます。事故は静かに起きます。

先に、この記事の主題を書いておきます。

> **vibe coding の成果物を、安易にクラウドに置かないでください。**

クラウドに置くというのは、多くの場合**データベースをインターネットに向けて公開する**ということです。Supabase も Firestore も、そういう設計になっています。ルールを1行書き忘れれば、中身は世界中から読めます。そして実際に、そうやって漏れています（セクション5）。

しかも多くの場合、**そこまでする必要がありません。** 手元で動かす、社内ネットワークで済ませる、入口と出口を既存のツールに任せる——先に試すべき段が3つあります（セクション10）。

クラウドを使うな、という話ではありません。**足りないとわかってから使え**、という話です。

そのうえで、各社の公式ドキュメントで確認できた事実だけを書きます。とくに「**その機能、どのプランから使えるのか**」まで書きます。無料プランでは使えない機能を前提に設計してしまうのが、最初のつまずきポイントだからです。

結論を先に並べます。

- **「誰に見せるか」を決めないとデプロイ先は決まらない。** 技術の問題ではなく、先に決めるべき仕様です
- **BaaS を使うと、データベースが世界中に公開されます。** Supabase も Firestore も同じです。設計しないと漏れます。この認識がすべての土台です
- **DB だけではありません。** ファイルストレージ、そして Slack や S3 でのファイル受け渡しにも、別の穴があります
- **だから、出たら困るデータは、外から触れる場所に置かない。** ルールを正しく書く話の前に、置き場所を分ける話があります
- **そして、そもそも出さないという選択肢がある。** 社内向けなら、手元で動くツールや社内サーバーのほうが強いことがあります
- **クラウドは最後の段です。** 手元 → 社内 → 既存ツールに任せる、を試してから

## 1. デプロイ先より先に決めること：誰に見せるか

公開範囲を4つに分けます。この分類がこの記事の背骨です。

| | 見せる相手 | 例 | 難易度 |
|---|---|---|---|
| **A** | 自分だけ | 自分用の集計ツール、議事録整形 | 低 |
| **B** | 社内の複数人 | 部内の申請フォーム、在庫照会 | 中 |
| **C** | 社外の特定の人 | 取引先に見せる見積シミュレータ | 中〜高 |
| **D** | 社外の不特定多数 | 誰でも使える公開サービス | **高** |

A から D に向かって、必要な守りが増えていきます。**そして A〜C と D のあいだには、他より大きな段差があります。** そこは後半で扱います。

まず「自分が作ろうとしているのはどれか」を1文で書いてください。これが決まらないまま「とりあえずデプロイ」をすると、だいたい D のつもりがないのに D になります。

## 2. Vercel と Supabase は役割が違う——ドアは1つではない

ここが最初の、そして一番大きな誤解です。

- **Vercel / Cloudflare Pages** … **画面**を置くところ（ホスティング）
- **Supabase** … **データ**を置くところ（BaaS。データベース＋認証＋ファイル保管）

この2つは別のサービスで、**別のドメインで、別々にインターネットに向いています**。

```
                ┌──────────────────────┐
  ブラウザ ─────→│ Vercel（画面）        │
      │         └──────────────────────┘
      │
      │         ┌──────────────────────┐
      └────────→│ Supabase（データ）    │  ← 別のドア
                └──────────────────────┘
```

矢印が**2本ある**のがポイントです。ブラウザは画面を取りに行き、そのあと**データベースに直接**問い合わせます。途中に Vercel は挟まりません。

昔ながらの構成（Web サーバー → アプリサーバー → データベース）では、データベースはインターネットから見えない場所にいました。外からの入口は1つで、そこを固めればよかった。

**BaaS は、データベースが最初からインターネット側にいます。** これは欠陥ではなく設計です。だからこそブラウザから直接使えて、サーバーを書かずに済む。**Supabase も Firestore も同じ構造**です。ただし前提が変わります。

> **画面に鍵をかけても、データのドアは別に開いている。**

この一文が、以降のすべての土台です。

## 3. 「IP 制限」が効かない、の正体

ここが本題のひとつです。

### 従来型（AWS など）でやっていたこと

社内向けシステムなら、送信元 IP アドレスで絞るのが定番でした。セキュリティグループやロードバランサの設定で「この会社のオフィスと VPN からだけ」と書けば、それ以外は届かない。データベースは VPC の中にいて、そもそも外から触れません。

**「どこから来たか」で守る**——境界防御です。シンプルで、強い。

### PaaS / BaaS ではどうなるか

公式ドキュメントで確認した結果です。

| サービス | IP で絞れるか | 条件 |
|---|---|---|
| **Vercel** | できる（Trusted IPs） | **Enterprise プランのみ** |
| **Cloudflare** | できる（WAF の IP Access Rules） | **全プランで利用可**（国単位のブロックのみ Enterprise） |
| **Supabase** | **部分的にしかできない** | 次項で詳述 |

[Vercel の Trusted IPs](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/trusted-ips) は Enterprise 限定です。つまり Hobby でも Pro でも、IP では絞れません。

[Cloudflare の IP Access Rules](https://developers.cloudflare.com/waf/tools/ip-access-rules/) は「すべてのお客様が利用可能」と明記されています。ここは Cloudflare が明確に強い部分です。

### Supabase の落とし穴——これが一番危ない

Supabase にも [Network Restrictions](https://supabase.com/docs/guides/platform/network-restrictions) という IP 制限機能があります。ダッシュボードから設定できます。

ただしドキュメントにこう書かれています。

> ネットワーク制限は、PostgREST、Storage、Auth といった HTTPS API や、supabase-js などのクライアントライブラリには適用されません。

読み替えます。**制限が効くのは、Postgres への直接接続と pooler だけ**。あなたのアプリが実際に使っている経路——`supabase-js` が叩く Data API——は**制限の対象外**です。

つまりこうなります。

```
IP 制限あり  ✕ ← DB クライアントからの直接接続（psql など）
IP 制限なし  ○ ← supabase-js / REST API ← ★アプリが使うのはこっち
```

**設定画面に「IP 制限: 有効」と表示されているのに、アプリの通り道は開いている。** 「対策した」という記憶だけが残るので、何もしていないより危険とも言えます。

### だから、守り方を変える

境界防御が使えないなら、発想を切り替えます。

> **「どこから来たか」で守るのをやめて、「誰が来たか」で守る。**

これがゼロトラスト、あるいは ID ベースのアクセス制御と呼ばれるものです。IP アドレスではなく、Google アカウントやメールアドレスで入口を判定します。

そして非エンジニアにとって朗報なのは、**こちらのほうが運用が簡単**だということです。「オフィスの固定 IP を情シスに聞く」「在宅の人はどうする」「VPN を通す」といった話が全部消えて、「この人を許可する／外す」だけになります。

## 4. パターン別：具体的にどう置くか

### A. 自分だけが使う

**まず、デプロイしないという選択肢があります。** ローカルで動かせば、そもそもインターネットに出ません。自分用の集計ツールなら、これで十分なことが多い。

スマホからも使いたいなど、どうしても置きたい場合は Cloudflare Access（後述）で自分のアカウントだけを許可するのが手軽です。

注意点はひとつだけ。**Supabase や Firestore を使っているなら、A であってもルールの確認は必要です**（セクション5）。画面を自分しか開かなくても、データのドアは別に開いているからです。

手元で動かす選択肢については、セクション9でもう少し詳しく書きます。

### B. 社内の複数人が使う

ここには2つの道があります。**インターネットに出さない**（社内サーバー、あるいは各自の PC で動くツール）か、**出したうえで入口を守る**か。前者はセクション9で扱うので、ここでは後者を書きます。

出す場合は **[Cloudflare Access](https://www.cloudflare.com/plans/zero-trust-services/) が本命**です。理由は3つあります。

1. **無料枠が 50 ユーザーまで。** 部やチーム単位なら、たいてい収まります
2. **Google Workspace / Microsoft Entra ID / GitHub / メール OTP に対応。** 会社が既に使っている ID をそのまま使えます
3. **ドメイン単位でポリシーが書ける。** 「`@yourcompany.co.jp` のメールアドレスなら通す」という書き方ができるので、人が増えるたびの作業が要りません

アプリの手前に立って、認証されていないアクセスは中に到達すらしません。**アプリ側にログイン機能を作らなくていい**、というのが非エンジニアにとって一番大きい点です。

Vercel を使っていて Pro プランなら、[Password Protection](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/password-protection) という選択肢もあります（**保護するプロジェクトごとに月額課金**、Hobby では使えません）。ただし性質が違います。

| | Cloudflare Access | パスワード保護 |
|---|---|---|
| 誰が入ったか | **分かる**（個人が特定できる） | 分からない |
| 人を外す | その人だけ外せる | **全員のパスワード変更が必要** |
| 共有されたら | 共有できない（本人の ID が要る） | **そのまま入られる** |
| 退職者 | ID 停止で自動的に締め出せる | **手作業で気づかないと入れる** |

パスワード保護は「ちょっと見せる」には便利ですが、**誰がアクセスしたか分からない**のが決定的です。社内システムで「誰が見たか」を答えられないのは、後々つらい。

### C. 社外の特定の人に見せる

意外に思われるかもしれませんが、**ここも Cloudflare Access が相性がいい**です。

メールアドレスを個別に指定して、**ワンタイムパスコード**で認証する方式が使えます。相手にアカウントを作ってもらう必要がありません。「メールアドレスを入力 → 届いた数字を入れる → 入れる」で終わります。取引先に「まずアカウント登録を」と言わずに済むのは、実務上かなり効きます。

やってはいけないのは、**「URL を知っている人だけ」で済ませること**です。これは認証ではありません。

- メールやチャットで転送されたら、そこで終わりです
- **誰がアクセスしたのか記録が残りません**
- 取引先の情シスに説明を求められたときに、説明できません

「推測できない長い URL だから大丈夫」は、鍵をかけていない家のドアを、草むらに隠しているのと同じです。

### D. 社外・不特定多数——ここが本当に難しい

正直に書きます。**非エンジニアが最初に取り組む対象としては、おすすめしません。** 理由を分解します。

**1. 入口で人を選べない。** A〜C は「入れる人を限定する」で解けました。D は**誰でも入れることが要件**なので、この一番強い手が最初から使えません。

**2. 認可をアプリの中に書かなければならない。** 「誰がどのデータを見ていいか」をコードとポリシーで表現する必要があります。ログインまでは作れても、**「A さんのデータを B さんが見られない」を保証するのは別の仕事**です。

**3. 入力をすべて疑う必要がある。** 悪意のある入力が来る前提で作ります。善意のユーザーだけを想定したコードは、ここで破られます。

**4. 止められない。** 社内向けなら「すみません、今日は止めます」で済みます。公開サービスを止めると障害対応になります。**問題が見つかってから直すまでの時間、穴が開いたまま**です。

**5. 個人情報が乗ると法令の話になる。** 技術で閉じなくなります。

D をやるなとは言いません。ただ、**A〜C で価値を出してから D に進む**ほうが、順番として圧倒的に安全です。「社内で毎日使われているツールを、外にも出す」なら、そのときには実績と、直すべき箇所の見当がついています。

## 5. BaaS 最大の罠：DB が世界に公開されている

ここがこの記事でいちばん大事なところです。**vibe coding でいちばん多い事故がここ**です。

そして、これは Supabase に限った話ではありません。**BaaS と呼ばれるものに共通する構造**で、Firestore もまったく同じです。

### key が公開されているのは仕様です

ブラウザで動かす以上、接続に使う key は**誰でも読めます**。開発者ツールを開けば出てきます。バグでも設定ミスでもなく、そういう設計です。

両社とも、公式にそう明言しています。

[Supabase](https://supabase.com/docs/guides/getting-started/api-keys):

> publishable key は公開しても安全です。**RLS が有効になっていれば。**

[Firebase](https://firebase.google.com/docs/projects/api-keys):

> Firebase 用の API キーは、コードやチェックイン済みの設定ファイルに含めて問題ありません。（…）バックエンドリソースへのアクセス制御には使われません。それができるのは Firebase Security Rules だけです。

太字は筆者によるものですが、言っていることは同じです。**key は鍵ではなく、住所です。** 実際に守っているのは別のもの——ルールのほうです。

### 構造は完全に同じ

| | Supabase | Firestore |
|---|---|---|
| ブラウザに出る key | publishable key（旧 anon key） | Firebase API key |
| その key は秘密か | **秘密ではない**（仕様） | **秘密ではない**（公式に明記） |
| 実際に守っているもの | **RLS ポリシー** | **Security Rules** |
| 中身が全部見える状態 | RLS が無効 | `allow read, write: if true`（テストモード） |
| ルールを迂回する鍵 | `service_role` key | Admin SDK（サーバー用ライブラリ） |

Firestore の**テストモード**は要注意です。ドキュメントには、このルールは**本番で絶対に使ってはならない**、誰でもデータベース全体を上書きできる、と書かれています。それでも作成時に選べてしまいますし、その状態でも**アプリは普通に動きます**。動いているかどうかでは気づけません。

そして Firebase のサーバー用ライブラリ（Admin SDK）は、**Security Rules をすべて迂回します**。これも仕様で、信頼できるサーバー側で使う前提だからです。裏を返すと、**この鍵がブラウザ側に渡った時点で、ルールは存在しないのと同じ**になります。Supabase の `service_role` key もまったく同じ性質です。

### つまり、どういうことか

> **ルールを書かなければ、DB の中身は世界中から読める。**

「ログイン画面をつけたから大丈夫」は成り立ちません。ログイン画面は画面の話であって、データのドアには関係がない。セクション2の「矢印が2本ある」図を思い出してください。

- ルールを**有効**にすると、ポリシーを書くまで**一切データが取れなくなります**。これが正しい初期状態です
- ルールが**無効、または全許可**だと、公開されている key で**中身が全部読めます**

### これは理論上の話ではありません

実際に、何度も起きています。

2024年3月に公開された調査では、**500万のドメインをスキャンして、916 のサイトでセキュリティルールが無効、または誤って設定されている**ことが見つかりました。そこから取り出せる状態にあったのは、メールアドレス・氏名・パスワード・電話番号・請求情報を含む**1億件を超えるユーザーレコード**。しかもパスワードのほとんどは**平文**でした（[BleepingComputer](https://www.bleepingcomputer.com/news/security/misconfigured-firebase-instances-leaked-19-million-plaintext-passwords/)、[SecurityWeek](https://www.securityweek.com/misconfigured-firebase-instances-expose-125-million-user-records/)、[GitGuardian](https://blog.gitguardian.com/misconfigurations-in-google-firebase-lead-to-over-19-8-million-leaked-secrets/)）。

**これらは攻撃を受けたわけではありません。ルールが書かれていなかっただけ**です。誰でも、普通にアクセスすれば読めました。

vibe coding で作られたアプリを対象にしたスキャンサービスの報告でも、検出される重大な問題は「ルールが有効になっていない」に集中しているとされています（こちらは提供元の集計なので、傾向として読んでください）。

つまり、この記事に書いているのは**起こりうる話ではなく、いま継続的に起きている話**です。

### 自分で確かめる方法

怖い話をしたので、確認方法も書きます。**自分のプロジェクトに対して**やってください。

1. ブラウザの開発者ツールで、通信内容から接続先の URL と key を拾う
2. その2つを使って、アプリを経由せずに直接データを取りに行ってみる
3. **ログインしていない状態で中身が返ってきたら、それは世界中の誰にでも返ってきます**

AI に「このテーブルのルールを確認して」と聞くこともできますが、**最終的には実際に叩いて確かめるのが確実**です。設定画面の表示と実際の挙動がずれることは、セクション3の Supabase の IP 制限で見たとおりです。

ルール設計に自信がないなら、**そこだけエンジニアに見てもらう**のが費用対効果として最良です。全部を見てもらう必要はありません。「ルールが有効か」「意図どおりか」の2点です。

## 6. DB だけではない——ファイルと、受け渡し経路

データが置かれるのは DB だけではありません。**ファイル**もありますし、**Slack や S3 でのやり取り**もあります。それぞれ別の穴があります。

### ファイルストレージ：公開にした瞬間、ルールが消える

Supabase Storage も Firebase Storage も S3 も、構造は同じです。[Supabase のドキュメント](https://supabase.com/docs/guides/storage/buckets/fundamentals)にこう書かれています。

> バケットを Public に指定すると、ファイルの取得と配信については**アクセス制御が迂回されます**。つまり、URL を知っている人なら誰でもファイルにアクセスできます。

バケットは既定では非公開です。非公開のまま使う方法は2つあります。

1. **認証トークンを付けてダウンロードする**（ストレージ側のポリシーで判定される）
2. **署名付き URL を作る** — 期限つきの URL を発行して渡す

S3 も歴史的にまったく同じ問題を抱えていました。公開バケットからの流出があまりに多かったため、[2023年4月から、新規バケットは Block Public Access が既定で有効](https://aws.amazon.com/about-aws/whats-new/2023/04/amazon-s3-security-best-practices-buckets-default/)になり、ACL も既定で無効になっています。**既定を変えるしかなかったほど事故が多かった**、ということです。

### ファイル特有の落とし穴が4つ

**1. 粒度がない。** DB は行単位でルールを書けます。ファイルは**渡すか渡さないかの二択**です。1枚の Excel に全社員の給与が入っていたら、そのファイルへの許可は全員分の給与への許可になります。**ファイルの中を分けられるのは、ファイルを作る時点だけ**です。

**2. 中身以外のものも入っている。** 写真の位置情報、Office ファイルの作成者名・変更履歴・非表示のシートや行。**画面で見えているものと、ファイルに入っているものは違います。**

**3. 署名なしの URL は、じわじわ広がる。** ブラウザの履歴、リファラ、チャットへの転送、検索エンジンのクロール。しかも**期限がないので、いつまでも有効**です。署名付き URL に期限を付ける理由はここにあります。

**4. 消したつもりが残る。** CDN のキャッシュ、バケットのバージョニング。Supabase のドキュメントにも、**署名付き URL の期限と CDN のキャッシュ期間は独立していて、URL の中のトークンが切れたあともキャッシュされた応答が配信されうる**と書かれています。

### Slack や S3 での「受け渡し」は、置き場所ではなく配布

ここが考え方の切り替えどころです。

ファイルを Slack に投げる、S3 に置いて URL を送る——これらは**置き場所を決める行為ではなく、複製を配る行為**です。

- Slack に上げたファイルは、**そのチャンネルを見られる人全員**が取れます。外部共有やゲストがいれば、その人たちも
- Slack には「**リンクを知っている人なら誰でも**」という公開リンクの機能があります。**これは認証ではありません**
- そして決定的なのは、**あとから消しても、すでにダウンロードされたものは戻らない**ことです

なので、原則はこうなります。

> **秘匿情報は「渡す」のではなく、「見に来てもらう」。**

ファイルを添付して送るのではなく、**アクセス制御された場所に置いて、そこへのアクセス権を渡す**。セクション4の C（社外の特定の人）で書いた Cloudflare Access の後ろにファイルを置けば、これが成立します。**誰がいつ見たかも残ります。**

### AI に頼むと、公開バケットになりがち

セクション8と同じ話が、ここにもあります。

- 「画像をアップロードできるようにして」→ **公開バケットを作られがち**です。表示するのが一番簡単だからです
- 「Slack に通知して」→ **Webhook の URL がブラウザ側に埋め込まれがち**です。そうなると、その URL を拾った誰もが、あなたのチャンネルに好きなだけ投稿できます

どちらも**普通に動きます**。だから動作確認では気づけません。

## 7. 逆方向：社外の人からファイルを受け取る

セクション6は「出す」方向の話でした。**受け取る**方向になると、リスクの種類が変わります。

### まず、OAuth の一番多い誤解

「Google ログインをつけたから安全」——これは成り立ちません。

- **認証**（あなたが誰か）と **認可**（入ってよいか）は別物です
- Google アカウントは世界中に何十億とあります。**「Google でログインできた人」は「入れてよい人」ではありません**
- 必要なのは、ログインの後ろに置く**許可リスト**です。「このメールアドレス」「このドメイン」だけを通す、という指定

そして vibe coding で「ログイン機能をつけて」と頼むと、**ログインは付きますが、許可リストは付きません**。誰でもログインできて、誰でも中に入れる画面ができあがります。**普通に動く**ので、動作確認では気づけません。

セクション4-B の Cloudflare Access が効くのは、まさにここです。**認証と許可リストが最初からセット**なので、アプリ側で間違えようがありません。

### 構成パターンは3つ

**パターン1: 認証の後ろにアップロード画面を置く（いちばん簡単）**

```
相手 ──[認証（Access）]──→ アップロード画面 ──→ 内側の保管先
```

- 相手は Google / Microsoft アカウント、またはメールのワンタイムパスコードで入る
- 通った人だけが画面に到達します。**アプリは「認証済み」を前提に書ける**
- 誰がいつアップロードしたかがログに残る

**非エンジニアにはこれが本命**です。アプリ側に認証を実装しなくて済みます。

**パターン2: 署名付きアップロード URL を発行する**

ファイル本体がサーバーを経由しないので、大きいファイルに強い構成です。

- Supabase なら [`createSignedUploadUrl`](https://supabase.com/docs/reference/javascript/storage-from-createsigneduploadurl)、S3 なら [presigned POST](https://docs.aws.amazon.com/AmazonS3/latest/API/sigv4-HTTPPOSTConstructPolicy.html)
- **発行するのはサーバー側**です。ここで「この人に」「この置き場所に」「この期限で」を決めます
- S3 の POST ポリシーなら、**ファイルサイズの上限や置き場所も署名の中に固定できます**

ただし AWS のドキュメントに、重要な注意書きがあります。

> S3 の署名付き URL は公開リソースであり、**ユーザーを認証しません**。有効な署名付き URL を持っている人なら誰でも、対象のリソースにアクセスできます。

つまり、**署名付き URL は「鍵」であって「門番」ではありません。** 誰にその鍵を渡すかを決めるのが認証（OAuth など）の仕事です。この2つは、セットで初めて成立します。

**パターン3: 既存の SaaS を使う（正直、これが最適なことも多い）**

Google Drive、Box、SharePoint には「特定の人だけがアップロードできるフォルダ」の機能があります。

- 相手の会社が**すでに使っている**可能性が高い
- 相手の情シスの承認が**通りやすい**
- 自分で作らないので、**壊れない**

「せっかく作れるから作る」の前に、ここを検討する価値はあります。**受け取るだけなら、作らないのが一番安全**です。

### 受け取る側に固有のリスク

出す方向にはなかった問題が出てきます。**外部の人に、自分の領域へデータを書き込ませる**からです。

**1. 受け取ったファイルを、そのまま配信しない。** これが最大の落とし穴です。アップロードされたファイルを公開バケットに置いて URL を返すと、**攻撃者が任意の HTML や JavaScript を、あなたのドメインで配れる**ことになります。**受信用の置き場所と、配信用の置き場所は分けてください。**

**2. ファイル名を信用しない。** 相手が付けた名前をそのまま保存先のパスに使うと、意図しない場所に書き込まれることがあります。サーバー側で ID を振り直すのが安全です。

**3. サイズと回数に上限を付ける。** 上限がなければ、置き場所を埋められます。S3 の POST ポリシーなら、署名の中に上限を入れられます。

**4. 中身の安全性は、自前では担保できません。** 受け取ったファイルにマルウェアが含まれる可能性は残ります。**業務で不特定多数から受け取るなら、そこは素直に SaaS に任せる**判断が要ります。

### まとめると

> **OAuth は「誰に鍵を渡すか」を決める。署名付き URL は「その鍵で何ができるか」を決める。**

片方だけでは成立しません。そして非エンジニアにとっては、**認証を Cloudflare Access のような仕組みに任せて、アプリは認証済みを前提に書く**のが、いちばん間違えにくい形です。

## 8. 秘匿情報は外に置かない——境界線を自分で引き直す

ここまでは「ルールを正しく書きましょう」という話でした。ただ、それだけでは一点に寄りかかりすぎです。**ルールを1行間違えたら全部出る**、という構造は変わっていません。

もう一段強い考え方があります。

> **そもそも、出たら困るデータを、外から触れる場所に置かない。**

### テーブルごとに、1つだけ問う

置く前に、テーブルごとにこれを問います。

> **「この中身が、いま全部そのまま流出したら、困るか？」**

- **困らない** → 公開側に置いて、ルールで守る
- **困る** → **置かない。** 内側に置く

判断は「漏れる確率」ではなく「**漏れたときの被害**」でします。確率の見積もりは当たりませんが、被害の大きさは今わかるからです。

外から触れる場所に置いてはいけないものの例です。

- 外部サービスの API キーやシークレット（**これは論外**。ブラウザに渡した時点で公開されています）
- 他人の個人情報のマスタ
- 原価、利益率、値引きの上限
- 人事・給与
- 監査ログそのもの

### 「内側」とは何か

内側とは、**ブラウザから直接叩けない場所**のことです。具体的には、自分が書いたサーバー側のコードだけが触れる場所。

```
【公開側】ブラウザから直接触れる
   ブラウザ ──→ BaaS ──→ 公開してよいデータ
                （ルールで守る）

【内側】ブラウザからは触れない
   ブラウザ ──→ サーバー関数 ──→ 秘匿データ
                （ここで権限判定）  （外から直接は叩けない）
```

サーバー関数として使えるものは、Supabase Edge Functions、Vercel Functions、Cloudflare Workers あたりです。

ポイントは、**`service_role` key や Admin SDK を使っていいのはここだけ**ということです。ここに置けば、ブラウザには渡りません。

やっているのは、BaaS でいったん消えた三層構造（画面 → アプリ → DB）を、**必要なところだけ自分で作り直す**ことです。全部をサーバー経由にする必要はありません。**秘匿情報だけ**。どこに線を引くかが、設計判断そのものです。

### AI は、放っておくと公開側に書く

vibe coding に固有の注意点を1つ。

**AI に「◯◯できるようにして」と頼むと、いちばん短いコードが返ってきます。そして最短経路は、たいていブラウザから直接 DB を触る形です。** サーバー関数を1枚挟むのは手数が増えるので、頼まれなければやりません。

なので、指示のしかたが変わります。

- ✕「取引先ごとの原価を表示する画面を作って」
- ○「原価はブラウザから直接 DB を読まないで。**サーバー側の関数を経由して、必要な値だけ返す**形にして」

**境界線をどこに引くかは、AI ではなく人間が決める仕事です。** 何が秘匿情報なのかを知っているのは、作っている本人だけだからです。

## 9. そもそもインターネットに出さない——社内サーバーと手元で動くツール

ここまで散々「外に出すときの守り方」を書いてきましたが、いちばん強い手は別にあります。

> **出さない。**

社内向け（パターン A・B）なら、これが現実的な選択肢です。

### 選択肢は2つ

**1. 社内にサーバーを立てる。** 社内ネットワークの中だけで動かせば、インターネットからは届きません。境界を自分で作る必要がなく、**会社のネットワークが既に境界**です。セクション3で悩んだ IP 制限の話も要りません。そもそも届かないので。

**2. 手元の PC で動くツールにする。** こちらのほうが手軽です。データはその PC から出ません。サーバーもドメインも認証基盤も要りません。

2つ目は vibe coding との相性がとてもいい。Web アプリを作ってデプロイして守るより、**デスクトップで動くツールにしてしまうほうが、やることが少ない**ことがよくあります。筆者が作っている [MulmoClaude](https://github.com/receptron/mulmoclaude) や MulmoTerminal も、この形です。

### 具体的に、どう立てるのか

「社内にサーバーを立てる」と言われても困ると思うので、選択肢を並べます。

| やり方 | 向いている規模 | 常時起動 | 手間 |
|---|---|---|---|
| 各自の PC で動かす | 1〜数人 | 不要 | 最小 |
| 常時起動の1台を社内に置く | チーム〜部 | 必要 | 中 |
| 社内の NAS の Docker 機能を使う | 既に NAS がある場合 | すでに動いている | 中 |
| 社内サーバー ＋ Cloudflare Tunnel | 在宅の人がいる | 必要 | 中 |

**Linux か Windows か。** どちらでもできます。

- **Linux（Ubuntu など）** … 情報が多く、常時起動に向きます。古い PC の再利用で十分動きます
- **Windows** … **できます。** Node.js は Windows でそのまま動きますし、**WSL2** を入れれば Ubuntu の環境がそのまま使えます

ただし Windows を常時起動のサーバーにするなら、**自動更新にともなう再起動**には気をつけてください。「金曜には動いていたのに月曜には止まっている」の定番の原因です。落ちても自動で起き上がる仕組み（pm2 など）を先に入れておくと、だいぶ楽になります。

**Apache や nginx は要るのか。** **たいていは要りません。**

vibe coding で出てくるものは Node.js（Express）や Python が多く、**それ自体がサーバーとして動きます**。起動して、社内の IP とポートを配れば、それで届きます。

Apache や nginx が必要になるのは、1つのドメインで複数のアプリを出し分けたいとき、HTTPS を終端したいとき、静的ファイルを大量に配りたいときです。**最初から入れると、うまく動かないときの切り分け先が1つ増えるだけ**です。要るとわかってから足してください。

**在宅の人がいる場合。** 社内サーバーの弱点は「社外から届かない」ことです。長所でもありますが、在宅勤務があると困ります。

そこで使えるのが **[Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/)** です。サーバー側から Cloudflare に向けて**外向きの接続を張る**方式なので、**ルーターのポートを開ける必要がありません**。ファイアウォールは外向きの通信を通すのが普通なので、そこに乗る形です。

これをセクション4-B の Cloudflare Access と組み合わせると、こうなります。

- サーバーはインターネットに直接晒されない
- それでいて、認証された社員だけが社外からも使える
- HTTPS も Cloudflare 側で終端される

**社内サーバーの弱点を埋めつつ、公開もしない。** 社内向けとしては、かなり良い落とし所だと思います。

**そして、一番のコストは機械ではなく人です。**

常時起動のサーバーを置くと、そこから**運用が始まります**。電源が落ちたら誰が起こすのか。OS の更新は誰がやるのか。バックアップは。その人が異動したらどうするのか。

**引き受ける人がいないなら、各自の PC で動かすほうが正しい判断です。** 「サーバーを立てられるか」ではなく、「面倒を見続けられるか」で決めてください。

あわせて、**社内ネットワークに機器を置いたりポートを開けたりするのは、たいてい社内ルールの対象です。** 先に情シスに聞いてください。後から止められると、作ったもの自体が無駄になります。

### 何がなくなるか

| | Web にデプロイ | 手元で動かす |
|---|---|---|
| 認証 | 必要 | **不要**（OS のログインが済んでいる） |
| アクセス制御 | 必要 | **不要**（その PC の持ち主だけ） |
| DB のルール設計 | 必要 | **不要**（外から届かない） |
| 秘匿情報の置き場所 | 悩む | **手元でいい** |
| 配布 | URL を渡すだけ | インストールが必要 |
| 更新 | 即時、全員に反映 | **各自に更新してもらう必要がある** |

**トレードオフは配布と更新に集約されます。** 使う人が数人なら、こちらのほうが総コストは低いことが多い。

そして、**人数が増えたら、あるいはデータを共有する必要が出たら、そのときに Web へ移す**。その頃には実際の使われ方がわかっているので、何を守るべきかの判断もつきます。順番として、こちらのほうが安全です。

### 手元で動かすなら、データの持ち方も選び直せる

そもそも BaaS を使う理由は、**ブラウザから直接データを読み書きしたいから**です。手元や社内で動かすなら、その理由が消えます。だから選択肢が一気に広がります。

| データの持ち方 | 向いている場面 | 注意点 |
|---|---|---|
| **JSON / CSV ファイル** | 件数が少なく、単純な一覧 | 同時に書くと壊れる。基本は1人用 |
| **SQLite** | 件数が増える、検索や集計がある | ファイル1つで完結する。書き込みは順番待ちになる |
| **手元／社内の PostgreSQL** | 複数人が同時に書く | 立てる手間と運用が発生する |

**JSON や CSV で足りることは、思ったより多い**です。「DB を使わないと本格的じゃない」ということはありません。むしろ **CSV なら Excel で開けます**——業務ツールでは、これは実際に強い利点です。渡すのも、中身を確認するのも簡単になります。

境目がはっきりしているのは**同時書き込み**です。JSON ファイルを2人が同時に書くと、**後から書いたほうが前の内容を消します**。しかも静かに消えるので気づけません。ここが SQLite や PostgreSQL に移る分岐点です。

そして重要なのは、**PostgreSQL を使うこと自体は、外に出すこととは関係がない**ということです。手元や社内に立てた PostgreSQL は、インターネットからは見えません。BaaS と同じ Postgres でも、**ドアの数が違う**。セクション2の図でいえば、**矢印が1本に戻る**ということです。

### 最初から決めなくていい

もうひとつ。**この選択は、後から変えられます。**

JSON で始めて、件数が増えたら SQLite に移し、同時に使う人が増えたら PostgreSQL に移す。**データが少ないうちの移行は簡単です。** 最初から BaaS を選んでおく必要はありません。

順番として、こうなります。

| 共有の必要 | データの置き場所 |
|---|---|
| 要らない（自分だけ） | 手元の JSON / CSV / SQLite |
| 社内の数人が見る | 社内サーバーの SQLite か PostgreSQL |
| 社内で同時に書く | PostgreSQL |
| 社外の人と共有する | ここで初めて、外に出す話になる |

**データを共有する必要が出た瞬間に、この記事の前半（セクション2〜8）に戻ってきます。** 逆に言えば、**共有が要らないうちは、あの話は全部不要**です。ルールも、境界線も、署名付き URL も。

「どのデータベースを使うか」は、実は技術の選択ではありません。**誰とデータを共有するか**の選択です。そしてそれは、セクション1で決めた「誰に見せるか」と同じ問いです。

### 「手元で動かす」は妥協ではない

念のため書いておくと、これは逃げではありません。**扱うものが秘匿情報なら、手元で動かすほうが正しい設計**です。守りやすいところに置く、というのはセキュリティの基本です。

「せっかく作ったから Web で公開したい」という気持ちと、「このデータは外に出したくない」という要件は、切り離して考えてください。

## 10. 段階の上げ方——下の段で足りないとわかってから、次へ

ここまでの内容を、実際に進む順番として並べ直します。**大事なのは、下の段で足りないとわかってから次に上がること**です。最初から一番上に行く必要はありません。

### 第1段：手元の PC で、JSON でプロトタイプを作る

まずここから。データは JSON、動かすのは自分の PC。

**この段階では、この記事に書いたことは何も要りません。** 認証もルールも境界線も不要です。作ることだけに集中できます。

ひとつだけ先を見て決めておくとよいのは、**Web サーバーの形で作っておく**ことです。ブラウザで開く形にしておけば、次の段に上がるのが楽になります。

### 第2段：同じ社内ネットワークの、他の PC から使う

Web サーバーの形にしてあれば、**設定を少し変えるだけで、同じネットワークの他の PC から使えます**。社内ネットワークの中だけなので、インターネットからは届きません。

**第1段からの追加コストは、ほぼゼロ**です。何人かに使ってもらって、本当に役に立つのかを確かめる段階として、ここは効率がいい。

**ただし、ノート PC を社外に持ち出すときは注意してください。**

「同じネットワークの他の機器から見える」設定のまま、カフェや空港の Wi-Fi につなぐと、**その場にいる他の人からも見えます**。社内では正しかった設定が、外では正しくありません。

- 自分だけで使うときは、**自分の PC からしかつながらない設定**に戻す（`localhost` だけで待ち受けるか、`0.0.0.0` で待ち受けるかの違いです）
- 持ち出す PC で常時起動しない
- できれば、常時動かす用途は据え置きの機械に移す

vibe coding で出てくる起動設定は、**「同じネットワークから見える」側になっていることが多い**です。一度は確認しておく価値があります。

### 第3段：入口と出口だけ、既存のツールに任せる

ここが飛ばされがちで、そして**いちばん効く段**です。

**社外の人とのやり取りが必要になったとき、いきなり「Web アプリを公開する」に飛ばないでください。** 公開するから認証が要るのであって、**公開しなければ認証は要りません**。

やり方は単純です。**入口と出口を、すでにある道具に任せる。**

```
相手 ──[メール / Slack / 既存のフォーム]──→ （認証も配送も、そのサービスの仕事）
                                                     │
                                              手元・社内で処理
                                                     │
      ←──[メール / Slack で結果を返す]───────────────┘
```

- **受け取りだけ外でやる。** 既存のフォームサービスや共有フォルダで受け取り、処理は手元でする
- **メールで受け取って、メールで返す。** 相手にとっては、いつもどおりの操作です
- **Slack に結果を返す。** 社内向けなら、画面を作るより読まれます

**この形なら、自分が公開するものはゼロです。** 守るべき入口がないので、この記事の前半に書いたことは、ほとんど要りません。認証も、アクセス制御も、ルールも。

そして相手にとっても、**新しい画面の使い方を覚えなくていい**。これは、使ってもらえるかどうかに直結します。

**「インターフェースを自作しない」**——これは手抜きではなく、設計の判断です。

### 第4段：BaaS やクラウドを使う

ここまでで足りないとわかって、初めて外に出します。必要になるのは、たとえばこういう場合です。

- 相手がその場で操作する画面が要る
- 常時つながっていないと成立しない
- 使う人数が増えて、メールや Slack では回らない
- 社外の不特定多数に開く

この段まで来たら、**セクション2から8に書いたことが、全部必要になります。** ルール、境界線、秘匿情報の置き場所、署名付き URL、認証と許可リスト。

逆に言えば、**第1段から第3段のあいだは、そのほとんどが不要**でした。

### 段を飛ばさない

| 段 | やること | 必要な守り |
|---|---|---|
| **1** | 手元の PC、JSON でプロト | ほぼ不要 |
| **2** | 社内ネットワークの他の PC から | 持ち出しに注意 |
| **3** | 入口と出口を既存ツールに任せる | 公開するものがない |
| **4** | BaaS / クラウド | この記事の全部 |

**上に行くほどできることは増えますが、守るものも増えます。** そして守り漏れの結果は、セクション5で見たとおりです。

いちばんもったいないのは、**第3段で足りたのに、第4段から始めてしまうこと**です。作るのに時間がかかり、守るのにも時間がかかり、そのうえ使われないかもしれない。

## 11. まとめ表

| 公開範囲 | 現実的な構成 | 一番の落とし穴 |
|---|---|---|
| **A. 自分だけ** | 手元で動かす／ローカル実行 | 出す必要がないのに、出してしまう |
| **B. 社内・複数人** | 手元で動くツール、社内サーバー、Cloudflare Access | パスワード共有で済ませ、誰が入ったか分からなくなる |
| **C. 社外・特定の人** | Cloudflare Access（メール指定＋ワンタイムパスコード） | 「URL を知っている人だけ」は認証ではない |
| **D. 社外・多数** | 認証・認可・入力検証をアプリ側で設計 | 入口で守れないので、全部アプリの責任になる |

全パターン共通で、4つ。

1. **BaaS を使うなら、ルール（RLS / Security Rules）は必須。** 書かなければ世界中から読めます
2. **ファイルのバケットを公開にしない。** 渡すなら、期限付きの署名 URL で
3. **秘匿情報は、外から触れる場所に置かない。** ルールの正しさに全部を賭けない
4. **IP 制限は BaaS の Data API には効かない。** 設定画面の表示を信じない

料金とプラン要件は変わります。最終的には一次情報（記事末尾のリンク）で確認してください。

## 12. で、何から始めるか

1. **「誰に見せるか」を1文で書く。** A / B / C / D のどれかを決める。ここが決まらないうちにデプロイしない
2. **セクション10の段を、下から順に試す。** 手元でプロト → 社内ネットワーク → 入口と出口を既存ツールに任せる → それでも足りなければクラウド。データも、共有が要らないうちは JSON / CSV / SQLite で足ります
3. **出すなら、A〜C は Cloudflare Access を検討する。** 無料枠で足りることが多く、アプリ側にログイン機能を作らなくて済む
4. **テーブルごとに「全部流出したら困るか」を問う。** 困るものは、外から触れる場所に置かない
5. **BaaS を使っているなら、ルールが有効かを実際に叩いて確認する。** 自信がなければ、そこだけ人に見てもらう
6. **ファイルを扱うなら、バケットが公開になっていないかを見る。** 渡すときは添付ではなく、期限付きのアクセス権で
7. **受け取る場合は、ログインの後ろに許可リストがあるかを確認する。** 「ログインできる」と「入ってよい」は別です
8. **D は、A〜C で実績を作ってから。** 最初の一歩にしない

最後に、この記事で覚えて帰ってほしいのは3行だけです。

> **画面に鍵をかけても、データのドアは別に開いている。**
>
> **出たら困るものは、そもそも外に置かない。**
>
> **そしてクラウドは、下の段で足りないとわかってから。**

vibe coding で作れるものの範囲は、これからも広がります。**作る力が先に手に入って、置く場所の判断だけが残る**——というのが、いまの状況だと思います。

そして「とりあえずクラウドに上げる」は、いちばん簡単に見えて、**いちばん守るものが多い選択**です。簡単なのは上げるところまでで、その先がずっと続きます。

置き場所の判断は、技術というより「誰に見せるか」「何が外に出てはいけないか」という業務の判断です。だとすれば、それを決められるのは作った本人しかいません。
