AI に話しかけるだけで、アプリが作れるようになりました。

問題は次です。**「で、これ、どこに置けばいいの？」**

先に結論から書きます。

> **安易にクラウドに置かないでください。**

クラウドに置くというのは、**データベースをインターネットに公開する**ということです。設定をひとつ間違えると、中身が世界中から読めます。実際に、そうやって漏れています。

そして多くの場合、**そこまでする必要がありません。** 手元で動かす、社内で動かす、メールや Slack で済ませる——先に試せる方法があります。

クラウドを使うな、という話ではありません。**足りないとわかってから使え**、という話です。

以下、Supabase / Firebase / Vercel / Cloudflare の公式ドキュメントで確認した事実をもとに、**誰に見せるかで何が変わるか**を整理します。どの機能がどのプランから使えるのかも、あわせて書きます。

---

## 1. デプロイ先より先に決めること：誰に見せるか

公開範囲を4つに分けます。この分類がこの記事の背骨です。

| | 見せる相手 | 例 | 難易度 |
|---|---|---|---|
| **A** | 自分だけ | 自分用の集計ツール、議事録整形 | 低 |
| **B** | 社内の複数人 | 部内の申請フォーム、在庫照会 | 中 |
| **C** | 社外の特定の人 | 取引先に見せる見積シミュレータ | 中〜高 |
| **D** | 社外の不特定多数 | 誰でも使える公開サービス | **高** |

A から D に向かって、必要な守りが増えていきます。**そして A〜C と D のあいだには、他より大きな段差があります。** そこは後半で扱います。

まず「自分が作ろうとしているのはどれか」を1文で書いてください。これが決まらないまま「とりあえずデプロイ」をすると、だいたい D のつもりがないのに D になります。

## 2. ネットに置くと、何が見えるのか

ここが最初の、そして一番大きな誤解です。

- **Vercel / Cloudflare Pages** … **画面**を置くところ（ホスティング）
- **Supabase** … **データ**を置くところ（データベース、ログイン、ファイル保管がセットになったサービス。こういうものを **BaaS** と呼びます。Firebase / Firestore も同じ仲間です）

この2つは別のサービスで、**別のドメインで、別々にインターネットに向いています**。

```
                ┌──────────────────────┐
  ブラウザ ─────→│ Vercel（画面）        │
      │         └──────────────────────┘
      │
      │         ┌──────────────────────┐
      └────────→│ Supabase（データ）    │  ← 別のドア
                └──────────────────────┘
```

矢印が**2本ある**のがポイントです。ブラウザは画面を取りに行き、そのあと**データベースに直接**問い合わせます。途中に Vercel は挟まりません。

昔ながらの構成（Web サーバー → アプリサーバー → データベース）では、データベースはインターネットから見えない場所にいました。外からの入口は1つで、そこを固めればよかった。

**BaaS は、データベースが最初からインターネット側にいます。** これは欠陥ではなく設計です。だからこそブラウザから直接使えて、サーバーを書かずに済む。**Supabase も Firestore も同じ構造**です。ただし前提が変わります。

> **画面に鍵をかけても、データのドアは別に開いている。**

この一文が、以降のすべての土台です。

### そして、作ったものの中身は読まれます

ネットに置くと、もうひとつ起きることがあります。

**画面を動かしているコードは、誰でも読めます。** ブラウザの「ソースを表示」で出てきます。隠す方法はありません。そういう作りです。

つまり、こういうことが分かります。

- どのサービスを使っているか（Supabase なのか Firebase なのか）
- データがどこにあるか
- どんな仕組みで動いているか

ここまでは、普通のことです。問題はこの先です。

**そこに鍵を書いてしまうと、鍵も一緒に公開されます。**

ただし、鍵には2種類あります。ここを混ぜると混乱するので、先に分けます。

### 公開してよい鍵と、いけない鍵

| | 例 | 公開してよいか |
|---|---|---|
| **ブラウザ用に作られた鍵** | Supabase の publishable key、Firebase の API キー、Google マップの API キー | **公開前提。書いてよい** |
| **それ以外の鍵** | OpenAI などの API キー、決済サービスの秘密鍵、Supabase の `service_role` key、Firebase の Admin SDK | **絶対に書かない** |

上の段は、**もともとブラウザで使うために作られた鍵**です。隠しても意味がありませんし、隠す必要もありません。守っているのは鍵ではなく、セクション5で書くルールのほうです。

下の段は、書いた瞬間に世界中から読めます。そして読まれると、**他人があなたの請求でそのサービスを使えます。**

### 「ブラウザ用の鍵」でも、油断はできません

ここが盲点です。**ブラウザ用の鍵にも、制限をかけておく必要があります。**

分かりやすいのが Google の鍵（Firebase、マップ）です。[公式ドキュメント](https://firebase.google.com/docs/projects/api-keys)にこう書かれています。

> 制限をかけていないキーは、**そのプロジェクトで有効になっているどの API にも使えます**。

つまり、マップ用に作ったつもりの鍵で、**あとから有効にした別のサービスまで呼べてしまう**ことがあります。うっかり有料のサービスを有効にすると、**その請求も自分に来ます**。

Firebase が自動で作る鍵は、最初から Firebase 関連だけに制限されています。ただし、こうも書かれています。

> 今後ほかの API を有効にした場合は、**そのキーの制限リストにも追加する必要があります**。

そして [Google は、こう勧めています](https://developers.google.com/maps/api-security-best-practices)。

- **使う場所ごとに、別の鍵を作る**
- 鍵ごとに、**どのサイトから使えるか**と、**どのサービスに使えるか**を制限する
- **ブラウザ用とサーバー用で、同じ鍵を使わない**

**「公開してよい鍵」は、「何をしてもいい鍵」ではありません。** 公開してよいのは、制限がかかっているからです。

### これは、実際よく起きます

AI に「◯◯の API を使って要約して」と頼むと、**ブラウザから直接その API を呼ぶコード**が返ってくることがあります。いちばん短いコードだからです。

そうすると、API キーはブラウザの中に入ります。**つまり、公開されます。**

しかも**普通に動きます**。動作確認では気づけません。

### 「環境変数に入れたから大丈夫」ではありません

よくある誤解です。環境変数に入れても、**それがブラウザに配られる設定なら、結果は同じ**です。

見分け方があります。名前の頭を見てください。

- `VITE_` で始まる
- `NEXT_PUBLIC_` で始まる

これらは「**ブラウザに出す**」という意味の名前です。ここに API キーを入れたら、公開したのと同じです。

### どうすればいいか

2つだけです。

1. **ブラウザ用でない鍵は、ブラウザに渡さない。** 置き場所は、セクション8で書く「内側」——自分のサーバー側です。ブラウザは自分のサーバーに頼み、サーバーが API を呼ぶ
2. **ブラウザ用の鍵にも、制限をかける。** どのサイトから使えるか、どのサービスに使えるか

そしてもっと簡単な答えもあります。**ネットに置かなければ、そもそも読まれません**（セクション10）。

## 3. 「特定の場所からだけ」は、もう効きません

昔からある守り方に、「**会社のオフィスからだけアクセスできるようにする**」というものがあります。IP アドレス（ネット上の住所）で絞る方法です。

これが、クラウドサービスではあまり使えません。

### 使えるところ、使えないところ

公式ドキュメントで確認した結果です。

| サービス | 場所で絞れるか |
|---|---|
| **Vercel** | できる。ただし[**いちばん高いプランだけ**](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/trusted-ips) |
| **Cloudflare** | [**できる。無料プランでも**](https://developers.cloudflare.com/waf/tools/ip-access-rules/) |
| **Supabase** | 設定はできる。**でも効かない入口がある**（次で説明します） |

### Supabase の落とし穴——ここが一番危ない

Supabase にも、場所で絞る設定があります。画面から設定できます。

ところが[公式ドキュメント](https://supabase.com/docs/guides/platform/network-restrictions)に、こう書かれています。

> ネットワーク制限は、PostgREST、Storage、Auth といった HTTPS API や、supabase-js などのクライアントライブラリには適用されません。

名前がいろいろ並んでいて分かりにくいのですが、**要するに、アプリが普段使っている入口には効かない**ということです。

```
制限がかかる     ← 管理ツールから直接つなぐとき
制限がかからない  ← アプリが使う入口  ← ★こっちが本番
```

**設定画面に「制限：有効」と出ているのに、アプリの通り道は開いている。** 「対策した」という記憶だけが残るので、何もしていないより危ないとも言えます。

### だから、守り方を変えます

場所で守れないなら、こうします。

> **「どこから来たか」で守るのをやめて、「誰が来たか」で守る。**

IP アドレスではなく、**Google アカウントやメールアドレス**で入口を判定するということです。

そして非エンジニアには、**こちらのほうがずっと簡単**です。「オフィスの固定 IP を情シスに聞く」「在宅の人はどうする」「VPN を通す」——こういう話が全部消えて、**「この人を許可する／外す」だけ**になります。

## 4. パターン別：具体的にどう置くか

### A. 自分だけが使う

**まず、デプロイしないという選択肢があります。** ローカルで動かせば、そもそもインターネットに出ません。自分用の集計ツールなら、これで十分なことが多い。

スマホからも使いたいなど、どうしても外に置きたい場合は、認証（後述）の後ろに置いて自分だけを許可します。

注意点はひとつだけ。**Supabase や Firestore を使っているなら、A であってもルールの確認は必要です**（セクション5）。画面を自分しか開かなくても、データのドアは別に開いているからです。

手元で動かす選択肢については、セクション9でもう少し詳しく書きます。

### B. 社内の複数人が使う

ここには2つの道があります。**インターネットに出さない**（社内サーバー、あるいは各自の PC で動くツール）か、**出したうえで入口を守る**か。前者はセクション9で扱うので、ここでは後者を書きます。

出す場合、よく候補に挙がるのが **[Cloudflare Access](https://www.cloudflare.com/plans/zero-trust-services/)** です。仕組みとしての利点は3つ。

1. **無料枠が 50 ユーザーまで。** 部やチーム単位なら、たいてい収まります
2. **Google アカウントや会社のアカウント、メールに届く数字で入れる。** 会社がすでに使っている ID をそのまま使えます
3. **「この会社のメールアドレスなら通す」と書ける。** 人が増えるたびの作業が要りません

いちばん大きいのは、**アプリ側にログイン機能を作らなくていい**ことです。アプリの手前で止めてくれるので、認証されていないアクセスは中に届きません。

**ただし、前提が1つあります。**

**独自ドメインを、Cloudflare の DNS 管理下に置く必要があります。**

- すでにドメインを Cloudflare で管理しているなら、**設定を足すだけ**です
- そうでないなら、まず**ドメインの引っ越し**から。ここが最初の壁になります

実際に使った人からは、こういう声もあります。

- 管理画面が分かりづらい。画面が更新されて、ネット上の解説と一致しないことがある
- **設定を間違えても、エラーが出ません。**「メールが届かない」という症状だけが出ます

「無料だし簡単そう」で始めると、ここで止まります。**先にドメインの状況を確認してから**検討してください。ドメインがないなら、セクション9（そもそも出さない）やセクション6（既存のサービスを使う）のほうが近道です。

Vercel を使っていて Pro プランなら、[Password Protection](https://vercel.com/docs/deployment-protection/methods-to-protect-deployments/password-protection) という選択肢もあります（**保護するプロジェクトごとに月額課金**、Hobby では使えません）。ただし性質が違います。

| | Cloudflare Access | パスワード保護 |
|---|---|---|
| 誰が入ったか | **分かる**（個人が特定できる） | 分からない |
| 人を外す | その人だけ外せる | **全員のパスワード変更が必要** |
| 共有されたら | 共有できない（本人の ID が要る） | **そのまま入られる** |
| 退職者 | ID 停止で自動的に締め出せる | **手作業で気づかないと入れる** |

パスワード保護は「ちょっと見せる」には便利ですが、**誰がアクセスしたか分からない**のが決定的です。社内システムで「誰が見たか」を答えられないのは、後々つらい。

### C. 社外の特定の人に見せる

**まずは、セクション6で書いた既存の共有サービスで足りないかを考えてください。** 相手がすでに使っているものを使うのが、いちばん確実です。

それで足りない（相手に画面を操作してもらう必要がある、など）なら、**ここも Cloudflare Access の仕組みが向いています**。ただしセクション4-B のとおり、ドメインの準備は要ります。

メールアドレスを個別に指定して、**ワンタイムパスコード**で認証する方式が使えます。相手にアカウントを作ってもらう必要がありません。「メールアドレスを入力 → 届いた数字を入れる → 入れる」で終わります。取引先に「まずアカウント登録を」と言わずに済むのは、実務上かなり効きます。

やってはいけないのは、**「URL を知っている人だけ」で済ませること**です。これは認証ではありません。

- メールやチャットで転送されたら、そこで終わりです
- **誰がアクセスしたのか記録が残りません**
- 取引先の情シスに説明を求められたときに、説明できません

「推測できない長い URL だから大丈夫」は、鍵をかけていない家のドアを、草むらに隠しているのと同じです。

### D. 社外・不特定多数——ここが本当に難しい

正直に書きます。**非エンジニアが最初に取り組む対象としては、おすすめしません。** 理由を分解します。

**1. 入口で人を選べない。** A〜C は「入れる人を限定する」で解けました。D は**誰でも入れることが要件**なので、この一番強い手が最初から使えません。

**2. 認可をアプリの中に書かなければならない。** 「誰がどのデータを見ていいか」をコードとポリシーで表現する必要があります。ログインまでは作れても、**「A さんのデータを B さんが見られない」を保証するのは別の仕事**です。

**3. 入力をすべて疑う必要がある。** 悪意のある入力が来る前提で作ります。善意のユーザーだけを想定したコードは、ここで破られます。

**4. 止められない。** 社内向けなら「すみません、今日は止めます」で済みます。公開サービスを止めると障害対応になります。**問題が見つかってから直すまでの時間、穴が開いたまま**です。

**5. 個人情報が乗ると法令の話になる。** 技術で閉じなくなります。

D をやるなとは言いません。ただ、**A〜C で価値を出してから D に進む**ほうが、順番として圧倒的に安全です。「社内で毎日使われているツールを、外にも出す」なら、そのときには実績と、直すべき箇所の見当がついています。

## 5. いちばん危ないところ：データベースが世界に公開されている

ここがこの記事でいちばん大事なところです。**vibe coding でいちばん多い事故がここ**です。

そして、これは Supabase に限った話ではありません。**この種のサービスに共通する作り**で、Firestore もまったく同じです。

### 画面に作っていない機能でも、データは取れます

ここが、いちばん誤解されるところです。

**「その機能を画面に作っていないから大丈夫」は、まったく成り立ちません。**

画面とデータベースは、別のドアだからです（セクション2）。データベースには、画面が使っているかどうかに関係なく、**入っているものが全部入っています**。

だから、設定が甘いとこうなります。

- 画面に「他の人のデータを見る」機能はない → **でも全員分が読めます**
- 管理者用の画面は作っていない → **でも管理用のデータが読めます**
- 画面には10件しか出していない → **でも全部取れます**
- 削除ボタンは付けていない → **でも消せます**（書き込みの設定も甘ければ）
- まだ公開していない下書き → **読めます**

**画面は、鍵ではありません。** 見た目を決めているだけです。

つまり、**データベースに入れた時点で、その中身は「設定次第で世界中から読めるもの」になります。** Supabase でも Firestore でも同じです。

ここは本当に気をつけてください。**設定をひとつ間違えるだけで、入れたデータが全部出ます。**

### key が公開されているのは仕様です

ブラウザで動かす以上、接続に使う key は**誰でも読めます**。開発者ツールを開けば出てきます。バグでも設定ミスでもなく、そういう設計です。

両社とも、公式にそう明言しています。

[Supabase](https://supabase.com/docs/guides/getting-started/api-keys):

> publishable key は公開しても安全です。**RLS が有効になっていれば。**

[Firebase](https://firebase.google.com/docs/projects/api-keys):

> Firebase 用の API キーは、コードやチェックイン済みの設定ファイルに含めて問題ありません。（…）バックエンドリソースへのアクセス制御には使われません。それができるのは Firebase Security Rules だけです。

太字は筆者によるものですが、言っていることは同じです。**key は鍵ではなく、住所です。** 実際に守っているのは別のもの——ルールのほうです。

### 構造は完全に同じ

| | Supabase | Firestore |
|---|---|---|
| ブラウザに出る key | publishable key（旧 anon key） | Firebase API key |
| その key は秘密か | **秘密ではない**（仕様） | **秘密ではない**（公式に明記） |
| 実際に守っているもの | **RLS ポリシー** | **Security Rules** |
| 中身が全部見える状態 | RLS が無効 | `allow read, write: if true`（テストモード） |
| ルールを迂回する鍵 | `service_role` key | Admin SDK（サーバー用ライブラリ） |

Firestore の**テストモード**は要注意です。ドキュメントには、このルールは**本番で絶対に使ってはならない**、誰でもデータベース全体を上書きできる、と書かれています。それでも作成時に選べてしまいますし、その状態でも**アプリは普通に動きます**。動いているかどうかでは気づけません。

そして Firebase のサーバー用ライブラリ（Admin SDK）は、**Security Rules をすべて迂回します**。これも仕様で、信頼できるサーバー側で使う前提だからです。裏を返すと、**この鍵がブラウザ側に渡った時点で、ルールは存在しないのと同じ**になります。Supabase の `service_role` key もまったく同じ性質です。

### つまり、どういうことか

> **ルールを書かなければ、DB の中身は世界中から読める。**

「ログイン画面をつけたから大丈夫」は成り立ちません。ログイン画面は画面の話であって、データのドアには関係がない。セクション2の「矢印が2本ある」図を思い出してください。

- ルールを**有効**にすると、ポリシーを書くまで**一切データが取れなくなります**。これが正しい初期状態です
- ルールが**無効、または全許可**だと、公開されている key で**中身が全部読めます**

### これは理論上の話ではありません

実際に、何度も起きています。

2024年3月に公開された調査では、**500万のドメインをスキャンして、916 のサイトでセキュリティルールが無効、または誤って設定されている**ことが見つかりました。そこから取り出せる状態にあったのは、メールアドレス・氏名・パスワード・電話番号・請求情報を含む**1億件を超えるユーザーレコード**。しかもパスワードのほとんどは**平文**でした（[BleepingComputer](https://www.bleepingcomputer.com/news/security/misconfigured-firebase-instances-leaked-19-million-plaintext-passwords/)、[SecurityWeek](https://www.securityweek.com/misconfigured-firebase-instances-expose-125-million-user-records/)、[GitGuardian](https://blog.gitguardian.com/misconfigurations-in-google-firebase-lead-to-over-19-8-million-leaked-secrets/)）。

**これらは攻撃を受けたわけではありません。ルールが書かれていなかっただけ**です。誰でも、普通にアクセスすれば読めました。

vibe coding で作られたアプリを対象にしたスキャンサービスの報告でも、検出される重大な問題は「ルールが有効になっていない」に集中しているとされています（こちらは提供元の集計なので、傾向として読んでください）。

つまり、この記事に書いているのは**起こりうる話ではなく、いま継続的に起きている話**です。

### 自分で確かめる方法

怖い話をしたので、確認方法も書きます。**自分のプロジェクトに対して**やってください。

1. ブラウザの開発者ツールで、通信内容から接続先の URL と key を拾う
2. その2つを使って、アプリを経由せずに直接データを取りに行ってみる
3. **ログインしていない状態で中身が返ってきたら、それは世界中の誰にでも返ってきます**

AI に「このテーブルのルールを確認して」と聞くこともできますが、**最終的には実際に叩いて確かめるのが確実**です。設定画面の表示と実際の挙動がずれることは、セクション3の Supabase の IP 制限で見たとおりです。

ルール設計に自信がないなら、**そこだけエンジニアに見てもらう**のが費用対効果として最良です。全部を見てもらう必要はありません。「ルールが有効か」「意図どおりか」の2点です。

## 6. ファイルの受け渡しは、どうすればいいか

データが入るのは、データベースだけではありません。**ファイル**もあります。写真、Excel、PDF。ここにも別の落とし穴があります。

### 先に、おすすめを書きます

> **ファイルを「送る」のをやめて、「置いた場所を見てもらう」形にする。**

そして置く場所は、**すでに会社で使っているもの**を使うのがいちばん安全です。

| やりたいこと | おすすめ |
|---|---|
| 社内の人に渡す | いま使っているもの（共有フォルダ、Google Drive、SharePoint、Box、Slack の非公開チャンネル） |
| 社外の特定の人に渡す | 同じものの「この人だけ」共有。または認証（セクション4の C）の後ろに置く |
| 社外の人から受け取る | 相手の会社も使っている共有サービス（セクション7） |
| 自分で作る | **できれば避ける。** 作るなら、この先を読んでください |

理由は単純です。**自分で作らなければ、壊れません。** ファイルの受け渡しは、すでに完成した道具がたくさんあります。vibe coding で作るべきなのは、その先の「処理」のほうです。

### 自分で作るなら、4つだけ

**1. 置き場所を「公開」にしない**

Supabase にも Firebase にも S3 にも、ファイルの置き場所があります。そしてどれにも「**公開**」という設定があります。

公開にすると、**URL を知っている人なら誰でもファイルを取れます**。ログインは要りません。

代わりに使うのが「**期限つきの URL**」です。「この人に、3日間だけ」という形で発行できて、期限が切れれば使えなくなります。

ちなみに S3 は、公開設定による事故があまりに多かったため、[**新しく作る置き場所は最初から公開できない設定に変わりました**](https://aws.amazon.com/about-aws/whats-new/2023/04/amazon-s3-security-best-practices-buckets-default/)。それくらい、よくある間違いだということです。

**2. 期限のない URL は、じわじわ広がる**

ブラウザの履歴、チャットの転送、検索エンジン。いろいろな経路で広がります。しかも**いつまでも使えます**。期限をつける理由は、ここにあります。

**3. ファイルは「中を分けられない」**

データベースなら「この行はこの人に」と細かく決められます。ファイルは**渡すか渡さないかの二択**です。

1枚の Excel に全社員の給与が入っていたら、そのファイルを渡すことは、**全員分の給与を渡すこと**です。分けられるのは、ファイルを作るときだけ。

**4. 見えていないものが入っている**

写真には撮影した場所、Office のファイルには作成者名・変更履歴・隠した行やシートが残ります。**画面で見えているものと、ファイルの中身は違います。**

### Slack やメールで送るのは、「配る」ことです

ここは考え方の話です。

ファイルを Slack に投げる、メールに添付する。これは**置き場所を決めているのではなく、コピーを配っている**のです。

- Slack に上げたファイルは、**そのチャンネルを見られる人が全員取れます**
- Slack には「**リンクを知っていれば誰でも**」という共有機能もあります。これは鍵がかかっていない状態です
- そして、**あとから消しても、すでに手元に落とした人からは消えません**

だから、最初のおすすめに戻ります。

> **秘匿情報は「送る」のではなく、「見に来てもらう」。**

見に来てもらう形なら、**あとから止められます**し、**誰が見たかも分かります**。

### AI に頼むと、公開設定になりがち

「画像をアップロードできるようにして」と頼むと、**公開の置き場所を作られがち**です。表示するのがいちばん簡単だからです。

「Slack に通知して」と頼むと、**通知用の URL が画面のコードに埋まりがち**です。そうなると、それを見つけた人が、あなたのチャンネルに好きなだけ投稿できます。

どちらも**普通に動きます**。だから、動作確認では気づけません。

## 7. 逆に、社外の人からファイルを受け取るには

セクション6は「渡す」話でした。**受け取る**ほうは、気をつける点が変わります。

### 先に、おすすめ

> **相手の会社も使っている共有サービス（Google Drive、Box、SharePoint など）を使う。**

「特定の人だけがアップロードできるフォルダ」は、どのサービスにもあります。**相手がすでに使っている可能性が高く、相手の情シスの承認も通りやすい。** そして自分で作らないので、壊れません。

それでも自分で作るなら、この先を読んでください。

### 「Google ログインをつけたから安全」ではありません

ここが、いちばん多い誤解です。

**ログインできること**と、**入っていいこと**は、別のことです。

Google アカウントは世界中に何十億とあります。「Google でログインできた人」は「入れてよい人」ではありません。**ログインをつけただけでは、誰でも入れます。**

必要なのは、ログインの後ろに置く**名簿**です。「このメールアドレスの人だけ」「この会社の人だけ」と指定する。

そして AI に「ログイン機能をつけて」と頼むと、**ログインは付きますが、名簿は付きません**。誰でもログインできて、誰でも中に入れる画面ができあがります。**普通に動く**ので、動作確認では気づけません。

セクション4-B の Cloudflare Access が効くのは、まさにここです。**ログインと名簿が最初からセット**なので、間違えようがありません。

### いちばん簡単な作り方

**認証の後ろに、アップロード画面を置く。** これだけです。

```
相手 ──[ログイン＋名簿チェック]──→ アップロード画面 ──→ 保管場所
```

- 相手は Google アカウントか、メールに届く数字で入ります
- 通った人だけが画面にたどり着きます。**アプリ側にログイン機能を作らなくていい**
- 誰がいつ上げたかも残ります

大きいファイルを扱うなど、もっと作り込む場合は「**期限つきのアップロード用の URL**」という仕組みもあります（Supabase にも S3 にもあります）。ただし注意が1つ。AWS のドキュメントにこう書かれています。

> 署名付き URL は公開リソースであり、**ユーザーを認証しません**。

**URL は「鍵」であって、「門番」ではありません。** その鍵を誰に渡すかは、やはりログインで決める必要があります。

### 受け取るときに気をつけること、4つ

**1. 受け取ったファイルを、そのまま人に見せない。** これが最大の落とし穴です。送られてきたファイルを公開の置き場所に入れて URL を配ると、**悪意のある人が、好きなプログラムをあなたのサイトの一部として動かせます**。**受け取る場所と、見せる場所は分けてください。**

**2. 相手がつけたファイル名を、そのまま使わない。** 意図しない場所に書き込まれることがあります。こちらで名前を付け直すのが安全です。

**3. サイズと回数に上限をつける。** 上限がないと、置き場所を埋められます。

**4. ウイルスのチェックは、自分ではできません。** 不特定多数から受け取るなら、そこは素直に既存のサービスに任せてください。

### 覚えておくこと

> **ログインは「誰か」を確かめるだけ。「入っていいか」は、自分で決める。**

## 8. 秘匿情報は外に置かない——境界線を自分で引き直す

ここまでは「ルールを正しく書きましょう」という話でした。ただ、それだけでは一点に寄りかかりすぎです。**ルールを1行間違えたら全部出る**、という構造は変わっていません。

もう一段強い考え方があります。

> **そもそも、出たら困るデータを、外から触れる場所に置かない。**

### データごとに、1つだけ問う

外に置く前に、データのまとまりごとに、これを問います。

> **「この中身が、いま全部そのまま流出したら、困るか？」**

- **困らない** → 公開側に置いて、ルールで守る
- **困る** → **置かない。** 内側に置く

判断は「漏れる確率」ではなく「**漏れたときの被害**」でします。確率の見積もりは当たりませんが、被害の大きさは今わかるからです。

外から触れる場所に置いてはいけないものの例です。

- ブラウザ用ではない API キーやパスワード（**これは論外**。セクション2のとおり、渡した時点で公開です）
- 他人の個人情報の一覧
- 原価、利益率、値引きの上限
- 人事や給与
- 誰が何をしたかの記録

### 「内側」とは何か

内側とは、**ブラウザから直接さわれない場所**のことです。自分が書いたサーバー側のプログラムだけが届く場所、と考えてください。

```
【公開側】ブラウザから直接触れる
   ブラウザ ──→ データベース ──→ 公開してよいデータ
                （ルールで守る）

【内側】ブラウザからはさわれない
   ブラウザ ──→ 自分のサーバー ──→ 見せたくないデータ
                （ここで判定する）   （外から直接は届かない）
```

この「自分のサーバー」は、大きなものを用意しなくても作れます（Supabase Edge Functions、Vercel Functions、Cloudflare Workers など）。

大事なのは、**「全部が見える強い鍵」を使っていいのは、ここだけ**ということです。セクション5の表に出てきた `service_role` key や Admin SDK がそれです。ここに置けば、ブラウザには渡りません。

**全部をサーバー経由にする必要はありません。見せたくないデータだけ**です。どこに線を引くかが、判断そのものになります。

### AI は、放っておくと公開側に書く

vibe coding に固有の注意点を1つ。

**AI に「◯◯できるようにして」と頼むと、いちばん短いコードが返ってきます。そして最短なのは、たいていブラウザから直接データベースをさわる形です。** サーバーを1枚はさむのは手数が増えるので、頼まなければやりません。

なので、指示のしかたが変わります。

- ✕「取引先ごとの原価を表示する画面を作って」
- ○「原価はブラウザから直接読まないで。**サーバー側を経由して、必要な値だけ返す**形にして」

**境界線をどこに引くかは、AI ではなく人間が決める仕事です。** 何が秘匿情報なのかを知っているのは、作っている本人だけだからです。

## 9. そもそもインターネットに出さない——社内サーバーと手元で動くツール

ここまで散々「外に出すときの守り方」を書いてきましたが、いちばん強い手は別にあります。

> **出さない。**

社内向け（パターン A・B）なら、これが現実的な選択肢です。

### 選択肢は2つ

**1. 社内にサーバーを立てる。** 社内ネットワークの中だけで動かせば、インターネットからは届きません。境界を自分で作る必要がなく、**会社のネットワークが既に境界**です。セクション3で悩んだ IP 制限の話も要りません。そもそも届かないので。

**2. 手元の PC で動くツールにする。** こちらのほうが手軽です。データはその PC から出ません。サーバーもドメインも認証基盤も要りません。

2つ目は vibe coding との相性がとてもいい。Web アプリを作ってデプロイして守るより、**デスクトップで動くツールにしてしまうほうが、やることが少ない**ことがよくあります。筆者が作っている [MulmoClaude](https://github.com/receptron/mulmoclaude) や MulmoTerminal も、この形です。

### 具体的に、どう立てるのか

「社内にサーバーを立てる」と言われても困ると思うので、選択肢だけ並べます。

| やり方 | 向いている規模 | 手間 |
|---|---|---|
| 各自の PC で動かす | 1〜数人 | 最小 |
| 常時つけっぱなしの1台を社内に置く | チーム〜部 | 中 |
| 社内にすでにある NAS を使う | NAS がある場合 | 中 |

**Linux でも Windows でも、どちらでもできます。**

- **Linux（Ubuntu など）** … 情報が多く、つけっぱなしに向きます。古い PC の再利用で十分です
- **Windows** … **できます。** そのままでも動きますし、**WSL2** という機能を入れれば Linux の環境も使えます

Windows をつけっぱなしにするなら、**自動更新の再起動**だけ気をつけてください。「金曜は動いていたのに月曜は止まっている」の定番の原因です。落ちても自動で起き上がる仕組みを、先に入れておくと楽になります。

**Apache や nginx といった名前を聞いたことがあるかもしれませんが、たいてい要りません。** vibe coding で出てくるものは、**それ自体がサーバーとして動きます**。起動して、社内の住所（IP アドレス）を配れば届きます。先に入れると、うまく動かないときに調べる場所が増えるだけです。

**在宅の人がいる場合。** 社内サーバーの弱点は「社外から届かない」ことです。長所でもありますが、在宅勤務があると困ります。

そこで使えるのが [Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/) です。**サーバー側から外に向かって接続を張る**方式なので、**ルーターに穴を開けなくて済みます**。セクション4-B の認証と組み合わせれば、サーバーを公開せずに、社員だけが社外からも使えます。

ただしこれも、**セクション4-B と同じくドメインの準備が要ります**。手軽ではありません。

**そして、いちばんのコストは機械ではなく人です。**

つけっぱなしのサーバーを置くと、そこから**運用が始まります**。電源が落ちたら誰が起こすのか。更新は誰がやるのか。バックアップは。その人が異動したら。

**引き受ける人がいないなら、各自の PC で動かすほうが正しい判断です。** 「立てられるか」ではなく「**面倒を見続けられるか**」で決めてください。

あわせて、**社内ネットワークに機器を置くのは、たいてい社内ルールの対象です。** 先に情シスに聞いてください。後から止められると、作ったもの自体が無駄になります。

### 何がなくなるか

| | Web にデプロイ | 手元で動かす |
|---|---|---|
| 認証 | 必要 | **不要**（OS のログインが済んでいる） |
| アクセス制御 | 必要 | **不要**（その PC の持ち主だけ） |
| DB のルール設計 | 必要 | **不要**（外から届かない） |
| 秘匿情報の置き場所 | 悩む | **手元でいい** |
| 配布 | URL を渡すだけ | インストールが必要 |
| 更新 | 即時、全員に反映 | **各自に更新してもらう必要がある** |

**トレードオフは配布と更新に集約されます。** 使う人が数人なら、こちらのほうが総コストは低いことが多い。

そして、**人数が増えたら、あるいはデータを共有する必要が出たら、そのときに Web へ移す**。その頃には実際の使われ方がわかっているので、何を守るべきかの判断もつきます。順番として、こちらのほうが安全です。

### 手元で動かすなら、データの持ち方も選び直せる

そもそも BaaS を使う理由は、**ブラウザから直接データを読み書きしたいから**です。手元や社内で動かすなら、その理由が消えます。だから選択肢が一気に広がります。

| データの持ち方 | 向いている場面 | 注意点 |
|---|---|---|
| **JSON / CSV ファイル** | 件数が少なく、単純な一覧 | 同時に書くと壊れる。基本は1人用 |
| **SQLite** | 件数が増える、検索や集計がある | ファイル1つで完結する。書き込みは順番待ちになる |
| **手元／社内の PostgreSQL** | 複数人が同時に書く | 立てる手間と運用が発生する |

**JSON や CSV で足りることは、思ったより多い**です。「DB を使わないと本格的じゃない」ということはありません。むしろ **CSV なら Excel で開けます**——業務ツールでは、これは実際に強い利点です。渡すのも、中身を確認するのも簡単になります。

境目がはっきりしているのは**同時書き込み**です。JSON ファイルを2人が同時に書くと、**後から書いたほうが前の内容を消します**。しかも静かに消えるので気づけません。ここが SQLite や PostgreSQL に移る分岐点です。

そして重要なのは、**PostgreSQL を使うこと自体は、外に出すこととは関係がない**ということです。手元や社内に立てた PostgreSQL は、インターネットからは見えません。BaaS と同じ Postgres でも、**ドアの数が違う**。セクション2の図でいえば、**矢印が1本に戻る**ということです。

### 最初から決めなくていい

もうひとつ。**この選択は、後から変えられます。**

JSON で始めて、件数が増えたら SQLite に移し、同時に使う人が増えたら PostgreSQL に移す。**データが少ないうちの移行は簡単です。** 最初から BaaS を選んでおく必要はありません。

順番として、こうなります。

| 共有の必要 | データの置き場所 |
|---|---|
| 要らない（自分だけ） | 手元の JSON / CSV / SQLite |
| 社内の数人が見る | 社内サーバーの SQLite か PostgreSQL |
| 社内で同時に書く | PostgreSQL |
| 社外の人と共有する | ここで初めて、外に出す話になる |

**データを共有する必要が出た瞬間に、この記事の前半（セクション2〜8）に戻ってきます。** 逆に言えば、**共有が要らないうちは、あの話は全部不要**です。ルールも、境界線も、署名付き URL も。

「どのデータベースを使うか」は、実は技術の選択ではありません。**誰とデータを共有するか**の選択です。そしてそれは、セクション1で決めた「誰に見せるか」と同じ問いです。

### 「手元で動かす」は妥協ではない

念のため書いておくと、これは逃げではありません。**扱うものが秘匿情報なら、手元で動かすほうが正しい設計**です。守りやすいところに置く、というのはセキュリティの基本です。

「せっかく作ったから Web で公開したい」という気持ちと、「このデータは外に出したくない」という要件は、切り離して考えてください。

## 10. 段階の上げ方——下の段で足りないとわかってから、次へ

ここまでの内容を、実際に進む順番として並べ直します。**大事なのは、下の段で足りないとわかってから次に上がること**です。最初から一番上に行く必要はありません。

### 第1段：手元の PC で、JSON でプロトタイプを作る

まずここから。データは JSON、動かすのは自分の PC。

**この段階では、この記事に書いたことは何も要りません。** 認証もルールも境界線も不要です。作ることだけに集中できます。

ひとつだけ先を見て決めておくとよいのは、**Web サーバーの形で作っておく**ことです。ブラウザで開く形にしておけば、次の段に上がるのが楽になります。

### 第2段：同じ社内ネットワークの、他の PC から使う

Web サーバーの形にしてあれば、**設定を少し変えるだけで、同じネットワークの他の PC から使えます**。社内ネットワークの中だけなので、インターネットからは届きません。

**第1段からの追加コストは、ほぼゼロ**です。何人かに使ってもらって、本当に役に立つのかを確かめる段階として、ここは効率がいい。

**ただし、ノート PC を社外に持ち出すときは注意してください。**

「同じネットワークの他の機器から見える」設定のまま、カフェや空港の Wi-Fi につなぐと、**その場にいる他の人からも見えます**。社内では正しかった設定が、外では正しくありません。

- 自分だけで使うときは、**自分の PC からしかつながらない設定**に戻す（`localhost` だけで待ち受けるか、`0.0.0.0` で待ち受けるかの違いです）
- 持ち出す PC で常時起動しない
- できれば、常時動かす用途は据え置きの機械に移す

vibe coding で出てくる起動設定は、**「同じネットワークから見える」側になっていることが多い**です。一度は確認しておく価値があります。

### 第3段：入口と出口だけ、既存のツールに任せる

ここが飛ばされがちで、そして**いちばん効く段**です。

**社外の人とのやり取りが必要になったとき、いきなり「Web アプリを公開する」に飛ばないでください。** 公開するから認証が要るのであって、**公開しなければ認証は要りません**。

やり方は単純です。**入口と出口を、すでにある道具に任せる。**

```
相手 ──[メール / Slack / 既存のフォーム]──→ （認証も配送も、そのサービスの仕事）
                                                     │
                                              手元・社内で処理
                                                     │
      ←──[メール / Slack で結果を返す]───────────────┘
```

- **受け取りだけ外でやる。** 既存のフォームサービスや共有フォルダで受け取り、処理は手元でする
- **メールで受け取って、メールで返す。** 相手にとっては、いつもどおりの操作です
- **Slack に結果を返す。** 社内向けなら、画面を作るより読まれます

**この形なら、自分が公開するものはゼロです。** 守るべき入口がないので、この記事の前半に書いたことは、ほとんど要りません。認証も、アクセス制御も、ルールも。

そして相手にとっても、**新しい画面の使い方を覚えなくていい**。これは、使ってもらえるかどうかに直結します。

**「インターフェースを自作しない」**——これは手抜きではなく、設計の判断です。

### 第4段：BaaS やクラウドを使う

ここまでで足りないとわかって、初めて外に出します。必要になるのは、たとえばこういう場合です。

- 相手がその場で操作する画面が要る
- 常時つながっていないと成立しない
- 使う人数が増えて、メールや Slack では回らない
- 社外の不特定多数に開く

この段まで来たら、**セクション2から8に書いたことが、全部必要になります。** ルール、境界線、秘匿情報の置き場所、署名付き URL、認証と許可リスト。

逆に言えば、**第1段から第3段のあいだは、そのほとんどが不要**でした。

### 段を飛ばさない

| 段 | やること | 必要な守り |
|---|---|---|
| **1** | 手元の PC、JSON でプロト | ほぼ不要 |
| **2** | 社内ネットワークの他の PC から | 持ち出しに注意 |
| **3** | 入口と出口を既存ツールに任せる | 公開するものがない |
| **4** | BaaS / クラウド | この記事の全部 |

**上に行くほどできることは増えますが、守るものも増えます。** そして守り漏れの結果は、セクション5で見たとおりです。

いちばんもったいないのは、**第3段で足りたのに、第4段から始めてしまうこと**です。作るのに時間がかかり、守るのにも時間がかかり、そのうえ使われないかもしれない。

## 11. まとめ表

| 公開範囲 | 現実的な構成 | 一番の落とし穴 |
|---|---|---|
| **A. 自分だけ** | 手元で動かす／ローカル実行 | 出す必要がないのに、出してしまう |
| **B. 社内・複数人** | 手元で動くツール、社内サーバー。外に出すなら認証をかける | パスワード共有で済ませ、誰が入ったか分からなくなる |
| **C. 社外・特定の人** | 既存の共有サービス、または認証をかけた場所 | 「URL を知っている人だけ」は認証ではない |
| **D. 社外・多数** | 認証・認可・入力検証をアプリ側で設計 | 入口で守れないので、全部アプリの責任になる |

全パターン共通で、5つ。

1. **ブラウザ用でない API キーを、ブラウザに渡さない。** 画面のコードは誰でも読めます。ブラウザ用の鍵にも、制限をかけておく
2. **BaaS を使うなら、ルール（RLS / Security Rules）は必須。** 書かなければ世界中から読めます
3. **ファイルの置き場所を公開にしない。** 渡すなら、期限つきの URL で
4. **秘匿情報は、外から触れる場所に置かない。** ルールの正しさに全部を賭けない
5. **場所で絞る設定は、アプリの入口には効かないことがある。** 設定画面の表示を信じない

料金とプラン要件は変わります。最終的には一次情報（記事末尾のリンク）で確認してください。

## 12. で、何から始めるか

1. **「誰に見せるか」を1文で書く。** A / B / C / D のどれかを決める。ここが決まらないうちにデプロイしない
2. **セクション10の段を、下から順に試す。** 手元でプロト → 社内ネットワーク → 入口と出口を既存ツールに任せる → それでも足りなければクラウド。データも、共有が要らないうちは JSON / CSV / SQLite で足ります
3. **出すなら、まず既存のサービスで済まないか考える。** 自分で認証を作らないほうが安全です。作るなら、ログインの後ろに名簿を置く
4. **テーブルごとに「全部流出したら困るか」を問う。** 困るものは、外から触れる場所に置かない
5. **BaaS を使っているなら、ルールが有効かを実際に叩いて確認する。** 自信がなければ、そこだけ人に見てもらう
6. **鍵を2種類に分けて確認する。** ブラウザ用でない鍵が `VITE_` や `NEXT_PUBLIC_` で始まる名前に入っていたら、それは公開されています。ブラウザ用の鍵は、制限がかかっているかを見る
7. **ファイルを扱うなら、置き場所が公開になっていないかを見る。** 渡すときは添付ではなく、期限つきの URL で
8. **受け取る場合は、ログインの後ろに許可リストがあるかを確認する。** 「ログインできる」と「入ってよい」は別です
9. **D は、A〜C で実績を作ってから。** 最初の一歩にしない

最後に、この記事で覚えて帰ってほしいのは3行だけです。

> **画面に鍵をかけても、データのドアは別に開いている。**
>
> **出たら困るものは、そもそも外に置かない。**
>
> **そしてクラウドは、下の段で足りないとわかってから。**

vibe coding で作れるものの範囲は、これからも広がります。**作る力が先に手に入って、置く場所の判断だけが残る**——というのが、いまの状況だと思います。

そして「とりあえずクラウドに上げる」は、いちばん簡単に見えて、**いちばん守るものが多い選択**です。簡単なのは上げるところまでで、その先がずっと続きます。

置き場所の判断は、技術というより「誰に見せるか」「何が外に出てはいけないか」という業務の判断です。だとすれば、それを決められるのは作った本人しかいません。
