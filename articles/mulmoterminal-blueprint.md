町内会の名簿は、最初は紙で回っていました。そのうち誰かがエクセルにして、メールに添付して回すようになり、どれが最新か分からなくなります。

詳しい人に「アプリにできないかな」と頼んでみると、「誰が見られるようにするの」「引っ越した人の記録は残すの」と聞き返されます。その場では答えられず、話はそこで止まりました。

最近は AI に「名簿のアプリを作って」と頼めば、それらしいものが数分で出てきます。画面もきれいで、名前を入れれば一覧に並びます。ところが、それは自分のパソコンの中でしか動いていません。役員の人にスマホで見てもらうには、どこかに公開しなければいけません。公開するとなると、ログインはどうするのか、関係ない人に見られないか、月にいくらかかるのか、と分からないことが次々に出てきます。

そんな経験はないでしょうか。

## 作ることと、みんなで使えることのあいだ

ソフトウェアを作ることは、この数年でずいぶん簡単になりました。それに比べて、作ったものを人に使ってもらえる形で置くことは、昔からあまり変わっていません。

みんなで使うアプリには、自分だけで使うアプリには無い決めごとがあります。誰がログインできるのか、誰が何を見られて、誰が何を消せるのか。公開した URL に知らない人が来たら、何を見せてよいのか。サーバーの費用は誰が払うのか。こうしたことを決めないまま公開すると、名簿のように個人情報を扱うものでは、取り返しのつかないことが起きます。

しかも、頼む側はたいてい、何を決めなければいけないのかを知りません。家を建てるときに似ています。注文住宅の打ち合わせでは、工務店の人が「コンセントはどこに何口」「収納の扉は引き戸か開き戸か」と順に聞いてくれます。聞かれて初めて、自分が決めていなかったことに気づきます。聞く項目の一覧が、長年の仕事の中で作り込まれているからできることです。

ソフトウェアの外注でも、要件定義という形で同じことをしてきました。ただ、それができる人は限られていて、個人や小さな集まりが頼むには高くつきます。AI に頼む場合は聞き手がいないので、決めることと手を動かすことが一つの会話に混ざります。AI が黙って埋めるか、作業のたびに止まって聞いてくるかのどちらかになりやすいです。後者だと、横に座って答え続けることになります。

## 手を動かす部分を任せられるようになった

この数年で変わったのは、手を動かす部分を AI に任せられるようになったことです。そうなると、順番を入れ替えることができます。決めることを最初にまとめて聞いて紙に書き、その紙ができたあとは、人がいなくても作業が進むようにします。

もう一つ必要なのは、人が見ていない間の作業を誰が確かめるかです。作業のたびに人が画面を見ていては、任せた意味がありません。工程ごとに、次へ進む前にプログラムで確かめるようにしておけば、人は決めるところにだけ戻ってくれば済みます。公開してよいかどうかの判断も、その決めるところの一つです。

## MulmoTerminal の「設計図」

[MulmoTerminal](https://github.com/receptron/mulmoterminal) は、Claude Code などの AI のコーディング道具を、ブラウザの中で何個も並べて動かすためのアプリです。自分のパソコンに入れて、ブラウザで開いて使います。MIT ライセンスの無料のソフトウェアです。

その中に、試験中の機能として「設計図」があります。作りたいアプリについて質問に答えると、それを仕様書にまとめ、その仕様書から Claude Code が工程ごとに組み立てていきます。組み立てたアプリは、自分のパソコンの中で動かすこともできますし、Firebase、Cloudflare、Supabase に公開して、ほかの人にスマホやパソコンから使ってもらうこともできます。

![設計図の画面。左に「新しく作る」と「マーケット」、右に始めるための例が並ぶ](https://raw.githubusercontent.com/receptron/mulmoterminal/main/docs/guide/images/v6.5.0-blueprints-ja.png)

できあがるのは、どこかのサービスの中に閉じたアプリではありません。画面も API も試験も、ふつうのコードとして自分のフォルダに置かれます。あとから自分で直すことも、別の人に引き継ぐこともできます。

## 公開先を選ぶ

設計図では、アプリを置く場所を「土台」と呼んでいます。いまある土台は4つです。

| 土台 | 中身 | 要るアカウント | 費用の目安 |
|---|---|---|---|
| ローカル | Express の API、SQLite のデータ、Vue の画面 | なし | かからない |
| Cloudflare | Worker の API、D1（SQLite）のデータ、同じ Worker が配る Vue の画面 | Cloudflare | 無料のアカウントで始められる |
| Supabase | Supabase（Postgres）のデータとログインと権限、Cloudflare が配る Vue の画面 | Supabase と Cloudflare | どちらも無料のアカウントで始められる |
| Firebase | Hosting、Authentication、Firestore、Cloud Functions | Google（Firebase と Google Cloud） | 従量課金（Blaze）への切り替えが要る。少人数ならたいてい無料枠に収まる |

ローカルは自分のパソコンの中だけで動くので、まず流れを見るのに向いています。みんなで使うなら、残りの3つのどれかです。

Cloudflare は、いちばん手軽に公開できる土台です。API とデータと画面がひとまとまりになっていて、ほかに用意するものがありません。

Supabase は、表ごとに誰が読めて誰が書けるかを、データベースの側で決めたいときに向いています。画面はブラウザから Supabase を直接読み書きするので、行ごとの権限（RLS）が守りの中心になります。

Firebase は、Google アカウントでのログインや、開発用と本番用を分けた運用をしたいときに向いています。開発用と本番用の2つのプロジェクトを作り、開発用で確かめたものと同じものを本番に出します。

どの土台でも、作業の途中は自分のパソコンの中で動かして確かめます。Cloudflare なら `wrangler dev`、Supabase なら Docker の中の Supabase 一式、Firebase ならエミュレータを使います。実際の公開は最後の工程で、承認してから初めて行われます。

## 聞き取り

作るものの種類で「自由に作る」を選ぶと、次のことを聞かれます。

- アプリの名前と、何を作りたいか、どんな困りごとを解決するか
- 誰が使うか
- 扱うもの（本、予約、在庫、レシピなど）と、使う人がすること（登録する、探す、予約する、集計を見るなど）
- 最初から必要な機能と、あとでよい機能
- ログインの方式と、役割を分けるか
- 扱う情報でいちばん気をつけるもの
- 似ているサービスやイメージ、画面の言葉

ログインは「なし」「共有のパスワード一つ」「一人ずつのアカウント」から選びます。一人ずつのアカウントを選ぶと、役割の分け方も聞かれます。例として「管理者はすべてのレシピを消せる。家族は自分のレシピだけ直せる」のような書き方が示されます。

扱う情報は「公開してよい情報のみ」「身内だけの情報」「個人情報を含む」「お金や健康など特に機微な情報」から選びます。ここで選んだものによって、保存の仕方やバックアップの厳しさが決まります。各質問には、それが何を決めるのかが添えてあるので、なぜ聞かれているのかが分かります。

公開する土台では、この聞き取りがそのまま守りの設計になります。たとえば Cloudflare に公開したアプリは、URL を知っている人なら誰でも開けます。ログインを「なし」にした場合は、仕様書で「ログインしない人に見せてよいもの」を決め、それ以外には届かないように作られます。

## 仕様書で止まる

最初の工程で仕様書ができると、そこで止まります。ここから先の作業は、すべてこの仕様書を元に進みます。

仕様書には、聞き取りの答えから組み立てた画面、データ、操作、ログインと権限が書かれています。Supabase の土台では、表ごとに「読める人・足せる人・変えられる人・消せる人」が必ず書かれます。決まっていない点は一覧になっています。

読んで変えたいことがあれば、下の欄に書いて送ります。たとえば「名簿の削除は会長だけができるようにして」と書くと、エージェントが仕様書を直して返事をします。何往復してもかまいません。納得したら「承認する」を押します。ここから先は、この仕様書が約束ごとになります。

## 工程と確かめ

承認したあとは、工程が順に進みます。Cloudflare の土台なら、工程は次のとおりです。

1. 仕様書を書く
2. 道具の確認
3. アプリの雛形
4. データの形（D1 の表とマイグレーションと試験）
5. API（入力の検査と試験）
6. 画面
7. ログイン
8. 起動して確かめる
9. セキュリティ診断
10. Cloudflare に公開
11. 使い方の説明と引き継ぎ

各工程は、次へ進む前にスクリプトで確かめられます。たとえば「ログイン」の工程は、ログインしていないリクエストが断られ、ログインしたリクエストが通り、間違ったパスワードが断られることを試験で確かめるまで終わりません。確かめが通らないときは、前の失敗を見比べて自動で直しにいきます。最初から必要だと答えた機能は、最後にそれぞれ試験で確かめられます。

作業中の工程では、エージェントが何をしているかと経過時間が画面に出ます。エージェントが質問してくることもあり、選択肢がある場合は、選んだときの費用と危険を添えたボタンが並びます。エージェントがおすすめするものには「推奨」と付きます。

## 公開の前に、攻める側の目で読む

どの土台でも、公開の手前にセキュリティ診断の工程があります。OWASP Top 10:2025 という、よくある攻撃の一覧に沿って作ったものを読み、突ける穴を直して試験を足し、報告を書きます。

確かめ方は土台ごとに違います。Cloudflare では、手元で起動した Worker に、別のサイトからの変更や壊れた JSON のような、攻撃と同じ形のリクエストを送って断ることを確かめます。

Supabase では、ログインしていない人と、何の役割も持たないログインした人として、全部の表を読み書きしてみます。仕様で許したこと以外が通らないことを確かめます。公開のときには、公開した画面に秘密の鍵が含まれていないことも確かめます。

Firebase では、データの決まり（`firestore.rules`）を最初はすべて拒否にしておき、仕様にある分だけ一つずつ開けます。本番の前に App Check を有効にし、本番のプロジェクトに予算アラートを設定する工程も入ります。セキュリティ診断で直したものは開発用に公開し直し、画面が壊れていないことまで確かめます。

## 人がやること

止まって人に聞くのは、人が決めることだけです。仕様の確認、費用のかかる操作、公開の承認のほかに、サービスへのログインがあります。

設計図は、パスワードや API のトークンを扱いません。Cloudflare なら `yarn wrangler login` を、Supabase なら `yarn supabase login` と `yarn supabase link` を、自分で実行してログインします。Supabase のプロジェクトは自分で作ります。Firebase の従量課金への切り替えも、画面の案内に従って自分で行います。自分でしてほしい操作があるときは、その手順が質問として設計図の画面に届きます。

## 終わったら

「すべての工程が完了しました」と出たら終わりです。そのすぐ下に「使い始め方」が出ます。

公開した土台なら、そこに公開した URL が書かれています。必須の機能を一つずつ試すチェックリストもあるので、上から順に試してから、みんなに URL を伝えます。手元での動かし方、次に直すときの手順、データのバックアップのしかたも、フォルダの `README.md` にまとめられています。

## 例から始める

自分で質問に答える前に、例を選んで流れを見ることもできます。選ぶと土台と質問への答えが入った状態で始まります。

- おうち図書館: 家にある本と、誰に貸しているかを記録する。ローカルで動く
- 家計簿、チームのタスクボード、見積書づくり: どれもローカルで動く
- ミニ SNS: 短い投稿を共有して、フォローした人の投稿をタイムラインで読む。Google アカウントでログインし、Firebase に公開する
- 稟議: 社員が稟議を起票し、承認者が順に承認や差し戻しをする。会社のドメインの人だけがログインでき、誰がいつ承認したかが監査ログに残る。Firebase で動く

稟議は「社内向け業務アプリ」という種類の例です。この種類では、会社のメールのドメインを持つ人だけがログインでき、役割によってできることが決まり、辞めた人はすぐに入れなくなり、権限の要る操作はすべて記録に残るように作られます。

## コレクションから、文書から

MulmoTerminal には、表の形でデータを持つ「コレクション」があります。設計図の「コレクションからアプリにする」を選ぶと、コレクションの形と画面と操作を写して、自分のコードとして持つアプリにできます。土台はローカル、Firebase、Cloudflare、Supabase から選べて、望めば中の記録も新しいアプリに移されます。手元で使っていたものを、みんなで使えるところへ出す道筋です。

作るものはアプリに限りません。契約書や規程の食い違いを、原文の引用付きで指摘してもらえます。旅程表の曜日のずれや、見積書の合計の誤りを機械で見つけることもできます。ほかにも、旧版と新版を比べて新旧対照表を作る、文書に質問してどこに書いてあるかを添えた答えをもらう、といった種類があります。

## Claude Code に直接頼むのと何が違うか

同じことは、Claude Code に直接頼んでもできなくはありません。仕様書を書かせて、確認して、順に作らせて公開することは、慣れた人なら一つの会話の中でやっています。

違うのは、聞く項目と確かめ方が、作るものの種類と土台ごとにパックとして用意されていることです。パックは、質問の一覧、工程の並び、各工程で使うスキル、工程が終わったかを確かめるスクリプトをまとめたフォルダです。工務店の聞き取りの一覧にあたるものが最初からあります。頼む側が何を決めればいいかを知らなくても、聞かれた順に答えていけば仕様書になります。公開に要る決めごとも、その中に入っています。

また、工程は MulmoTerminal が一つずつ起こして見張っています。途中で MulmoTerminal を止めて起こし直しても、その工程をやり直して続きます。待っているビルドは画面の左の「あなたを待っている」にまとまるので、いくつか並べて走らせておき、呼ばれたものから答えていく使い方もできます。

## マーケット（試作）

パックは MulmoTerminal に入っているものだけでなく、外から取り込むこともできます。それが「マーケット」の画面です。

パックの一覧を書いた JSON ファイルの URL を登録すると、そこに載っているパックが並びます。一覧の一件は、パックが置いてある git リポジトリとブランチと、その中のフォルダを指しています。「取り込む」を押すと、そこから MulmoTerminal のフォルダに写されます。一覧に載っていないリポジトリから直接取り込むことはできません。

いまは仕組みを試すための段階で、公式の一覧はまだありません。動作を確かめるためのダミーの一覧が一つあるだけで、そこにはパックが一件だけ載っています。誰かが作った聞き取りの一覧や、別の公開先の土台を取り込んで使えるようになるのは、これからです。

## 試してみる

必要なものは次のとおりです。

- Node.js 22.13 以上と git
- Claude Code と、それを使うための Claude の有料プラン（無料プランでは Claude Code は使えません）

公開する土台を使うときは、それぞれ次のものが加わります。

- Cloudflare: Cloudflare のアカウント（無料のものでよい）。`wrangler` はプロジェクトに入るので、別に入れる必要はありません
- Supabase: 起動した Docker Desktop と、Supabase と Cloudflare のアカウント（どちらも無料のものでよい）
- Firebase: Google アカウント、支払い方法を登録できる Google Cloud の請求先アカウント、Firebase CLI、`gcloud`、JDK 21 以上

ターミナル（Windows なら PowerShell、Mac ならターミナル）で次を実行し、ブラウザで `http://localhost:34567` を開きます。

```bash
npx mulmoterminal@latest
```

上のバーの「その他の機能」のメニューに「設計図」があります。

始める前に一つだけ準備があります。エージェントは誰も見ていないところで動くので、Claude Code の「このフォルダを信頼しますか」の確認で止まると先へ進めません。試し用の親フォルダを作り、そこで一度 `claude` を起動して信頼すると答えておきます。その中に作るフォルダは、親の信頼を引き継ぎます。作ったフォルダで `git init` をすると引き継がなくなるので、git で管理したいときはビルドが終わってからにしてください。

最初の一回は、ローカルの「おうち図書館」で流れを見てから、Cloudflare の土台で「自由に作る」を試すのがおすすめです。Cloudflare なら無料のアカウントだけで、公開までを一通り体験できます。

## 気をつけること

設計図は試験中の機能で、見た目も中身も変わっていく途中です。

Firebase の土台は、いまのところ開発用のプロジェクトへの公開までを確かめています。本番への公開は、まだ十分に確かめていません。試すときは開発用までにしておいてください。

1 回のビルドは工程ごとに Claude Code のセッションを起こすので、ふつうにチャットするよりまとまった量を使います。また、設計図を動かせるのは、1 台のパソコンで 1 つの MulmoTerminal だけです。

準備から試してほしいことまでは、[設計図のガイド](https://www.mulmoterminal.com/guide/ja/blueprints.html)にまとめています。

## まとめ

AI のおかげでアプリを作ることは簡単になりましたが、それをみんなで使える形で公開するには、ログイン、権限、費用、攻撃への備えと、決めることがたくさんありました。しかも頼む側は、何を決めればいいのかを知らないことがほとんどです。

設計図は、決めることを最初にまとめて聞いて仕様書にし、そのあとは工程ごとに機械で確かめながら、人がいなくても進むようにしています。公開するかどうかは最後に人が決め、承認してから Cloudflare、Supabase、Firebase に出ていきます。町内会の名簿のようなものでも、聞かれたことに答えていけば、役員のスマホから開ける形まで持っていけるはずです。
