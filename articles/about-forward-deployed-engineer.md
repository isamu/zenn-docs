**FDE（Forward Deployed Engineer）** という職種名を、この1年でよく見るようになりました。ただ、紹介のされ方が「AI 時代の花形職種」「年収が高い」「スーパーエンジニア」といった雰囲気の話に偏っていて、**実際に何をやるのか**が曖昧なままになっている印象があります。

この記事では、推測を一切書きません。読むのは次の**2つの一次資料**だけです。

1. **Anthropic 自身が出している FDE の求人票**（[Anthropic Careers](https://www.anthropic.com/careers/jobs)、Greenhouse 掲載）— 会社が「何をさせたいか」を書いたもの
2. **FDE の面接ガイド**（[Anthropic Forward Deployed Engineer (FDE) Interview Guide](https://www.chillinterview.com/learn/interview-guides/anthropic-forward-deployed-engineer-fde-interview-guide)）— 面接ループの各ラウンドで**何が問われ、何が評価されるか**を整理したもの

求人票は「何をさせるか」を、面接ガイドは「何ができる人を採るか」を書いています。**募集要項と選考基準**という、方向の違う2つの文書です。これを突き合わせると、職種の輪郭は意外なほどはっきり出てきます。

そのうえで日本の SI・客先常駐・コンサルと比較します。というのも、FDE の説明を聞いた日本のエンジニアの反応は、だいたい「それ、客先常駐では？」か「大手コンサルの DX 支援と何が違うの？」だからです。実際、日本でも2025年あたりから FDE を名乗る求人が出はじめ、[SIer が「日本型 FDE」をどう設計するか](https://note.com/shin_sasaki/n/n859daecafd76)を論じる記事や、[「米国流 FDE は日本の客先常駐とは似て非なるもの」と釘を刺す記事](https://xtech.nikkei.com/atcl/nxt/column/18/03079/120400025/)が出てきています。言葉が先に輸入されて、中身が後から議論されている状態です。

結論を先に書いておくと、求人票と面接ガイドから読み取れる FDE の異常さは、**スキルの高さではなく、工程を一つも分けないこと**にあります。

---

## 1. 一次資料その1：Anthropic の求人票

まず求人票そのものです。Anthropic の FDE は単発の実験ポジションではありません。Greenhouse には **Applied AI / Custom Agents / Federal Civilian** といったバリエーションが並んでおり、さらに **Manager, Forward Deployed Engineering** と **Head of Forward Deployed Engineering** の募集まで出ています。つまり**部門として組織されている**ということです。

職務内容（Responsibilities）は、おおむねこうです。

- 顧客の長期的な関係を構築し、エンゲージメントのライフサイクルを通じて**新しい AI 適用機会を能動的に見つける**
- **顧客のシステムの中で**、Claude を使った**本番アプリケーションを作る**（顧客要件を満たすことに責任を持つ）
- **MCP サーバー、サブエージェント、Agent Skills** といった技術成果物を納品する — しかも「本番ワークフローで使われるもの」と明記されている
- エンタープライズ環境への導入を**ホワイトグローブで支援する**
- 再現性のある導入パターンを**特定して言語化し、プロダクト／エンジニアリングチームに還元する**
- LLM の能力、実装パターン、AI プロダクト開発スタックの最新動向を追い続ける

そして出張。Applied AI では「勤務地によっては顧客先へ出張の可能性」ですが、**Federal Civilian や Custom Agents では「25〜50% の頻度で顧客サイトへ出張し、対面で一緒に作る」と明記されています**。リモートで納品する仕事ではなく、**顧客の隣に座って作る**のが前提です。

応募要件（求人票および面接ガイドの整理）はこうなっています。米国の求人票は、求めるスペックがかなり具体的に明示されるのが特徴です。

- 技術的な顧客対応職で **4年以上**、または SWE ＋コンサルティング経験
- 強い **Python**、本番アプリケーションを出荷した経験
- おもちゃのプロンプトではない、**本番の LLM 経験**
- 高度なプロンプトエンジニアリング、エージェント開発、**評価（eval）フレームワーク**
- **MCP サーバー**の作成、サブエージェント開発、Agent Skills
- 顧客ディスカバリーのコミュニケーションと、エンタープライズの関係構築
- ハイエージェンシーかつ低エゴな協働姿勢
- 安全で有益な AI システムへの情熱

読んでいて引っかかるのはここです。**これ、日本なら何社で分担する話だろう？**

## 2. 一次資料その2：面接ガイド

もう一方の資料は面接ガイドです。求人票が「やること」なら、こちらは「**何ができれば受かるか**」が書いてある文書で、職種の実像はむしろこちらのほうが正確に出ます。

ガイドはまず、FDE に必要な力を5つの軸に分けています。

| 軸 | 内容 |
|---|---|
| プロダクションエンジニアリング | きれいな Python / TypeScript を書き、**顧客環境の中で**動く信頼できるコードを出荷する。API 統合、デバッグ、MCP サーバー開発 |
| Claude / エージェント AI の深さ | プロンプティング、コンテキストエンジニアリング、ツール利用、MCP、サブエージェント、Agent Skills、evals、大規模展開 |
| 顧客ディスカバリーとエンタープライズ判断 | **曖昧な顧客ワークフローを、スコープの切れた出荷可能な AI システムに変換する**。エンジニアリング・セキュリティ・法務・オペレーションのステークホルダーを捌く |
| 安全性と信頼性の姿勢 | ハルシネーション、誤用、プライバシー、評価、運用リスクを管理しながら強力な AI を展開する |
| 曖昧さの中での高い当事者性 | 自律的に動き、顧客のブロッカーを外し、再現可能なパターンを作り、現場の学びをプロダクト開発に還す |

そのうえでガイドは、強い候補者は**この全次元にまたがっている**必要があり、**LeetCode だけ／プロンプトエンジニアリングだけ／ソリューションアーキテクチャだけ／AI 好きなだけ、のどれでもない**と強調しています。

面接ループの詳細（何ラウンドあって、それぞれ何を見るか）はこの記事の後半、セクション8で扱います。先に、この2つの資料から見えてくる**構造**の話をします。

## 3. 「Forward Deployed」は軍事用語だった

言葉の出どころを押さえておくと理解が早くなります。

`forward deployed` は軍事用語で、**後方の基地からではなく、事が起きている現場に部隊を置く**ことを指します。これをソフトウェアに持ち込んだのが Palantir でした。

Palantir の顧客は情報機関でした。何が欲しいかを、機密上そもそも言えない。要件定義ができない顧客です。そこで Palantir は発想を変えました。

> ソフトウェアを送るのをやめて、エンジニアを送ることにした。

現場に engineer を置き、彼らがそこでワークフローを直接作る。この形を再現可能なモデルに仕立てたのが初期社員の Shyam Sankar だとされています。Palantir 自身は FDE の職責をこう表現しています。

> FDE の責任範囲はスタートアップの CTO に近い。小さなチームで、重要なプロジェクトのエンドツーエンドの実行を own する。

**「要件が出てこない顧客のために発明された職種」**——これが出自です。そして今、まったく同じ条件が AI 導入の現場に再現されています。

## 4. 何が普通じゃないのか：工程が一つも分かれていない

日本の典型的な大規模システム導入を、工程で並べてみます。

| 工程 | 日本の典型的な担い手 | FDE |
|---|---|---|
| 業務課題の発見・整理 | 戦略／業務コンサル | 同じ人 |
| 要件定義 | 元請け SIer の上流 SE | 同じ人 |
| 基本設計・方式設計 | 元請け SIer | 同じ人 |
| 実装 | 協力会社・オフショア | 同じ人 |
| セキュリティ・権限設計 | 情報システム部／セキュリティ部門 | 同じ人 |
| インフラ・本番デプロイ | 基盤チーム／運用会社 | 同じ人 |
| ドキュメント作成 | 別途、専任 | 同じ人 |
| 受け入れテスト設計 | 顧客側＋品証 | 同じ人 |
| **現場知見のプロダクト反映** | **担い手が存在しない** | 同じ人 |

上から8行目までは「誰がやるか」の違いです。9行目だけは質が違います。**日本の分業モデルには、この工程そのものが存在しない**。案件で得た知見は案件で終わり、良くて社内ナレッジになる。FDE の場合、それは自社プロダクトの改善に直結します。ここが SES との最大の分岐点で、[SES が売っているのは「工数」だが、FDE が売っているのは「自社プロダクトによる課題解決」](https://note.com/alphakt_official/n/n9e0468228742)という整理はその通りです。

なので FDE に必要なスキルセットを素直に書き下すと、こうなります。

- 業務を聞き出して構造化する（コンサル）
- 何を作るか決める（プロダクトマネージャー）
- きれいに書いて、テストを書く（ソフトウェアエンジニア）
- クラウドに載せて、監視を付ける（プラットフォームエンジニア）
- 権限・監査ログ・PII を設計する（セキュリティエンジニア）
- 画面を作る（フロントエンド）
- 法務・セキュリティ部門と合意を取る（交渉）
- 引き継げるドキュメントを書く（テクニカルライター）

一人で。**これが成立するのか**、というのが最初の疑問になります。

## 5. なぜ一人で成立しうるのか——米国側の前提

ここで、日本から見えにくい前提が効いてきます。

米国のテック企業では、ソフトウェアエンジニアが **CS の学位を持っているのが標準線**です。学士が最低ラインで、修士も珍しくない。これは学歴信仰の話ではなく、**共通言語の話**です。OS、ネットワーク、DB、分散システム、アルゴリズム、計算量、セキュリティの基礎を、全員が一度は同じ教科書で通っている。だから「認証と認可の違い」や「この処理の計算量」を説明するところから始めなくていい。守備範囲を広げるときのコストが、そもそも低い。

もう一つ、構造的な違いがあります。**コードを書く人が、キャリアの終点になれる**こと。

日本では、優秀な SE は数年で設計に上がり、やがて PM になり、管理職になり、コードを書かなくなります。書き続ける人は「上がれなかった人」に見えてしまう。米国には Staff / Principal / Distinguished Engineer というトラックがあり、**書き続けたまま組織の最上位に行ける**。結果として、15年書き続けて、UI からセキュリティまで一通り自分で作り、事故も出し、顧客とも話してきた人材が、市場に厚く存在します。

FDE は、その層の上に成立しています。「何でもできるスーパーマンを探している」のではなく、**分業しない前提で20年積み上げた人が普通にいる市場**だから、こういう求人が書ける。

日本の分業モデルは、人材の質のばらつきを工程の分割で吸収する、よくできた仕組みです。ばらつきを前提にするなら合理的でもある。FDE はその逆を張っている、というだけの話です。

## 6. なぜ工程を分けては「いけない」のか——AI 側の理由

ただし、「できるから分けない」だけなら、単なる贅沢な人員配置です。FDE が今必要とされている理由は別にあります。**LLM を使うシステムでは、工程を分けると原理的に破綻する**からです。

日経クロステックの記事が、この核心を一行で書いています。

> SaaS は A と入力すれば B という結果が必ず出力される（決定論的）のに対し、LLM をベースにする AI エージェントは、A という入力をしても、出力が B になったり D や G になったりする。

工程分割モデルは、**仕様が事前に凍結できること**を前提に組まれています。要件定義で仕様を固め、設計に落とし、実装し、仕様通りかを検収する。この連鎖のすべてのノードが「正解が事前に書ける」ことに依存しています。

LLM ではこれが二段階で壊れます。

**一段目：何が効くか、触るまで分からない。** プロンプトの言い回し、コンテキストの入れ方、ツールの切り方、どのモデルを使うか。これらは机上で決められません。試して、ログを見て、直す。要件定義フェーズで確定できることが、ほとんど残らない。

**二段目：「仕様通り」が定義できない。** 同じ入力に対して出力が揺れるので、従来の受け入れテストが書けません。代わりに必要になるのが **evals** です。ゴールデンタスクを用意して、正答率・根拠の妥当性・エスカレーション品質といった指標を決め、閾値を超えたかどうかで判定する。

これは日本の SI の**請負契約と検収**という商習慣に、真正面からぶつかります。「検収基準は正答率92%以上」という契約書を、誰が、いつ書くのか。要件定義の時点では、92% が妥当なのか、そもそも到達可能なのかが誰にも分からない。

だから、発見と実装と評価を**同じ人が同じ週にやる**必要があります。分けられないのではなく、分けると情報が失われて意思決定できなくなる。FDE はこの制約から逆算された職種です。

インタビューガイドの中で、いちばん職種の本質を表している回答例がこれです。

> 私ならエージェントを作ることから始めません。まずワークフローとリスクを定義します。アシスタントが下書きを作るだけなら、システムはもっと自律的でいい。顧客レコードを更新したり外部にメッセージを送るなら、ツールスキーマ、権限チェック、監査ログ、高リスク操作への人間の承認を要求します。

技術力の話をしているようで、していません。**業務上のリスクの大きさから、システムの自律度を決めている**。これは業務が分かっていないと書けず、同時に実装できないと絵に描いた餅になります。

## 7. コンサルとの違い：成果物がスライドではない

ここまで来ると、いわゆる大手コンサルのシステム導入支援との違いが具体的に言えます。

| | コンサル／Solutions Architect | FDE |
|---|---|---|
| 最終成果物 | 提案書・設計書・推奨事項 | 動いている本番システム |
| コードを書くか | 基本的に書かない（設計・助言） | 顧客リポジトリにコミットする |
| 関与期間 | プロジェクト単位で切れる | 長期で張り付く |
| 責任の終点 | 引き渡し | 本番で使われ続けること |
| 自社プロダクトへの影響 | なし | 現場知見が製品仕様になる |

インタビューガイドは Solutions Architect との違いをこう切っています。FDE は**作って納める**、Solutions Architect は**助言して設計する**。OpenAI の説明も同じ線で、FDE は「従来のクラウド Solutions Architect よりも大きな曖昧さの中で」働き、顧客のインフラ上で直接コードを書く、としています。

そして Pragmatic Engineer の整理が端的です。

> コンサルタントは一度きりの推奨を提供する。FDE は顧客と長期で働き、かつ自社プロダクトそのものに貢献する。

「作らないこと」がコンサルの弱点だと言いたいのではありません。**曖昧なまま作り始められるかどうか**が、この領域では決定的だという話です。仕様が凍結できない以上、助言と実装が分かれた瞬間に、往復のコストが発生し続けます。

## 8. 面接プロセスが、職種を一番正確に語っている

求人票よりも、面接で何を見られるかのほうが、職種の実像をよく表します。Anthropic の FDE のループは、おおむね次の構成です。

1. **コーディング** — Python / TypeScript の本番品質。JSON パース、エラーハンドリング、async、ユニットテスト、リトライと指数バックオフ、認証フィルタ、構造化出力のバリデーション
2. **Applied AI ビルド** — プロンプト／コンテキストエンジニアリング、ツール設計、MCP サーバー、Agent Skills、サブエージェント、evals、RAG、モデル選定
3. **エンタープライズ AI システム設計** — ワークフローの明確化、成功指標の定義、データとシステムのマッピング、アクション境界、アーキテクチャ、セキュリティ（認証・最小権限・監査）、evals、可観測性、ロールアウト計画
4. **顧客ディスカバリー／導入ケース** — 曖昧なエンタープライズのシナリオを、ステークホルダーマッピングとパイロットのスコープに落とす
5. **バリュー／ミッション** — 安全性のトレードオフをどう判断するか
6. **行動面接** — 顧客との緊張関係をどう扱ったか、技術的トレードオフ、失敗からの学習

1番と3番と4番が**同じ一人の面接ループに入っている**、というのがこの職種のすべてです。日本なら1番は開発ベンダーの、3番はアーキテクトの、4番はコンサルの面接です。

ガイドが挙げている「弱い言い方／強い言い方」の対比も、期待値の高さがよく分かります。

| 弱い | 強い |
|---|---|
| 「Claude でチャットボットを作りました」 | 「顧客のチケットを読み、社内ツールを呼び、引用付きで解決案を生成する Claude ワークフローを作り、ロールアウト前に evals で根拠妥当性とエスカレーション品質を測定しました」 |
| 「顧客対応の経験があります」 | 「顧客のサポート・セキュリティ・プラットフォームの3部門とディスカバリーを回し、曖昧な自動化目標をスコープの切れたパイロットに変え、統合を実装し、リスクゲート付きのロールアウト計画を作りました」 |
| 「プロンプトエンジニアリングができます」 | 「プロンプトはシステムの一部として扱っています。コンテキスト選択、ツール定義、スキーマ制約、eval ケース、トレースレビュー、レイテンシとコストの予算、ロールバックまで含めて」 |

右列は全部、**一人が最初から最後まで通した人にしか書けない文章**です。ガイドはリクルーター面接の最大の失敗を「エンタープライズの現実に耐えるシステムを出荷するエンジニアではなく、**AI デモビルダーに聞こえてしまうこと**」だと書いています。

## 9. で、日本で「FDE」と呼ばれているものは

ここが、この記事を書いた理由でもあります。

日本でも2025年以降 FDE の求人が出はじめ、AI 時代の花形職種として紹介されはじめました。一方で、SIer 側からは「日本型 FDE」という言い方も出てきています。**客先常駐という既存の形に、新しいラベルを貼れるのではないか**という発想です。

形だけ見れば、確かに似ています。顧客先に行く。顧客の業務を理解する。顧客のシステムを触る。

決定的に違うのは、ここまで見てきた2点です。

**第一に、自社プロダクトを持っているかどうか。** FDE は自社プロダクトの会社の社員で、現場の知見はプロダクトに還る。note の記事が指摘するとおり、Palantir は FDE を CEO 直轄に置いていました。フィードバックの経路が組織図に埋め込まれている。売っているものが工数であるかぎり、この経路は構造上生まれません。

**第二に、要件が固まる前に入るかどうか。** 客先常駐 SE は、顧客が定義した要件に基づいて開発・運用します。FDE は、顧客がまだ言語化できていない課題を発見して、**何を作るべきかを決める**ところから入ります。つまり FDE にとって、顧客が要件を言えないことは事故ではなく**前提条件**です。

この2つがないまま「FDE」と名乗ると、単に常駐 SE の呼び名が変わっただけになります。そして残念ながら、名前が変わっても、契約が請負で、検収が仕様一致で、知見の戻り先がないなら、LLM 導入は同じ理由で失敗します。**確率的に振る舞うシステムを、決定論を前提にした契約で作ろうとしている**という理由で。

## 10. 日本で「FDE」という職種を作るのは、たぶん無理

ここまで読んで、正直に言います。**この職種を日本で成立させるのは、ほぼ不可能だと思っています。**

理由は、この記事で挙げてきたものがそのまま効いてきます。

- **人材の層がない。** 求人票の要件を全部満たす人 — 業務を聞き出せて、本番品質のコードを書けて、クラウドに載せられて、権限と監査ログを設計できて、法務とも話せる人 — を採ろうとしても、市場にほとんどいません。いないのは能力の問題ではなく、**分業を前提にキャリアを設計してきた**からです。20年かけてできた層は、20年かけないと戻りません
- **契約モデルが噛み合わない。** 請負・検収という商習慣は「正解が事前に書ける」ことに依存しています。確率的に振る舞うシステムには、この枠がそもそも被せられません
- **還流の経路が組織図にない。** FDE の価値の半分は「現場知見が自社プロダクトに戻ること」です。売っているものが工数であるかぎり、この経路は作れません
- **そして何より、暗黙知の壁が厚い。** 日本の現場の業務知識は、ドキュメントではなく人の頭と慣習の中にあります。外から来た人が数週間のディスカバリーで取り出せる量ではありません

つまり、いま日本で「FDE を採用します」と言っても、高い確率で**常駐 SE の呼び名が変わるだけ**で終わります。

## 11. 方向を逆にする——中の人を強くするほうが、距離が短い

ただ、ここで諦める必要はありません。**向きを逆にすればいい**と思っています。

FDE という仕組みの本質は、肩書きでも出張でもありません。**「業務を分かっている人が、そのまま作れる状態」を作ること**です。Palantir はそれを「エンジニアを現場に送り込む」ことで実現しました。要件を言えない顧客から要件を引き出すには、それが最短だったからです。

でも、最短経路は条件で変わります。いま日本の会社を見ると、埋めるべきギャップはこうなっています。

| 必要なもの | 外部の技術者 | 社内の業務担当者 |
|---|---|---|
| 業務の暗黙知 | **ほぼゼロから。数ヶ月〜** | **すでに持っている** |
| 何が正解かの判定 | **できない**（顧客に聞くしかない） | **本人が正解を知っている** |
| 部門をまたいだ合意 | 社外の人として調整 | 社内の人として調整 |
| 実装・デプロイ・評価の技術 | 持っている | 持っていない |

**上3行は、取得にいちばん時間がかかる資産です。そしてそれは、すでに社内にあります。** 一方、いちばん下の1行 — 実装とデプロイ — は、この2年でもっとも急速に安くなった部分です。コーディングエージェント、MCP、Agent Skills。コードを書く工程のコストが、桁で下がりました。

だとすると、**「エンジニアに業務を教える」より「業務の人に作る力を渡す」ほうが、距離が短い。** 少なくとも日本ではそうなっている会社が多いはずです。

### エンジニアの仕事は、前線に立つことではなく足場を作ること

この向きでいくと、社内エンジニアの役割が変わります。**自分が作るのをやめて、現場の人が安全に作れる足場を用意する側に回る**、ということです。

- **壊しても戻せる環境。** サンドボックス、権限の最小化、監査ログ、ロールバック手順。現場の人が「触っていいですよ」と言われるために必要な条件はこれです
- **社内の部品。** 基幹システムや SaaS を叩く **MCP サーバー**、業務手順を固めた **Agent Skills**。現場の人が組み合わせられる粒度で用意する
- **評価（evals）の型。** ここが一番大事です。LLM の出力が「合っているか」を判定できるのは、**業務を知っている人だけ**です。エンジニアには判定できません。だからエンジニアがやるべきなのは判定そのものではなく、**現場の人が判定結果を入力すれば回る仕組み**を作ることです
- **本番に出すまでの導線。** パイロット、人間のレビュー、合格ゲート、段階的な展開。セクション1で見た FDE の職務内容のうち、これは社内エンジニアがそのまま引き受けられる部分です

面接ガイドが挙げるエンタープライズ設計の10ステップ（ワークフローの明確化 → 成功指標 → データとシステムのマッピング → アクション境界 → アーキテクチャ → セキュリティ → evals → 可観測性 → ロールアウト → プロダクトへの還流）は、**一人でやる必要はありません**。重要なのは、**同じ建物の中で、同じ週に回ること**です。一人でやるのは手段であって、目的ではない。

## まとめ

- FDE は、**要件を言えない顧客のために発明された**職種（出自は Palantir、軍事用語の「前線配備」から）
- 求人票と面接ガイドから読み取れる異常さは、スキルの高さではなく、**業務発見から実装・本番デプロイ・ドキュメント・製品フィードバックまで、工程を一つも分けない**こと
- それが成立するのは、CS の共通教育とコードを書き続けられるキャリアトラックによって、**守備範囲の広い個人が市場に厚くいる**から
- それが必要なのは、LLM が確率的で、**仕様を事前に凍結できず、検収が定義できない**から。分けると意思決定に必要な情報が失われる
- コンサルとの違いは成果物（スライドか、動く本番システムか）。常駐 SE との違いは**自社プロダクトへの還流経路**と、**要件確定前に入るか**
- **日本で「FDE」という職種を作るのは、たぶん無理。** 人材の層、契約モデル、還流経路、暗黙知の壁のすべてが逆を向いている
- だから**向きを逆にする**。外から技術者を入れて業務を覚えさせるより、**中にいる業務の人に作る力を渡す**ほうが距離が短い。社内エンジニアは前線に立つのではなく、**足場（権限・部品・evals・導線）を作る側**に回る

最後にもう一度、求人票の要件を眺めてみてください。あそこに並んでいる項目のうち、**いちばん代替が効かないもの**は何でしょうか。

Python でも、MCP でも、クラウドでもありません。**曖昧な業務ワークフローを、スコープの切れた出荷可能なシステムに変換できること**。そして**何が正解かを判定できること**です。

そして、その2つを持っている人は、**あなたの会社に、もう、たくさんいます。** 経理にも、営業事務にも、品質保証にも、カスタマーサポートにも。ただ、作る手段を渡されてこなかっただけです。

**革命は、外から来ません。** FDE を輸入しても来ないし、たぶん大手に発注しても来ない。中から起こすしかない。

非エンジニアのみなさん、がんばれ。エンジニアのみなさんは、その人たちが踏める足場を作りましょう。
