スキル（`SKILL.md`）は、書いたその日はうまく動きます。悪くなるのは、そのあとです。失敗するたびに規則が足され、別の人が別の規則を足し、似たスキルが増え、半年後には誰も全体を把握していない長い文書になります。

本稿では、スキルでよく見る失敗（アンチパターン）を 13 個集め、それぞれについて次の 4 つをまとめました。

- **症状：** どんな見た目になっているか
- **なぜ悪いか：** 論文や公式の指針の根拠
- **見つけ方：** そのまま使えるスクリプトや指示文
- **直し方：** 直す前と後の例

:::message
数字はそれぞれの出典の設定での値です。自分の環境に持ち込めるのは数字ではなく、やり方と結論の向きです。
:::

## 0. 一覧

| # | アンチパターン | 一言で |
|---|---|---|
| 1 | 長すぎる | 背景と例が大半を占めている |
| 2 | 網羅しすぎる | あらゆる場合を列挙している |
| 3 | 複数人で書き足して矛盾する | 同じ場面に、逆の規則が 2 つある |
| 4 | 同じ規則が 2 か所にある | `CLAUDE.md` とスキル、スキル同士で重複している |
| 5 | 説明文が要約になっている | 「何をするか」だけで「いつ使うか」がない |
| 6 | 似たスキルが乱立する | 取り違えが起きる |
| 7 | 強調の乱発と但し書き | `ALWAYS`、`NEVER`、「ただし重要な場合を除く」 |
| 8 | 「確認せよ」の積み増し | 失敗のたびに確認の規則が増える |
| 9 | 固定パスとテンプレート | 作業ごとの指示を上書きする |
| 10 | 時期に依存する記述と古い手順の残骸 | 「2025 年 8 月までは…」 |
| 11 | 参照の入れ子 | 参照ファイルがさらに参照ファイルを呼ぶ |
| 12 | 用語の揺れ | 同じものを 3 通りの名前で呼ぶ |
| 13 | 測らずに足す・モデルに一から書かせる | 効いているか誰も知らない |

1〜4 は「中身が膨らむ」、5〜6 は「使われ方がおかしい」、7〜12 は「書き方」、13 は「運用」の問題です。

## 1. 先に全部を検査する

13 個のうち、機械的に見つけられるものをまとめて検査するスクリプトです。手元のスキルが置いてある場所で実行します。

```bash
#!/usr/bin/env bash
# 使い方: ./skill-lint.sh  （~/.claude/skills と .claude/skills を検査する）
for f in ~/.claude/skills/*/SKILL.md .claude/skills/*/SKILL.md; do
  [ -f "$f" ] || continue
  lines=$(wc -l < "$f")
  desc=$(awk '/^---$/{n++; next} n==1 && /^description:/{sub(/^description:[ ]*/,""); print; exit}' "$f")
  shout=$(grep -cE '\b(ALWAYS|NEVER|MUST|IMPORTANT|CRITICAL)\b' "$f")
  paths=$(grep -cE '(/Users/|/home/|C:\\|~/[A-Za-z])' "$f")
  dates=$(grep -cE '20[0-9]{2} ?年|20[0-9]{2}-[0-9]{2}' "$f")
  checks=$(grep -cE '確認(せよ|する|してください)|verify|double-check' "$f")
  printf '%5d 行 | 説明 %4d 字 | 強調 %2d | 固定パス %2d | 日付 %2d | 確認 %2d | %s\n' \
    "$lines" "${#desc}" "$shout" "$paths" "$dates" "$checks" "$f"
done | sort -rn
```

（説明文を複数行で書いている場合は、1 行目しか数えません。）

目安は次のとおりです。

| 列 | 目安 | 対応するアンチパターン |
|---|---|---|
| 行 | 500 行未満（公式の指針） | 1・2 |
| 説明 | 1,024 文字以内（公式の上限）。短すぎるのも問題 | 5 |
| 強調 | 0 に近いほど良い | 7 |
| 固定パス | 0 | 9 |
| 日付 | 0 に近いほど良い | 10 |
| 確認 | 増え続けていないか | 8 |

矛盾（3）、重複（4）、似たスキル（6）、用語の揺れ（12）は機械では見つけにくいので、Claude に探させます（各節の指示文）。

## 2. 中身が膨らむ

### アンチパターン 1：長すぎる

**症状：** 数百行から千行を超える。冒頭に背景説明が何段落も続き、例が何個も並び、肝心の手順はその下に埋もれている。

**なぜ悪いか：**

- Claude Code では、会話が要約されたあと、各スキルは**先頭の 5,000 トークンだけ**が添付し直されます。長いスキルの後ろの方の規則は、長い作業の途中で消えます
- [SkillReducer](https://arxiv.org/abs/2603.29919) が GitHub から集めた 55,315 個のスキルを調べると、本文の 6 割以上は**手順として実行できない内容**（背景 41%、例 13%、ひな形 8%）でした。同じ論文は、本文を平均 39% 縮めても、86% の課題で出来が元と同等以上だったと報告しています
- 公式の指針は「Claude はもともと十分に賢い」ことを前提に、知っていることを書かないよう求めています

**見つけ方：** 1 章のスクリプトで 500 行を超えるものを探します。

**直し方：** 本文を「中核の規則／背景／例／ひな形／重複」に分け、種類ごとに扱います（SkillReducer の分け方）。

| 種類 | 扱い |
|---|---|
| 中核の規則 | 残す。似たものは統合して箇条書きにする。先頭に置く |
| 背景 | 数値・閾値・接続先などの事実だけ残して要約する。モデルが知っている一般論は消す |
| 例 | 概念ごとに代表 1 つだけ残す |
| ひな形 | 別ファイル（`templates/`）に出し、本文からは参照だけにする |
| 重複 | 消す |

**Claude に分けさせる指示文：**

```text
次の SKILL.md を段落ごとに「中核の規則／背景／例／ひな形／重複」のどれかに分類し、表にしてください。
そのうえで、次の方針で書き直した案を出してください。
- 中核の規則は統合して箇条書きにし、本文の先頭に置く
- 背景は、数値・閾値・接続先などの事実だけを残して要約する。Claude が一般に知っていることは消す
- 例は概念ごとに 1 つだけ残す
- ひな形は templates/ に出す前提で、本文からは参照だけにする
- 最後に「消した内容」と「別ファイルに移した内容」を一覧で示す

<ここに SKILL.md を貼る>
```

最後の一覧は必ず人が読みます。モデルは要約するたびに固有の知見を落とす傾向があるからです（[ACE](https://arxiv.org/abs/2510.04618) の言う「簡潔さへの偏り」）。

### アンチパターン 2：網羅しすぎる

**症状：** 「〜の場合は A、〜の場合は B、〜の場合は C…」と、起こりうる場合を全部書こうとしている。規則が数十個並んでいる。

**なぜ悪いか：**

- [SkillsBench](https://arxiv.org/abs/2602.12670) は同じスキルを長さ 4 段階で比べました。簡潔な版で +19.0 ポイント、標準で +21.5、詳細で +14.5、**網羅的な版で +0.7**。網羅すると、効果がほぼ消えます
- [IFScale](https://arxiv.org/abs/2507.11538) は、指示の数を増やしたときの守られ方を測りました。指示が増えるほど守られなくなり、最も良いモデルでも指示 500 個では 68% しか守れませんでした。また、**先に書いた指示ほど守られやすい**傾向がありました
- 規則が多いほど、規則同士がぶつかる組み合わせも増えます（アンチパターン 3）

**見つけ方：** 本文の箇条書きの数を数えます。

```bash
grep -cE '^\s*([-*]|[0-9]+\.)\s' path/to/SKILL.md
```

**直し方：** 場合分けを並べる代わりに、**判断の基準**を書きます。

```markdown
<!-- 前 -->
- TypeScript のファイルは `yarn lint` を実行する
- Vue のファイルは `yarn lint` を実行する
- JSON のファイルは `yarn format` を実行する
- Markdown のファイルは `yarn format` を実行する
- テストのファイルは `yarn test` も実行する
（以下 20 行）

<!-- 後 -->
## 完了の条件
- `yarn format && yarn lint && yarn test` がすべて通っている
```

公式の指針は、これを**自由度**の問題として説明しています。壊れやすい手順はスクリプトにして「この通りに実行する」と書き、判断が要る作業は方針と完了の条件だけを書きます。場合分けを全部書くのは、そのどちらでもない中途半端な状態です。

### アンチパターン 3：複数人で書き足して矛盾する

**症状：** チームで共有しているスキルに、別々の人が別々の時期に規則を足した結果、同じ場面に逆の規則が 2 つある。

```markdown
## 手順
3. テストが落ちたら、原因を調べて直してから先に進む
...
## つまずきどころ
- 既存のテストが落ちている場合は、気にせず先に進む（2026-03 追記）
...
## 注意
- テストが 1 つでも落ちていたら、作業を止めて報告する
```

**なぜ悪いか：**

- 矛盾した指示を与えると、モデルの指示の守り方は大きく崩れます。[IHEval](https://arxiv.org/abs/2502.08745) は、優先度の違う指示が矛盾する場面で、**評価したすべてのモデルの性能が急に落ちた**と報告しています
- [Control Illusion](https://arxiv.org/abs/2502.15851) は、システムプロンプトと利用者の指示を分けても、**どちらを優先するかは安定しない**ことを示しました。モデルは、指示の位置づけより、制約の種類そのものに対する好みで動きます
- つまり、「後から書いた方が優先される」「『注意』の節の方が強い」といった、書いた人の想定どおりには動きません。どちらが選ばれるかは、実行のたびに変わりえます

**なぜ起きるか：**

- 書き足す人は、スキル全体を読まずに、自分が困った場面の規則だけを足す
- 足すときに、既存の規則を消したり直したりしない（消すのは怖い）
- 誰がその規則をなぜ書いたかが残っていないので、古い規則を消してよいか判断できない

**見つけ方：** Claude に矛盾を探させます。

```text
次の SKILL.md の規則をすべて抜き出し、番号を付けて一覧にしてください。
そのうえで、同じ場面に対して矛盾する指示をしている規則の組を挙げてください。
組ごとに、
- どの場面で矛盾するか（具体的な状況の例）
- どちらかを残すならどちらか、その理由
- 両方を 1 つの規則に統合した案
を書いてください。矛盾がない場合は「なし」と書いてください。

<ここに SKILL.md を貼る>
```

**直し方：**

1. **矛盾した規則を 1 つにする。** 「既存のテストが落ちている場合」と「自分の変更でテストが落ちた場合」のように、場面を分けて書けば両立することが多い

   ```markdown
   - 自分の変更でテストが落ちたら、直してから先に進む
   - 作業前から落ちているテストは、直さずに報告に書く（別の作業で直すため）
   ```

2. **規則に理由を付ける。** 理由が書いてあれば、次に書き足す人が既存の規則の意図を理解でき、消してよいかを判断できます。全部大文字の強調より理由の方が効く、という `skill-creator` の助言とも一致します
3. **持ち主を決める。** スキルごとに責任者を 1 人決めます。リポジトリに置いているなら、`CODEOWNERS` で `.claude/skills/` の変更に責任者のレビューを必須にします

   ```text
   # .github/CODEOWNERS
   /.claude/skills/review-pr/  @alice
   /.claude/skills/deploy/     @bob
   ```

4. **書き足すときの手順を決める。** 足す前に全体を読み、同じ場面の規則がないかを探し、あれば足すのではなく直す。この手順自体を、スキルの冒頭やチームの手引きに書いておきます
5. **プルリクエストで矛盾を検査する。** スキルを変更したプルリクエストでは、上の指示文で矛盾を探させます

### アンチパターン 4：同じ規則が 2 か所にある

**症状：** 同じ規則が、`CLAUDE.md` とスキルの両方、または複数のスキルに書かれている。最初は同じ内容だったが、片方だけが更新されて食い違っている。

**なぜ悪いか：** 重複は、矛盾（アンチパターン 3）の予備軍です。片方だけを直すと、その時点で矛盾になります。また、同じ規則を何度も読ませるのは文脈の無駄です。

**見つけ方：**

```text
次の CLAUDE.md と、各スキルの SKILL.md を読んでください。
同じ内容の規則が 2 か所以上に書かれている箇所を、場所と一緒に一覧にしてください。
内容が食い違っているものは、特に印を付けてください。

<CLAUDE.md と各 SKILL.md を貼るか、パスを指定する>
```

**直し方：** **1 つの規則は 1 か所に書く**、を原則にします。置き場所は、その規則がいつ必要かで決めます。

| いつ必要か | 置き場所 |
|---|---|
| どの作業でも必ず守る | `CLAUDE.md`、または確実に実行させたいならフック |
| 特定の作業のときだけ | その作業のスキル |
| 複数のスキルで共通 | 1 つの参照ファイルにまとめ、各スキルからは参照だけにする |

毎回必ず守らせたい規則は、文章よりフックに移す方が確実です。Claude Code の文書も、作業全体にかかる規則はフックに移すよう勧めています。

## 3. 使われ方がおかしい

### アンチパターン 5：説明文が要約になっている

**症状：** `description` が「PR のレビューを手伝います」のような、何をするかの要約だけになっている。または、手順の要約が書いてある。または、説明文がない。

**なぜ悪いか：**

- モデルがスキルを使うかどうかは、ほぼ説明文だけで決まります。公式の指針は「何をするか」と「いつ使うか」の両方を書くよう求めていて、悪い例として "Helps with documents" を挙げています
- 公開スキル集 superpowers は、説明文に**手順の要約を書くと、モデルが本文を読まずに要約どおりに動いてしまう**と注意しています
- SkillReducer の調査では、GitHub のスキルの 26% に説明文がありませんでした

**見つけ方：** 1 章のスクリプトで、説明文が短すぎるもの（数十文字）を探します。使用回数を記録して、一度も使われていないスキルを探すのも有効です（アンチパターン 13）。

**直し方：** 説明文を、発火の条件として書き直します。

```yaml
# 前
description: PR のレビューを手伝います。差分を取得し、観点ごとに確認し、結果をまとめます。

# 後
description: >
  プルリクエストの差分を、チームのレビュー観点（認証・エラー処理・テスト）で確認する。
  ユーザーが「レビューして」「PR を見て」と言ったとき、またはプルリクエストの番号や URL が渡されたときに使う。
  コードの書き換えまで頼まれたときは使わない（通常の編集で行う）。
```

### アンチパターン 6：似たスキルが乱立する

**症状：** `review-pr`、`code-review`、`pr-check`、`review-helper` のように、似た名前と似た説明文のスキルが並んでいる。人によって使うスキルが違う。

**なぜ悪いか：**

- [Skill Shadowing](https://arxiv.org/abs/2605.24050) は、スキルを 202 個まで増やすと性能が最大 21% 落ちると報告しています。主な原因は文脈が長くなることではなく、**別のスキルを誤って選ぶこと**でした
- SkillsBench では、1 つの作業に渡すスキルが 2〜3 個なら +19.0 ポイント、4 個以上だと +10.1 ポイントでした
- 似たスキルがあると、規則がそれぞれに書き足され、アンチパターン 3・4 も起きやすくなります

**見つけ方：**

```text
~/.claude/skills/*/SKILL.md と .claude/skills/*/SKILL.md の name と description を読んで、
説明文が似ていて取り違えが起きそうな組を挙げてください。
組ごとに「統合する」「説明文で使い分ける（それぞれに足す一文の案つき）」「片方を消す」のどれが良いか提案してください。
```

**直し方：** 統合できるものは統合します。統合できないものは、説明文に「使わない場合」を書いて使い分けます。一度も使われていないものは消します。

## 4. 書き方

### アンチパターン 7：強調の乱発と但し書き

**症状：** `IMPORTANT:`、`ALWAYS`、`NEVER`、`MUST` が何十個も並んでいる。または、「ただし重要な場合を除く」「状況に応じて」のような但し書きが付いている。

**なぜ悪いか：**

- 全部を強調すると、どれも強調されていないのと同じです
- 公式の `skill-creator` は、全部大文字の `ALWAYS` や `NEVER` を「黄色信号」と呼び、代わりに理由を書くよう勧めています。理由があれば、モデルは書かれていない場面でも正しく判断できます
- superpowers は、但し書きを付けると結果が不安定になると注意しています。「重要な場合」がどれかを、モデルが毎回違うふうに判断するからです

**見つけ方：** 1 章のスクリプトの「強調」の列。但し書きは次で探します。

```bash
grep -nE 'ただし|場合を除|状況に応じ|必要に応じ|unless|except when' path/to/SKILL.md
```

**直し方：**

```markdown
<!-- 前 -->
- NEVER edit generated files unless absolutely necessary.

<!-- 後 -->
- `*.gen.ts` は手で直さない。次の生成で上書きされ、変更が消えるため。生成元の `schema.yaml` を直して `yarn gen` を実行する。
```

### アンチパターン 8：「確認せよ」の積み増し

**症状：** 失敗するたびに「〜を確認する」「〜を必ず確かめる」という規則が足され、確認の規則が十数個並んでいる。

**なぜ悪いか：** [BiPA](https://arxiv.org/abs/2610.37201) は、自動の最適化器がスキルに足した規則 337 個を調べ、その**半分が「確認せよ」だった**と報告しています。そのうえで、次のことを示しました。

- 確認の規則は、スキルの文章を少し長くするだけでなく、**確認のための手番（モデルの呼び出し）を増やす**。増えた入力トークンの 73% は手番の増加によるもので、スキルの文章そのものは 21% だった
- 手番が増えると、それまでの履歴を毎回送り直すので、費用は手番の数以上に増える
- それでいて、テストの成功率は手書きの初期スキルとほぼ変わらなかった

人が書き足す場合も同じことが起きます。「念のため確認」は、費用は確実に増えるのに、効果は測られていないことがほとんどです。

**見つけ方：** 1 章のスクリプトの「確認」の列。

**直し方：**

- 確認を**検証スクリプト 1 つにまとめる**。「A を確認、B を確認、C を確認」を並べる代わりに、`scripts/check.sh` を作り、「完了前に `scripts/check.sh` を実行し、通るまで直す」と 1 行で書く
- 確認の規則を足すときは、**その失敗が実際に何回起きたか**を書き添える。一度しか起きていない失敗のために、毎回の作業で確認させない
- 定期的に確認の規則を 1 つずつ外して、失敗が増えるか確かめる。増えないものは消す

### アンチパターン 9：固定パスとテンプレート

**症状：** `/Users/alice/work/app/` のような特定の人のパスや、「出力は必ずこの形式で」という固定のテンプレートが本文に書いてある。

**なぜ悪いか：** 公開スキル 98 本を、スキルあり・なしの対で測った [SWE-Skills-Bench](https://arxiv.org/abs/2603.15401) では、有害だったスキルは、本文の固定パスやテンプレートが**作業ごとの指示を上書きしていました**。スキルを書いた人の環境では正しくても、別の人や別の作業では誤った指示になります。

**見つけ方：** 1 章のスクリプトの「固定パス」の列。

**直し方：**

- パスは、リポジトリのルートからの相対パスにするか、「`git rev-parse --show-toplevel` の下の `app/`」のように求め方を書く
- テンプレートは別ファイルに出し、「依頼に形式の指定がなければ `templates/report.md` を使う」と、**依頼の指示を優先する**ことを明記する

### アンチパターン 10：時期に依存する記述と古い手順の残骸

**症状：** 「2025 年 8 月までは旧 API を使う」「来月から新しい手順に変わる」のような記述。新しい手順に変わったのに、古い手順も消されずに残っている。

**なぜ悪いか：** 公式の指針は、時期に依存する記述を避けるよう求めています。書いた時点では正しくても、いつか必ず誤りになり、しかも誤りになったことに誰も気づきません。古い手順と新しい手順が並んでいると、どちらを使うかはモデル次第です（アンチパターン 3 と同じ問題）。

**見つけ方：** 1 章のスクリプトの「日付」の列。

**直し方：** いまの手順だけを本文に書きます。古い手順を残す必要があるなら、「古いやり方」という節に分け、「この節は、旧バージョンのリポジトリを扱うときだけ読む」と条件を書きます。

### アンチパターン 11：参照の入れ子

**症状：** `SKILL.md` が `reference.md` を参照し、`reference.md` がさらに `details/api.md` を参照し…と、何段も参照が続いている。

**なぜ悪いか：** 公式の指針は、参照を **`SKILL.md` から 1 階層だけ**にするよう求めています。参照ファイルからさらに別のファイルを参照すると、モデルが途中までしか読まない（先頭の数十行だけを読んで済ませる）ことがあるからです。

**見つけ方：**

```bash
grep -rnE '\]\([^)]+\.md\)' path/to/skill/ --include='*.md' | grep -v '/SKILL.md:'
```

`SKILL.md` 以外のファイルから `.md` へのリンクが出てきたら、入れ子になっています。

**直し方：** 参照ファイルは全部 `SKILL.md` から直接参照し、それぞれに「いつ読むか」を書きます。100 行を超える参照ファイルには、冒頭に目次を置きます。

```markdown
## 詳しい資料
- API の仕様（エンドポイントを追加・変更するときに読む）: [api.md](api.md)
- エラーコードの一覧（エラー処理を書くときに読む）: [errors.md](errors.md)
```

### アンチパターン 12：用語の揺れ

**症状：** 同じものを「フィールド」「欄」「項目」「カラム」と、場所によって違う名前で呼んでいる。複数人で書き足したスキルに多い。

**なぜ悪いか：** 公式の指針は、1 つの概念に 1 つの語を使うよう求めています。名前が違うと、モデルは別のものだと解釈することがあります。

**見つけ方：**

```text
次の SKILL.md で、同じものを違う名前で呼んでいる箇所を探してください。
用語ごとに、使われている呼び方と出てくる行を一覧にし、統一する呼び方を提案してください。

<ここに SKILL.md を貼る>
```

**直し方：** 呼び方を 1 つに決めて置き換えます。用語が多いスキルでは、冒頭に短い用語の表を置きます。

## 5. 運用

### アンチパターン 13：測らずに足す・モデルに一から書かせる

**症状：** スキルを書いたり直したりしたが、スキルがある場合とない場合で出来が変わったかを、誰も確かめていない。または、モデルに「〜のスキルを書いて」と頼んで、できたものをそのまま使っている。

**なぜ悪いか：**

- SkillsBench では、**モデルに一から書かせたスキルは、スキルなしより悪くなりました**
- SWE-Skills-Bench では、公開スキル 98 本のうち 92 本は効果を検出できず、2 本は有害でした
- 測らずに足した規則は、効いているかどうか分からないので、消す判断もできません。その結果、アンチパターン 1〜4 と 8 が進みます

**見つけ方：** 使用回数を記録します。`PreToolUse` フックで、スキルが使われるたびに記録する設定です（`~/.claude/settings.json`）。

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Skill",
        "hooks": [
          {
            "type": "command",
            "command": "jq -c '{ts: (now | todate), skill: .tool_input.skill, cwd: .cwd}' >> ~/.claude/skill-usage.jsonl"
          }
        ]
      }
    ]
  }
}
```

1〜2 週間たったら集計します。

```bash
jq -r .skill ~/.claude/skill-usage.jsonl | sort | uniq -c | sort -rn
```

**直し方：**

1. **書く前に、スキルなしで失敗させる。** スキルなしで代表的な作業をさせ、失敗を記録し、その失敗を直すのに必要な最小限の指示だけを書く（公式の指針の「評価を先に作る」）
2. **スキルあり・なしを比べる。** `--disable-slash-commands` はすべてのスキルを無効にするフラグです。同じ依頼を両方で 3 回ずつ走らせて比べます

   ```bash
   for r in 1 2 3; do
     claude -p "PR #123 をレビューして" > "with_${r}.md"
     claude -p --disable-slash-commands "PR #123 をレビューして" > "without_${r}.md"
   done
   ```

3. **規則を足すときは、何の失敗に対するものかを書き残す。** 「つまずきどころ」の節に、「<どんな状況で> <何をしてしまう> → <代わりにどうする>（<理由>）」の形で 1 行ずつ足す
4. **モデルに書かせるなら、検査とセットにする。** 書かせたスキルで実際に作業させ、スキルなしより良くなったときだけ採用する

## 6. 直す順番

13 個を一度に直す必要はありません。効果と手間の釣り合いで、次の順に進めます。

1. **1 章のスクリプトを流す。** 数字の悪いスキルから手を付ける
2. **矛盾を消す（3・4）。** 矛盾は、どちらが選ばれるかが実行のたびに変わる、一番たちの悪い失敗です。共有しているスキルから先に
3. **説明文を直し、似たスキルを統合する（5・6）。** 使われ方が直ると、本文の問題も見えやすくなります
4. **本文を縮める（1・2・7・8）。** 中核の規則を先頭に、背景と例を削り、強調を理由に、確認をスクリプトに
5. **書き方を整える（9〜12）。** 固定パス、日付、参照の入れ子、用語
6. **測る仕組みを入れる（13）。** 使用回数の記録と、スキルあり・なしの比較。これがないと、半年後にまた同じ状態に戻ります

## まとめ

- スキルは、書いた日ではなく、**書き足されていくうちに**悪くなります。長くなり、網羅的になり、矛盾し、似たスキルが増えます。
- 長さと網羅性は、効果を消します。網羅的に書いたスキルの効果はほぼゼロでした（SkillsBench）。指示は増えるほど守られなくなり、先に書いたものほど守られます（IFScale）。
- 矛盾した規則は、どちらが選ばれるか分かりません。矛盾があるとモデルの守り方は大きく崩れ、優先順位の指定も安定しません（IHEval、Control Illusion）。**1 つの規則は 1 か所に、理由を付けて、持ち主を決めて**書きます。
- 「確認せよ」の積み増しは、手番を増やして費用を上げるだけで、効果が測られていないことがほとんどです（BiPA）。確認は検証スクリプト 1 つにまとめます。
- どのアンチパターンも、根っこは「**測らずに足す**」ことです。使用回数を記録し、スキルあり・なしを比べ、効いていない規則を消せる状態にしておきます。
