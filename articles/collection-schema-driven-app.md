カメラのレンズを何本か持っていて、**一度売って、後悔して、買い直した**ものがあります。

これを記録したい。焦点距離とF値だけなら既製のアプリにもありますが、「**いつ買って、いつ売って、いくらで、そして買い直したのはいつか**」を持てるものは見つかりませんでした。通算でいくら払ったのかも知りたい。

こういうことが、たぶん誰にでもあります。**自分のこだわりに合うアプリは、たいてい存在しない。**

スプレッドシートに逃げると、今度は続きません。**開いて、行を足して、15列を埋める**のが面倒だからです。

## 何が変わるか

いま僕のレンズ一覧はこうなっています。

```
「シグマの 35mm、売った。8万円」
```

これだけで、所有期間テーブルに売却の行が入り、通算収支が引き直されます。**フォームは開いていません。**

見るときは別です。一覧は「図鑑」という画面で、焦点距離のバーが並んで、どこに穴があるか一目で分かります。

**入力は会話、閲覧は専用の画面。** これが分かれているのが効きます。手で入力するのが面倒な理由と、一覧を眺めたい理由は、別のものだからです。

## 3つ動いています

僕と同僚が作ったものが、いま3つあります。**性格がぜんぶ違います。**

**映画リスト** — 観たい・観た映画。ジャンル・監督・視聴方法・評価・鑑賞日。「この映画観た、★4」で入る。見るときは **Netflix 風の横スクロール棚**で、テーマ別にポスターが並びます。

**カメラのレンズ** — 上の話です。焦点距離・F値・マウント・対応フォーマット、そして所有期間テーブル。**「図鑑」** ビューで焦点距離バーと35mm換算が出ます。

**気象庁の天気予報** — こちらは毎時、気象庁の公開 API から予報・警報注意報・台風・天気図を取り込みます。個人の記録ではありません。**テレビのニュース風**の画面で5モード。

3つ目が大事で、**これは個人メモの道具ではない**ということです。外部 API を叩いて定期更新し、業務で見られる画面を出せます。

## 何を書くとこうなるのか

レンズのコレクションの中身は、これだけです。

```
collections/isamu/lens/
  schema.json      116行   ← データモデルと画面の宣言
  SKILL.md          36行   ← エージェントへの説明
  meta.json         10行   ← 作者・説明・ライセンス
  views/図鑑.html          ← 任意。凝った画面が欲しいときだけ
  seed/items/*.json        ← 任意。サンプルデータ
```

**アプリ側のコードは1行も書いていません。**

`schema.json` はこういうものです。

```json
{
  "title": "映画リスト",
  "icon": "movie",
  "dataPath": "data/movies/items",
  "primaryKey": "id",
  "fields": {
    "title":  { "type": "string", "label": "タイトル", "required": true },
    "year":   { "type": "number", "label": "公開年" },
    "genre":  { "type": "enum", "label": "ジャンル",
                "values": ["アクション", "SF", "ドラマ", "コメディ"] },
    "rating": { "type": "number", "label": "評価" },
    "poster": { "type": "image", "label": "ポスター" }
  },
  "views": [
    { "id": "cinema", "label": "シネマ", "file": "views/cinema.html" }
  ]
}
```

これを置くと、**表・入力フォーム・カレンダー**が出ます。`views` を足すと自分の画面も足せます。フィールドを1つ増やしたければ、`fields` に1行足すだけです。

データは **1件1ファイルの JSON** で、`dataPath` の下に置かれます。DB はありません。**git に入れられるし、エディタで開けるし、消したければ `rm` です。**

## なぜエージェントが「この映画観た、★4」で分かるのか

`SKILL.md` がいるからです。これはエージェントへの説明書で、こう書いてあります。

```markdown
---
name: movies
description: 個人の映画リストコレクション。ユーザーが「この映画を追加して」
  「観たい映画を登録」「この映画を観た、★4」「未鑑賞の映画は?」などと
  言ったら使う。記録は dataPath に1件1ファイルの JSON で保存する。
---

## レコードの形
- `id` — kebab-case slug、主キー
- `watched` — boolean。`rating`(1〜5) と `watchDate` は `watched` のときだけ表示
...
```

**「こう言われたらこれを使え」と「データはこういう形だ」を、日本語で書いてあるだけ**です。エージェントはこれを読んで、`manageCollection` というツールで JSON を読み書きします。

だから**スキーマを変えたら SKILL.md も直す**必要があります。そこは自動ではありません。

## 共有は任意

コレクションはたいてい、**自分用に作って自分だけで使います**。レンズの所有履歴を他人に配る
理由はありませんし、配らなくても困りません。**作った数と、公開した数は別物です。**

そのうえで、配りたくなったときの口はあります。[レジストリ](https://github.com/receptron/mulmoclaude-collections)
に出すと、アプリの中の **Collections → Discover** に並び、import すると `/collections/<slug>` に
生えます。サンプルデータも一緒に入るので、**中身を見て自分用に書き換える**のが一番早い作り方です。

出すのはディレクトリを足して PR を出すだけです。

```
collections/<自分の GitHub ログイン名>/<slug>/
  SKILL.md  schema.json  meta.json
  screenshot.png?  views/*.html?  seed/items/*.json?
```

**他人の名前空間には出せません**（CI が弾きます）。

作るのが重いかというと、**スキーマのほとんどはフィールド定義**で、これは自分が何を記録したいかを
書いているだけです。凝った画面（`views/*.html`）は任意で、無くても表とフォームは出ます。

## 試すには

```bash
npx mulmoterminal@latest
```

起動したら Collections を開いて、Discover から好きなものを import してください。中身を見て、`schema.json` を自分用に書き換えるのが、たぶん一番早い作り方です。
