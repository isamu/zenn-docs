その日も、いつもどおりでした。

エージェントを30体ばかり並べて、それぞれに別の仕事を投げて、僕は色が変わるのを待っている。ファンはずっと唸っていましたが、**もうそれが普通の音**になっていたので、気にもしていませんでした。

そうしたら、**画面が暗くなりました。**

一瞬、スリープに入ったのかと思いました。キーを叩いても戻らない。電源ボタンを押しても、うんともすんとも言わない。

熱で落ちたんです。エアコンは効いていました。真夏の昼間でもありません。

[ターミナルを自作したら1日500コミットを超えた話](https://zenn.dev/singularity/articles/diy-terminal-500-commits)を書いてから、僕はずっと並列度を上げ続けてきました。**その結果が、これです。**

正直、こうなるとは思っていませんでした。ソフトウェアの話をしていたはずが、いつの間にか**部屋の温度の話**になっている。

ただ、ここに至るまでの過程が、自分でも妙に面白かったんです。**壁を1枚壊すたびに、次の壁が下の層から出てきました。**

```
認知  →  課金  →  CPU  →  OS  →  物理
```

先に断っておくと、これは趣味の環境の話ではありません。**仕事で、毎日こう回しています。** だから止められないし、だから壁に当たり続けています。

上から順に書きます。

## まず、自分の頭が限界だった

最初に詰まったのは、マシンではなく僕でした。

プレーンなターミナルを6分割して並べていた頃、同時に追えたのは **5〜6体まで**。それ以上並べても、どのセッションで何を頼んだのか、どれが自分を待っているのか、パッと見で分からなくなる。結局ひとつずつ覗きに行くことになるので、**並べた意味が無くなる。**

**6分割だったのは、選んだからではありません。そこが認知の天井だったからです。**

これは[ターミナルを自作して](https://github.com/receptron/mulmoterminal)、状態を色と音で外に出したら抜けました。**頭で覚えるのをやめた**、というだけです。天井は、道具に肩代わりさせれば動きます。

……と、そのときは思っていました。動いた天井の先に、次が待っているとは思わずに。

## 全部が同時に黙る

並列度を上げていったら、**今度はレート制限に当たりました。**

これ自体は当然です。ただ、1体ずつ動かしていた頃には見えなかった性質がありました。

**上限に当たると、全部が同時に止まるんです。**

1体なら「待たされているな」で済みます。30体が一斉に黙ると、**画面がまるごと静かになる。** 動いているものが1つも無い。あの瞬間の「あれ、全部死んだ？」という感じは、慣れたいまでもちょっと嫌です。

### 結局、契約を増やしました

**Claude Code の Max 20x を、複数アカウント持っています。**

書いていて、なかなかの話だなとは思います。ただ、30体を同時に回すというのは、**要するにそういうことでした。**

1アカウントで足りていた頃は、上限は「たまに当たるもの」でした。並列度を上げると、**上限は毎日必ず当たるもの**になります。そうなると、並列度を決めているのは技術ではなく契約数です。

**1つ目の壁は道具で越えられました。2つ目は、お金で越えるしかありませんでした。** ここは正直、あまり気持ちのいい解き方ではありません。

### 寝ている間も回しています

いまの生活はこうです。

寝る前に「**8時間ノンストップで進めておいて**」とお願いして、寝る。

そして朝起きると、**たいてい途中で止まっています。**

8時間ぶん頼んで、実際に進んだのは半分くらい。**残りの時間、マシンはただ黙って朝を待っていた**わけです。これを毎日やっています。

**上限がどこにあるかは、僕が寝ている間に決まる。** そういう感覚になってきました。

## 20コアあっても足りない

課金の壁の向こうにいたのは、**自分のマシンでした。**

いまの動かし方はこうです。

```
worktree ひとつにつき1セッション
5 worktree × 6 で、30ほど同時に動かす
   ↓
それぞれが unit test と lint を回す
   ↓
load average が 100 を超える
```

**20コアあります。それでも足りませんでした。**

エージェントが遅いのではありません。**マシンが順番待ちになっているだけ**です。でも、それぞれのセッションから見ると「テストが遅い」としか見えない。

### 一番時間を溶かしたのは、これでした

**この状態でテストがタイムアウトすると、変更のせいに見えます。**

実際は負荷のせいなのに、原因を変更のほうに探しに行く。差分を読み返して、ロジックを疑って、書き直して、また落ちる。**もう一度読み返す。**

そして、しばらくして負荷が下がった頃に、**何もしていないのに通ります。**

あれは本当に虚しい。**マシンが混んでいただけの時間を、自分のコードを疑って過ごしていた**わけです。これで溶かした時間が、たぶん一番長いと思います。

### 「CI に逃がせばいい」は、そんなに簡単じゃなかった

ここで当然、「ローカルで回さずに CI に投げればいいのでは」と思います。実際そうしてもいます。

**でも、逃げ切れませんでした。**

1日500コミット、PR も1日に何十本という規模になると、**今度は CI 側がキュー待ちになります。**

```
ローカルで回す    load average が上がる
CI に逃がす       CI のキューが伸びる
```

**置き場所が変わっただけで、同じ有限のリソースを取り合っている。** しかも CI が詰まるとマージが止まるので、**次の作業が始められない**という別の遅さになって返ってきます。

どちらにどれだけ寄せるか。**このバランスが、思っていたよりずっと重要でした。**

本当は「変更されたところだけ差分で回す」仕組みを作るべきです。**全部を毎回回しているから、ローカルでも CI でも同じ壁に当たる。** ここはまだ宿題です。

### で、どうしたか

`CLAUDE.md` に、**load average を見てから新しい作業を足す**というルールを入れました。

**判断ではなく手順にした**、というのが大事なところです。「重そうだから待とう」は、**忙しいときほど守れない**ので。

### ついでに、ターミナル側にも出しました

ルールを入れたのはいいものの、**そのたびに `uptime` を打つのが面倒でした。**

なので MulmoTerminal の**ヘッダーに load average を表示する機能**を足しました。設定でオン・オフできます。

書いてから気づいたんですが、これ、**1つ目の壁でやったこととまったく同じ**でした。**状態を頭から追い出して、道具に出させる。** 見に行かないと分からないものは、結局見ないので。

自分で作っているものなので、**困ったらその場で足せる。** ここは正直、かなり楽しいところです。

## 犯人が macOS だと気づくまで

CPU を空けても、まだ重い。**ここでしばらく混乱しました。**

自分が動かしているものは全部疑いました。エージェントの数、テストの並列度、watch プロセス。どれも違う。

犯人は **macOS 自身**でした。**Spotlight と Time Machine です。**

言われてみれば当たり前なんですが、**「自分が起動したもの」しか疑っていなかった**ので、なかなか辿り着きませんでした。

### worktree と Spotlight は、とにかく相性が悪い

これは worktree を使っていない人には起きない話なので、少し丁寧に書きます。

手元のリポジトリを1つ、数えてみました。

```
node_modules のファイル数    60,625
サイズ                       1.1 GB
```

これで**1つのリポジトリ**です。そして **worktree を切るたびに、これがまるごと増えます。**

```
worktree 1つ    60,625 ファイル
worktree 5つ    303,125 ファイル   ← 中身はほとんど同じもの
```

yarn は実体をコピーするので、**5つとも本物のファイル**です。Spotlight から見れば、ほぼ同じ内容のファイルが30万個、別々の場所に転がっているように見えます。**全部、律儀に索引しにいきます。**

そして、ここからが本当に相性の悪いところです。

**worktree は使い捨てなんです。**

```
worktree を切る       6万ファイルが一気に生まれる
   ↓
Spotlight が索引する  数分〜数十分かけて
   ↓
作業が終わる
   ↓
worktree を消す       6万ファイルが一気に消える
   ↓
Spotlight が索引を消す
   ↓
また次の worktree を切る  ← ここに戻る
```

**数時間で消えるファイルを、必死に索引しては消している。**

worktree を1日に何本も切っては捨てる使い方だと、**Spotlight は永久に終わらない仕事をやらされ続けます。** Time Machine も同じ構図で、差分を取るために**「昨日は無くて今日はある6万ファイル」を毎回見にいく。**

worktree の利点は「作るのも捨てるのも軽いこと」なのに、**OS 側から見ると毎回が大事件**なんです。ここが噛み合っていませんでした。

### やるべきだった設定

**Spotlight から外す**

```
システム設定 → Spotlight → 検索プライバシー
→ ＋ で worktree を置いているディレクトリを追加
```

コマンドでやるなら、そのディレクトリに空ファイルを置く方法もあります。

```bash
touch /path/to/worktrees/.metadata_never_index
```

> ⚠️ こちらは**ボリューム直下での挙動が本来の用途**で、任意のディレクトリでの効果は環境によります。
> **確実なのはプライバシー一覧のほう**です。

**Time Machine から外す**

```bash
sudo tmutil addexclusion -p /path/to/worktrees

# 効いているか確認
tmutil isexcluded /path/to/worktrees
# → [Excluded] /path/to/worktrees
```

`-p` はパスに対する指定なので、**そのディレクトリが一度消えて作り直されても効き続けます。** worktree のように生き死にするものには、こちらが正解です。`sudo` が要ります。

### ある日、ディスクが埋まりました

……と、ここまで書いておいて何ですが、**僕は Time Machine ごと切りました。**

理由があります。**一度、詰まったんです。**

Time Machine は、バックアップ先に書けないときや処理が追いつかないとき、**ローカルディスクにスナップショットを溜めます。** 普段は自動で消えるので、存在を意識することもありません。

**その掃除が、追いつかなくなりました。**

作っては消える大量のファイルを追いかけ続けた結果、**溜まる速度が、消える速度を上回った。** そしてある日、**ディスクが埋まりました。**

一番たちが悪いのは、見え方です。何もインストールしていないのに、ディスクだけが減っていく。そして `du` で探しても、**普通のファイルとしては出てきません。** どこが食っているのか、しばらく分かりませんでした。

見るならこれです。

```bash
# 溜まっているローカルスナップショットを一覧
tmutil listlocalsnapshots /

# 消す
sudo tmutil deletelocalsnapshots <日付>
```

いまは1つも無い状態にしてあります。

```
$ tmutil listlocalsnapshots /
Snapshots for disk /:
```

**この一件があってから、Time Machine を切りました。** 遅いから切ったのではなく、**マシンが止まったから切りました。**

とはいえ、**バックアップが無い状態で、しかも熱で落ちるマシンを使っている**わけです。分かっていてやっているので、**余計にたちが悪い。**

正しい直し方は、切ることではなく **worktree を1箇所に集めて、そこだけ除外すること**でした。ここは早く戻したいと思っています。

## そして、解決策が「散歩」でした

冒頭の話に戻ります。

**熱で落ちるのは、これまでに3回くらいありました。** 不定期です。

厄介なのは、**落ちたあとです。**

再起動しても、**起動の途中でまた止まります。** もう一度やっても止まる。三度目も止まる。

この時点で、だいぶ嫌な気持ちになりました。**ディスクが壊れたか、と思いました。** 頭の中では、バックアップを切っていたことがちらついています。

### 諦めて、外に出ました

何をやっても起動しないので、その日はもう諦めました。**散歩に出ました。**

しばらく歩いて、戻ってきて、ダメ元でもう一度電源を入れたら。

**普通に起動しました。**

**冷えるのを待っていただけでした。**

これはさすがに、しばらく笑ってしまいました。**朝から晩まで並列化だ自動化だと言っている人間の、最後の解決策が「外に出て、戻ってくる」なんです。**

```
1つ目の壁    道具で越えた
2つ目の壁    お金で越えた
3つ目の壁    ルールと表示で凌いだ
4つ目の壁    設定で回避（できるはずだった）
5つ目の壁    散歩
```

**下に降りるほど、ソフトウェアで殴れなくなる。** 今回いちばん実感したのは、これでした。

### そもそも、再起動する隙が無い

もう1つ、地味に効いている問題があります。

**AI を並列で動かしていると、再起動する隙が無いんです。**

普通なら「切りのいいところで再起動しよう」で済みます。でも**30体が別々のことをやっていると、全員が同時に切りのいいところに来ることが、まず無い。** 誰かは必ず途中です。

しかも寝ている間も動かしているので、**「使っていない時間」も存在しません。**

結果、OS のアップデートも、まとまった再起動も、**ずるずる後回しになります。** そして溜まったまま、熱で強制的に落とされる。**一番やってほしくない形で再起動が来る**わけです。

ここも、まだ答えが出ていません。

## 消えたと思ったら、戻ってきた

事故の話ばかり書きましたが、**1つだけ、完全に助かったことがあります。**

散歩から戻って、ようやく起動したとき、僕は**「終わったな」と思っていました。**

30セッションぶんの続きが、全部消えたはずだと。どのディレクトリで何をやらせていたかも、正直あやふやです。**全部開き直して、思い出しながら投げ直すのか**と考えて、げんなりしていました。

そして、MulmoTerminal を開いたら。

**そのまま全部、続きから戻ってきました。**

裏で **tmux** がセッションを保っていたからです。しかも**どのディレクトリで何を動かしていたかを、こちらが覚えている必要がありませんでした。** 開いたら、そこにありました。

**これは狙って作った機能ではありません。** 「タブを閉じてもサーバを再起動してもセッションが生きる」ように作ってあったものが、**マシンごと吹っ飛ぶ事故で効いただけ**です。

30セッションを手で開き直すところを想像すると、**ここだけは本当に運が良かった**と思っています。

## まとめ

- 並列度を上げていくと、**詰まる場所が認知 → 課金 → CPU → OS → 物理と降りていく**
- **下に降りるほど、ソフトウェアでは殴れなくなる**
- 2つ目の壁は**お金でしか越えられなかった。** 並列度を決めるのは技術ではなく契約数
- **寝ている間の8時間は、だいたい半分しか進まない**
- 負荷が高い状態でのテスト失敗は、**変更のせいに見える。** これが一番時間を溶かす
- **CI に逃がしても、キューが伸びるだけ。** 差分だけ回す仕組みが要る
- 「重かったら待つ」は判断ではなく**手順**にする。そして**見に行かなくても目に入る場所**に出す
- **パッケージマネージャの選択が、3つ先の層（OSの索引）で効いてくる。** yarn より pnpm のような共有方式
- worktree は**1箇所に集めて、そこだけ除外**するのが正解だった
- Time Machine が詰まると、**ローカルスナップショットが溜まってディスクが埋まる。** `du` では見えない
- 熱で落ちる前提のマシンでは、**`/tmp` は「消えると困る場所」になる**
- **熱で落ちたら、冷えるまで待つしかない。** 対処法が散歩
- **並列で回していると、再起動する隙が無い**
- **tmux でセッションが生きていると、マシンごと落ちても戻れる**

そして5つ目の壁は、**まだ解けていません。**

エアコンを効かせても落ちるので、次は排熱の話か、そもそも手元で全部回すのをやめるか、という話になります。

**ここ、みなさんどうしているんでしょうか。** 熱で落ちるところまで来ている人、他にもいると思うんですが。
