[ターミナルを自作したら、1日のコミット数が500を超えた話](https://zenn.dev/singularity/articles/diy-terminal-500-commits)を書いてから、僕はずっと並列度を上げ続けてきました。

その結果、いま何が起きているか。

**Macが、熱で落ちます。**

エアコンは効いています。真夏の昼間でもありません。それでも、長時間回していると、ある瞬間に画面が暗くなる。

正直、こうなるとは思っていませんでした。**ソフトウェアの話をしていたつもりが、部屋の温度の話になっている。**

でも、ここに至るまでの過程が、自分でも面白かったんです。**壁を1枚壊すたびに、次の壁が下の層から出てきました。**

```
認知  →  課金  →  CPU  →  OS  →  物理
```

上から順に書きます。

## 第1の壁：自分の頭が先に限界だった

最初に詰まったのは、マシンではなく僕でした。

プレーンなターミナルを6分割して並べていた頃、同時に追えたのは **5〜6体まで**。それ以上は、どのセッションで何を頼んだのか、どれが自分を待っているのかが分からなくなる。

**6分割だったのは、選んだからではありません。そこが認知の天井だったからです。**

これは[ターミナルを自作して](https://github.com/receptron/mulmoterminal)、状態を色と音で外に出したら抜けました。頭で覚えるのをやめた、というだけです。**天井は、道具に肩代わりさせれば動きます。**

そして、動いた天井の先に、次が待っていました。

## 第2の壁：全部が同時に止まる

並列度を上げたら、**今度はレート制限に当たりました。**

これ自体は当然です。ただ、1体ずつ動かしていた頃には見えなかった性質がありました。

**上限に当たると、全部が同時に止まるんです。**

1体なら「待たされているな」で済みます。30体が一斉に黙ると、**画面がまるごと静かになる。** あの瞬間の「あれ、全部死んだ？」という感じは、いまでもちょっと嫌です。

### 結局、契約を増やしました

**Claude Code の Max 20x を、複数アカウント持っています。**

書いていて、なかなかの話だなとは思います。ただ、**30体を同時に回すというのはそういうことでした。**

1アカウントで足りていた頃は、上限は「たまに当たるもの」でした。並列度を上げると、**上限は毎日必ず当たるもの**になります。そうなると、**並列度の上限を決めているのは技術ではなく契約数**です。

**第1の壁は道具で越えられました。第2の壁は、お金で越えるしかありませんでした。** ここは正直、あまり気持ちのいい解き方ではありません。

### 寝ている間も回しています

いま僕がやっているのは、**寝る前に「8時間ノンストップで進めて」とお願いしてから寝る**、という生活です。

そして朝起きると、**たいてい途中で止まっています。**

8時間ぶん頼んで、実際に進んだのは半分くらい。**残りの時間、マシンはただ黙って朝を待っていた**わけです。

これを毎日やっています。**上限がどこにあるかは、寝ている間に決まる。** そういう感覚になってきました。

## 第3の壁：20コアあっても足りない

課金の壁の向こうにいたのは、**自分のマシンでした。**

いまの動かし方はこうです。

```
worktree ひとつにつき1セッション
5 worktree × 6 で、30ほど同時に動かす
   ↓
それぞれが unit test と lint を回す
   ↓
load average が 100 を超える
```

**20コアあります。それでも足りませんでした。**

エージェントが遅いのではありません。**マシンが順番待ちになっているだけです。** それぞれのセッションから見ると「テストが遅い」としか見えない。

### 一番時間を溶かしたのは、これでした

**この状態でテストがタイムアウトすると、変更のせいに見えます。**

実際は負荷のせいなのに、原因を変更のほうに探しに行く。差分を読み返して、ロジックを疑って、書き直して、また落ちる。**そして負荷が下がった頃に、何もしていないのに通る。**

これで溶かした時間が、たぶん一番長いです。

### 「CI に逃がせばいい」は、そんなに簡単じゃなかった

ここで当然、「ローカルで回さずに CI に投げればいいのでは」と思います。**実際そうしてもいます。**

**でも、逃げ切れませんでした。**

1日500コミット、PR も1日に何十本という規模になると、**今度は CI 側がキュー待ちになります。**

```
ローカルで回す    load average が上がる
CI に逃がす       CI のキューが伸びる
```

**置き場所が変わっただけで、同じ有限のリソースを取り合っている。** しかも CI のキューが伸びると、**マージが詰まって、次の作業が始められない**という別の遅さになって返ってきます。

**どちらにどれだけ寄せるか。ここのバランスが、思っていたよりずっと重要でした。**

いまは手で加減していますが、**本当は「変更されたところだけ差分で回す」仕組みを作るべき**です。全部を毎回回しているから、ローカルでも CI でも同じ壁に当たる。**ここはまだ宿題です。**

### で、どうしたか

対処として、`CLAUDE.md` に**load average を見てから新しい作業を足す**というルールを入れました。**判断ではなく手順にした**、というのが大事なところです。「重そうだから待とう」は、忙しいときほど守れないので。

### ついでに、MulmoTerminal 側にも出しました

ルールを入れたのはいいものの、**そのたびに `uptime` を打つのが面倒でした。**

なので**ヘッダーに load average を表示する機能**を足しました。設定でオン・オフできます。

**「重いかどうか」を、見に行かなくても目に入る場所に置く。** 第1の壁でやったことと、まったく同じ解き方です。**状態を頭から追い出して、道具に出させる。**

自分で作っているものなので、**困ったらその場で足せる**のは、正直かなり楽しいところです。

## 第4の壁：犯人は macOS 自身だった

CPU を空けても、まだ重い。**ここで少し混乱しました。**

犯人は macOS でした。**Spotlight と Time Machine です。**

言われてみれば当たり前なんですが、**「自分が動かしているもの」しか疑っていなかった**ので、しばらく気づきませんでした。

### worktree と Spotlight は、とにかく相性が悪い

これは worktree を使っていない人には起きない話なので、少し丁寧に書きます。

**手元のリポジトリを1つ数えてみました。**

```
node_modules のファイル数    60,625
サイズ                       1.1 GB
```

これが**1つのリポジトリ**です。そして **worktree を切るたびに、これがまるごと増えます。**

```
worktree 1つ    60,625 ファイル
worktree 5つ    303,125 ファイル   ← 中身はほとんど同じもの
```

**yarn は実体をコピーするので、5つとも本物のファイルです。** Spotlight から見れば、**ほぼ同じ内容のファイルが30万個、別々の場所にある**ように見えます。全部律儀に索引しにいきます。

そして、ここからが本当に相性の悪いところです。

**worktree は使い捨てです。**

```
worktree を切る       6万ファイルが一気に生まれる
   ↓
Spotlight が索引する  数分〜数十分かけて
   ↓
作業が終わる
   ↓
worktree を消す       6万ファイルが一気に消える
   ↓
Spotlight が索引を消す
   ↓
また次の worktree を切る  ← ここに戻る
```

**数時間で消えるファイルを、必死に索引しては消している。** worktree を1日に何本も切っては捨てる使い方だと、**Spotlight は永久に終わらない仕事をやらされ続けます。**

**Time Machine も同じ構図です。** 差分を取るために毎回スキャンするので、**「昨日は無くて今日はある6万ファイル」を毎回律儀に見にいく。**

worktree の利点は「作るのも捨てるのも軽いこと」なのに、**OS 側から見ると毎回が大事件**なんです。ここが噛み合っていませんでした。

### 実際にやった設定

**Spotlight から外す**（システム設定のプライバシー一覧に入れる）

```
システム設定 → Spotlight → 検索プライバシー
→ ＋ で worktree を置いているディレクトリを追加
```

コマンドでやるなら、そのディレクトリに空ファイルを1つ置く方法もあります。

```bash
touch /path/to/worktrees/.metadata_never_index
```

> ⚠️ こちらは**ボリューム直下での挙動が本来の用途**で、任意のディレクトリでの効果は環境によります。
> **確実なのはプライバシー一覧のほう**です。

**Time Machine から外す**

```bash
sudo tmutil addexclusion -p /path/to/worktrees

# 効いているか確認
tmutil isexcluded /path/to/worktrees
# → [Excluded] /path/to/worktrees
```

`-p` はパスに対する指定なので、**そのディレクトリが一度消えて作り直されても効き続けます。** worktree のように生き死にするものには、こちらが正解です。**`sudo` が要ります。**

### そして、一度これでディスクが溢れました

上に書いたのは「こうすべきだった」という話です。**実際には、Time Machine ごと切りました。**

理由があります。**一度、詰まったんです。**

Time Machine は、バックアップ先に書けないときや処理が追いつかないとき、**ローカルディスクにスナップショットを溜めます。** 普段は自動で消えるので、存在を意識することもありません。

**その掃除が、追いつかなくなりました。**

作っては消える大量のファイルを追いかけ続けた結果、**スナップショットが溜まる速度が、消える速度を上回った。** そして気づいたときには、**ディスクが埋まっていました。**

一番たちが悪いのは、見え方です。何もインストールしていないのに、ディスクだけが減っていく。そして `du` で探しても、**普通のファイルとしては出てきません。**

見るならこれです。

```bash
# 溜まっているローカルスナップショットを一覧
tmutil listlocalsnapshots /

# 消す（日付を指定するか、マウントポイントごと）
sudo tmutil deletelocalsnapshots <日付>
```

いまは1つも無い状態にしてあります。

```
$ tmutil listlocalsnapshots /
Snapshots for disk /:
```

**この一件があってから、Time Machine を切りました。** 遅いから切ったのではなく、**マシンが止まったから切りました。**

**とはいえ、バックアップが無い状態で、しかも熱で落ちるマシンを使っている**わけです。分かっていてやっているので、**余計にたちが悪い。**

**正しい直し方は、切ることではなく worktree を1箇所に集めて除外することでした。** ここは早く戻したいところです。

## 第5の壁：もうソフトウェアの問題ではない

そして、いまここです。

**長時間回すと、Macが落ちます。** 熱暴走です。

第1の壁は道具で解けました。第3の壁もルールで解けました。**でも第5の壁は、コードを書いても1ミリも動きません。**

**下に降りるほど、ソフトウェアで殴れなくなる。** これが今回いちばん実感したことです。

## 反省点 ── 最初からこうしておけばよかった

### ① パッケージマネージャは共有方式にすべきだった

**yarn + worktree は、ファイルが増えます。**

worktree を切るたびに `node_modules` がまるごと増えるので、**worktree の数だけディスクとファイル数が倍々になる。**

そして第4の壁（Spotlight / Time Machine）は、**これがあるから起きています。**

**pnpm のように実体を共有してリンクを張る方式なら、ここまでにはなりませんでした。** 最初に何気なく選んだものが、**3つ先の層で効いてくる。** これは覚えておきたい話です。

### ② worktree を1箇所に集めるべきだった

いまは worktree があちこちに散っています。なので **Spotlight や Time Machine の除外設定が場当たり的**になっている。

**`~/worktrees/` のような1箇所に集めて、そのディレクトリだけを OS の各種索引から外す。**

そうすれば、**Time Machine を全部切る必要はありませんでした。** いま一番後悔しているのはここです。

### ③ `/tmp` を使いすぎない

作業を `/tmp` に置いていると、**Mac が急に落ちたときに継続できません。**

普段なら「再起動したら消える一時領域」で済む話です。でも熱で予告なく落ちるマシンでは、**`/tmp` は「消える前提の場所」ではなく「消えると困る場所」でした。**

## 消えたと思ったら、戻ってきた

ここまで事故の話ばかりですが、**1つだけ、完全に助かったことがあります。**

熱で落ちたあと、僕は正直「終わったな」と思っていました。**30セッションぶんの続き**が、全部消えたはずだと。

再起動して、MulmoTerminal を開き直したら。

**そのまま全部、続きから戻ってきました。**

裏で **tmux** がセッションを保っていたからです。しかも**どのディレクトリで何を動かしていたかを、こちらが覚えている必要がありませんでした。** 開いたら、そこにありました。

**これは狙って作った機能ではありません。** 「タブを閉じてもサーバを再起動してもセッションが生きる」ように作ってあったものが、**マシンごと落ちる事故で効いただけです。**

30セッションを手で開き直すところを想像すると、**ここだけは本当に運が良かった**と思っています。

## まとめ

- 並列度を上げていくと、**詰まる場所が認知 → 課金 → CPU → OS → 物理と降りていく**
- **下に降りるほど、ソフトウェアでは殴れなくなる**
- 負荷が高い状態でのテスト失敗は、**変更のせいに見える。** これが一番時間を溶かす
- **CI に逃がしても、キューが伸びるだけ。** 置き場所が変わるだけで同じリソースを取り合う。**差分だけ回す仕組みが要る**
- 「重かったら待つ」は判断ではなく**手順**にする。そして**見に行かなくても目に入る場所**に出す
- **パッケージマネージャの選択が、3つ先の層（OSの索引）で効いてくる**
- worktree は**1箇所に集めて、そこだけ除外**するのが正解だった
- Time Machine が詰まると、**ローカルスナップショットが溜まってディスクが埋まる。** `du` では見えない。`tmutil listlocalsnapshots /` で見る
- 第2の壁は**お金でしか越えられなかった。** 並列度の上限を決めるのは技術ではなく契約数
- **寝ている間の8時間は、だいたい半分しか進まない。** 上限は寝ている間に決まる
- 熱で落ちる前提のマシンでは、**`/tmp` は「消えると困る場所」になる**
- **tmux でセッションが生きていると、マシンごと落ちても戻れる**

そして第5の壁は、**まだ解けていません。**

エアコンを効かせても落ちるので、次は排熱の話か、そもそも手元で全部回すのをやめるか、という話になります。

**ここ、みなさんどうしているんでしょうか。** 熱で落ちるところまで来ている人、他にもいると思うんですが。
