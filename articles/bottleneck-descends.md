[ターミナルを自作したら1日500コミットを超えた話](https://zenn.dev/singularity/articles/diy-terminal-500-commits)を書いてから、ずっと並列度を上げ続けてきました。

その結果、いま何が起きているかというと、**Macが熱で落ちます。** エアコンは効いています。

面白いのは、そこに至るまでの過程です。**壁を1枚壊すたびに、次の壁が下の層から出てきました。**

```
認知  →  課金  →  CPU  →  OS  →  物理
```

上から順に書きます。**下に行くほど、ソフトウェアでは殴れなくなります。**

## 第1の壁：認知

最初に詰まったのは、自分の頭でした。

プレーンなターミナルを6分割して並べていた頃、同時に追えたのは **5〜6体まで**。それ以上は、どのセッションで何を頼んだのか、どれが自分を待っているのかが分からなくなります。

**6分割だったのは、選んだからではありません。そこが認知の天井だったからです。**

これは[ターミナルを自作して](https://github.com/receptron/mulmoterminal)、状態を色と音で外に出したら抜けました。頭で覚えるのをやめた、というだけです。

## 第2の壁：課金

認知の天井が外れたので、並列度を上げました。**今度はレート制限に当たります。**

エージェントは待たせておけますが、**上限に当たると全部が同時に止まります。** 1体ずつ動かしていた頃は気づかなかった性質です。

## 第3の壁：CPU

**20コアあります。それでも足りませんでした。**

いまの動かし方はこうです。

```
worktree ひとつにつき1セッション
5 worktree × 6 で、30ほど同時に動かす
   ↓
それぞれが unit test と lint を回す
   ↓
load average が 100 を超える
```

**エージェントが遅いのではなく、マシンが順番待ちになります。**

そして厄介なのは、**この状態でテストがタイムアウトすると、変更のせいに見える**ことです。実際は負荷のせいなのに、原因を変更のほうに探しに行ってしまう。**これで無駄にした時間が一番長い**かもしれません。

対処として、`CLAUDE.md` に**load average を見てから新しい作業を足す**というルールを入れました。判断ではなく手順にしています。

## 第4の壁：OS

CPU を空けても、まだ重い。**犯人は macOS 自身でした。**

```
Spotlight        node_modules を索引しようとする
Time Machine     同じファイル群を毎回スキャンする
```

**npm が数万ファイルを作っては消すので、OS の常駐サービスが延々と追いかけています。**

- **Spotlight** は、対象ディレクトリを走査しないよう設定から除外しました
- **Time Machine** は、いまは切っています

**Time Machine を切っているのは、正直まずいです。** バックアップが無い状態で、しかも熱で落ちるマシンを使っている。**分かっていてやっているので、余計にたちが悪い。**

## 第5の壁：物理

**長時間回すと、Macが落ちます。**

熱暴走です。エアコンを効かせていても落ちます。**ここはもうソフトウェアの問題ではありません。**

## 反省点

ここまでの過程で、**最初からこうしておけばよかった**と思っていることを書きます。

### ① パッケージマネージャは共有方式にすべきだった

**yarn + worktree は、ファイルが増えます。**

worktree を切るたびに `node_modules` がまるごと増えるので、**worktree の数だけディスクとファイル数が倍々になる**。第4の壁（Spotlight / Time Machine）は、**これがあるから起きています。**

**pnpm のように、実体を共有してリンクを張る方式なら、ここまでにはなりません。** 最初の選択が、3つ先の層で効いてきました。

### ② worktree 専用のディレクトリを決めて、そこだけ除外すべきだった

いまは worktree があちこちに散っているので、**Spotlight や Time Machine の除外設定が場当たり的**になっています。

**`~/worktrees/` のような1箇所に集めて、そのディレクトリだけを OS の各種索引から外す。** そうすれば、Time Machine を全部切る必要はありませんでした。**いま一番後悔しているのはここです。**

### ③ `/tmp` を使いすぎない

作業を `/tmp` に置いていると、**Mac が急に落ちたときに継続できません。**

普段なら「再起動したら消える一時領域」で済む話ですが、**熱で予告なく落ちるマシンでは、`/tmp` は消える前提の場所ではなく、消えると困る場所**になっていました。

## それでも、落ちたあとに戻れた

ここまで事故の話ばかり書きましたが、**1つだけ、想定していなかった形で助かったことがあります。**

熱で Mac が落ちたあと、MulmoTerminal を起動し直したら、**そのまま全部再開できました。**

```
複数ディレクトリで動かしていたセッション
   ↓ Mac が突然落ちる
   ↓ 起動し直す
そのまま続きから戻ってきた
```

裏で **tmux** がセッションを保っているからです。そして**どのディレクトリで何を動かしていたかを、こちらが覚えている必要がありませんでした。**

**これは狙って作った機能ではありません。** タブを閉じてもサーバを再起動してもセッションが生きるように作ってあったものが、**マシンごと落ちる事故で効きました。**

30セッションを手で開き直すことを想像すると、ここだけは運が良かったと思っています。

## まとめ

- 並列度を上げていくと、**詰まる場所が認知 → 課金 → CPU → OS → 物理と降りていく**
- **下に行くほど、ソフトウェアでは殴れなくなる**
- 負荷が高い状態でのテスト失敗は、**変更のせいに見える。** これが一番時間を溶かす
- **パッケージマネージャの選択が、3つ先の層（OS の索引）で効いてくる**
- worktree は**1箇所に集めて、そこだけ除外**するのが正解だった
- 熱で落ちる前提のマシンでは、**`/tmp` は「消えると困る場所」になる**
- **tmux でセッションが生きていると、マシンごと落ちても戻れる**

そして第5の壁は、**まだ解けていません。**

エアコンを効かせても落ちるので、次は排熱か、そもそも手元で全部回すのをやめるか、という話になります。**ここ、みなさんどうしているんでしょうか。**
