大きな不正アクセスや情報漏えいのニュースが、ここのところ続いています。

そのたびに気になるのが、**自分が普段使っているサイトは大丈夫なのか**ということです。カード番号を入れているあのサイトは？ 会員登録しているあのサービスは？

もちろん、外から見ただけで「安全」とは言えません。でも、外から見て分かる「**危なそうなサイン**」はあります。何年も前にサポートが終わったフレームワークを使っている。カード番号をサイト自身のフォームでそのまま受け取っている。サーバーのバージョンを堂々と公開している。そういうことです。

もう 1 つ気になるのが、**そもそも本物のショップなのか**です。偽の通販サイトの被害も、警察や国民生活センターが繰り返し注意を呼びかけています。

それを、自分のブラウザの中だけで確かめられる道具が欲しくなりました。探しても、ちょうどいいものがありませんでした。そこで、**LLM（Claude Code）と相談しながら作りました。** SafePeek という Chrome 拡張です。

https://github.com/isamu/SafePeek

## まず使ってみる

Chrome ウェブストアには置いていません。GitHub から入手して、自分で Chrome に読み込みます（Edge・Brave も同じ手順です）。

1. [Releases](https://github.com/isamu/SafePeek/releases) から最新版の `safepeek-vX.Y.Z.zip` をダウンロードして解凍します。解凍したフォルダは Chrome が使い続けるので、消さない場所に置いてください。
2. アドレスバーに `chrome://extensions` と入力し、右上の **デベロッパーモード** をオンにします。
3. **パッケージ化されていない拡張機能を読み込む** を押して、解凍したフォルダ（中に `manifest.json` があるフォルダ）を選びます。
4. ツールバーの拡張機能アイコンから、SafePeek を **ピン留め** しておくと便利です。

あとは、調べたいページを開いた状態で SafePeek のアイコンを押すだけです。そのタブだけをその場で解析して、結果をポップアップに表示します。

- 一番上に全体の判定が出ます。「重大な懸念があります」「注意点があります」「大きな問題は見つかりませんでした」の 3 段階です。
- その下に「カード決済」「バックエンド（推定）」「セキュリティ」「データの送信先」「使われている技術」の順で結果が並びます。偽ショップの兆候は「セキュリティ」の中に出ます。
- 指摘には重大・注意・軽微・情報・良好の印が付き、何を見てそう判断したかという根拠も表示されます。
- カード番号をどこに入力させているかを確かめたいときは、**カード番号を入力する画面で開いてください**。商品ページでは、決済の方式までは分かりません。
- 特定商取引法に基づく表記を確かめたいときは、表記のページで開いてください。

解析はすべてブラウザの中で行い、SafePeek が自分から外部へ何かを送ることはありません。判定がおかしいと思ったら、指摘の下にある **誤判定を報告** から GitHub の Issue フォームを開けます。フォームを送信したときだけ公開されます。

## 一番知りたいこと：カード情報は誰が持つのか

いろいろ見られるようにしましたが、僕が一番知りたいのは 1 つです。

**カード情報を、Stripe や GMO ペイメントゲートウェイのような決済会社に直接渡しているのか。それとも、そのサービス自身が受け取って、自前で処理しているのか。**

前者なら、カード番号はサービスのサーバーに残りません。万一サービスが侵入されても、カード情報までは漏れにくい。後者なら、サービスのセキュリティ次第です。

これは、ページが読み込んでいる JavaScript を見ると**ある程度は判断できます。** Stripe の入力欄（iframe）を埋め込んでいる、GMO-PG の `token.js` を読み込んでいる、といった具合です。

難しいのは、**そういう手がかりがページに出ていないサイト**です。サーバー側で決済会社とやり取りしているのか、本当に自前で処理しているのか。外からは区別がつきません。このツールでも、そこは「判断できない」としか言えません。

## 何が分かるのか

調べたいページでアイコンを押すと、そのページについて次のことを表示します。

1. **使われている技術**：CMS、フレームワーク、Web サーバー、言語などです。見える場合はバージョンも出します。
2. **古い・脆弱なソフトウェア**：既知の脆弱性がある JavaScript ライブラリや、サポートが終わったサーバー・フロントエンドのソフトウェアです。
3. **カード決済の方式**：カード番号を入力する場所がどこかを見分けます。決済会社の画面（iframe）の中なのか、決済会社のページへ移動するのか、サイト自身のページで入力してブラウザ内でトークンに変えているのか、サイト自身のフォームでそのまま受け取っているのか。決済会社の入力枠の横に、ページ自身のカード番号欄が並んでいる「盗む手口の形」も見つけます。
4. **バックエンドの推定**：サーバー側のフレームワークは直接は見えません。そこで、ページに残った痕跡から推定します。サポートが終わったもの（Struts 1、Seasar2、symfony 1 など）は警告します。
5. **BaaS と配信元**：Firebase、Supabase、AWS などでバックエンドが動いているのか。それとも Vercel や Netlify はページを配信しているだけで、裏の API は別の場所なのか。この 2 つを分けて表示します。
6. **ショップの運営元**：独自ドメインの EC サイトでも、裏で MakeShop、BASE、futureshop、Shopify などのカートサービスを使っているのか、EC-CUBE などのソフトを自社で動かしているのか、を見分けます。どちらも「情報」として出します。カートサービスは誰でも使えるので、良い印とはしていません。
7. **ログインの認証サービス**：Auth0、Amazon Cognito、Firebase Authentication、Okta、Keycloak、Google のログインなどを使っているかどうかです。
8. **データの送信先**：画面操作を記録するサービス（セッションリプレイ）、エラー監視、広告、アクセス解析、マーケティングのサービスを使っているかどうかです。セッションリプレイとエラー監視は、実際にデータを送っている送信先のホストまで見ます。
9. **WordPress**：本体のバージョンがサポート範囲か、どのプラグインを使っているか、を見ます。
10. **基本的なセキュリティ**：HTTPS、HSTS、CSP、クリックジャッキング対策、JavaScript から読めるセッション Cookie、混在コンテンツ、外部スクリプトなどです。ほかに、次のようなものも見ます。
    - 乗っ取られたことが報告されている配信元（CDN）から、スクリプトを読み込もうとしていないか
    - カード番号やパスワードを入力するページで、別のドメインのスクリプトが動いていないか（種類のラベル付き）
    - パスワードを、別の組織らしいドメインへ送るログインフォームになっていないか
    - サーバーの中だけに置くべき秘密の鍵らしき値が、ページのコードに含まれていないか
11. **偽ショップの兆候**：警察・国民生活センター・日本サイバー犯罪対策センター（JC3）やセキュリティ研究者が挙げる、偽の（または改ざんされた）通販サイトの特徴です。特定商取引法に基づく表記、中国語（簡体字）の痕跡、テンプレートの消し忘れ、コピーされたショップ、カード情報を盗むキットなどを見ます。

**すべての指摘に根拠を表示します。** どのヘッダー、どのスクリプト、どの入力欄から判断したのかが分かるので、自分で確かめられます。

## まず決めたこと：それ自体が安全であること

他人のサイトの安全性を調べる道具が、それ自体危なかったら本末転倒です。LLM と最初に話し合ったのは、機能ではなくこちらでした。

- **外部に何も送らない。** 解析はすべてブラウザの中で行います。拡張機能のページは CSP の `connect-src 'self'` で、通信先を自分自身に限っています。通信するのは、ヘッダーを読むために表示中のページを読み直すことと、ページが読み込み済みのスクリプトを取り直すことだけです。
- **権限は `activeTab` と `scripting` の 2 つだけ。** アイコンを押したときに、そのタブだけを読みます。すべてのサイトを常に読む権限は持ちません。
- **リモートコードなし、`eval` なし、ビルド工程なし。** リポジトリの `extension/` にあるファイルが、そのままブラウザで動きます。
- **ストアでは配布しない。** GitHub のリリース（zip と SHA-256）からだけ配ります。拡張機能でよくある事故は、人気の拡張が売却されて、自動更新で悪意あるコードが配られることです。手動で入れる方式なら、その経路がそもそもありません。

これらの約束は、**CI のテストで強制しています。** 権限を増やしたり、`innerHTML` を使ったりすると、テストが落ちます。

もう 1 つ、機能を足すたびに立ち返っている約束があります。

- **訪問者が判断するのに必要なことだけを伝え、攻撃する側に狙う場所を教えない。** 足すチェックは、「カード番号やパスワードは読まれうるか」「データはどこへ行くか」「ソフトウェアは手入れされているか」といった、訪問者の問いに答えるものだけにします。秘密の値そのもの、それがページのどこにあるか、社内や検証用のホスト名、防御をすり抜ける経路、書き換えられそうな入力欄のような、主に攻撃に役立つ具体的な情報は出しません。出すとしても一般的な言い方にとどめ、「サイトの運営者に知らせてください」と添えます。

この記事の後半に出てくるチェックの多くは、この線引きで表示内容を決めています。

## 技術的な背景：既存のツールに乗っている部分

技術を見分ける「エンジン」は、数百行で書けます。レスポンスヘッダー、`<script src>` の URL、`<meta name="generator">`、`window.jQuery` のようなグローバル変数を、正規表現で突き合わせるだけです。

大変なのは、**「何が見えたら何と判断するか」というデータを最新に保つこと**です。数千の技術について、これを一人で維持するのは無理です。なので、ここは既存の成果物に乗りました。

- **技術の判定：[webappanalyzer](https://github.com/enthec/webappanalyzer)**。Wappalyzer 形式のルールを、コミュニティが保守しているものです（GPL-3.0）。Wappalyzer 本体は 2023 年にクローズドソースになりましたが、こちらは公開で更新が続いています。
- **脆弱なライブラリ：[Retire.js](https://github.com/RetireJS/retire.js) のシグネチャ DB**（Apache-2.0）。jQuery や Angular などのバージョンを、既知の CVE と照らし合わせます。

どちらも拡張機能に**同梱**しています。調べるたびにどこかへ問い合わせる方式にはしていません。データは GitHub Actions が毎週更新の PR を作り、差分を確認してから取り込みます。

Retire.js のルールには、JavaScript の式をそのまま評価してバージョンを読むもの（`func`）があります。これを `eval` せずに済ませるため、単純なプロパティの参照（`jQuery.fn.jquery` など）に書き換えて使っています。書き換えられない複雑な式は、あえて使いません。

## 気になるので追加でチェックしている部分

既存のデータだけでは足りないところを、自分で足しています。ここがこのツールの本題です。

### 1. カード番号をどこで入力させているか

一番知りたかったのはこれです。カードの入力欄がどこにあるかで、リスクがまるで違います。

| 入力する場所 | 評価 |
| --- | --- |
| 決済会社の iframe の中（Stripe、PAY.JP など） | 良好：サイト側のスクリプトからはカード番号が読めない |
| 決済会社のページへ移動 | 良好 |
| サイト自身のページで入力し、ブラウザ内でトークン化（GMO-PG の token.js など） | 注意：サーバーには届かないが、ページ上の他のスクリプトからは読める |
| サイト自身のフォームでそのまま受け取る | 重大 |
| 決済会社のカード入力枠の横に、ページ自身のカード番号欄もある | 重大：カード情報を盗む手口の形 |

最後の行は、あとから足したものです。本物の決済画面なら、カード番号を入力する場所は決済会社の枠かページの欄のどちらか一方です。両方あるのは、本物の枠を隠して偽の入力欄を重ねる手口と同じ形です（Sansec などが報告しています）。ただし、同じページに決済会社のトークン化スクリプトがあれば、ページの欄も正規の入力方法の 1 つなので、通常の判定に戻します。

判定は、ページのフォームと iframe から行います。実際のサイトで試すと、単純な判定ではうまくいかないことが分かりました。

- **会員カードの番号**：ログイン画面で会員番号を「カード番号」と呼んでいるサイトがあります。パスワード欄のあるフォームでは、セキュリティコードか有効期限の欄もそろっているときだけ、決済カードとみなします。
- **決済会社の見えない iframe**：Stripe などは、カード入力と関係ない制御用の iframe を全ページに置きます。なので「決済会社の iframe があれば良好」とは言えません。カード入力用の iframe の URL パターンを決済会社ごとに登録して、それに合うものだけを数えます。
- **同じサイトの iframe**：サイト自身のオリジンで配信している iframe の中のカード欄は、サイト自身のページと同じ扱いにしています。

### 2. サポートが終わったバックエンド

僕が一番気にしているのは、ここです。**サポートが終わった Java や PHP のフレームワークが、何年も放置されているサイトは少なくありません。** サポートが終わると、脆弱性が見つかっても直す人がいなくなります。

ところが、サーバー側のフレームワークはページにほとんど痕跡を残しません。そこで、**弱い痕跡を足し合わせて確度を出す**ことにしました。

- URL の形（Struts の `.do`、`.action`）
- 隠しフィールドの名前（Struts 1 の `org.apache.struts.taglib.html.TOKEN`）
- マークアップの XML 名前空間（Teeda の `xmlns:te="http://www.seasar.org/teeda/extension"`）
- スクリプトのファイル名やグローバル変数（Seasar の `kumu.js`、`window.Kumu`）
- Cookie、レスポンスヘッダー、エラー画面のスタックトレース

痕跡ごとに重み（強・中・弱）を決めて、合計が一定を超えたら報告します。表示では、**推定の確度と、どの痕跡がどれだけ効いたか**をすべて出します。推定ですから、根拠が見えないと信用できないからです。

ただし、**根拠として見せる文字列は、決まった文言だけ**にしました。以前は、ルールに当たった箇所の前後の文章も根拠に出していました。ところが、PHP の警告やスタックトレースは、バックエンドの強い手がかりであると同時に、サーバー上のファイルの場所、データベースのユーザー名、社内のアドレスが漏れる場所でもあります。スクリプトのコードやその URL にも、トークンが含まれることがあります。そこで、ページの文章・スクリプトのコード・スクリプトの URL から取った痕跡は、ルールの決まった文言に当たった部分か、「PHP のエラーメッセージが表示されている」のような説明だけを出すようにしました。ルールごとの設定ではなくパターンの形で決めているので、新しいルールを足すときに付け忘れることもありません。

このルールは、ユーザーから Issue で痕跡を投稿してもらい、PR で取り込む形にしています。取り込んだルールの形式は CI のテストで自動チェックします。

### 3. BaaS と、WordPress

- **BaaS**：Firebase のような BaaS で動いているサイトに、webappanalyzer のルールの連鎖で「PHP」「MySQL」と出てしまうことがありました。BaaS だと強く判定できたときは、連鎖だけで付いたサーバー側の技術を外します。
- **WordPress**：本体のバージョンを、サポートされている系列と比べます。古い系列のうち一部は、セキュリティ修正の提供がすでに終わっています。読み込んでいるプラグインとテーマも一覧にして、脆弱性情報を調べるリンクを付けます。

### 4. ショップの運営元：独自ドメインでも、裏はカートサービス

`shop.example.jp` のような独自ドメインの EC サイトでも、中身は MakeShop や BASE のようなカートサービスということがよくあります。画像の URL が `gigaplus.makeshop.jp` だったり、カートのページで決まった形の Cookie が付いたりします。

国内外の主要なカートサービスを調べました。実在の店舗で、どのホストから画像やスクリプトを読むか、どんなグローバル変数や Cookie があるかを確かめ、それを判定に使っています。カートサービスなら決済画面もサービス側が用意するのが一般的です。自社で EC ソフトを動かしているなら、更新は運営者の責任になります。

最初は、カートサービスを使っていることを「良好」として出していました。これは改めました。**カートサービスはカード決済を引き受けてくれますが、販売者が実在することや、商品が届くことは保証しません。** 誰でもショップを開けるので、偽のショップにも使われます。偽の通販サイトを調べた研究（BEYOND PHISH）でも、カートサービス上のショップに詐欺サイトが多く見つかっています。「良好」と出すと、販売者まで保証しているように読めてしまうので、今は「情報」として出しています。

ここでも実際のサイトで気づいたことがありました。ブログがカートサービスの画像を 1 枚埋め込むだけで、スクリプト・DOM・ホストの痕跡がいっぺんに付きます。なので、埋め込みで付く痕跡はまとめて 1 系統と数えます。店舗そのものでしか出ないグローバル変数・Cookie・ヘッダーのどれかと、2 系統そろったときだけ判定するようにしました。

### 5. ページ自身の通信から分かること

ブラウザは、ページが読み込んだものや API に送ったリクエストを記録しています（Resource Timing）。**新しい通信はせずに、それを読むだけ**で分かることがあります。

- **バックエンドの手がかり**：Laravel の `/sanctum/csrf-cookie`、Rails の `/rails/active_storage/...`、Blazor の `/_blazor/negotiate` のような API の形です。
- **ログインの認証サービス**：Auth0 の `/authorize`、Cognito の `cognito-idp.<リージョン>.amazonaws.com`、Keycloak の `/protocol/openid-connect/` などです。ベンダーのドメイン全体ではなく、ログイン用のエンドポイントだけを見ます。ドキュメントやサポートのページを読み込んだだけで「使っている」と出ないようにするためです。
- **データの送信先**：セッションリプレイやエラー監視のサービスが、どのホストにデータを送るかは、各社が CSP の設定例として公開しています。それを一覧にしています。ベンダーのドメイン全体ではなく、資料に書かれた送信用のホストだけを見ます。ドキュメントやステータスページを読み込んだだけでは出ません。アクセス解析や広告は「使っている」とだけ表示します。自社のサーバーで動かしている場合もあるからです。セッションリプレイは、マウスの動きや入力内容まで記録することがあります。個人情報を入れる前に、知っておきたいところです。

URL にはトークンや ID が入っていることがあるので、クエリ文字列は捨て、ID のように見えるパスは伏せて扱います。画面に出すのは、ホスト名とルールに当たった部分だけです。

### 6. カードやパスワードを入力するページ

ページで動くスクリプトは、どれでもそのページの入力欄に打ち込まれた内容を読めます。なので、**カード番号やパスワードを入力するページに限って**、別のドメインのスクリプトを数えるようにしました。

- **カード番号をページ自身の欄に入力するページ**（「注意」）：別のドメインのスクリプトは、有名な解析ツールやタグマネージャーも含めてすべて数えます。カード情報を盗む攻撃（Magecart と呼ばれるもの）は、ありふれたタグマネージャーや解析タグの改ざんを入口にしたことが何度もあるからです。PCI DSS 4.0 も、決済ページのすべてのスクリプトを、誰が作ったものかにかかわらず把握するよう求めています。除くのは、決済会社自身のホストから読むトークン化のスクリプトだけです。
- **パスワードをページ自身の欄に入力するページ**：ロボット対策（reCAPTCHA、hCaptcha、Turnstile）とログインサービスは、ログインを守るためのものなので除きます。残りが解析・タグマネージャー・エラー監視だけなら「情報」、画面操作の記録（セッションリプレイ）や広告、正体の分からないドメインがあれば「軽微」です。

どちらも、ホストごとに「不明」「セッションリプレイ」「広告」「エラー監視」「解析」「ログイン」「ロボット対策」のような種類を付けて並べます。「サードパーティ」ではなく「別のドメイン」と呼んでいるのは、サイト自身の配信用ドメインが、サイトと関係なさそうな名前のこともあるからです。同じ組織らしいホストは除き、残りは種類付きで見せて、判断は訪問者に任せます。

もう 1 つ、**パスワードを別の組織らしいドメインへ送るログインフォーム**も「注意」として出します。フィッシングによくある形か、フォームの設定の誤りです。ページと同じ登録ドメインと、Auth0 や Okta のような知られたログインサービスは除きます。ここでは、同じ組織らしいホストを見分けるいつもの規則（同じ名前なら別のドメインでも同じ組織とみなす）をあえて使っていません。`mybank.co.jp` と `mybank.net` のように同じ名前を別のドメインで取るのは、まさに偽サイトの作り方だからです。送信先のドメインは公開されている情報で、訪問者が判断するのに必要なので、そのまま表示します。

ただし、見ているのはフォームの既定の送信先だけです。送信ボタンの `formaction` や、スクリプトで送る場合は見えません。作り込んだフィッシングページなら、この判定は避けられます。

### 7. ヘッダーは「ブラウザが従う形」で数える

HSTS やクリックジャッキング対策は、ヘッダーがあれば良いわけではありません。ブラウザが無視する書き方なら、何も守っていないのと同じです。Mozilla HTTP Observatory の採点基準にならって、ブラウザが実際に従う形だけを守りとして数えるようにしました。

- **HSTS**：`max-age=0` は「HSTS を忘れなさい」という指示なので、無いのと同じに扱います。RFC 6797 でブラウザが無視する書き方（同じ指示の重複、数字でない `max-age`）も同じです。6 か月より短い `max-age` は、しばらく訪れないと切れてしまうので別に出します。ブラウザに組み込まれた HSTS プリロードリストに載っているサイトはヘッダーがなくても守られますが、SafePeek はそのリストを持っていないので、そのことをメッセージに書いています。
- **クリックジャッキング対策**：CSP のヘッダーに `frame-ancestors` があれば、ブラウザは `X-Frame-Options` を無視するので、`frame-ancestors` だけで判断します。どのホストでも埋め込めてしまう `frame-ancestors *` は守りになりません。`<meta>` に書いた `frame-ancestors` はブラウザが無視します。`X-Frame-Options` は HTML の仕様どおりに読みます。廃止された `ALLOW-FROM` は守りとして数えません。
- **CSP**：インラインスクリプトの許可に加えて、`*`、`https:`、`data:` のように**どこからでもスクリプトを読み込める**設定も出すようにしました。どの指示がスクリプトに効くかは、CSP Level 3 の決まりどおり（`script-src-elem` や `script-src-attr`、なければ `script-src`、なければ `default-src`）に読みます。複数のポリシーがあるときは、すべてが許しているときだけ出します。

逆に、**CSP で許可されているどのホストを使えば回避できるか**は出しません。それは防御をすり抜ける経路そのもので、訪問者の判断には要らないからです。

### 8. 乗っ取られた配信元と、ページに残った秘密の鍵

- **乗っ取られた配信元（CDN）**（「重大」）：2024 年に Sansec が報告した polyfill.io の件のように、多くのサイトがスクリプトを読み込んでいた配信元が乗っ取られ、悪意のあるコードを配ったことがあります。報告でそう名指しされた配信元から、スクリプトを読み込もうとしているページを知らせます。すでに何も配っていないドメインもありますし、別のドメインのスクリプトが実際に動いたかどうかはブラウザから見えないので、表現は「読み込もうとしています」にしています。攻撃者自身の転送先のドメインは、わざわざ読み込むサイトがないので一覧に入れていません。
- **ページのコードに残ったサーバー用の秘密の鍵**（「注意」）：決済やサービス連携に使う、本来サーバーの中だけに置くべき鍵の形をした値が、訪問者全員に送られるページやスクリプトに入っていないかを見ます。対象は、Stripe の本番用の秘密鍵、GitHub や Slack のトークン、PEM 形式の秘密鍵のように、**公式の資料で決まった接頭辞があるものだけ**です。「長いランダムな文字列」を拾うと、ハッシュやビルド ID をすべて拾ってしまうからです。もともとページに置くための公開用の鍵や、お金を動かせないテスト用の鍵は除きます。`sk_live_xxxx` のような見本の値も、ランダムな部分の文字の種類が少ないので数えません。

秘密の鍵については、**見つけたという事実だけ**を出します。鍵の種類、値、どのスクリプトのどこにあったかは出しません。どれも、攻撃する側が探す手間を減らすだけだからです。訪問者に必要なのは「このサイトは自分の秘密を守れていない」ということで、あとはサイトの運営者に知らせてもらえれば十分です。

### 9. 誤判定を報告しやすく

推定である以上、誤判定は避けられません。それぞれの指摘に「誤判定を報告」のリンクを付けました。押すと、判定内容を入れた状態で GitHub の Issue フォームが開きます。

入れる情報は、**許可した項目だけ**に絞っています。サイトのオリジン、指摘の種類、ルール由来の名前、数字だけのバージョン番号です。URL のパスやヘッダーの値、ページの文章は入れません。セッション ID やトークンが紛れ込みうるからです。

## 偽ショップを見分ける

カード決済の方式が分かっても、**ショップそのものが偽物なら意味がありません。** 決済会社の画面でカード番号を入れても、商品が届かなければ同じことです。そこで、偽の通販サイトの見分け方として公的機関や研究者が挙げている特徴を調べ、1 ページから見えるものをチェックにしました。

### 調べたこと

警察、国民生活センター、日本サイバー犯罪対策センター（JC3）、消費者庁が公開している注意喚起と、偽ショップ網を追ったセキュリティ研究（Sansec、BEYOND PHISH など）を読み、次のように整理しました。

- **見られるのは 1 ページだけ。** 特定商取引法に基づく表記、ご利用ガイド、決済画面はそれぞれ別のページで、SafePeek は取りに行きません。なので、そのページへのリンクがあるかを見るか、訪問者がそのページで開いたときに読むか、のどちらかです。
- **1 つの特徴だけでは決まらない。** どの機関もそう書いていて、国民生活センターは、どれにも当てはまらない偽サイトもあると注意しています。弱い特徴は、重なったときだけ出します。
- **鍵マーク（HTTPS）は、本物のショップの印ではない。** 通信が暗号化されているだけで、販売者が実在するかとは関係ありません。
- **ページから見えないものは扱わない。** ドメインの取得日や登録者情報、期限切れドメインの再利用、評判のリスト、会社や住所が実在するか、振込先の口座名義は、ページからは見えません。

### 見ているもの

| 特徴 | 評価 | 見ていること |
| --- | --- | --- |
| 決済会社の入力枠の横に、ページ自身のカード番号欄 | 重大 | 前述の「盗む手口の形」 |
| カード情報を盗むキットとして報告されたもの | 重大 | 研究者の報告にあるファイル名・通信先・コード中の名前のうち、**違う種類の痕跡が 2 つ**そろったとき |
| 特定商取引法に基づく表記へのリンクがない | 注意 | 日本語で、購入の導線がある（「カートに入れる」など）ショップのページなのに、表記への言及がどこにもない |
| 表記に必要な項目がない | 注意 または 軽微 | 表記のページそのもので、法律が求める項目の見出しが見当たらない |
| 表記がテンプレートの仮の値のまま | 軽微 | 販売業者名や電話番号の行が「株式会社〇〇」「000-0000-0000」のまま |
| 別のサイトを本来の住所として示している | 注意 | `canonical` や `og:url` が、関係のない別の組織のサイトを指している |
| 中国語（簡体字）の痕跡 | 軽微 または 注意 | 日本語のショップのページに、日本では使わない簡体字、中国語の言語指定、「365天受付」のような日数の書き方 |
| 弱い特徴の重なり（`shop_weak_signs`） | 2 つで軽微、3 つ以上で注意 | 下で説明 |

いくつか補足します。

- **キットの判定に 2 種類の痕跡を求める理由**：キットを検知する正規のスクリプトは、キットの名前を全部自分のコードに並べています。キットに使われている名前の中には、ほかの用途でも使われる一般的なものもあります。1 種類の痕跡だけで出すと、検知する側を「キットが動いている」と判定してしまいます。キットそのものなら、ファイルとその中の名前、またはコードとその送信先のように、2 種類が同時に残ります。キットを解説した記事の本文も同じ名前を引用するので、ページの文章は読みません。
- **特定商取引法の表記**：法律が求めるのは、販売業者名、所在地、電話番号、代表者または責任者、販売価格、送料などの費用、支払方法、引渡し時期、返品の条件です。項目は、見出しの言葉がどこかにあれば「ある」とみなす、甘めの判定にしています。「請求があれば遅滞なく提供します」という書き方で省略できる項目は、消費者庁の整理どおりに扱います（返品の条件は省略できません）。表記ならではの書き方の揺れが多いので、販売業者名・所在地・電話番号・返品の条件以外は、1 項目だけ見当たらないときは出しません。根拠に出すのは**見当たらない項目の種類だけ**で、表記に書かれた値は出しません。
- **コピーされたショップ**：本物のショップのページを丸ごとコピーした偽ショップは、元のショップの正規 URL を埋め込んだままのことがあります。同じブランドの国別ドメインや同じ組織のサブドメインは、同じ組織として扱います。表示するのは相手の登録ドメインだけで、完全なホスト名は出しません。社内や検証用のホスト名かもしれないからです。
- **中国語の痕跡**：日本語でふつう別の字を使う簡体字（这、购 など）が、日本語の文の中に**いくつか紛れ込んでいる**ときだけ数えます。

### 弱い特徴は、重なったときだけ

JC3 や国民生活センターが挙げる特徴には、本物のショップにもよくあるものが含まれます。

- 偽サイトに多いと JC3 が名指ししたトップレベルドメイン（`.xyz`、`.top`、`.bid`）。`.shop` は正規のショップも多く使うので入れていません
- 連絡先がフリーメールだけで、ショップ自身のドメインのアドレスがない
- 支払方法が銀行振込だけ
- 70% 以上の大幅割引がたくさん並んでいる
- SNS アイコンのリンク先が、どれも各 SNS のトップページだけ（BEYOND PHISH の研究による）

小さなショップが Gmail を使っていたり、銀行振込しか受けていなかったりするのは普通のことです。なので、**どれも 1 つだけでは出しません。** 2 つ重なれば「軽微」、3 つ以上で「注意」です。

### 文言で判定するチェックは、実際のページで確かめた

偽ショップのチェックの多くは、ページの日本語を読んで判定します。文言の判定は、書いた本人が思いつく例では正しく動いても、実際のページでは思わぬところに当たります。

そこで、**文言で判定するチェックは、レビューのたびに実際の日本語のページ何十件に当てて確かめました。** 誤判定が見つかるたびに「この例外を足す」ではなく、「その誤判定の仲間をまとめて除く規則」にしました。見つかった仲間の例です。

- **入力フォームの記入例**：購入画面や問い合わせフォームは「入力例：000-0000-0000」と書きます。テンプレートの消し忘れは、特定商取引法の表記そのものの、販売業者名や電話番号の行でだけ数えることにしました。「例」「入力」「記入」のような言葉がある行も除きます。
- **印刷物の注文**：はんこや名刺の印刷を受けるショップでは、「株式会社〇〇」は買い手が印刷したい内容の見本です。
- **表記の書き方の解説**：「特商法とは」「特定商取引法に基づく表記の書き方」「テンプレート」のような解説ページは、表記そのものではありません。
- **デモストア・テストストア**：自分でそう名乗り、わざと仮の値を見せています。偽ショップは自分をデモとは名乗りません。
- **FAX が 000**：FAX を持っていないという意味で、消し忘れではありません。
- **英語の決まり文句**：本物のショップも、サイズ表に lorem ipsum を残していたり、EC ソフトの初期の表示名をそのまま使っていたりします。英語の決まり文句は使わないことにしました。
- **中国語のお客さま向けページ**：日本のショップが、日本語のヘッダーとフッターの下に中国語で書いた案内ページを持っていることがあります。海外発送の短い中国語の注意書きが、商品ページに入っていることもあります。簡体字は、日本語の文に**少しだけ紛れ込んでいる**ときだけ数えるようにしました。
- **中国語の教材**：中国語の学習ページは、わざと簡体字を引用しています。
- **「天」の付く言葉**：「天体」「天然」のような言葉も数字のあとに来ます。「天」を日数とみなすのは、「受付」「以内」のように中国語で日数のあとに続く言葉の前か、句の終わりのときだけです。
- **フォントの指定**：よく使われる CSS フレームワークは、中国語のフォント名を予備として並べています。フォント名は使いません。
- **カートサービス自身のサイト**：ショップの話はしていても、商品を売っていません。購入の導線があるページだけを対象にしました。
- **カートや購入手続きのページ**：本物のショップでも、フッターを外していることがよくあります。表記へのリンクがないことは、こうしたページでは判定しません。
- **SNS の共有ボタン**：小さな本物のショップは、共有ボタンだけを置いていることがよくあります。共有ボタンは数えません。

どれも、実際のページに当てるまで気づけませんでした。

## 実際のサイトで試して分かったこと

作ってから、実在のサイトを何十件も流して精度を上げました。**単体テストが全部通っていても、実際のサイトでは誤判定だらけ**でした。いくつか紹介します。

- **あちこちで「WordPress」と出る。** Laravel、Next.js、Shopify のサイトでも出ていました。タグマネージャーや JavaScript のバンドルが、どこかで `/wp-content` という文字列に触れていたからです。スクリプト本文の文字列だけでは、サイトの土台（CMS、言語、DB）を判定しないことにしました。
- **自分のリポジトリのページで「Seasar2 の可能性」と出る。** SafePeek の GitHub ページには、Seasar を検出するルールやテストの話が書いてあります。それを痕跡として拾っていました。**ページが「その技術について書いている」ことと「その技術で動いている」ことは違います。** EOL の判定は、動いているアプリが出すもの（名前空間、生成されたフィールド名、配信されたスクリプトなど）でだけ下すようにしました。スタックトレースのような文章は、解説記事にも載るので裏付けにしか使いません。
- **S3 を使っているだけで「PaaS: AWS」と出る。** 画像を S3 から配信しているだけなのに、サイト自体が AWS 上で動いていることにしていました。どこでホストされているかは、直接見えたときだけ表示します。
- **「Vercel がバックエンド」と出る。** ある部品の EC サイトで、レスポンスヘッダーに `Server: Vercel` がありました。確かにページは Vercel 上の Next.js が配信しています。ただ、読み込んでいる JavaScript を追うと、顧客・カート・請求はサービスごとに分かれた API（`/customer/v1/...` など）で、注文は別ホストの Java のシステム（URL が `.do`）でした。Vercel は「このページの配信元」であって、サイトのバックエンド全体ではありません。Vercel、Netlify、Cloudflare Pages などは「配信元」として分けて表示するようにしました。
- **ニュースサイトで「Facebook のログインを使っています」と出る。** シェアボタンのために Facebook の SDK を読み込むだけで、ログイン用のルールに当たっていました。ログインに特有の痕跡だけを数えるようにしました。
- **ログイン画面で、SafePeek 自体が止まる。** フォームの中に `name="action"` の入力欄があると、`form.action` がその入力欄を指してしまいます（DOM clobbering）。収集処理が例外で止まり、何も表示されませんでした。フォームの属性は、要素のプロパティを経由せずに読むように直しました。
- **localhost で「HTTPS ではありません（重大）」と出る。** ブラウザは localhost を安全な接続として扱います。ここでは判定しないようにしました。

どれも「言われてみれば当然」ですが、**実際のサイトに当てるまで気づけませんでした。**

## 作り方：LLM と相談しながら、PR ごとにクロスレビュー

作業はほぼ Claude Code との対話で進めました。

- 最初に「既存のツールはあるか」「自分で作るならどういう構成か」を相談して、安全性の方針と機能の範囲を決めました。
- 依頼は 1 つずつ PR にして、PR ごとに別の LLM（Codex）にレビューさせています。指摘を受けて直し、指摘がなくなるまで繰り返してからマージします。
- 誤判定の修正は「このルールを直す」ではなく、**「どういう形なら判定してよいか」を決め直す**ほうがうまくいきました。例外を 1 つずつ足していくと、レビューのたびに新しい抜け道が見つかったからです。
- ページの日本語を読んで判定するチェック（特定商取引法の表記、簡体字、テンプレートの消し忘れなど）は、レビューの中で実際の日本語のページに当てて確かめ、見つかった誤判定を仲間ごとに規則にしました（前述の「文言で判定するチェックは、実際のページで確かめた」）。
- 新しいチェックを足すときは、毎回「これは訪問者の判断に必要か、攻撃する側の役に立つだけではないか」を確かめています。秘密の鍵の場所やコピー元の完全なホスト名を出さないのは、この確認の結果です。

## 実際に使ってみる

いくつかのサイトで開いてみた結果を紹介します。サイト名は出しません。こんな感じで見えます。

### 例 1：個人の EC サイト

![個人のECサイトでの結果](/images/safepeek/personal-ec.png)

個人で運営している EC サイトのトップページです。決済はこのサイト自身で処理していて、カード番号は購入手続きの画面で入力します。

**カード決済**は「このページにカード入力欄はありません」です。このページには入力欄がないので、SafePeek からは**決済会社に直接渡しているのか、自前で処理しているのかは判断できません。** 冒頭で書いた「難しいケース」がこれです。決済方式を確かめるには、カード番号を入力する画面でもう一度開く必要があります。そこでも決済会社の JavaScript や iframe が見当たらなければ、「自前で受け取っているかもしれない」と考えることになります。

**バックエンド（推定）の欄**は「なし」です。サーバー側のフレームワークを示す痕跡は、ページに残っていませんでした。

目につくのは**セキュリティ**の欄です。

- **jQuery 3.3.1**：既知の脆弱性がある版です。修正版が出てから何年も経っています。
- **Bootstrap 3.4.1**：既知の脆弱性に加えて、Bootstrap 3 系そのものがサポートを終えています。
- **HSTS・CSP が未設定**：どちらも「軽微」ですが、ブラウザ側の防御を効かせる設定がされていません。

どれも、それだけで「危ない」とは言えません。ただ、**フロントエンドのライブラリが何年も更新されていない**ことは分かります。決済を自前で処理しているサイトで、見える部分の手入れがこの状態だと、見えないサーバー側や決済まわりはどうなっているのかが気になります。この記事で言いたい「技術要素からセキュリティ意識を推し量る」は、こういう読み方です。

### 例 2：サポートが終わったバックエンドが残っているサイト

![サポート終了のバックエンドが推定されたサイト](/images/safepeek/legacy-backend.png)

このツールを作るきっかけになった、ある大きなサービスのサイトです。

一番上に「**重大な懸念があります**」と出ています。重大 1、注意 2、軽微 1 です。

**バックエンド（推定）の欄**に「**サポート終了のバックエンドの可能性: Seasar2 (SAStruts / Teeda)**」が出ました。Seasar2 は Java のフレームワークで、2016 年にサポートが終わっています。根拠は、ページに残っていた次の痕跡です。

- マークアップにある Teeda の XML 名前空間（`xmlns:te="http://www.seasar.org/teeda/extension"`）
- ページの JavaScript にある、Seasar 系のライブラリのグローバル変数（`window.Kumu`）

どちらも、動いているアプリが出力するものです。フレームワークについて書かれた解説ページには出てきません。痕跡の重みを足した確度は最大の 100 でした。ほかに、`.jsp` の URL から「Java Servlet / JSP」も確度 低（40）で出ています。

**セキュリティ**の「注意」2 件は、サポートが終わった jQuery 1.x 系と、その版にある既知の脆弱性です。「軽微」は CSP が未設定なことです。

**カード決済**は「このページにカード入力欄はありません」です。実は開発の途中では、ここに「**カード番号をサイト自身のページで入力させています**（重大）」と出ていました。ログイン欄の「会員カード番号」を決済用のカード番号と取り違えていたのです。パスワード欄のあるフォームは、カード番号とセキュリティコードや有効期限がそろったときだけ決済カードとみなすように直し、今の表示になりました。

これも、これだけで「このサイトは危ない」とは言えません。サポートが終わった製品でも、運営者が自分で修正を当て続けている可能性はあります。ただ、**外から見える範囲にこれだけの痕跡が残っている**ことは、判断材料の 1 つになります。

### 例 3：証券会社のサイト

![証券会社のサイトでの結果](/images/safepeek/securities.png)

ある証券会社のサイトです。

**セキュリティ**の欄に古いライブラリは出てきません。バックエンドの痕跡もありません。**見える範囲の手入れはされている**サイトです。

出ているのは、次の 2 種類です。

- **軽微**：CSP、`X-Content-Type-Options`、クリックジャッキング対策のヘッダーが設定されていません。ブラウザ側の防御を足す設定なので、あるに越したことはありません。
- **情報**：**12 ドメインから 36 件の外部スクリプト**を読み込んでいて、どれにも改ざん検知（SRI）が付いていません。

気になるのは後者です。外部のスクリプトは、ページと同じ権限で動きます。つまり、**ログイン画面で入力する ID やパスワードも読めます。** 広告や計測のタグが多いサイトほど、そのうちの 1 つが乗っ取られたときの影響が大きくなります。証券口座のようなお金に直結するサイトで、これだけの数の外部スクリプトが入っているのは、個人的には少し意外でした。

このスクリーンショットはトップページのものです。今の SafePeek では、パスワードを入力するページで開くと、そこで動いている別のドメインのスクリプトを、解析・広告・セッションリプレイのような種類付きで出します（前述の「カードやパスワードを入力するページ」）。

**カード決済**には「決済会社のページへ移動して支払う方式です（Rakuten Pay）」と出ています。ただ、これは**誤判定**でした。当時の SafePeek は、決済会社のサイトへのリンクがあるだけで「決済会社のページへ移動する方式」と判定していました。証券会社のトップページなので、入金方法やキャンペーンの案内として楽天ペイへリンクしているだけです。

この記事を書きながら気づいたので、直しました。決済会社ごとに、支払いページの URL の形を登録しておきます。それに当たるリンクか、決済会社へ POST するフォームだけを「移動して支払う方式」として数えます。楽天ペイは支払いページの URL の形を公開情報で確かめられなかったので、リンクでは判定せず、フォームでだけ判定します。スクリーンショットは直す前のものです。

### 例 4：大きな EC サイト

![ECサイトでの結果](/images/safepeek/ec-legacy-js.png)

ある大きな EC サイトです。

**セキュリティ**の欄に「注意」が並びました。

- **jQuery が 2 つの版で同時に読み込まれています。** 1.4.2 と 1.12.2 です。1.4.2 は 2010 年ごろの版で、既知の脆弱性があり、サポートも終わっています。
- **jQuery UI（とその dialog）も 1.8.16** と古く、既知の脆弱性がある版です。
- **HSTS** が設定されていません。

同じページに jQuery の別々の版が入っているのは、**長い年月のあいだに、別々の時期・別々のチームが作った部品が積み重なってきた**ことをうかがわせます。大きなサイトほど、全体を一度に入れ替えるのは大変です。古い部品が、どこかに残り続けます。

ただし、ライブラリの脆弱性の多くは、「外から来た文字列を、特定の関数にそのまま渡す」といった使い方をしたときに問題になるものです。古い版が入っているだけで、すぐ攻撃できるとは限りません。SafePeek の根拠欄には、どのスクリプトの URL から判定したかが出るので、そのファイルがどのページの何の部品なのかまで追いかけることはできます。

### 例 5：レンタカーのサイト

![レンタカーのサイトでの結果](/images/safepeek/rental-car.png)

あるレンタカー会社のサイトです。

**バックエンド（推定）の欄**に「**古い世代のバックエンドの可能性: ASP.NET Web Forms**」が出ました。例 2 の「サポート終了」とは区分が違います。

- **サポート終了**（例 2 の Seasar2 など）：開発元のサポートが終わっていて、脆弱性が見つかっても修正が出ません。
- **古い世代**（今回の Web Forms など）：まだ動くし、修正も出ます。ただし、新しい開発はもう止まっていて、長く手を入れていないサイトで見かけることが多い技術です。

Web Forms は Microsoft の古い Web フレームワークで、.NET Framework の一部として今も修正は提供されています。ただ、新しい機能はもう追加されていません。後継の技術への移行が勧められています。SafePeek は、Web Forms が必ず埋め込む隠しフィールド（`__VIEWSTATE`）などの痕跡から推定しています。

**セキュリティ**の「注意」は、レスポンスヘッダーで**サーバーの種類とバージョンを公開している**ことです（`Microsoft-IIS/10.0`）。IIS 10 自体は現行の版なので、古いから問題というわけではありません。ただ、攻撃する側にとっては、狙う相手を選ぶ手がかりになります。多くのサイトは、この情報を隠すか削る設定にしています。あとは HSTS と CSP が未設定です。

**カード決済**は「このページにカード入力欄はありません」です。予約の最後でカードを入力するなら、その画面で開き直せば方式が分かります。

### 例 6：銀行のサイト

![銀行のサイトでの結果](/images/safepeek/bank.png)

ある銀行のサイトです。

**セキュリティ**の一番上に、「**重大**」で「既知の脆弱性があるライブラリ: swiper 7.4.1」と出ています。Swiper は、画像を横にスライドさせるカルーセルでよく使われるライブラリです。該当するのは **CVE-2026-27212**（プロトタイプ汚染）です。6.5.1 以上 12.1.2 未満のすべての版が対象で、脆弱性情報の深刻度は critical です。

ここで知っておいてほしいのは、**SafePeek の「重大」「注意」は、脆弱性情報に付いている深刻度をそのまま使っている**ということです。そのサイトで実際に攻撃できるかどうかまでは判定していません。プロトタイプ汚染は、外から来た値がライブラリの設定にそのまま渡るような使い方をしていなければ、突くのは難しい種類の脆弱性です。カルーセルに固定の設定を渡しているだけなら、影響はまずありません。

それでも、**修正版が出ている脆弱性のある版を使い続けている**ことは分かります。ほかにも、サポートが終わった jQuery 1.x 系（1.11.3）を使っていて、8 ドメインから 10 件の外部スクリプトを読み込んでいます。

もう 1 つ大事なのは、**銀行の公開サイトと、ネットバンキングのシステムは、たいてい別物**だということです。ドメインも、作っている部隊も違うことが多いです。公開サイトでの結果は、ネットバンキングの安全性を直接は表しません。ネットバンキングのログイン画面で開けば、そちらの結果が分かります。

### 例 7：国立大学のサイト

![国立大学のサイトでの結果](/images/safepeek/university.png)

ある国立大学のサイトです。

サポートが終わった **jQuery 1.11.1** を使っていて、その版には既知の脆弱性があります。HSTS と CSP も設定されていません。バックエンドの痕跡はありません。

大学のサイトは、広報のページ、学部ごとのページ、学生や受験生向けのシステムが、別々に作られていることがほとんどです。見たのは公開されている広報のページで、出願や学内システムはまた別です。とはいえ、個人情報を預ける入口も同じドメインの下にあることが多いので、気になるところではあります。

### 例 8：テレビ局のサイト

![テレビ局のサイトでの結果](/images/safepeek/tv-station.png)

あるテレビ局のサイトです。

「**重大**」は、テンプレートライブラリの **Handlebars 4.7.7** です。Handlebars は、4.7.x 系でずっと安定していたライブラリです。ところが 2026 年に入って、**4.0.0 以上 4.7.9 未満を対象にした脆弱性がまとめて公表されました**（CVE-2026-33937 など）。中には、コード実行（RCE）につながる深刻度 critical・high のものも含まれています。

これは、例 4 や例 7 の「何年も前にサポートが終わったライブラリ」とは違う種類の話です。**長く「枯れていて安全」と思われていたライブラリにも、ある日まとめて脆弱性が見つかることがあります。** そのときに更新できる体制があるかどうかが、サイトの手入れの差になって表れます。

もっとも、これらの脆弱性の多くは、攻撃者が用意したテンプレートやデータを Handlebars に渡せる場合に成り立つものです。ブラウザで固定のテンプレートを表示しているだけなら、すぐに悪用できるとは限りません。例 6 と同じく、「重大」は脆弱性情報の深刻度をそのまま表示しています。

ほかに、サポートが終わった jQuery 1.11.3（既知の脆弱性あり）と、HSTS の未設定が出ています。

### 並べてみて見えたこと

- **jQuery 1.x 系は、あちこちに残っています。** 銀行、大きな EC サイト、国立大学、テレビ局のどれにも出てきました。サポートは 2016 年ごろに終わっています。一度作ったページのライブラリは、そのまま何年も残りがちです。
- **HSTS や CSP のようなヘッダーは、設定されていないことが多いです。** 大きな組織のサイトでも同じでした。
- **カード決済の方式は、トップページでは判断できません。** どのサイトでも、確かめるにはカード番号を入力する画面で開く必要があります。
- **一番はっきり「危ないサイン」が出たのは、サポートが終わったバックエンドでした（例 2）。** フロントエンドのライブラリと違って、サーバー側のフレームワークは入れ替えに大きな手間がかかります。それだけに、残っていると目立ちます。


## サイト側にお願いしたいこと

作ってみて、外から推測するのには限界があるとよく分かりました。だからこそ、サイト側にお願いしたいことがあります。

- **決済手段の詳細を、どこかに載せてほしい。** どの決済会社を使っているのか。カード情報をサービス自身が持つのか、決済会社に直接渡しているのか。利用規約やプライバシーポリシーの片隅でいいので、書いてあれば安心して使えます。
- **カード以外の個人情報も、扱い方を知りたい。** 名前、住所、電話番号、購入履歴を取るなら、どう管理しているのか。退会したらいつ、どう消えるのか。

これが書いてあるサイトは、それだけでセキュリティを意識していると感じます。

## このツールの位置づけ

結局、このツールで分かるのは「安全かどうか」そのものではありません。**使っている技術要素から、そのサイトのセキュリティ意識を推し量る**ためのものです。

サポートが何年も前に終わったフレームワークが動いている。サーバーのバージョンを公開したままにしている。カード番号を自前のフォームで受け取っている。どれか 1 つで危ないとは言えませんが、重なっていれば、見えないところの手入れも行き届いていないかもしれません。逆に、決済は決済会社に任せ、ヘッダーもきちんと設定されていれば、少なくとも気にかけている人がいると分かります。

偽ショップの兆候も同じです。1 つ当てはまったから偽物、どれにも当てはまらないから本物、とは言えません。気になる兆候が出たら、会社が実在するか（法人番号の検索など）や、特定商取引法に基づく表記を自分で確かめるきっかけにしてください。

そのくらいの「目安」として使ってもらえればと思います。

## 限界

- **外から見える範囲の推定です。** きちんと運用されているサイトほど、サーバーの情報を隠しています。
- Linux ディストリビューションのパッケージのように、**古いバージョン番号のまま修正だけ取り込んでいる**場合もあります。
- **決済画面は、今見ているページと違うことがあります。** 決済方式を確かめたいときは、カード番号を入力する画面で開いてください。
- **画面をサーバー側で作るサイトでは、裏側がほとんど見えません。** Next.js などでサーバーがデータを取ってから HTML を返すと、ブラウザからは API の呼び出しすら見えないことがあります。
- **自社ドメイン経由で送っている通信は、送信先として分かりません。** 計測やエラー監視のデータを、自社のドメインを経由して送る設定にしていると見えません。
- **見るのは開いたページ 1 枚だけです。** 特定商取引法に基づく表記や決済画面は、そのページで開いたときにだけ読みます。
- **偽ショップの兆候は手がかりにすぎません。** ドメインの取得日、会社や住所が実在するか、振込先の口座名義は、ページからは見えません。どの兆候にも当てはまらない偽ショップもあります。表記の項目は見出しの言葉があれば「ある」とみなすので、でたらめな値で埋めた表記は見抜けません。機械翻訳の不自然な日本語も、簡体字などの痕跡がなければ判定しません。
- **パスワードの送信先は、フォームの既定の送信先だけを見ています。** 送信ボタンの `formaction` やスクリプトで別の場所へ送るページは見分けられません。
- **HSTS プリロードリストは持っていません。** リストに載っているサイトは、ヘッダーがなくても守られています。
- 「大きな問題は見つかりませんでした」は、**安全の保証ではありません。**
