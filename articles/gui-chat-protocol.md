経費を登録したくて、AI に頼みました。

```
私 : 経費を登録して
AI : 日付はいつですか？
私 : 9月12日
AI : 金額は？
私 : 4,800円
AI : 勘定科目は？
私 : ええと、会議費
AI : 支払い方法は？
```

**まだ半分です。** このあと相手先、但し書き、税区分と続きます。

紙の伝票なら15秒で終わります。**項目が全部見えていて、上から埋めるだけ**だからです。会話にすると、見えないものを1つずつ思い出させられる作業になります。

## 出るべきものが、出るようになる

いま同じことを頼むと、**フォームが1枚出ます。**

日付・金額・勘定科目・支払い方法・相手先が全部並んでいて、埋めて送信ボタンを押すと、それが AI に返ります。**往復は1回です。**

逆向きも同じです。「今期の支出を見せて」と頼むと、数字の羅列ではなく**グラフ**が出ます。「この構成で3Dの図を作って」と言えば、**回せる図**が出ます。

**答えは、答えにふさわしい形で返ってくるべきです。** 表は表、カレンダーはカレンダー、地図は地図。全部テキストに潰す理由はどこにもありません。

## ファイルは、投げ込める

もう1つ変わるのは入口です。

チャットに**画像を貼り付ける**、**ファイルをドラッグして落とす**。それをツールが受け取って処理します。「このレシートを読んで」と言ってからパスを打ち込む、ではなく、**落とすだけ**です。

## いま何が描けるのか

MulmoTerminal と MulmoClaude に入っているものを並べます。

| ツール | 出るもの |
|---|---|
| `presentChart` | グラフ（ECharts） |
| `presentForm` | 入力フォーム |
| `presentDocument` | Markdown 文書、Marp スライド |
| `presentHtml` | 自己完結した HTML ページ |
| `presentCollection` | スキーマ駆動のデータ画面（表・カレンダー・フォーム） |
| `presentShapeScript` | 触れる3D |
| `presentMulmoScript` | 動画・スライドの絵コンテ |
| 会計 | 複式簿記の帳簿 |
| 画像生成 | 生成した画像 |

**どれも「AI がテキストで説明する」のではなく、その物が出ます。**

## 仕組みは、拍子抜けするほど小さい

ここまでが価値の話で、ここからが作りの話です。

普通の tool call はこうです。

```
ツールが動く → テキストを返す → LLM が返答に混ぜる
```

[GUI Chat Protocol](https://github.com/receptron/gui-chat-protocol) はこれに**もう1つ口を足すだけ**です。

```
ツールが動く → LLM にテキストを返す（ここは今までどおり）
            → 同時に、型の付いたデータを UI に渡す → 画面が描かれる
```

`ToolResult` が2つの荷物を持ちます。

- `message` — LLM が読む。会話はこれで続く
- `data` — UI が読む。`type` が付いていて、`"chart"` ならグラフが、`"form"` ならフォームが描かれる

**LLM から見ると、何も変わっていません。** システムプロンプトでツール定義を受け取り、呼び、結果をテキストで受け取る。**新しい概念を覚える必要がない。**

だからこれは**新しいアーキテクチャではなく、既存の tool call への小さな足し算**です。function calling とも MCP とも喧嘩しません。使っているモデルを変えても、そのまま動きます。

## なぜ「プロトコル」にしたのか

プラグインを**チャットアプリを跨いで**使えるようにするためです。

型を固定してあるので、`presentChart` は MulmoTerminal でも MulmoClaude でも同じように動きます。**アプリ側はプラグインを知らなくていいし、プラグイン側はアプリを知らなくていい。**

パッケージは[npm にあります](https://www.npmjs.com/package/gui-chat-protocol)。構成はこうです。

- **コア** — フレームワーク非依存。型と入力ハンドラだけ
- **Vue アダプタ** / **React アダプタ** — コンポーネントの型

UI を持たないプラグインのロジックはコアだけで書けて、描画の部分だけフレームワークごとに分かれます。

## 自分で書くとどうなるか

ツールが返すものは、だいたいこの形です。

```ts
return {
  message: "9月の支出をグラフにしました",   // LLM が読む
  data: {
    type: "chart",                          // どの UI で描くか
    option: { /* ECharts の設定 */ },
  },
};
```

これを返すツールを定義して、対応するコンポーネントを登録すれば終わりです。**`type` が UI との唯一の契約**で、それ以外は自由です。

入力を受け取る側も同じ形で、ファイルや貼り付けた画像を受け取るハンドラを宣言すると、チャットに落とされたものがそこへ流れます。

## 正直なところ

**この形が要らない場面のほうが多いです。** 「これ直して」「なぜ落ちた？」はテキストで十分で、そこに画面を出しても邪魔なだけです。

効くのは**項目が多いとき**と**形のあるデータのとき**です。経費の登録、家計の把握、在庫、予定。**「一覧で見たい」「まとめて埋めたい」と思った瞬間**が、このプロトコルの出番です。
