FDE（Forward Deployed Engineer）という職種、日本だと「それ客先常駐では？」で会話が終わりがちです。

Anthropic が実際に出している求人票と、FDE の面接ガイドを読んでみました。推測ではなく、書いてあることだけを。

■ 異常なのはスキルの高さじゃなかった

一番驚いたのは「工程を一つも分けない」ことです。

業務課題の発見 → 要件定義 → 設計 → 実装 → セキュリティ・権限設計 → 本番デプロイ → ドキュメント → 受け入れテスト設計

日本なら何社かで分担するこの全部を、同じ人がやる。しかも最後にもう一工程あって、それが「現場知見を自社プロダクトに反映する」。日本の分業モデルには、この工程そのものが存在しません。

そして出張25〜50%。顧客の隣に座って作るのが前提です。

■ なぜ一人でできるのか

米国側の前提が効いています。CS の学位が共通言語になっているので、守備範囲を広げるコストがそもそも低い。そして Staff / Principal というトラックがあり、コードを書き続けたまま組織の最上位に行ける。

日本だと優秀な SE は数年で設計に上がり、PM になり、管理職になってコードを書かなくなる。書き続ける人は「上がれなかった人」に見えてしまう。この差が20年積み上がった結果が、人材の層の厚さです。

■ なぜ分けては「いけない」のか

ここが本題でした。LLM は確率的に振る舞うので、

・何が効くかは触るまで分からない → 要件定義で確定できることが残らない
・出力が揺れるので「仕様通り」が定義できない → 従来の受け入れテストが書けない

つまり請負・検収という商習慣と真正面からぶつかります。「検収基準は正答率92%以上」という契約書を、誰が、いつ書くのか。

分けることで生まれていたコストもあります。伝言コスト、判断待ちの遅延、そして責任の分断。「要件どおりに作った」「設計どおりに実装した」「言われたとおりに運用した」で全員が正しく、それでもシステムは使われていない。

■ で、日本はどうするか

正直に書きました。日本で FDE を職種として成立させるのは、たぶん無理です。人材の層、契約モデル、知見の還流経路、暗黙知の壁、全部が逆を向いている。

だから向きを逆にしたほうがいい、というのが結論です。

業務の暗黙知・何が正解かの判定・部門をまたいだ合意。これは取得にいちばん時間がかかる資産で、すでに社内にあります。一方、実装とデプロイはこの2年で桁で安くなった。

だとすると「エンジニアに業務を教える」より「業務の人に作る力を渡す」ほうが、距離が短い。エンジニアは前線に立つのではなく、足場（権限とサンドボックス、社内 MCP サーバー、evals の型、本番への導線）を作る側に回る。

LLM の出力が合っているかを判定できるのは、業務を知っている人だけです。エンジニアには判定できません。
